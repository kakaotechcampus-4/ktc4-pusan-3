## 1. 04 대화는 라우트다

🚨 **04 대화는 라우트다** (#226). 한동안 03 홈 위의 레이어였다 — 화면을 벗어나면 스트림과 원문이
같이 죽어서였는데, 지금은 보내기 · 구독 · 끝 처리가 **화면 밖**(`stores/conversation.ts`)에 있어서
그 이유가 사라졌다. 라우트여야 하는 이유는 **뒤로가기**다 — 웹뷰의 기기 뒤로가기가 히스토리 기반이라
레이어로 덮으면 대화 중 뒤로가기가 앱 밖으로 나갈 수 있다 (11-1 과 같은 이유).

- 🚨 **보내는 순간 넘어간다.** 202 를 기다리지 않는다 — 말풍선이 먼저 서고 요청은 뒤에서 나간다.
  그래서 **보내기 실패는 홈에서 보냈든 대화에서 보냈든 늘 대화 화면의 그 말풍선 아래에** 선다.
  03 홈에는 실패 카드가 없다
- 🚨 **흐름 화면이라 네비가 없다.** 돌아가기는 `IconButtonLink`("홈으로 돌아가기") 하나다
- 🚨 **대화는 하루에 하나다.** 날짜 경계는 한국 시간 자정이고 코드가 정한다(`toSeoulDateKey` —
  기기 시간대가 아니다). 보낸 순간에 그 한 줄의 날이 정해지고, **답은 질문이 나온 날을 물려받는다**
- 🚨 **03 홈에서 보낸 한 줄은 질문의 답이 아니다** (`asReply: false`). 답은 질문이 화면에 떠 있는
  대화 화면에서만 나간다 — 홈은 "답을 기다리는 질문이 있어요" 입구로 그리로 부른다
- 🚨 **대화 스토어는 여전히 메모리 전용이다.** 앱을 끄면 비고, 다시 켜면 서버가 남긴 대화를 다시 그린다 (§4 · #228)
- 화면 전환은 디자인 시스템 §8 "허용하는 화면 전환" — 열 때 대화가 오른쪽에서 들어오고, 막 보낸
  한 줄이 말풍선 자리로 날아간다. 🚨 **방향은 이동을 일으키는 쪽이 붙인다** (`lib/view-transition.ts` 의
  `FORWARD` · `BACK` 을 `router.push(href, FORWARD)` · `<Link {...BACK}>` · `IconButtonLink` 에 넘긴다).
  안 붙이면 화면은 움직이지 않는다 — 두 화면을 감싸는 `ScreenTransition` 이 `default: "none"` 이다 (#426 에서
  03 ↔ 04 전용이던 것을 다른 부모 ↔ 자식 쌍과 같은 것으로 바꿨다)
- 🚨 **대화 안에서 말풍선이 붙는 것에는 움직임이 없다** (§8 "하지 않는 것"). 움직이는 것은 이미 서 있던 진행 카드가
  결과로 바뀌는 순간(`ChatThread` 의 `Swap` · 교체)뿐이다
- 🚨 **03 의 "오늘 대화 이어보기" 는 제안 줄 맨 앞의 알약이다** (`HomeComposer` 의 `lead` · `PROMPT_PILL`).
  따로 한 줄을 주면 각진 버튼 하나가 알약 줄 위에 혼자 떠 보인다

## 2. SSE

`EventSource` 를 쓰지 않는다. Authorization 헤더를 못 붙여서 NF-09 를 깬다.
`streamRunEvents(runId, signal)` 을 async iterator 로 돌린다.

```ts
const controller = new AbortController();
for await (const e of streamRunEvents(runId, controller.signal)) { ... }
```

## 3. run 상태 — `runReducer` · `subscribeRun`

run 상태는 **서버 상태도 클라이언트 상태도 아니다.** 구독형이라 위 이분법에 안 맞는다.
리듀서와 구독(20초 침묵 · EOF 처리)은 `hooks/use-run-stream.ts` 한 벌이고, **누가 들고 있는가**만 갈린다.

| | 누가 | 화면을 떠나면 |
| --- | --- | --- |
| 04 대화 | `stores/conversation.ts` (run 여러 개 · 말풍선마다 하나) | 🚨 **끊지 않는다** — 홈에 갔다 와도 결과가 빠짐없이 그려져야 한다 |
| 08 사진 | `useRunStream` 훅 (run 하나) | 끊는다 — 커밋 전에는 저장된 것이 없다 |

- 🚨 **대화 스토어는 끝난 run 을 굳혀 둔다.** 서버는 끝난 채널을 5분만 보관한다
  (`apps/api/app/api/runs/registry.py` 의 `sweep`) — 다시 구독해서 그리는 구조로 만들면 5분 뒤에 빈 답이 된다
- 🚨 **한 번에 하나** (`isBusy`). 답을 기다리는 동안에는 다음 한 줄을 못 보낸다 — 두 run 이 겹치면
  어느 쪽이 질문의 답인지, 질문을 언제 닫는지가 도착 순서에 달린다. 🚨 **마지막 줄만 보지 않고 전체 줄을
  본다** — 앞 줄을 다시 시도하는 동안 마지막 줄은 끝나 있어서, 마지막만 보면 run 이 겹친다 (#231 리뷰)
  - 🚨 **막는 것은 보내기뿐이다. 입력창은 열어 둔다** (`HomeComposer` 의 `pending` · #231 리뷰). 입력까지
    잠그는 것(`locked`)은 03 홈이 막 보내고 넘어가는 한 순간뿐이다. 그 대가로 입력창에 글이 있는 채로 실패가
    오는 일이 흔해서, 원문을 입력창에 옮기는 쪽이 그 글을 덮지 않는다 (아래 원문 항목)

- `runReducer` 는 순수 함수다. 훅 없이 이벤트 배열만 흘려서 검증할 수 있다
- 끝나면 **`qk.child(cid)` 를 통째로** 무효화한다 — run 하나가 홈·관찰·프로필을 동시에 바꾼다.
  🚨 **04 대화 목록(`qk.chat`)만 빼고 오늘 장을 갈아 끼운다** (`refreshAfterRun` · §4). 무한 목록이라 무효화하면
  받아 둔 장을 전부 다시 받는다
- 🚨 **`partial` 이 왔으면 `done` 이 와도 부분 결과다.** 성공 화면으로 덮지 않는다 (NF-06)
- 🚨 **`done` 이 `completed: false` 로 오면 저장한 뒤에 끊긴 run 이다** (#253 · #271 · `RunState.interrupted`).
  서버는 쓴 것을 commit 한 뒤 예외나 60초 안전망에 걸리면 `failed` 가 아니라 이 길로 닫고 Idempotency 키와
  이어받기 맥락을 놓지 않는다 — `failed` 로 닫으면 다시 보낸 한 줄이 두 번 저장되기 때문이다. 키가 없으면 `true` 다.
  - 🚨 **실패가 아니다.** `status` 는 `done`(또는 `partial`)이고 `isRunConfirmed` 도 참이라 질문도 닫힌다
  - 🚨 **받은 기록이 없어도 "저장하지 않았어요" 를 세우지 않는다.** `saved` 를 보내기 전에 끊겼을 수 있고, 쓴 것이
    일정 변경일 수도 있다 — 제목은 "적어주신 내용은 반영했어요" 다
  - 🚨 **다시 시도 · 고쳐 쓰기를 세우지 않는다.** 대신 "같은 말을 다시 보내지 않아도 돼요" 를 글자로 말한다.
    무엇이 빠졌는지("추천을 못 만들었어요")도 단정하지 않는다
- 🚨 **`guidance` · `note` · `unavailable` 은 실패가 아니다** (#141). 셋 다 `done` 으로 끝나는
  run 에 실려 오고, 04 답 묶음 안의 카드로 선다 — 실패 화면으로 빼면 **같은 run 에서 저장된
  기록이 화면에서 사라진다.** 특히 `unavailable` 은 라우팅 직후 Memory 보다 **먼저** 나가서
  (`apps/api/app/agents/pipeline.py`) 혼합형 한 줄이면 `saved` 와 같이 온다
- 🚨 **셋 중 하나라도 있으면 "아이에 관한 기록은 찾지 못했어요" 를 세우지 않는다.** 안내가 이미
  이유를 말했는데 그 아래에서 다른 이유를 대면 화면이 자기 말을 뒤집는다 (`RunReply` 의 `noticedWhy`).
  같은 이유로 저장이 0건이면 제목도 "이렇게 저장했어요" 가 아니다
- 🚨 **안내·준비 중 카드는 같은 run 에서 저장된 것이 있으면 그 사실을 함께 말한다**
  ("아래 기록은 그대로 저장했어요" · `partial` 카드와 같은 문장이다). 한 줄에 두 얘기가 섞여
  들어오는 경우가 실제로 있어서다 — "계란 잘 먹었어. 그리고 땅콩 알레르기 있어" 면 서버는 앞을
  저장하고 뒤를 안내로 돌린다. 안내만 읽고 **전부 저장 안 된 줄 아는 것**을 막는 한 줄이다
- 🚨 **`unavailable` 을 `partial` 카드(`CardFailed`)로 그리지 않는다.** `partial` 은 Agent 가 해 보다
  실패한 것이고 이건 Agent 가 **아직 없는** 것이다 — 회색 각주로 깔면 그 추천을 기대한 보호자가
  아무 답도 못 받은 것으로 읽는다. 🚨 다만 타일은 `neutral` 이다: 안내와 달리 **할 수 있는 일이
  없어서**, 브랜드 타일을 주면 눌러 볼 것이 있는 줄 안다
- 🚨 **`note.kind` 가 없으면 질문으로 취급하지 않는다.** 서버가 종류를 실어 주기 전까지는
  요약 문장과 되묻기를 가를 수 없는데, 모르는 채로 답할 자리를 열면 화면이 답을 재촉한다.
  ⚠️ `kind` 는 #141 에서 요청한 값이다 — 👉 `apps/api` Owner 협의 대상 (최상위 §8)
- 🚨 **되묻기에 답하는 것은 새 한 줄이다** — 같은 run 에 이어 붙이는 경로가 서버에 없어서
  (§5 run = 입력 1건) 하루 입력 횟수(#147)를 한 번 더 쓴다. 그래서 답을 떠미는 화면을 만들지 않는다.
  **답은 대화 화면 안에서 한다** (#226) — 질문이 오면 입력창이 그 질문을 기본 대상으로 잡고 위에
  "위 질문에 답하는 중" 이 선다. 예전엔 질문을 `stores/pending-question.ts` 에 옮겨 담아 03 홈까지
  끌고 갔는데, 그 왕복에서 리뷰 버그가 세 번 났다 (#141 · #158 · #175)
  - 🚨 **답을 강요하지 않는다.** "답하지 않고 새로 적기" 로 내려놓을 수 있고, 내려놓아도 질문은
    대화에 **열린 채로** 남아 "이 질문에 답하기" 로 다시 고른다. 예전 "나중에 할게요" 는 질문과
    `runId` 를 지워서 실제로는 그만두기였다 — 서버는 15분 기다리는데 화면이 잊었다
  - 🚨 **이어받기 run 이 또 물으면 다음 답의 `reply_to` 는 그 run 이다** — 처음 run 은 서버가 이미
    한 번 꺼내 썼다 (목 `?scenario=reply_asks_again`)
  - 🚨 **상한에 닿으면 질문 대신 안내가 온다** (#246 · 서버 #251). 한 조각에 처음 질문까지 4번 물었는데
    또 물으려 하면 서버는 맥락을 남기지 않고 `kind=message` 로 "저장하지 않았어요" 를 낸다. 화면이 따로
    할 일은 없다 — `settle` 이 message 에는 질문을 열지 않고 답하던 질문만 닫는다. 🚨 그래서 **`kind` 가
    message 인 note 에 답할 자리를 열지 않는 규칙**이 상한을 지킨다 (목 `?scenario=reply_ask_limit`)
- 🚨 **답할 때 원문을 입력창에 되돌리지 않는다** (#158 리뷰).
  한동안 되돌려 놨었다 — 답이 새 run 이라 앞의 한 줄을 모르니 맥락을 화면이 만들어 주려던
  것이었다. 그런데 **일부는 저장되고 질문이 같이 오는 run** 이 있다("계란 잘 먹었어. 요즘 기침해"
  → 계란 저장 + 기침 되묻기 · `apps/api/app/agents/pipeline.py` 의 `Saved` + `MemoryNote`).
  원문을 다시 보내면 **계란이 두 번 저장되고**, 7일 승격 집계가 한 번의 관찰을 두 번으로 센다
  (최상위 §2 · #154).
  - 🚨 **맥락은 `reply_to` 로 서버가 찾는다** — 답에 그 질문이 나온 `run_id` 를 싣는다.
    그래서 대화 스토어의 질문(`ChatQuestion`)이 문자열이 아니라 `{ text, runId }` 다
    (서버 구현 #175 — 서버는 그 run 이 남긴 조각 하나를 **한 번만** 꺼내 답을 붙인다)
  - 🚨 **질문은 202 가 아니라 run 이 끝까지 처리됐을 때 닫는다** (`settle` 의 `isRunConfirmed`).
    이어받기 run 이 `failed` 로 끝나면 서버가 맥락을 원래 자리에 되돌려 두는데, 202 에서 닫으면
    "다시 시도" · "고쳐 쓰기" 뒤의 요청에 `reply_to` 가 빠져 답만 맥락 없는 새 입력으로 나간다.
    같은 이유로 다시 시도는 **그때의 입력창이 아니라 그 말풍선의 본문 · 키**를 그대로 싣는다
  - 🚨 **화면은 "답만 적으면 된다" 고 말한다.** 앞서 적은 말을 다시 쓰게 하면 부모가 손으로
    중복을 만든다 — 앞 이야기가 이미 저장돼 있다는 것을 같이 알린다
  - 🚨 **Idempotency-Key 를 `text` 에만 묶지 않는다** (`keyPayload`). 서버는 본문 **전체**로 같은
    요청인지 보므로, 같은 답("네")을 다른 질문에 보내면 "같은 키 · 다른 본문" 이라 422 다.
    본문에 필드를 더하면 `keyPayload` 에도 같이 더한다
- 🚨 **`agent_result` 는 도메인 Agent 결과 한 건 = 답 묶음 안의 블록 하나다** (#227 · 서버 #276).
  도착한 순서대로 붙이고 재정렬하지 않는다. 같은 Agent 가 두 번 올 수 있고(task 둘) 묶지 않는다.
  보일 것이 없는 결과(쓰는 task)는 블록을 세우지 않는다 (`visibleAgentResults`).
  - 🚨 **Agent 결과도 이유를 말한 것이다.** 블록이 서면 "아이에 관한 기록은 찾지 못했어요" 를 세우지 않는다 —
    요청형 한 줄은 저장할 관찰이 없는 것이 정상이다 (`noticedWhy`)
  - 🚨 **Agent 의 되묻기(`question`)에는 답할 자리를 열지 않는다.** Memory 의 되묻기(`note`)와 답의 쓰임이
    달라서 `reply_to` 로 보내면 400 이다. 답을 받는 길은 #246 에서 정하고, 그때까지는 안내 문장이다
  - 🚨 **추천이 든 결과는 "후보 N개" · 이유 한 문장 · "후보 보기" 가 블록에 선다** (#227 3단계). 링크는 그 블록의
    Agent 하나와 그 run 을 싣는다(`?agents=<agent>&run=<run_id>`) — 05 가 그 run 의 추천을 되살린다 (#249).
    후보가 있으면 개수 안내(`code`)는 "후보 N개" 가 대신해 그리지 않고, `code` 가 없는 readout(날씨 안내)은 그대로
    그린다 (`lib/agent-result.ts`)
  - 🚨 **일반 묶음(`kind: "general"`)은 "또래 기준 일반 추천" 과 쌓인 기록 수를 그대로 적는다.** 0건도 적는다.
    서버가 세지 못했으면(`record_count: null`) 건수만 빼고 라벨은 남긴다. 색으로 가르지 않는다
  - ⚠️ 개인화 · 일반이 섞인 묶음은 `kind: "personalized"` 로 온다 — 섞인 일반 추천은 05 가 따로 보여 준다
  - 🚨 **부분 실패 카드의 "다시 준비하기" 는 `partial.retryable` 의 Agent 만 싣는다** — 화면이 `failed` 에서 고르지
    않는다(급식 갱신만 실패한 식사는 05 화면이 없다). 05 가 그 run 의 처음 시각 · 문장으로 다시 만들고, 15분이
    지났으면 "이어서 할 수 없어요" 안내를 낸다 (#249)
- 🚨 **`ping` 은 아무것도 하지 않는다** (#140). 20초 타이머는 `pumpRunEvents` 의 `onEvent` 가
  되살리고, 리듀서에서 새 state 를 만들면 조용한 채널에서 10초마다 04 가 다시 그려진다
- 🚨 **20초 안전망이 `subscribeRun` 안에 있다.** 전체 시간이 아니라 *조용한 시간*을 잰다 —
  전환의 정본은 서버가 보내는 `partial` 이고, 이건 스트림이 멎었을 때의 그물이다
- 🚨 **서버가 말한 끝과 클라이언트가 스스로 끝낸 것을 섞지 않는다.** `done` · `partial` · `failed` 는
  서버가 말한 끝이고, `unconfirmed` 하나만 다르다 — 20초 침묵 · 종료 이벤트 없는 EOF · 연결 실패라
  **서버가 무엇을 저장했는지 모르는** 상태다. 섞으면 화면이 "저장됐어요" 라고 말하고 입력창의 원문까지
  지운다. 원문을 비워도 되는지는 `isRunConfirmed(status)` 하나로 판단한다 (PR #71 리뷰)
- 🚨 **종료 이벤트 없이 스트림이 닫히는 경우를 반드시 처리한다.** `for await` 는 EOF 에서 예외 없이
  끝난다 — 거기서 아무것도 안 하면 status 가 `streaming` 에 남고, idle 타이머까지 해제된 뒤라
  20초 전환조차 돌지 않아 진행 화면이 영원히 돈다. `pumpRunEvents()` 가 그 자리를 막는다
- 🚨 **입력 원문을 run 상태에 두지 않는다.** 실패 시 원문을 입력창에 되돌려야 하는데, `failed`
  이벤트의 `raw_text` 는 네트워크가 끊기면 못 받는다. **원문의 정본은 보내기 전엔 `stores/draft.ts`,
  보낸 뒤엔 그 한 줄의 말풍선**(`ChatTurn.body.text`)이다 — 둘 다 메모리 전용이다.
  🚨 **말풍선을 지우는 길은 하나다 — 원문을 입력창에 옮겼을 때** (`handedBack` · #231 리뷰).
  "고쳐 쓰기" 와 429 · 403 이 원문을 옮기고, 그 말풍선만 다음 한 줄이 대체한다(`isReplaceable`).
  - 🚨 **네트워크 · 5xx 실패는 대체하지 않는다.** 응답만 못 받은 것이라 서버가 받았을 수 있고, 보낼 때
    입력창을 비웠으니 지우면 원문이 어디에도 안 남는다 — 다시 시도 · 고쳐 쓰기로만 정리된다.
    한동안 "서버에 닿지 못한 실패" 로 묶어서 다음 한 줄이 통째로 지웠다
  - 🚨 **입력창에 쓰던 글이 있으면 옮기지 않는다** — 덮으면 그 글이, 안 덮고 지우면 이 글이 사라진다.
    고쳐 쓰기는 잠기고(`RewriteButton`) 이유를 글자로 말한다. 429 · 403 도 그때는 말풍선에 남긴다
  - 🚨 **202 를 한 번이라도 받은 줄은 다시 시도가 네트워크로 실패해도 결과 미확인으로 남는다.** 앞 run 이
    무언가를 저장했을 수 있다. 같은 이유로 다시 보내는 동안 앞 run 을 지우지 않는다(202 를 받으면 갈아 끼운다)
  - 🚨 **키는 말풍선에 붙들어 둔다** — 다시 시도는 그 키 그대로다. 새 한 줄의 키는 아이별
    **(본문 지문 → 키) 표**(`keyBooks`)가 내고, 서버가 그 줄을 끝까지 처리했을 때만 그 항목을 지운다.
    그래서 결과 미확인 줄을 다른 줄 뒤에 고치지 않고 그대로 다시 보내도 같은 키다. 🚨 **한 칸짜리 보관함으로
    되돌리지 않는다** — 다른 줄을 보내는 순간 앞 본문을 잊어서 같은 관찰이 두 번 저장됐다 (#231 리뷰)
- 🚨 **아직 안 보낸 한 줄은 화면 로컬 상태로 두지 않는다** (`stores/draft.ts`). 하단 네비가 보내기 버튼
  21px 아래에 다른 화면으로 가는 문을 세 개 열어서, `useState` 로 두면 잘못 누른 한 번에 쓰던 글이
  언마운트와 함께 죽는다. 승인을 하나 더 다는 건 답이 아니다 (최상위 §2 — 승인 게이트는 딱 2곳).
  🚨 **그 스토어에 `persist` 를 붙이지 않는다** — 아이에 대한 발화 원문이라 디스크에 남기지 않는다
  (최상위 §2 개인정보). 로그아웃에서 `clearAll()` 로 지운다

목의 `?scenario=partial` · `failed` · `disconnected` · `interrupted` 로 네 경로를 바로 확인할 수 있다 (§7).
대화 스토어의 규칙은 `stores/conversation.test.ts` 가 목 서버와 실제로 돌려서 건다 (§8).

## 4. 지난 대화 (#228)

서버는 `done` 으로 끝난 run 하나를 대화 한 턴으로 남기고 `GET /children/{cid}/chat` 으로 하루씩 돌려준다
(서버 문서 [`docs/api/chat-v1.md`](../api/chat-v1.md)). 화면은 그것을 이 앱에서 보낸 줄과 합쳐 하나의 대화로 그린다.

- 🚨 **지난 턴도 같은 리듀서 · 같은 답 묶음이다.** 서버가 남긴 답은 SSE 와 같은 이름 · 같은 칸이라 `type` 을 떼어
  `runReducer` 에 흘리면 그날의 `RunState` 가 나온다 (`lib/chat-history.ts`). 지난 턴용 화면을 따로 만들지 않는다 —
  만들면 같은 답이 오늘과 어제 다르게 그려지고, `partial` 뒤 `done` 같은 규칙을 두 곳에서 지켜야 한다
- 🚨 **지난 턴은 대화 스토어에 넣지 않는다.** 서버 상태라 TanStack Query 가 든다 (`useChatHistory` · `qk.chat`).
  🚨 특히 **초안 보관함에 얹지 않는다** — 실시간 run 은 일정 초안이 오는 순간 `seedDrafts` 로 얹는데, 지난 턴을
  그 길로 흘리면 이미 넣은 일정이 초안으로 되살아난다. 리듀서만 부르고 스토어의 `dispatch` 를 거치지 않는다
- 🚨 **`run_id` 로 합치고, 겹치면 이 앱의 줄이 정본이다** (`ChatThread`). run 이 끝나면 서버도 그 턴을 남겨 같은 run 이
  두 곳에 생긴다. 이 앱의 줄은 진행 중이거나 다시 시도할 수 있는 줄이고 서버는 끝난 run 만 남기므로, 지난 쪽을 뺀다.
  같은 날 안에서는 지난 줄이 먼저다. 서버는 채널을 닫은 뒤에 쓰니 run 이 끝나자마자 다시 받으면 방금 턴이 빠질 수
  있는데, 이 합치기 때문에 화면에는 드러나지 않는다
- 🚨 **날짜는 서버가 정한 것이다.** 지난 턴의 날은 응답의 `date` 이고 화면이 `created_at` 으로 다시 계산하지 않는다.
  run 이 끝나면 `qk.child` 를 무효화하므로(§3) 그 턴의 `calendarDay` 와 대화 목록의 오늘 장도 같이 갱신된다 —
  "그 턴의 날짜" 를 화면이 고르지 않는다
- 🚨 **지난 턴에서는 지금 누르면 막다른 길이 되는 버튼만 뺀다** (`RunReply` 의 `archived`).
  - 일정 초안은 그때 내용만 읽기 전용으로 선다 — 초안은 서버에 남지 않아서 넣었는지 모르고, 넣게 하면 같은 일정이 또 들어간다
  - 부분 실패 카드에 "다시 준비하기" 가 없다 — 05 의 실패 맥락은 15분이라 "이어서 할 수 없어요" 만 나온다
  - 지난 되묻기에는 답할 자리가 없다 — 서버의 앞 이야기도 15분이다. 뒤에 `reply_to` 로 답한 줄이 있으면 "답함", 없으면 "닫힘"
  - "후보 보기" 는 남긴다 — 05 가 그 run 의 추천을 지금 상태(채택 · 만료)로 거른다
- 🚨 **지운 기록은 내용 없이 "이 기록은 지웠어요" 한 줄이다.** 서버도 id 만 준다. 저장 건수에는 넣는다 — 그날 저장한 것이다
- 🚨 **위로 올리면 더 이른 장을 붙이되, 사람이 굴린 뒤에만 건다.** 대화가 짧으면 처음부터 맨 위라 저절로 걸면 열자마자
  지난 대화를 끝까지 받는다. 이미 맨 위에서 올리면 스크롤 이벤트가 없어서 휠 · 터치도 본다. 키보드는 걸기만 한다 —
  짧은 화면에서 입력창에 칠 때마다 받게 된다. 붙는 동안 보던 줄은 붙은 높이만큼 다시 내려 제자리에 둔다
  (`overflow-anchor` 는 웹뷰마다 달라서 쓰지 않는다). 화면이 짧아 올릴 수 없을 때를 위해 "이전 대화 보기" 를 세운다
- 🚨 **다음 장은 그날 안의 커서가 먼저, 그다음 전날(`prev_date`)이다.** 커서는 날짜를 품고 있어서 커서만 보낸다
- 🚨 **run 이 끝나면 대화 목록은 오늘 장만 다시 받아 끼운다** (`refreshAfterRun` · #228 리뷰). TanStack 은 무한 목록을
  무효화하면 받아 둔 장을 전부 순서대로 다시 받아서, 지난 날을 멀리 올려 둔 화면에서 한 줄 보낼 때마다 그만큼 요청이 나갔다.
  run 이 바꾸는 것은 오늘 장 하나다. 자정을 넘겼거나 오늘이 여러 장이거나 전날(`prev_date`)이 바뀌었으면 갈아 끼우면
  장이 어긋나서 그때만 통째로 다시 받는다 (`withNewestPage`)
- 🚨 **`?date=` 로 열면 그날까지 이어 받고 그 자리로 내린다** (09 하루 보기의 입구). 그날만 따로 여는 화면으로 만들지
  않는다 — 거기서 보낸 한 줄이 며칠을 건너뛰고 붙는다. 돌아가기는 그날의 캘린더다
- 🚨 **받는 중에 빈 상태를 세우지 않는다** — 앱을 다시 켤 때마다 "아무것도 없다" 가 깜빡인다. 지난 대화를 못 받아도 이 앱의
  줄은 그리고(NF-06), 실패는 위 한 자리에서만 말한다
- 03 홈의 "오늘 대화 이어보기" 는 스토어의 줄 **또는 서버의 오늘 대화**가 있으면 선다. 홈은 첫 장만 따로 받는다
  (`qk.chatToday`) — 대화 목록과 같은 키면 홈에 올 때마다 받아 둔 지난 날을 전부 다시 받는다

목의 `?scenario=chat_history` 가 오늘 · 어제 · 사흘 전 대화를 깔고, 탭을 새로 여는 것이 곧 앱을 다시 켠 것이다.
기본 시나리오에서도 목은 끝난 run 을 남겨서 합치기가 보인다 (`mocks/handlers/chat.ts`).
