## 1. 라우팅 — 왜 이 화면이 라우트인가

🚨 **03 홈 버튼은 05 에 문장이 아니라 키를 넘긴다** (`?prompt=dinner` · #286). 05 는 그 키를 추천 요청의
`prompt_key` 에 그대로 싣고, Agent 에 넘길 문장("저녁 추천해줘")은 서버가 키로 꺼낸다. 문장을 화면이 보내면
Supervisor 안전 사전검사를 거치지 않은 문장으로 Agent 가 돈다 (#249). 05 는 **아는 키만** 싣는다 — 주소는
누구나 고칠 수 있다. 🚨 키는 05 쿼리 키에도 들어간다 — 빼면 다른 버튼을 눌러도 앞 버튼의 제안이 뜬다
(`staleTime: Infinity`).

🚨 **04 제안("이것도 도와드릴까요?")은 `run_id` 없이 05 로 간다** (#249). 이어서 하는 것이 아니라 새로
고른 것이라 홈처럼 처음 요청으로 돈다. 실으면 서버는 그 run 에 이 Agent 기록이 없어 "이어서 할 수 없어요"
를 낸다. `run=` 은 #227 "후보 보기" 에만 붙는다.

`/onboarding` · `/start` · `/invite` 는 아이 스코프 **밖**이다 — `POST /children` 이나 초대 수락이
성공해야 `childId` 가 생긴다. 이 경계를 흐리면 childId 가 없는 상태의 아이 스코프 라우트가 생긴다.

🚨 **`/account-deletion` 은 로그인 밖이다** (#166). Play Console 데이터 보안 양식의 "계정 삭제 URL" 과
"데이터 삭제 URL"(계정은 두고 기록만 지우는 길) 두 칸이 함께 가리키는 페이지라, 앱을 지웠거나 로그인할 수 없는 사람이 스토어에서 바로 연다. `AuthGate` 를 씌우지 않고
API 도 부르지 않는 서버 컴포넌트로 둔다. 문장은 처리방침 제1장 ③ · 제5장 · 제9장을 옮긴 것이라
**처리방침 판이 바뀌면 같이 고친다** — 어긋나면 처리방침이 정본이다. 앱 안에서 이 페이지로 오는 길은
만들지 않는다 (앱 안의 길은 설정 › 계정 › 탈퇴하기).

🚨 **아이가 0명이면 `/onboarding` 이 아니라 `/start` 로 보낸다** (#96). 초대를 기다리는 사람이
아이 만들기에 바로 떨어지면 **같은 아이를 또 등록**하고, 아이는 보호자당 한 명이라 그 뒤로는
초대를 수락할 수 없다 (`409 child_already_exists`). 되돌리는 길이 없어서 고르기 전에 묻는다.
기준이 "신규 회원" 이 아니라 **아이 0명**인 이유는, 초대를 기다리는 기존 회원도 같은 화면이
필요하기 때문이다.

🚨 **`useSearchParams()` 를 쓰는 화면은 `<Suspense>` 경계 안에 둔다.** 경계가 없으면 프리렌더가
CSR bailout 을 일으켜 **프로덕션 빌드가 그 화면에서 멈춘다** (`Missing Suspense boundary with useSearchParams`).
`pnpm dev` 에서는 드러나지 않아서 `pnpm build` 로만 잡힌다 — 실제로 `/auth/callback` 이 그렇게 빠져 있었다 (PR #71 리뷰).
위 표에서 `?` 가 붙은 화면(04 · 05 · 07 · 09)과 `/auth/callback` 이 대상이다. `fallback` 에는 그 화면이
hydrate 직후 그릴 것과 **같은 것**을 둔다. 다른 것을 끼우면 정적 HTML 과 hydrate 결과가 한 번 어긋나 깜빡인다.

🚨 **11-1 은 11 안의 시트가 아니라 라우트다.** 잰 기록이 쌓이면 목록이 길어져서 프로필의
다른 두 구역(부르는 이름 · 알레르기)을 화면 밖으로 민다. 그래서 프로필은 **가장 최근 한 줄**만
세우고 목록과 변화 그래프는 이 주소가 진다. 시트로 하지 않은 이유는 **뒤로가기**다 — 웹뷰의
기기 뒤로가기가 히스토리 기반이라([`apps/mobile/App.tsx`](../../apps/mobile/App.tsx)) 시트는 그 버튼으로
안 닫히거나, 닫히면서 앱을 벗어난다. 그 화면에서 뒤로 가는 길은 링크로도 함께 세운다
(주소로 바로 들어오면 히스토리에 프로필이 없어서 `router.back()` 이 앱 밖으로 나간다).

🚨 **11-2 도 시트가 아니라 라우트다. 다만 11-1 과 이유가 다르다.** 검사지 한 장에서 열 줄 넘게
나오는데, 시트 높이 안에서는 `caution` 배너 · 검사지 사진 · 후보 목록 · 승인 버튼이 서로 자리를
뺏는다 — 사진을 96px 까지 줄여야 목록이 보였다. 08 사진으로 적기와 같은 모양으로 화면을 내줬다.

- 🚨 **네비를 붙이지 않는다** (11-1 과 반대다). 11-1 은 **가는 곳**이라 네비가 있지만 11-2 는
  **흐름 중인 화면**이고 승인 게이트가 걸려 있다 — 고르다 마는 길을 만들지 않는다
- 🚨 **여기는 승인 게이트 ㉡ 다.** 08 사진이 만드는 `event` 는 `draft` 라 `caution`·`btn-approve`
  를 안 쓰지만, 11-2 의 등록은 되돌릴 수 없어서 **둘 다 쓴다.** 게이트를 늘린 것이 아니라
  **있던 게이트가 시트에서 화면으로 옮겨온 것**이다 (최상위 §2 — 늘리지도 줄이지도 않는다)
- 🚨 **고른 파일은 URL 로 못 넘긴다.** 화면 밖 스토어(`stores/safety-scan-draft.ts`)에 한 칸
  두고 넘긴다. 라우트 이동이 사용자 제스처를 소비해서 도착한 뒤 `input.click()` 을 부르는
  방법은 브라우저가 막는다. 🚨 그 스토어에 `persist` 를 붙이지 말 것 — **의료 기록 사진**이다

🚨 **화면이 읽는 `childId` 의 정본은 URL 이다.** `stores/session.ts` 의 `activeChildId` 는
"마지막에 본 아이" 복원용일 뿐이고, `components/child-scope.tsx` 가 URL → 스토어 **한 방향으로만** 흘린다.

- 🚨 **스토어는 서버 컴포넌트에서 못 읽는다.** `localStorage` 기반이라, 서버가 아이를 아는 방법은
  URL 아니면 쿠키뿐이다. 쿠키로 옮기면 쿠키·스토어·쿼리 키 세 곳이 어긋날 때 **다른 아이의 데이터가
  보일 수 있다** (§2 개인정보). URL 이면 그 사고가 구조적으로 불가능하다 — 이게 URL 을 고른 첫째 이유다
- 뒤로가기가 웹뷰 히스토리 기반이라([`apps/mobile/App.tsx`](../../apps/mobile/App.tsx)), 아이를 바꾼 게 히스토리에 안 남으면 뒤로가기가 어긋난다
  ⚠️ 하단 네비 네 칸에서는 셸이 히스토리로 가지 않고 두 번 눌러 종료한다 (#462). 그래서 이 이유는 **하위 화면**(설정 · 11-1 등)에서 아이를 바꾼 경우에만 남는다 — URL 을 고른 첫째 이유(위)는 그대로다
- 쿼리 키가 이미 `qk.child(cid)` 스코프라 URL 파라미터와 1:1 이다

⚠️ 계약서의 `deeplink` 는 **아이를 안 담은 상대 경로**다. 서버가 내는 값은 `profile` · `profile/growth` · `settings`
셋뿐이고 정본은 [`apps/api/app/core/deeplinks.py`](../../apps/api/app/core/deeplinks.py) 다 (#625 — 허용 목록 테스트가 웹 경로와 맞는지 본다).

| 어디서 | code | deeplink | 웹이 보내는 곳 |
| --- | --- | --- | --- |
| 04 안내 (`guidance`) | `safety_record` | `profile` | 11 아이 프로필 |
| 04 안내 (`guidance`) | `growth_record` | `profile/growth` | 11-1 키 · 몸무게 |
| 05 `guards` | `safety_unknown` | `profile` | 11 아이 프로필 |
| 403 `consent_required` (건강정보) | — | `settings` | 10 설정 |

🚨 **그 값을 주소로 쓰지 않는다.** 서버가 준 문자열이라 없는 경로(예전 `settings/health-safety` · 목의 `settings/consents`)가
오기도 했고, 외부 주소가 오면 화면이 앱 밖으로 나간다. 가는 곳은 화면의 code 별 표가 정하고(`run-result.tsx` 의 `GUIDANCE_KIND` ·
05 배너 · `ConsentRequiredCard`), 딥링크는 **어느 구역인지 힌트**로만 쓴다. 새 안내가 생기면 서버 표와 화면 표를 같이 고친다.

클라이언트 컴포넌트에서는 `useChildId()`, 서버 컴포넌트에서는 `params` 를 그대로 쓴다.
**스토어를 읽어 화면을 그리지 않는다.**

## 2. 05 제안 후보 — 채택 · 알레르기 확인 · 일반 추천

- 🚨 **05 는 고르기와 일정 만들기가 다른 단계다** (#151). ① 고른 것을 **채택**하고
  (`POST /children/{cid}/suggestions/approve` · ⚠️ 계약서에 없다) ② "일정으로도 만들까요?" 를
  따로 묻는다. 버튼 하나로 합치면 **"이걸로 할 건데 캘린더엔 안 넣을래"** 를 표현할 방법이 없고,
  고르기만 하고 나간 선택은 24시간 뒤 `expired` 로 사라진다.
  - 🚨 **채택은 승인 게이트가 아니다** — 캘린더를 안 쓰고 되돌릴 수 있다. `btn-approve` ·
    `caution` 을 쓰지 않고 `Idempotency-Key` 도 받지 않는다(되돌릴 수 없는 5곳에 여섯 번째를
    더하지 않는다). 🚨 **"기억해 뒀어요" 라고 쓰지 않는다** — "기억" 은 `profile_affinity` 를
    가리키는 화면 용어인데 채택은 그것을 만들지 않는다
  - 🚨 **`approved` 는 "채택했다" 하나의 뜻이다** (#206). 일정이 됐는지는 상태가 아니라 제안 ↔ 일정
    연결로 본다 — 초안 제출은 제안 `status` 를 바꾸지 않는다 (`docs/web/event-draft-ui-v1.md` §2 ㉡)
  - 🚨 **채택 뒤에는 고르기를 잠근다**(`SuggestionList` 의 `busy`) — 서버가 받은 것과 화면이
    달라지면 안 된다. 다음 단계에 쓰는 id 는 **응답이 준 것**이지 화면이 들고 있던 것이 아니다
  - 🚨 **"안 만들래요" 버튼을 두지 않는다** — 안 만들 사람은 그냥 나간다(하단 "홈으로").
    아무 일도 안 하는 것을 한 번 더 확인시키는 칸이다. 대신 **나가도 된다는 사실을 글자로** 말한다
- 🚨 **알레르기 확인(게이트 ㉡)은 채택보다 먼저다** (`SafetyCheckSheet` · #151). 한동안 초안을
  만든 뒤 승인 시트 안에서 물었는데, 채택과 일정 만들기가 갈리면서 **일정을 안 만드는
  보호자에게는 영영 안 묻게** 됐다 — 알레르기는 캘린더가 아니라 **그 음식을 먹이는 일**의 위험이다.
  - 🚨 **채택을 되돌리는 길이 없어서 먼저 묻는다.** 알레르기가 확인된 제안은 **채택 자체를
    안 한다** — 그러면 초안도 안 생기고 "막힌 초안" 이라는 상태도 필요 없어진다
  - 🚨 **시트를 승인 시트와 합치지 않는다.** 게이트 ㉡ 와 ㉠ 은 다른 단계라, 한 시트에 두면
    "알레르기를 확인했다" 와 "캘린더에 넣었다" 가 한 화면에서 섞인다
  - 🚨 **고른 것에 걸린 검사만 묻는다.** 🚨 `suggestion_id` 가 없어 어느 제안인지 모르면
    **고른 것 전부를 막는다** — 알레르기에서 덜 막는 쪽으로 기울 수 없다
- 🚨 **일반 추천(`GeneralSuggestionCard`)과 개인화 목록(`SuggestionList`)은 다른 컴포넌트 · 다른 타입 ·
  응답의 다른 필드다.** 한 곳에 플래그로 섞으면 언젠가 근거 0건인 것이 개인화로 그려지고, 그러면
  "개인화인데 근거 0행이면 버그" 라는 하드 기준이 무의미해진다 (최상위 §2).
  `GeneralSuggestion.evidence` 는 아이 기록이 아니라 **문서 행**(`DocEvidence[]`)이라 개인화 쪽에 넘기면
  컴파일이 막는다. 🚨 카드는 **출처 기관 · 출처 제목**을 같이 적는다 — CC BY 문서는 출처 표시가 이용 조건이고,
  "사용한 기록 N건" 으로 세지 않는다 (#249).
  ⚠️ 서버가 `general` 을 안 보내면(예전 응답) 질문 1개만 그린다.
  - 🚨 **일반 추천도 고르고 채택하고 일정으로 만든다** (#509). 그리는 컴포넌트만 다르고, 고른 id · 채택 ·
    알레르기 확인 · 초안 만들기는 개인화와 **한 흐름**이다 (서버의 채택 · 초안 · 제출은 `kind` 를 보지 않는다).
    그래서 일반 카드는 **"이렇게 준비할게요" 요약 카드보다 위**에 선다 — 다음 행동이 고를 것보다 먼저 서면
    안 된다. 순서는 개인화 목록 → 일반 카드 → 요약 카드 → 안내 · 실패 → 되묻는 질문이다
  - ⚠️ 채택 응답(`ApproveSuggestionsResponse`)은 일반 추천도 개인화 모양(`SuggestionOut`)에 `kind: "general"` 을
    실어 보내고, 근거를 읽지 않아 **개인화도 `evidence: []`** 다. 화면은 거기서 `id` 만 쓴다.
    서버 계약은 [`docs/api/suggestions-v1.md`](../api/suggestions-v1.md) §7 (#545)
- 🚨 **실패는 "묶음이 없는 Agent" 다** (#249). 0개로 끝난 Agent 도 안내(`groups[].notice`)와 함께 묶음이
  오고, 이어서 할 수 없는 Agent(`cannot_resume`)도 안내만 온다 — 둘 다 **실패 카드가 아니고 다시 시도를
  두지 않는다**(눌러도 같은 응답이 온다). 문구는 서버 것을 그대로 그린다. `groups` 를 안 보내던 응답은 예전
  규칙(결과 · 규칙에 막힘이 없는 Agent)으로 본다.
  - 🚨 guard 배너의 "알레르기 적으러 가기" 는 `safety_unknown` 일 때만 둔다 — 준비 중(`not_ready`) ·
    지원하지 않는 주제(`unsupported`)는 알레르기를 적어도 풀리지 않는다
  - 🚨 `looked_at` 이 비어 오면 그 줄을 그리지 않는다 · `scarcity.question` 이 없으면 질문을 세우지 않고,
    `options` 가 비어 오면(답하는 길 #246 전) 답하는 칩 없이 문장으로만 세운다
  - 🚨 **새로고침해도 채택은 남는다** — `run_id` 로 들어오면 서버가 채택한 추천(`status: approved`)도
    돌려준다. 화면은 그 `status` 로 "이렇게 하기로 했어요" 를 되살리고, 다시 고르게 그리지 않는다
    (다시 고르게 하면 채택 API 가 `not_draft` 로 거절한다)
- 🚨 **식품 아닌 알레르기 확인 문구(`groups[].cautions`)는 목록보다 위에 그대로 그린다** (#433 리뷰 ③). 서버
  코드 문구라 화면이 고르지 않는다. `caution` 색을 쓰지 않는다(승인 게이트 2곳 전용)
- 🚨 **05 쿼리는 자동 재시도를 끈다** — 요청마다 Agent 를 돌리고 하루 한도를 쓴다. `daily_input_limit` 에는
  다시 시도를 세우지 않고, 한도에 걸린 Agent 묶음이 `notice.code = "daily_limit"` 로 오면 안내로만 그린다
- 🚨 **일반 추천 카드의 "기록 N건" 은 `general[].record_count`(그 Agent 도메인 수)다** — `scarcity.count` 는 합이라
  질문 카드에만 쓴다

## 3. 07 기록 · 기억 — 색 · 이름 · 교정 · 필터

- 🚨 **07 의 도메인 색은 왼쪽 아이콘 타일 하나까지다** (디자인 시스템 §3 예외 ㉡). 도메인 색의 뜻을
  "어느 Agent 결과인가" 에서 **"어느 영역인가"** 로 넓히면서 열린 자리다 — 07 은 제안을 고르는 화면이
  아니라 쌓인 것을 훑는 화면이고(제안 피드백 탭도 이미 지난 제안의 이력이다 · #592), 목록이 네 영역을
  섞어 내려주므로 "한 화면에 2개" 상한의 예외이기도 하다 (그 상한은 제안 화면의 규칙이다). 🚨 **색 면을 타일 밖으로 넓히지 않는다** — 목록에서 줄 전체를 칠하면
  화면이 색 덩어리가 된다. 05 의 열린 제안 줄이 그렇게 칠하고 있었는데, Agent 당 후보가 3가지가
  되면서 면이 여섯이 되어 **거기서도 걷어냈다** (#151 · 도메인은 묶음 머리줄의 칩이 진다).
  🚨 **영역 이름은 항상 글자로 함께 선다** (색이 단독 신호가 될 수 없다).
  🚨 **브랜드는 여전히 못 쓴다** — "어디서 왔나"(도메인) 와 "무엇을 하는가"(브랜드) 를 같은 색으로 쓰지 않는다

- 🚨 **피드백 탭은 채택한 일반 추천도 평가한다** (#509). 05 에서 일반 추천을 채택할 수 있게 됐으니
  해 본 뒤의 평가도 받는다. 줄에 **"또래 기준 일반 추천" 을 글자로** 적고(색 · 점선으로 가르지 않는다),
  둘은 `kind` 로 가른다. 일반 추천 줄의 타입(`ReceivedGeneralSuggestion`)에는 근거 필드가 아예 없다 —
  이 목록은 근거를 그리지 않아서 05 와 달리 한 컴포넌트에 둔다.
  목록(`GET /children/{cid}/suggestions`)과 평가(`PATCH /children/{cid}/suggestions/{sid}/feedback`)는 `kind` 를 가리지 않고, 기본 목록은 `draft` 를 뺀다 —
  05 에서 고르지 않은 일반 추천은 이 탭에 서지 않는다. 일반 추천 줄에 기록 건수를 적지 않는 것도 계약이다
  (`record_count` 는 05 응답 때 세는 값이라 저장되지 않는다). 서버 계약은
  [`docs/api/suggestions-v1.md`](../api/suggestions-v1.md) §7 (#545)

- 🚨 **피드백 탭은 두 보기다 — 피드백 전 / 피드백 완료** (#592). 서버 `?rated=false` · `?rated=true` 이고,
  처음 열면 **피드백 전**이다(이 탭을 여는 일이 평가라서). 주소에는 피드백 완료일 때만 `?view=rated` 가 남는다.
  🚨 **피드백 전에서 평가한 줄은 그 보기에서 빠지고 피드백 완료로 옮겨 간다** — 평가한 줄이 계속 서 있으면
  할 일이 줄지 않는다. 다시 고르는 것은 피드백 완료에서 한다(`PATCH` 가 덮어쓴다).
  🚨 **"전체" 보기를 두지 않는다** — 둘을 다시 한 목록에 섞으면 처음 문제로 돌아간다.
  보기 전환은 `ChoiceField`(legend `sr-only`)라 기록 · 기억 탭의 검색 줄과 같은 자리 · 같은 높이에 선다.
  쪽은 기록 · 기억과 같은 번호 쪽(`Pagination` · 건수 줄은 그 보기의 `total`)이다.
  ⚠️ **받아 둔 목록은 쪽을 넘길 때만 둔다** — 기록 · 기억 탭은 조건을 바꿔도 목록을 두지만, 이 탭은 보기를
  바꾸면 스켈레톤으로 기다린다. 다른 보기의 줄이 남으면 그 사이 칩이 눌리고, 빈 목록이었으면 새 보기의 빈 문구가
  사실과 반대로 선다(피드백 전을 다 평가하고 피드백 완료로 오면 "아직 남긴 피드백이 없어요").
  🚨 **평가하면 지금 쪽을 다시 받는다** (두 보기 모두 무효화) — 안 받고 다음 쪽으로 가면 앞으로 당겨진 한 줄이
  어느 쪽에도 안 보인다. 마지막 쪽의 마지막 줄을 평가해 쪽이 사라지면 앞 쪽으로 옮긴다(기록 · 기억과 같은 처리).
  🚨 **피드백 전이 비어도 "받은 제안이 없다" 고 하지 않는다** — 다 평가해서 비었을 수 있다

- 🚨 **화면에서 부르는 말과 코드의 이름이 다르다** — 관찰(`observation`)은 **기록**, 프로필
  (`profile_affinity`)은 **기억**으로 보여준다. 🚨 **코드·타입·쿼리 키의 이름은 계약서를 따른다.**
  화면 문구만 바꾸고 식별자를 같이 바꾸지 않는다 (바꾸면 계약서와 어긋난다)
- 🚨 **관찰(`ObservationList`)과 프로필(`AffinityList`)을 한 컴포넌트로 만들지 않는다.** 줄과 카드로
  모양이 다른 것이 이 화면의 요점이다 — 한 목록에 섞으면 "한 번 본 것" 과 "확정된 성향" 이 같은
  무게로 읽혀서 최상위 §2("한 번의 관찰을 성향으로 확정하지 않는다")가 화면에서 사라진다.
  두 목록은 **같은 아이콘 타일**을 왼쪽에 세운다 — 한 화면의 두 탭이라 기준선이 다르면 남남으로
  읽힌다. 제안 피드백 카드도 같은 타일 · 같은 글자 층(제목 `body` 600 · 메타 `caption`)이다 (#592). 🚨 `is_stale` 기억 카드만 뉴트럴 타일이다 (카드 전체가 `surface-muted` 인데 색 타일이
  서면 "근거에서 빠져 있다" 를 화면이 되받아친다)
- 🚨 **교정은 기록과 기억이 서로 다른 것을 묻는다** (디자인 시스템 §7 "교정"). 기록은
  `once_only`·`wrong` 둘, 기억은 `need_more_observation`·`outdated`·`wrong` 셋이다.
  `confirm`(맞아요)은 없다 — 서버가 이력으로도 남기지 않아서 타입에서도 뺐다 (#277)
- 🚨 **고르면 확인 단계가 뜨지만 그건 승인 게이트가 아니다.** 승인 게이트는 딱 2곳이고 늘리지
  않는다 (최상위 §2) — `btn-approve` 도 `caution` 도 쓰지 않는다. 게이트가 되돌릴 수 없는 것을
  막는 장치라면 이 단계는 **되돌릴 수 있다는 사실까지 같이 말해 주는** 자리다.
  🚨 확인 문구에 예측을 쓰지 않는다(일어날 일만) · 성공하면 패널을 닫고 버튼으로 되돌린다
  (`key={result?.correction.id}`) · 실패하면 남는다(다시 누르는 것이 재시도다)
- 🚨 **라벨에 조사를 박지 않는다.** `josa(label, "으로/로")`(`es-hangul`)가 받침으로 고른다 —
  라벨은 데이터고 조사는 문법이라, 박아 두면 다른 문장에서 못 쓴다.
  ⚠️ 옵션 키는 **받침형이 앞**이다(`"으로/로"`). `"로/으로"` 는 타입 에러다 교정은 append-only 라
  반대 교정으로 되돌린다 — `wrong` 도 `btn-danger` 가 아니다.
  🚨 **교정을 되돌리는 기능은 주지 않는다** (제품 결정). 기록은 고쳐도 목록에 남지만 서버가 한 번
  고친 기록을 다시 받지 않는다(409 `already_corrected`) — 그래서 **확인 단계가 그 무게를 진다.**
  🚨 **고친 기록은 `status` 로 갈라 그린다** (#266 — 목록이 `deleted` 만 뺀다). 줄은 기억 칩 대신
  고친 표시(아이콘 + 문장 · 칩 모양이면 기억 이름처럼 읽혀서 칩이 아니다)를 달고, `inactive` 는
  `surface-muted` 로 물러선다. 상세는 버튼 대신 무엇으로 고쳤는지(`CORRECTED_OBSERVATION`)를 세우고,
  묶인 기억은 "세지 않는 기억" 라벨로 남긴다 (고친 기록도 `affinity` 가 실려 온다 — 고치기는
  `status` 만 바꾼다). 상세의 "지금 상태" 는 방금 응답 → 다시 받은 상세 → 목록 값 순으로 믿는다 —
  목록 값만 보면 시트를 연 뒤 고친 기록에 버튼이 또 서서 409 를 맞는다.
  ⚠️ 그래서 기록 줄은 한 덩어리가 아니라 하나씩 떨어진다 — 카드와는 모서리 · 간격 · 글자 크기로
  갈린다 (`ObservationList` 주석)
  🚨 **기억 고치기는 명령이 아니라 의견이다** (#277). 서버는 판정으로 기억의 상태를 바꾸지 않고
  쌓인 기록 수로만 다시 센다 — 세 판정 모두 기억이 목록에 남고, `wrong` 만 확인됨의 기준을 한동안
  올린다. 그래서 확인 문구는 어느 기억에서든 확실한 것만 말하고, 실제로 바뀐 상태는 **누른 뒤
  응답으로** 말한다 (`CascadeResult` 가 직전 상태와 비교)
  🚨 **확인 문구의 둘째 줄은 판정마다 둔다** (`VerdictSpec.after`). 대상마다 한 줄로 묶었더니
  목록에 남는 판정에도 "목록에서 빠지고" 가 붙어 첫 줄과 반대말을 했다 (#270 리뷰)
  🚨 화면 문구도 "다시 고칠 수 있어요" 라고 쓰지 않는다. 한동안 "고쳐서 뺀 기록" 필터로 되살릴 수
  있게 뒀다가 내린 자리라, 문구가 남으면 **찾지 못할 길을 약속**하게 된다.
  ⚠️ 기억 탭의 상태 필터에 **`archived` 를 두지 않는다.** 처음 이유는 "고치기로 뺀 기억을 필터로만
  되살리지 않는다" 였는데, 서버(#277)에서 `archived` 는 고치기가 아니라 **기록이 오래 없을 때만**
  생긴다. 그 이유는 사라졌고, 필터를 다시 열지는 따로 정한다
- 🚨 **기록과 기억을 한 단어로 묶지 않는다.** 목록은 줄과 카드로 갈라 놓고 교정 시트의 문구가
  둘을 도로 합치면, 부모는 기억을 고치면서 자기가 기록 한 건을 고치는 줄 안다
  (`CorrectionButtons` 와 `CascadeResult` 가 `targetKind` 로 갈린다)

- 🚨 **07 목록의 필터는 계약서가 주는 것만 만든다** (기록 탭 `?domain=` · `?status=`, 기억 탭
  `?domain=` · `?state=`, 두 탭 공통 `?q=` · `?from=` · `?to=` · `?page=` · #584 · 화면 주소 이름이다 — API 쿼리는 `date_from` · `date_to`). 기록 탭의 상태 필터는 서버 `status` 하나를 고르고(#266), 이름은 고치기
  버튼과 같은 말이다. ⚠️ 그 자리에 있던 "사용되지 않은 기록만"(`unused_in_suggestions`)은 내렸고,
  쓰는 곳이 없어 서버에서도 지웠다 (#286). 🚨 **정렬을 만들지 않는다** — 두 엔드포인트 다 정렬 파라미터가 없고
  기록은 `observed_to DESC`, 기억은 `last_observed_on DESC` 고정이다. 번호 쪽으로 나눠 받으므로 받은 쪽만
  다시 정렬하면 쪽 사이의 순서가 어긋난다. 정렬이 필요하면 계약서 먼저다 (최상위 §8)
- 🚨 **검색어 · 기간 · 쪽도 필터처럼 주소에 남고, 탭을 옮기면 따라가지 않는다** (#584). 화면 주소는
  `?q=` · `?from=` · `?to=` · `?page=` 다 — API 쿼리 이름(`date_from` · `date_to`)과 다르니 링크를 만들 때 헷갈리지 않는다. 쪽 말고 다른
  것을 바꾸면 1쪽으로 돌아간다 — 조건이 바뀌면 쪽 번호는 다른 목록의 번호가 된다. 주소의 값은 그대로
  믿지 않는다: 100자 넘는 검색어, 없는 날짜, 거꾸로 된 기간, 10,000 넘는 쪽은 서버가 400 으로 돌려주므로
  없는 것으로 읽는다 (`?domain=health` 를 전체로 읽는 것과 같다). 한쪽 끝만 있는 기간도 버린다 — 기간 칸은
  그런 기간을 만들지 않는다
  - 🚨 **분류 · 상태 · 기간은 목록 위가 아니라 필터 시트 안에 둔다.** 목록 위에 다 펼치니 검색칸까지 네 줄이
    목록을 화면 아래로 밀었다. 목록 위에는 **검색칸 + 필터 단추 한 줄**과, 걸린 조건이 있을 때만 **조건 칩 줄**이
    선다(칩을 누르면 그 조건만 풀린다 · 검색어는 칩으로 세우지 않는다 — 칸에 이미 보인다).
    시트에서 고른 것은 **"적용하기" 를 눌러야** 걸린다 — 고를 때마다 걸면 시트 뒤의 목록이 칸마다 다시 받아진다.
    "초기화" 는 시트 안의 값만 비운다. 🚨 승인 게이트가 아니다 — `btn-approve` · `caution` 을 쓰지 않는다
  - 🚨 **검색은 치는 동안 부르지 않는다** — 보내기(키보드의 검색)로만 찾는다. 한글은 조합 중인 글자가
    값에 섞여서 칠 때마다 부르면 "ㄱ" · "계" 가 다 요청이 된다. 칸을 비우면(칸 안의 지우기 아이콘 포함) 바로 전체로 돌아간다.
    보내지 않은 검색어는 다른 조건이 바뀌면 칸에서 지운다 — 칸에 보이는 말로 걸러진 목록처럼 읽히지 않게.
    기억 검색은 서버가 띄어쓰기를 무시하고 기록 검색은 그대로 비교한다 — 화면은 둘을 갈라 안내하지 않는다
    (기억은 짧은 이름, 기록은 보호자가 쓴 문장이라 각자 자연스럽다)
  - 🚨 **기간을 계산해서 만들지 않는다** — "최근 한 달" 같은 단추는 그 자체가 날짜 계산이다 (apps/web/CLAUDE.md §4).
    기간은 **한 칸**(`DateRangeField`)의 범위 달력에서 고른다. 두 날을 차례로 누르면 그 사이, 한 날만 누르면 그날 하루다
    (첫 누름이 늘 새 기간이다 — 걸린 기간이 있어도) —
    거꾸로 된 기간도, 한쪽만 열린 기간도 생기지 않는다.
    🚨 **기억 탭은 날짜 기준을 글자로 적는다** — 기록은 관찰 기간이 겹치면, 기억은 **마지막 기록 날짜**가
    범위 안이면 든다. 같은 기간을 골라도 두 탭이 어긋나 보일 수 있는 자리다
  - 🚨 **건수는 그 쪽의 줄 수가 아니라 `total` 이다.** 쪽을 넘기는 줄은 디자인 시스템 §7 "쪽 넘기기"
    (`Pagination`). 받은 쪽이 `total_pages` 를 넘으면(고치기로 건수가 줄었거나 손으로 고친 주소) 빈 목록이라고
    말하지 않고 마지막 쪽으로 옮긴다 — 서버는 범위 밖 쪽에 오류가 아니라 빈 목록을 준다

  - 🚨 **`replace` 로 간다.** `push` 면 뒤로가기가 **저장을 끝낸 확인 화면**으로 돌아오고, 거기서

- 🚨 **목록의 버튼 문구가 그 시트에서 할 수 있는 일을 다 말한다** — "고치기" 만 적어 두니 캘린더에

  - 🚨 **넣은 항목은 목록에서 갈린다** — 칩 + **넣은 일시** 한 줄. 일시까지 세우는 이유는 시트를
    닫으면 방금 고른 일시가 화면 어디에도 안 남기 때문이다. 🚨 위 칸이 같은 날을 이미 말하고
    있으면 **시각만** 낸다 (`formatTimeOfDay` 가 있는 이유 · §4)
  - 🚨 **넣으면서 확인한 값을 그 줄에도 얹는다**(`needs_review: false`). 승인 게이트를 지난 값이라

    "못 읽었어요 · 고쳐야 저장돼요" 라고 계속 말한다. 🚨 그래도 **기록이 저장되는 것은 아니다** —
    저장은 맨 아래 버튼 하나이고 빼는 길("이 항목은 저장하지 않기")도 그대로다
  - 🚨 확인된 줄은 접힌 "잘 읽었어요" 로 옮겨 가므로 **그때 그 묶음을 펼친다** — 안 그러면 방금
    넣은 줄이 화면에서 사라진 것처럼 보인다 (넣었다는 표시를 달고 그 표시를 접는 셈이다)
- 🚨 **사진을 고르는 자리는 08 화면이 아니라 시트다** (`PhotoSourceSheet`). 03 홈 · 04 대화의 카메라
  버튼이 **그 자리에서** 시트를 열고, 촬영/앨범을 고르면 바로 08 의 **읽는 중**으로 넘어간다 —
  고르기만 하는 화면을 한 칸 두지 않는다.
  시트는 세 곳(03 홈 · 04 대화 · 08 의 "다른 사진 고르기")이 **한 벌을 같이 쓴다** —
  화면마다 다른 방식으로 고르게 하면 부모가 매번 다시 찾는다.
  🚨 **파일 입력이 두 개인 이유는 `capture` 다.** 하나만 두면 우리 시트에서 고른 것을 OS 가 또 묻는다
  - 🚨 **고른 파일은 `stores/photo-draft.ts` 로 넘긴다.** `File` 은 URL 에 못 싣고, 라우트 이동이
    사용자 제스처를 소비해서 "08 에 도착한 뒤 파일 입력을 대신 눌러 주기" 도 막힌다.
    **`persist` 금지** (아이 사진 원본 · `draft.ts` 와 같은 규칙) · 한 번 쓰면 `release` 로 뗀다
    (안 떼면 08 을 다시 열 때 지난번 사진이 저절로 올라간다) · `childId` 를 함께 확인한다
  - 🚨 **넘겨받은 사진은 effect 가 아니라 `useState` 초기값으로 받는다.** effect 에서 `setState`
    하면 08 의 첫 프레임이 **사진 없는 화면**이라 "고르면 바로 읽는 화면" 이 한 번 깜빡인다
    (lint 의 `react-hooks/set-state-in-effect` 가 같은 것을 잡는다). `peek` 은 순수한 읽기다
  - 🚨 **objectURL 해제를 effect cleanup 에 걸지 않는다.** StrictMode 가 mount 직후 cleanup 을
    한 번 돌려서 방금 넘겨받은 사진이 그 자리에서 해제된다 (`ERR_FILE_NOT_FOUND` 로 났다).
    만드는 것도 해제하는 것도 스토어 한 곳이고, 해제는 **다음 사진**과 **로그아웃** 두 이벤트뿐이다 —
    살아 있는 URL 은 언제나 최대 한 개다
- 🚨 **`lane` 은 부모가 시트에서 **고른다.** 서버 추측이 정하지 않는다.** 계약서 §09 의 `lane`
  이벤트는 추측이고, 무엇을 찍었는지는 찍은 사람이 안다 — 그래서 시트가 먼저 묻고
  (`어떤 사진인가요?` 라디오 2칸) 고른 값을 업로드 multipart 의 `lane` 으로 싣는다.
  🚨 **서버 추측은 선언을 덮지 않는다.** 어긋날 때만(`confidence >= 0.6`) 확인 화면에 한 줄이
  서고, 바꾸는 버튼에는 "아니에요" 가 아니라 **바뀔 결과**를 쓴다(`아이 활동 사진이에요`).
  🚨 **시트는 두 단계다. 한 화면에 쌓지 않는다** — ㉠ 어떤 사진인가 → ㉡ 어디서 가져오나
  (최근 사진 · 촬영 · 앨범). 처음엔 한 화면에 셋을 세우고 앞을 안 고르면 뒤를 비활성으로 뒀는데,
  **할 일이 하나인 순간에 세 덩어리를 보여 주고** 꺼진 것들이 "왜 안 눌리지" 를 먼저 묻게 만들었다.
  🚨 **시트 제목이 지금 묻는 것**이다 (㉠ "어떤 사진인가요?" · ㉡ 고른 종류의 이름) — 같은 제목을
  쓰면 넘어간 것이 화면에 안 보인다. 🚨 ㉠ 에 확인 버튼을 두지 않는다(고르면 바로 ㉡)
- 🚨 **최근 사진 줄은 네이티브 셸이 있을 때만 선다** (`lib/native/recent-photos.ts`).
  **웹은 기기 갤러리를 읽을 수 없다** — 파일 입력은 OS 피커를 열 뿐이고 목록을 먼저 가져오는
  API 가 없다. 셸(`apps/mobile`)이 `expo-media-library` 로 읽어 `window.icatch.recentPhotos` 에
  꽂아 주는 구조였는데, ⚠️ **첫 스토어 배포 전에 셸 구현을 뺐다** (#408 — Google Play 사진 권한 심사).
  그래서 지금은 앱에서도 이 줄이 서지 않는다. 계약은 다시 넣을 때를 위해 남겨 둔다.
  🚨 **셸이 없으면 줄 자체를 그리지 않는다** — 빈 상자도 권한 안내도 띄우지 않는다
  (브라우저에는 허용할 권한이 아예 없다). 개발 환경에서 화면을 보려면 목 스위치를 켠다
  (`mocks/native-bridge.ts` 가 가짜 썸네일을 꽂는다)
- 🚨 **08 의 문서 lane 은 항목을 미리 골라 두고, 활동 lane 은 하나도 고르지 않은 채로 시작한다.**
  기관이 적어 준 글자를 옮긴 것과 모델이 아이에 대해 추측한 것을 같은 무게로 두지 않는다
  (최상위 §2 "한 번의 관찰을 성향으로 확정하지 않는다"). 같은 이유로 활동 lane 은 태그를 하나도
  안 고르면 저장 버튼이 눌리지 않는다 — 화면이 바로 위에서 한 말을 스스로 뒤집지 않게

## 5. 09 캘린더 — 표식 · 일기 · 준비물

- 🚨 **09 월 그리드의 표식은 색이 아니라 모양이다** (디자인 시스템 §7 캘린더 그리드). 전부
  `currentColor` 라 고른 날·오늘·비활성의 글자색을 따라간다 — 표식에 색을 주면 도메인 4색과 섞인다.
  🚨 **범례를 지우지 않는다.** 모양을 뜻으로 잇는 자리가 거기 하나뿐이라, 없으면 단독 신호가 된다

- 🚨 **일기를 관찰과 같은 구역·같은 표식으로 그리지 않는다.** 일기는 관찰로 자동 추출되지 않는다
  (계약서 §09). 같은 점을 찍거나 한 목록에 합치면 화면이 그 규칙의 반대말을 한다
- 🚨 **"채우려고 만들지 않아요" 와 채우는 버튼을 붙여 놓지 않는다.** 빈 날의 `EmptyState` 에 일기 쓰기
  버튼을 달았더니 화면이 스스로를 부정했다 — 사실을 말하는 자리와 할 일을 주는 자리를 나눈다.
  쓰기 줄은 빈 상태가 아니라 일기 구역에 따로 서고, 쓰는 동안에는 빈 상태를 내린다.
  같은 이유로 요약 줄은 빈 날에 아무 말도 하지 않는다 — 같은 패널의 빈 상태가 같은 말을 더 크게 한다
- **하루 패널은 일기, 일정, 기록, 대화, 사진 순서로 선다** (#503). 그날을 다시 연 보호자가 먼저 찾는 것은
  자기가 쓴 글인데, 기록 아래에 두니 기록이 있는 날마다 스크롤해야 보였다
- 🚨 **일기 구역은 누른 자리가 그대로 바뀐다** (#503).
  - 일기가 없으면 글 카드가 설 자리에 **"이날의 일기 쓰기" 줄**이 서고(아이콘 · 글 · 화살표, 아래 "이날 남긴 기록"
    줄과 같은 모양), 누르면 그 줄이 편집기가 된다. 제목 줄 오른쪽에 "쓰기" 버튼 하나를 둔 적이 있는데, 덩그러니
    놓여 무엇을 쓰는지 약했고 일기가 생기면 자리도 바뀌었다. 이 줄은 입력창이 아니다 — 아래 빈 입력창 규칙 그대로다
  - 일기가 있으면 "고치기" · "지우기" 가 제목 줄 오른쪽에 선다. 한동안 "일기 쓰기" 를 09 화면 머리에, 고치기 · 지우기를
    카드 아래 바깥에 뒀는데, 쓰기를 누르면 멀리 떨어진 자리에서 편집기가 열렸고 고치기 · 지우기는 카드와
    따로 노는 줄로 보였다. 제목을 카드 안에 넣었던 때도 있는데, 한 패널에 구역 머리 모양이 둘이 됐다
  - **하루 패널의 구역 머리는 한 모양이다** (`Section`). 제목 줄은 버튼이 없어도 버튼 높이(`min-h-touch`)라,
    버튼이 선 구역만 제목과 내용 사이가 벌어지지 않는다
  - **빈 날에도 일기 구역이 서지만 쓰기 줄 하나뿐이다.** 빈 입력창을 세우지 않는다 — 쓰겠다고 누른 날만
    편집기가 열린다. 그날 일기를 쓰는 법이 날마다 같다
  - **고치기 · 지우기는 아이콘(`Pencil` · `Trash2`)이다.** 글자 버튼 둘을 제목 옆에 두면 일기 글보다 버튼이
    먼저 읽혀서, 11-1 측정 기록 줄처럼 아이콘으로 두었다. 이름은 "일기 고치기" · "일기 지우기" 다 —
    스크린리더로 버튼만 훑어도 무엇을 하는지 안다
  - **일기 카드는 칸 둘이 구분선으로 나뉜다** — 글 / 확인 띠(지우기 확인). 확인 띠만 바탕이 `surface-muted` 다 —
    11-1 측정 기록 줄의 확인 띠와 같은 모양이라, 한 건 지우기가 같은 모양으로 묻는다. 칸마다 상자를 따로
    두르지 않는다(카드 안에 카드가 생긴다)
  - **편집기는 열리면 포커스를 받고, 저장 · 취소 · 지우기 뒤에는 다시 선 쓰기 줄이나 고치기가 받는다.**
    누른 버튼이 편집기나 확인 띠째 사라져서, 그대로 두면 포커스가 `<body>` 로 떨어진다
  - **지우기 확인은 "이 일기를 지울까요?" 한 줄이다.** "되살릴 수 없어요 · 사진은 그대로 남아요" 를 붙였었는데,
    한 편을 지우는 확인치고 글이 길어 띠가 무거웠다 (10-17 결정)
  - **"일기는 아이 기록으로 저장되지 않아요" 는 쓰는 동안에만 보인다.** 알고 써야 하는 순간이 그때고,
    읽는 카드마다 붙으면 카드가 일기보다 안내문으로 읽힌다
  - **편집기는 1000자까지 받고, 입력칸 아래 오른쪽에 `n/1000` 을 보여준다** (#549). 10 문제 알리기와 같은
    마크업이다(`maxLength` · 스크린리더용 "글자 수"). 서버도 1000자를 넘으면 400 으로 거절한다.
    🚨 신고와 달리 앞뒤 공백을 떼지 않고 센다 — 일기는 원문 그대로 저장되고 서버도 원문 길이로 센다.
    상한은 `DIARY_CONTENT_MAX_LENGTH`(`lib/api/types.ts`)이고 서버 상수와 같은 값이다.
    이미 1000자를 넘게 저장된 일기는 따로 다루지 않는다(실사용 데이터가 없다). 고치기로 열면 카운터가
    1000을 넘고 저장이 거절된다
- **일정 카드의 준비물은 두 열로 선다** (#568). 체크 한 줄이 누르는 영역(44px)이라 세로로만 쌓으면 8개에
  350px 을 넘었다. 줄 높이는 못 줄여서 배치를 바꿨다.
  - **열 수는 카드 폭으로 정한다** (`@container` · `@2xs` = 18rem). 360 폭 폰까지 두 열이고, 320 폭에서는
    한 열이다. 기준이 rem 이라 root 글자 크기를 키우면(130%) 390 폭에서도 한 열로 돌아간다
  - ⚠️ **글자 토큰만 키우는 검사**(디자인 시스템 §10 "글자만 확대 200%")에서는 기준이 그대로라 **두 열로 남는다.**
    칸 안에서 서너 글자씩 꺾일 뿐 가로로 넘치지는 않는다(`Checkbox` 라벨의 `min-w-0` · `break-words`).
    안드로이드 웹뷰의 시스템 글꼴 크기(`textZoom`)가 둘 중 어느 쪽으로 동작하는지는 실기기로 아직 확인 전이다
  - 🚨 **체크한 준비물을 아래로 보내거나 숨기지 않는다.** 누른 손가락 아래에서 목록이 움직여 다음 항목을
    잘못 누른다 (디자인 시스템 §8)
  - 칩 줄로 바꾸지 않은 이유: 이 앱에서 칩은 "고르는 것"(01 관심사, 07 피드백)이라 눌린 칩이 "챙겼다" 로
    읽히지 않는다. 일부만 보여주고 접기는 펼치는 한 번이 매번 더해져서 두 열로도 길면 그때 더한다
- 🚨 **하루 패널에서 사진을 넣지 않는다** (#503). 사진 구역은 이미 남은 사진이 있는 날에만 서고 사진만 보여준다.
  넣는 길은 03 홈의 카메라다. 그래서 08 의 `?date=` 를 싣는 화면이 지금은 없다 — 08 은 날짜가 없으면 오늘로 둔다
- 🚨 **"이날 나눈 대화" 는 대화가 있는 날에만 선다** (`chat_count` · #228). 일기와 달리 여기서 대화를 시작하지
  않아서, 빈 날에 세우면 아무것도 없는 곳으로 가는 문이 된다. 내 대화만 센 수다. 누르면 04 를 `?date=` 로 열어
  그날부터 그린다 ([`chat-run-v1.md`](chat-run-v1.md) §4). 대화만 있는 날도 "아무것도 없어요" 가 아니다
- **하루 패널의 누르는 줄은 한 모양이다** (#503). "이날의 일기 쓰기" 와 "대화 N개 보기" 는 "이날 남긴 기록" 줄과
  같은 줄(아이콘 · 글 · 화살표, `PANEL_ROW`)이다. 테두리 버튼 하나를 구역에 두면 덩그러니 놓여 보였다.
  대화 줄은 04 로 가는 것이라 `<Link>`, 쓰기 줄은 그 자리를 편집기로 바꾸는 것이라 `<button>` 이다
