# 일정 초안 화면 v1

문서 목적: 일정 초안(event draft)이 **언제 생기고 어떤 흐름으로 캘린더에 들어가는지**를 경로 3개 기준으로 고정한다.

기준 브랜치: `feat/fe-151-event-draft-card`
작성일: 2026-09-25
담당: 고태영
선행 문서: [`docs/event/event-draft-flow-v1.md`](../event/event-draft-flow-v1.md) (서버가 내는 payload 계약. 이 문서는 그 payload 를 **화면이 어떻게 다루는지**를 정한다)

---

## 1. 초안이 생기는 시점 — 세 곳

| | 언제 생기나 | 만드는 곳 | 장수 | `op` |
| --- | --- | --- | --- | --- |
| ㉠ 한 줄 입력 | 보호자가 03 홈에 일정을 말한 run 에서 | Memory Agent | **N** | `create` + `update` 섞임 |
| ㉡ 제안 카드 | 05 에서 제안을 고른 순간 | suggestion 도메인 (서버) | **1** | `create` |
| ㉢ 사진(알림장) | 08 에서 사진을 읽은 뒤 | OCR 파이프라인 | **N** | `create` |

🚨 **셋 다 같은 payload 를 낸다** (#121 · #122 합의). 모양이 갈리면 화면이 여러 벌이 된다.

## 2. 경로별 Flow

### ㉠ 한 줄 입력

```
03 홈 "금요일에 물놀이 있어"
  → POST /children/{cid}/inputs        (202, run_id)
  → SSE 초안 프레임                     ⚠️ 이름만 잠정이다. 모양은 확정 (§4)
  → 04 저장 결과 레이어에 카드 N장
  → 카드마다 제출                       ← 승인 게이트 ㉠
```

### ㉡ 제안 카드

```
05 제안 후보에서 하나 고르기
  → POST /suggestions/{sid}/event      🚨 쓰기 없음. { draft, prechecks } 만 (#121)
  → 05 위 바텀시트에 카드 1장 + 알레르기 사전검사
  → 제출                                ← 승인 게이트 ㉠
```

🚨 **제안 정보만으로는 일자를 모른다.** 초안의 `starts_at` 이 `null` 로 오고, 보호자가 채우기 전에는 제출이 잠긴다.

### ㉢ 사진(알림장)

```
08 사진 업로드
  → POST /photo-runs/{rid}/commit      🚨 쓰기 없음. 초안만 낸다 (§4 — 결정 대기)
  → 08 화면에 카드 N장 (확인이 필요한 것 위 · 잘 읽은 것 아래)
  → 카드마다 제출                       ← 승인 게이트 ㉠
```

## 3. 세 경로가 공유하는 규칙

### 3-1. 그릇은 셋, 카드는 한 벌

카드는 `apps/web/src/components/event-draft-card.tsx` 하나다. 그릇(04 레이어 · 05 시트 · 08 화면)만 셋이다.

"한 벌"의 목적은 **payload 가 같아서 그리는 코드가 한 벌**인 것이다. 한 장을 위해 화면을 따로 띄우거나 N 장을 시트에 밀어넣는 쪽은 이미 두 번 실패했다 ([`apps/web/CLAUDE.md`](../../apps/web/CLAUDE.md) §3 · `safety-scan-review.tsx` 머리말).

### 3-2. 초안을 만드는 것은 게이트가 아니다

9/17 에 `event.status` 가 없어지면서 **승인 전 행을 DB 에 두지 않는다.** 초안은 SSE 와 응답에만 있다.

| | 쓰나 | 게이트인가 |
| --- | --- | --- |
| 초안 만들기 (세 경로 전부) | ✗ | 아니다 |
| 제출 | ✓ | 🚨 **승인 게이트 ㉠** |

그래서 카드의 제출 버튼만 `btn-approve` 이고, 게이트를 늘린 것이 아니라 **있던 게이트가 그 버튼으로 옮겨온 것**이다 (최상위 [`CLAUDE.md`](../../CLAUDE.md) §2 — 딱 2곳).

### 3-3. 제출은 건별이다 (9/21 회의)

초안 여러 장을 한 요청으로 묶지 않는다. 카드마다 자기 버튼을 갖고 성공·실패도 따로 선다.

- `op` 에 따라 엔드포인트가 갈린다 — create 는 `POST`, update 는 `PATCH`
- 본문은 **보호자가 확인한 최종 상태 전체**다 (부분 갱신이 아니다). `items` 배열에서 빠진 `item_id` 가 삭제다
- `draft_id` 는 싣지 않는다 — 화면이 카드를 가리키고 세션 스토리지 키로 쓰는 **화면 전용 키**다
- ⚠️ 그래서 화면에 카드가 N장이면 `btn-approve` 도 N개다. 디자인 시스템 §7 "한 화면에 primary 하나"와 부딪히는 자리인데, 화면 결정이 아니라 **건별 제출 결정에서 온 제약**이다 (§5)

### 3-4. 못 읽은 값을 화면이 채우지 않는다

일자가 비어서 오는 경로가 둘이다 (㉡ 제안 · ㉢ 사진). 🚨 **오늘로 기본값을 넣지 않는다** — 넣으면 "확인하고 넣은 것"과 "들어간 것"이 달라진다.

- 비면 제출 버튼이 잠기고, **왜 잠겼는지**가 버튼 위에 선다
- 왜 비었는지는 경로를 아는 쪽(`review_reason`)이 말한다. 🚨 **카드가 출처를 지어내지 않는다**

### 3-5. 준비물

- `items` 가 최종 목록이라 **빼기가 화면에 있어야 계약이 성립**한다
- 🚨 **체크박스를 그리지 않는다.** `is_prepared` 는 payload 에 없고 체크는 `PATCH /event-items/{iid}` 만의 몫이다

### 3-6. 초안의 수명

서버에 남지 않는다 (9/21). **화면이 세션 스토리지에 들고, 같은 `event_id` 의 초안은 최신 한 장만 남긴다.**

새로고침하면 사라진다 — 화면 문구를 그 기준으로 쓴다.

## 4. 셋을 같은 모양으로 맞추면서 생기는 것

세 경로를 **전부 초안 + 건별 제출**로 짠다. 아직 계약이 덜 정해진 자리는 잠정으로 잡고, 확정되면 한 곳만 고친다.

| | 잠정으로 잡는 것 | 확정되면 고칠 곳 |
| --- | --- | --- |
| ㉠ 한 줄 입력 | SSE 이벤트 **이름**. 모양(`{ drafts: [...] }` 한 프레임)은 확정이다 (#122) | `lib/api/sse.ts` 의 `RunEvent` 한 줄 · 목 |
| ㉡ 제안 | 제출 엔드포인트 경로 | `lib/api/idempotency.ts` 의 `idempotentPath` 표 한 줄 (차단·목·테스트가 따라온다) |
| ㉢ 사진 | `POST /photo-runs/{rid}/commit` 이 **쓰지 않고 초안만 낸다** | 아래 🚨 |

### 🚨 ㉢ 은 결정이 아직 안 났다 — 따로 공유한다

`event.status` 가 없어지면서(9/17 · #118) `commit` 이 **게이트 없이 캘린더에 쓰는 유일한 경로**가 됐다.
#121 에서 제기했지만 답이 오지 않은 항목이다.

| 갈래 | 화면이 어떻게 되나 |
| --- | --- |
| commit 이 게이트 ㉠ 이다 | 08 이 곧 승인 화면. 초안 카드가 안 들어가고 `caution`·`btn-approve` 를 쓴다 |
| **commit 은 초안만 낸다** (지금 짜는 쪽) | 다른 둘과 같아진다. 카드 N장 → 건별 제출 |

후자로 짜 둔 이유는 그쪽이 **결정이 날 때까지 §2 를 안 깨는** 방향이기 때문이다 —
초안만 내면 쓰는 것은 카드의 제출 하나뿐이고, 게이트 없는 쓰기 경로가 생기지 않는다.
전자로 정해지면 08 을 승인 화면으로 되돌리고 계약서와 최상위 `CLAUDE.md` §2 에 게이트로 명시해야 한다.

🚨 **승인 게이트 정책이라 PM 최종 결정 사안이다** (최상위 [`CLAUDE.md`](../../CLAUDE.md) §8).

## 5. 정해야 하는 것

1. **빈 필드 표시를 한 모양으로 통일할지** — 사진 경로의 `needs_review` / `review_reason` 을 세 경로 공통으로 쓰자는 제안이다. 경로마다 다르게 말하면 카드가 경로별로 분기한다
2. **`suggestion_id` 를 초안 payload 어디에 실을지** — #122 에서 "제안 경로 PR 에서 정한다"로 미뤄 둔 자리
3. **카드 N장일 때 `btn-approve` 가 N개인 것** (§3-3) — 목록 항목 예외로 읽고 있지만 디자인 시스템에 근거를 남길지
