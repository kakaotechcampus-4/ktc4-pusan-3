# 일정 초안 화면 v1

문서 목적: 일정 초안(event draft)이 **언제 생기고 어떤 흐름으로 캘린더에 들어가는지**를 경로 3개 기준으로 고정한다.

기준 브랜치: `feat/fe-151-event-draft-card`
작성일: 2026-09-25
담당: 고태영
선행 문서: [`docs/event/event-draft-flow-v1.md`](../event/event-draft-flow-v1.md) (서버가 내는 payload 계약. 이 문서는 그 payload 를 **화면이 어떻게 다루는지**를 정한다)

---

## 1. 초안이 생기는 시점 — 세 곳

| | 언제 생기나 | 만드는 곳 | 장수 | `op` |
| --- | --- | --- | --- | --- |
| ㉠ 한 줄 입력 | 보호자가 03 홈에 일정을 말한 run 에서 | Memory Agent | **N** | `create` + `update` 섞임 |
| ㉡ 제안 카드 | 05 에서 고른 제안들을 "일정 만들기" 로 넘길 때 | suggestion 도메인 (서버) | **1~N** (아래) | `create` |
| ㉢ 사진(알림장) | 08 에서 항목을 열어 "일정으로도 넣기" 를 켤 때 | 보호자 (읽은 값 위에서) | **항목마다 1** | `create` |

🚨 **셋 다 같은 것을 만든다** — `POST /children/{cid}/events` 로 가는 같은 본문이다 (#121 · #122 합의). 모양이 갈리면 화면이 여러 벌이 된다.

🚨 **그리는 방식은 둘이다.** ㉠·㉡ 은 서버가 만든 초안을 **카드**로 그리고, ㉢ 은 보호자가 고치는 **시트 안**에서 만든다 (§2 ㉢ 참고) — 사진은 확인·수정하는 자리가 이미 있어서 카드를 한 번 더 세우면 같은 항목을 두 번 확인하게 된다.

---

## 2. 경로별 Flow

### ㉠ 한 줄 입력

```
03 홈 "금요일에 물놀이 있어"
  → POST /children/{cid}/inputs        (202, run_id)
  → SSE 초안 프레임                     ⚠️ 이름만 잠정이다. 모양은 확정 (§4)
                                       🚨 한 run 이 create·update 를 같이 낸다
  → 04 저장 결과 레이어에 카드 N장
  → 카드마다 제출                       ← 승인 게이트 ㉠
```

### ㉡ 제안 카드

```
05 제안 후보 — Agent 마다 후보 3가지. 🚨 여러 개 고를 수 있다 (체크박스)
  → POST /children/{cid}/suggestions/event-drafts  { suggestion_ids: [...] }
      🚨 쓰기 없음. { drafts, prechecks } 만
  → 05 위 바텀시트 = 알레르기 사전검사(게이트 ㉡) + 초안 N장 (한 장씩 넘김)
  → 카드마다 제출                       ← 승인 게이트 ㉠
```

🚨 **고른 개수와 초안 개수가 1:1 이 아니다.**

| 고른 제안 | 초안 |
| --- | --- |
| `food` 여러 건 | **한 끼로 묶여 1건** ("저녁 식사" · 고른 제안이 준비물로 붙는다) |
| 나머지 Agent | 고른 수만큼 |

🚨 **묶는 판단은 화면이 하지 않는다.** 저녁 반찬 둘이 한 끼인지는 도메인 지식이라 서버가 정하고, 화면은 응답이 준 장수를 그대로 쓴다 — 그래서 요약 카드도 "고른 것 3건" 까지만 말하고 "일정 2건이 돼요" 라고 미리 말하지 않는다 (응답과 다르면 거짓말이 된다).

🚨 **묶인 초안은 `suggestion_ids` 가 여러 개다.** 단수로 두면 묶인 나머지 제안이 `draft` 인 채 24시간 뒤 만료된다 — 보호자는 골랐는데.

🚨 **`health` 제안에는 체크박스가 없다.** 고를 수 있는 것이 아니라 모아 둔 기록을 보여주는 줄이다 (Health Agent 는 진단하지 않는다 · 최상위 §2).

🚨 **제안 정보만으로는 일자를 모른다.** 초안의 `starts_at` 이 `null` 로 오고, 보호자가 채우기 전에는 제출이 잠긴다.

🚨 **알레르기 사전검사(`prechecks`)는 카드가 아니라 시트가 진다.** 게이트 ㉡ 이고 이 경로에만 오기 때문이다. 🚨 **막히는 것은 그 재료가 든 초안뿐이다** — 식사 초안의 알레르기로 놀이 초안까지 막으면 버그다. 어느 초안 것인지는 `Precheck.draft_id` 가 말하고, ⚠️ **서버가 안 실으면 전부 막는다** (알레르기에서 덜 막는 쪽으로 기울 수 없다).

🚨 **사전검사를 붙이는 것은 서버다. 화면이 `agent` 로 거르지 않는다** (최상위 [`CLAUDE.md`](../../CLAUDE.md) §3 — 알레르기 필터는 코드가 막는다). 목은 `food` 일 때만 붙이고, 계약 테스트가 그 동작을 건다. ⚠️ 기준이 `agent === "food"` 인지 "재료가 있을 때" 인지는 §6 의 열린 질문이다.

### ㉢ 사진(알림장)

```
08 사진 업로드
  → SSE parsed (entries[])             확인이 필요한 것 위 · 잘 읽은 것 아래
  → 항목의 "고치기 · 일정 넣기" → 시트
      ☐ 일정으로도 넣기 → POST /children/{cid}/events   ← 승인 게이트 ㉠ (항목마다)
      넣은 항목은 목록에서 칩 + 넣은 일시로 갈린다
  → 화면 맨 아래 "이 내용으로 저장"
      → POST /photo-runs/{rid}/commit  관찰 여러 건을 한 번에. 🚨 일정은 안 만든다
      → 끝나면 03 홈으로 (결과 화면 없음)
```

🚨 **버튼 문구가 그 시트에서 할 수 있는 일을 다 말한다** (#151). "고치기" 만 적어 두니 **캘린더에
쓰는 일이 그 안에 있다는 것이 목록 어디에도 안 보였다** — 열어 본 사람만 아는 기능이 됐다.
급식 항목은 예외다(일정 칸을 아예 안 세운다) · 이미 넣은 항목도 "고치기" 로 돌아간다(넣을 일이 없다).

🚨 **넣은 항목은 목록에서 갈린다.** 칩("캘린더에 넣었어요") + **넣은 일시** 한 줄이 선다.
일시까지 세우는 이유는, 시트를 닫으면 방금 고른 일시가 화면 어디에도 안 남아서 확인하려면
캘린더까지 가야 하기 때문이다. 🚨 **기록의 "언제" 와 다른 줄이다** — 위는 아직 저장 안 한 기록의
값이고 아래는 이미 들어간 값이라, 한 줄에 합치면 저장하지도 않은 것이 들어간 것처럼 읽힌다.

🚨 **저장하면 바로 홈이다** (#151). 저장 결과 화면과 "사진 하나 더 넣기" 를 없앴다 — 여기서 할 일은
끝났고 저장한 것은 홈·07·09 가 이미 보여준다. 확인만 하는 화면이 한 칸 더 서면 부모는 **끝난 일을
한 번 더 닫아야** 한다. 🚨 `replace` 로 간다 — `push` 면 뒤로가기가 **저장을 끝낸 확인 화면**으로
돌아오고 거기서 같은 것을 또 누를 수 있다 (웹뷰의 기기 뒤로가기가 히스토리 기반이다).
🚨 커밋 성공에서 `qk.child` 를 무효화한다 — run 이 끝날 때의 무효화는 커밋보다 **먼저** 돈다.

🚨 **여기만 카드를 쓰지 않는다.** 다른 둘은 초안 카드로 그리는데, 사진은 **고치는 자리가 이미 있다** — 알림장에서 읽은 값을 보호자가 확인·수정하는 시트가 그것이다. 거기서 일정 칸을 한 번 더 열면 같은 항목을 두 화면에서 두 번 확인하게 된다.

🚨 **일정과 기록은 버튼이 다르고, 시점도 다르다.**

| | 어디서 | 언제 | 몇 건 |
| --- | --- | --- | --- |
| 일정 | 고치기 시트의 `btn-approve` | 누르는 즉시 (게이트 ㉠) | 항목마다 한 건 |
| 기록 | 화면 맨 아래 저장 버튼 | 맨 마지막 | 확인한 것 **여러 건 한 번에** |

하나를 눌렀다고 다른 하나가 되지 않는다. 그래서 저장 버튼 아래 한 줄이 **"일정 N건은 이미 캘린더에 넣었어요(저장과는 따로예요)"** 를 말한다 — 안 말하면 저장만 누르고 일정도 됐다고 믿거나, 반대로 이미 들어간 것을 아직 안 들어갔다고 믿는다.

🚨 **요약 카드에 회색 면을 쌓지 않는다.** 한동안 이 말과 "확인하지 않은 N건은 저장하지 않아요" 가 **각자 회색 상자**로 서서, 카드 하나에 같은 면이 세 겹이었다(미저장 안내까지). 셋 다 **"무엇이 저장되나"** 한 질문의 답이라 자리를 나눴다 — 빠지는 건수는 `확인한 것` 바로 아래 **목록의 한 줄**(`확인 안 한 것  1건 · 저장하지 않아요`)로, 넣은 일정은 **저장 버튼 아래 한 줄**로. 남는 회색 면은 "아직 아무것도 저장되지 않았어요" 하나다 (디자인 시스템 §11 이 정한 중립 라벨).

🚨 **`commit` 은 일정을 만들지 않는다.** `event.status` 가 없어진 뒤(#118) 이 커밋이 게이트 없이 캘린더에 쓰는 유일한 경로였는데, 일정을 아예 안 만들면 그 경로 자체가 사라진다 (§4 의 미결이 이 방향으로 닫혔다).

🚨 **급식 항목에는 일정 칸을 세우지 않는다.** 식단표는 전부 날짜가 있지만 일정이 아니다 — 세우면 한 달치 급식마다 "일정으로 넣을까" 를 묻게 된다.

## 3. 세 경로가 공유하는 규칙

### 3-1. 카드는 한 벌, 그릇은 둘 (사진은 카드를 안 쓴다)

카드는 `apps/web/src/components/event-draft-card.tsx` 하나이고, 여러 장을 넘기는 묶음은
`event-draft-list.tsx` 하나다. 그릇은 **04 결과 레이어**와 **05 승인 시트** 둘이다.
🚨 **08 은 카드를 안 쓴다** — 고치기 시트가 그 일을 한다 (§2 ㉢).

"한 벌"의 목적은 **payload 가 같아서 그리는 코드가 한 벌**인 것이다. 한 장을 위해 화면을 따로 띄우거나 N 장을 시트에 밀어넣는 쪽은 이미 두 번 실패했다 ([`apps/web/CLAUDE.md`](../../apps/web/CLAUDE.md) §3 · `safety-scan-review.tsx` 머리말).

### 3-2. 초안을 만드는 것은 게이트가 아니다

9/17 에 `event.status` 가 없어지면서 **승인 전 행을 DB 에 두지 않는다.** 초안은 SSE 와 응답에만 있다.

| | 쓰나 | 게이트인가 |
| --- | --- | --- |
| 초안 만들기 (세 경로 전부) | ✗ | 아니다 |
| 제출 | ✓ | 🚨 **승인 게이트 ㉠** |

그래서 카드의 제출 버튼만 `btn-approve` 이고, 게이트를 늘린 것이 아니라 **있던 게이트가 그 버튼으로 옮겨온 것**이다 (최상위 [`CLAUDE.md`](../../CLAUDE.md) §2 — 딱 2곳).

### 3-3. 제출은 건별이다 (9/21 회의)

초안 여러 장을 한 요청으로 묶지 않는다. 카드마다 자기 버튼을 갖고 성공·실패도 따로 선다.

- `op` 에 따라 엔드포인트가 갈린다 — create 는 `POST`, update 는 `PATCH`. 🚨 **키는 create 만 받는다** — `items` 가 최종 목록이라 PATCH 는 같은 본문을 두 번 보내도 결과가 같다(멱등). 이 판단이 틀리면 `idempotentPath` 표에 줄을 더한다
- 본문은 **보호자가 확인한 최종 상태 전체**다 (부분 갱신이 아니다). `items` 배열에서 빠진 `item_id` 가 삭제다
- `draft_id` 는 싣지 않는다 — 화면이 카드를 가리키고 세션 스토리지 키로 쓰는 **화면 전용 키**다
- 카드마다 승인 버튼이 붙지만 **화면에는 하나만 선다** — 여러 장이면 한 장씩 넘기기 때문이다 (아래 3-7). 05 도 같은 문제를 풀었는데 **답이 다르다**: 거기는 후보 3가지가 한 화면에 전부 펼쳐져 있어서, 고르는 것을 버튼이 아니라 **체크박스(제안 문장이 라벨)** 로 만들어 초록을 하단 CTA 하나로 몰았다

### 3-4. 못 읽은 값을 화면이 채우지 않는다

일자가 비어서 오는 경로가 둘이다 (㉡ 제안 · ㉢ 사진). 🚨 **오늘로 기본값을 넣지 않는다** — 넣으면 "확인하고 넣은 것"과 "들어간 것"이 달라진다.

- 비면 제출 버튼이 잠기고, **왜 잠겼는지**가 버튼 위에 선다
- 왜 비었는지는 경로를 아는 쪽(`review_reason`)이 말한다. 🚨 **카드가 출처를 지어내지 않는다**

🚨 **시각도 같은 규칙이다** (#151). 한동안 이 규칙이 **날짜에만** 걸려 있어서, 날짜를 고르면 시각이 **자정으로 접혀** `all_day: false` 로 제출됐다 — 아무도 고르지 않은 "오전 12:00" 이 승인 게이트를 지나갔다. 지금은 시각 칸(`time-field`)이 서고, 안 고르면 날짜와 똑같이 제출이 잠긴다.

- 🚨 **"하루 종일" 은 시각을 안 묻는 것**이지 자정을 고른 것이 아니다. 그때만 자정을 쓰고 `all_day: true` 가 그 사실을 함께 나른다 — 시각이 비어서 자정이 된 것과 화면에서도 payload 에서도 구분된다
- 🚨 **날짜와 시각을 `starts_at` 하나로 들지 않는다.** 그러면 "날짜는 골랐고 시각은 아직" 을 담을 자리가 없어서 그 상태가 자정으로 접힌다 (그게 위 버그였다). 화면은 둘을 따로 들고, `starts_at` 은 둘이 다 차야 생긴다 (`withSeoulDateTime`)

### 3-5. 준비물

- `items` 가 최종 목록이라 **빼기가 화면에 있어야 계약이 성립**한다
- 🚨 **체크박스를 그리지 않는다.** `is_prepared` 는 payload 에 없고 체크는 `PATCH /event-items/{iid}` 만의 몫이다

### 3-6. 초안의 수명

서버에 남지 않는다 (9/21). **화면이 세션 스토리지에 들고, 같은 `event_id` 의 초안은 최신 한 장만 남긴다.**

새로고침하면 사라진다 — 화면 문구를 그 기준으로 쓴다.

### 3-7. 여러 장이면 한 장씩 넘긴다

카드는 제목·일시·하루 종일·준비물·제출까지 든 **긴 물건**이라, 알림장에서 셋이 나오면 세로로 쌓았을 때 화면 서너 폭이 된다. 부모는 스크롤로만 전체를 알게 된다.

🚨 **05 제안 목록과 반대로 간다.** 거기도 후보가 여럿인데 접지 않고 전부 펼친다 — **고르는 화면**이라 셋을 견주려면 이유와 근거가 같이 보여야 하기 때문이다. 여기는 고르는 화면이 아니라 **하나씩 처리하고 넘기는** 화면이고, 줄이 아니라 **폼**이라 견줄 것도 없다. 그래서 같은 "여럿" 을 한쪽은 펼치고 한쪽은 한 장씩 넘긴다.

- 아래에 `이전 · 3건 중 2번째 · 다음` 줄이 선다. 🚨 넘긴 것을 `aria-live` 로 소리로도 알린다
- 🚨 **제출해도 자동으로 다음 장이 열리지 않는다.** 방금 무엇을 넣었는지 확인할 자리가 사라진다 — 넣은 카드는 "넣었어요" 로 그 자리에 남고, 넘기는 것은 부모가 한다
- 🚨 **넣은 건수를 말한다** ("3건 중 1건 넣었어요"). 한 장씩 보여주면 남은 것이 화면 밖이라, 한 장 넣고 다 끝난 줄 알고 나가는 길이 생긴다

## 4. 셋을 같은 모양으로 맞추면서 생기는 것

세 경로를 **전부 초안 + 건별 제출**로 짠다. 아직 계약이 덜 정해진 자리는 잠정으로 잡고, 확정되면 한 곳만 고친다.

| | 잠정으로 잡는 것 | 확정되면 고칠 곳 |
| --- | --- | --- |
| ㉠ 한 줄 입력 | SSE 이벤트 **이름**. 모양(`{ drafts: [...] }` 한 프레임)은 확정이다 (#122) | `lib/api/sse.ts` 의 `RunEvent` 한 줄 · 목 |
| ㉡ 제안 | 제출 엔드포인트 경로 | `lib/api/idempotency.ts` 의 `idempotentPath` 표 한 줄 (차단·목·테스트가 따라온다) |
| ㉢ 사진 | `commit` 은 **일정을 아예 만들지 않는다.** 일정은 고치기 시트가 넣는다 | 닫혔다 (아래) |

### ㉢ `commit` 이 게이트인가 — 안 만드는 쪽으로 닫았다

`event.status` 가 없어지면서(9/17 · #118) `commit` 이 **게이트 없이 캘린더에 쓰는 유일한 경로**가 됐다. #121 에서 제기했지만 답이 오지 않은 항목이었다.

**커밋이 일정을 아예 안 만들게 해서 질문 자체를 없앴다.** 일정은 고치기 시트의 승인 게이트가 넣고, 커밋은 관찰만 저장한다 — 게이트 없는 캘린더 쓰기 경로가 구조적으로 존재하지 않는다.

🚨 그래서 08 화면의 저장 버튼에는 여전히 `btn-approve` · `caution` 을 쓰지 않는다. 그 둘은 시트 안의 일정 버튼이 가져간다.

## 6. 정해야 하는 것

1. **빈 필드 표시를 한 모양으로 통일할지** — 사진 경로의 `needs_review` / `review_reason` 을 세 경로 공통으로 쓰자는 제안이다. 경로마다 다르게 말하면 카드가 경로별로 분기한다
2. **`suggestion_id` 를 초안 payload 어디에 실을지** — #122 에서 "제안 경로 PR 에서 정한다"로 미뤄 둔 자리
3. **한 장씩 넘기는 방식을 디자인 시스템에 올릴지** (§3-7) — §7 에 사양이 없는 배치다
4. **SSE 초안 프레임의 이벤트 이름** — 모양은 #122 에서 확정됐고 이름만 답이 없다. 지금은 `event_draft` · `event_drafts` 둘 다 받는다
5. **제출 엔드포인트 경로** — create `POST` / update `PATCH` 까지만 정했다 ([event-draft-flow-v1](../event/event-draft-flow-v1.md) §6)
6. **사전검사를 붙이는 기준** — `agent === "food"` 인지 "재료가 있을 때" 인지. 전자면 활동 제안의 도시락·간식은 영영 안 걸린다
7. ~~`POST /photo-runs/{rid}/commit` 이 승인 게이트인가~~ — **닫혔다.** 커밋이 일정을 안 만들게 해서 질문이 사라졌다 (§4)
