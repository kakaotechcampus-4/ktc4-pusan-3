## 1. 왜 공지 단위가 아니라 항목 단위인가

처음 계획은 OCR 이 공지 한 장을 세 갈래(일반 공지 / 일정성 공지 / 급식표) 중 하나로 보내는 것이었다. 실제 공지를 모아 보니 한 장에 여러 종류가 섞여 있는 것이 보통이었다. 현장학습 안내 한 장에 행사 일시 · 준비물 · 비용 · 그날 운영 변경 · 날씨 규칙 · 건강 주의 · 회신서가 같이 있다. 한 갈래로 보내면 나머지가 사라진다.

그래서 원문 1건을 `notice` 한 행으로 두고, 거기서 뽑은 것을 `notice_item` 여러 행으로 둔다. K-6 "섞인 공지를 어떻게 나눌지" 의 답이다.

아이 관찰과 급식 메뉴는 `notice_item` 에 없다. 자기 표에 들어가 `source_notice_id` 로 원문을 가리킨다.

## 2. 흐름

```
POST /children/{cid}/photos                 202 + run_id. 아무것도 저장하지 않는다
   ↓ (뒤에서)
모델이 사진을 읽어 글자와 항목을 낸다          app/providers/notice/extractor.py
   ↓
규칙이 값을 검사하고 날짜를 계산한다           app/domains/notice/assemble.py · app/rules/notice_dates.py
   ↓
식단표면 표를 한 번 더 읽는다                 app/providers/meal_plan/image_ocr.py
   ↓
GET /runs/{rid}/events                       step → lane → step → parsed → done
   ↓
화면에서 보호자가 확인 · 수정, 캘린더에 넣을 항목을 체크
   ↓ 맨 아래 버튼 하나 (#824)
   ├─ ① 체크한 항목마다 POST /children/{cid}/events   🚨 승인 게이트 ㉠ (체크가 있을 때만)
   └─ ② POST /photo-runs/{rid}/commit                 ①에서 받은 event.id 를 그 항목의 event_id 로
                                      notice + notice_item + daycare_meal
```

🚨 **commit 은 캘린더에 쓰지 않는다.** 캘린더에 쓰는 문은 지금도 `POST /children/{cid}/events` 하나다. 화면이 체크한 개수만큼 부르고, 하나라도 실패하면 commit 하지 않는다 (`docs/web/event-draft-ui-v1.md` §2 ㉢).

🚨 읽은 결과는 저장을 누르기 전까지 서버 DB(`run_hold` · UNLOGGED · 백업에서 내용 제외)에 30분만 있다 (`app/api/runs/photo_run.py` · #877). 워커가 여럿이어도 저장 요청이 같은 결과를 본다. 저장은 그 행을 잠근 트랜잭션에서 해서, 같은 저장이 동시에 와도 한 번만 들어간다.

**받는 것은 사진뿐이다** (11-04 재형님). PNG · JPEG · HEIC(갤럭시 "고효율 사진") 등 그림 파일만 연다. PDF · HWP 는 받지 않는다 (§8).

**저장(commit)이 받지 않는 것** (#726 명성님 검증) — 항목 200개 초과 · 같은 id 반복 · 빈 제목 · 빈 준비물이나 100자 넘는 준비물 · 오늘 기준 앞뒤 3년 밖의 날짜 · 메뉴를 다 지운 끼니 · 읽은 뒤 아이와 연결이 끊긴 보호자(403).

**실패로 끝나는 경우** — 두 경우 모두 하루 한도는 이미 한 번 썼다 (재형님: 일단 그대로).

| `failed.reason` | 언제 | 화면 |
| --- | --- | --- |
| `unparsable` | 그림을 못 열었거나 · 글자를 못 찾았거나 · 너무 크다 | "글자가 더 잘 보이는 사진이면 읽을 수 있어요" + 다시 시도 |
| `not_document` | 글자는 읽었는데 저장할 공지 · 식단표 항목이 없다 (영수증 · 게임 화면) | "기관에서 받은 문서 사진을 올려 주세요" + 다른 사진 고르기 |

전에는 `not_document` 경우에 빈 확인 화면이 떠서 저장 버튼만 꺼져 있었다. 목 서버는 처음부터 실패로 끝냈다.

**큰 그림** — 펼치기 전에 화소 수를 본다 (6,000만 화소 상한, `document_text.py`). 0.5MB 짜리 13000×13000 PNG 가 메모리를 1.3GB 쓰던 것을 0.1ms 만에 거절한다.

### 사진은 S3 를 거친다 (11-04, 멘토님 제안)

```
화면 → POST /children/{cid}/photos/uploads     5분짜리 업로드 주소 (mode: s3)
화면 → S3 에 바로 POST                          서버는 사진 본문을 받지 않는다. 15MB 상한은 S3 가 검사
화면 → POST /children/{cid}/photos (upload_key)  서버가 내려받자마자 S3 에서 지운다 → 위 흐름 그대로
```

- **원본을 남기지 않는다.** 서버는 내려받은 뒤 성공 · 실패와 상관없이 지운다 (`app/integrations/photo_uploads.py`). 올리기만 하고 읽히지 않은 사진은 버킷 수명 규칙이 하루 뒤 지운다. 그래서 버킷의 **버전 관리를 켜면 안 된다** — 켜면 지워도 옛 판이 남는다.
- 열쇠에 보호자 id 가 들어가고, 서버는 그 보호자의 열쇠만 읽는다.
- 버킷(`PHOTO_UPLOAD_BUCKET`)이 비어 있으면 `mode: direct` 라 지금처럼 서버가 사진을 받는다. 로컬 개발이 AWS 로그인 없이 돈다. 버킷이 있으면 본문으로 온 사진은 400 으로 받지 않는다.
- 버킷 설정 (11-04 박재형 계정으로 만듦): 서울 · 공개 접근 4가지 차단 · 기본 암호화 · 버전 관리 꺼짐 · 수명 규칙 하루 · CORS 는 `https://icatch.ai.kr` · `http://localhost:3000` 의 POST 만 · http 연결 거부 정책. 실제 버킷에서 올리기 · 내려받기 · 지우기 · 상한 초과 거절 · 다른 출처 거절을 확인했다.
- 🚨 boto3 는 **서울 지역 주소**로 서명한다. 기본값인 전 세계 주소는 새 버킷에 하루쯤 307 을 돌려줘서 화면의 업로드가 실패했다.
- 서버가 사진을 읽지 않고 돌려보내는 길(스위치 꺼짐 · 활동 사진 · 키 재생 · 형식 오류)에서도 올라온 사진을 바로 지운다. 남의 열쇠는 건드리지 않는다. 지우기가 실패한 것만 수명 규칙이 하루 안에 지운다 (#726 적대적 리뷰).

**서버 역할의 열쇠를 api 상자에만** — 키는 만들지 않는다 (카테캠 계정은 IAM 사용자 · 액세스 키를 막는다). 서버 역할(`PowerUserAccess`)은 S3 를 쓸 수 있지만, 도커 상자는 서버보다 한 칸 안쪽이라 EC2 메타데이터의 hop limit 이 1 이면 열쇠가 닿지 않는다. 2 로 올리면 web · caddy · redis · postgres 상자도 닿으므로, 서버 방화벽이 api 상자(`172.30.0.20`)만 연다.

| 저장소에 들어간 것 | 파일 |
| --- | --- |
| api 상자 고정 주소 `172.30.0.20` — 공용 네트워크 `ktc4-edge` 의 prod api 주소. dev api 는 `.21` 이라 막힌다. 나가는 길은 `gw_priority` 로 edge 고정 (#747) | `deploy/docker/docker-compose.deploy.yml` |
| 방화벽 — `DOCKER-USER` 에서 메타데이터 주소를 막고 api 만 연다. 여러 번 돌려도 한 벌, 재부팅 뒤에도 systemd 가 다시 건다. 서버 자신의 길(SSM · CloudWatch)은 안 막는다 | `deploy/scripts/imds-firewall.sh` · `make deploy-up` 이 부른다 |
| Caddy 본문 상한 16MB (api 주소) — S3 를 써도 누가 API 에 큰 본문을 직접 보내는 것은 앞에서 잘라야 막힌다 | `deploy/caddy/Caddyfile` |

로컬에서 확인한 것: Caddy 설정 검사(같은 2.10.0) · compose 설정 검사 · 방화벽 스크립트를 버리는 리눅스 상자에서 세 번 돌려 규칙 한 벌 · 순서 맞음 · 체인이 없으면 실패.

운영 서버를 읽기만 해서 확인한 것 (11-05, SSM): 도커 29.9 · 방화벽 방식 `iptables` · `DOCKER-USER` 체인 있음(비어 있음) · 상자 주소는 db .2 · redis .3 · web .4 · api .5(매번 바뀜) · caddy .10 이라 `.20` 은 비어 있다 · 서버 본체는 메타데이터 토큰을 받고(200) api 상자는 못 받는다(시간 초과 — hop limit 1). 바꾼 것은 없다.

**머지 뒤 순서** (🚨 공용 계정 · 운영 서버라 한 번에 하나씩, 이 순서대로)

1. 이 PR 이 `develop` 에 머지되면 배포가 돌며 방화벽이 걸린다. Session Manager 에서 `sudo deploy/scripts/imds-firewall.sh --check` 로 규칙 두 줄을 확인한다.
2. 그다음에 hop limit 1 → 2: `aws ec2 modify-instance-metadata-options --instance-id <팀 서버> --http-put-response-hop-limit 2 --http-tokens required` (되돌리기는 1). dry-run 으로 권한은 확인했다. **1 보다 먼저 하지 않는다** — 그 사이 모든 상자가 열쇠를 받을 수 있다.
3. 확인: api 상자에서는 메타데이터 토큰이 받아지고, web 상자에서는 막혀야 한다.
4. 운영 `.env` (`apps/api/.env`) 에 `PHOTO_UPLOAD_BUCKET=ktc4-icatch-photo-uploads` 를 넣고 api 를 다시 띄운다.
5. 화면에서 지어낸 공지 사진 한 장을 올려 끝까지 확인하고, 버킷이 비었는지 본다.
6. 처리방침 (#166) — "사진은 읽은 즉시 지우고, 늦어도 하루 안에 지운다".

## 3. 항목 처리는 셋이다

코드가 갈라지는 기준은 `handling` 하나다. "회신 · 비용 · 운영 변경" 같은 내용 이름은 `label` 글자 칸이다. 공지에 무엇이 나올지 미리 다 알 수 없고, 이름이 늘어도 처리는 안 늘어난다.

| `handling` | 무엇 | 화면 `kind` | 사람이 하는 것 |
| --- | --- | --- | --- |
| `calendar` | 날짜가 있는 행사 · 일정 | `event` | 저장은 확인만. 캘린더에 넣으면 게이트 ㉠ |
| `todo` | 회신 · 신청 · 제출 · 납부 · 준비물 | `todo` | 확인 저장 |
| `info` | 운영 변경 · 건강 안내 · 교사 변경 · 외부 기관 안내 | `info` | 확인 저장 |

- 🚨 **알림은 일정에만 붙는다.** `reminder.event_id` 가 필수고, 승인 없는 알림 발송 경로를 만들지 않는다 (`apps/api/CLAUDE.md`). 회신 마감에 알림이 필요하면 확인 화면에서 그 할 일을 일정으로 넣으며 알림을 건다 (시작하는 날과 알림은 고치기 시트에서 고른다). 그래서 게이트 ㉠ 안의 일이고, 게이트를 늘리지 않는다.
- 🚨 **건강 안내는 `health_safety` 로 가지 않는다.** 기관이 보낸 글이지 아이의 기록이 아니다. 이 경로는 건강 · 알레르기 확정(게이트 ㉡)을 만들지 않는다.
- 건강검진 받기 · 소견서 제출처럼 보호자에게 요청한 일은 `todo` 다. 프롬프트가 금지하는 것은 아이의 건강을 판단하는 일이지, 요청을 옮기는 일이 아니다.
- 안내(`info`)는 보호자에게 묻지 않는다. 그래서 못 믿을 날짜는 남기지 않고 버린다. 묻지도 않고 틀린 값을 두면 조용한 오류가 된다.

## 4. 표

정본은 `app/domains/notice/models.py`. 칸의 뜻은 거기 있고, 여기는 이유만 적는다.

- `notice.content_hash` + `(child_id, content_hash)` 유니크 — 글자가 똑같은 공지를 막는다. 공백은 무시한다.
- 같은 공지를 다시 읽은 경우 — 사진은 읽을 때마다 글자가 조금씩 달라 해시로 못 잡는다 (같은 사진 17쌍 중 8쌍만 해시가 같았다). 그래서 저장 전에 같은 아이의 최근 공지 30건과 비교한다 (`same_notice`). 글자가 97% 이상 같고 **숫자가 전부 같을 때만** 같은 공지다. 달마다 같은 양식으로 나오는 공지와 날짜만 바꾼 공지가 글자로는 97% 넘게 같기 때문이다. 정정 공지는 비교하지 않는다.
  - 이미 저장된 공지면 원문은 그대로 두고 **없던 항목만 이어 붙인다**. 같은 항목(처리 · 제목 · 시작 · 마감이 같은 것)은 건너뛴다. 앞에서 일부만 저장하고 다시 읽어 나머지를 저장하면 뒤의 항목이 사라지던 것을 고쳤다 (#726 리뷰).
- `notice.relation` — 정정 공지면 `correction` 이 들어간다. 어느 공지를 고치는지(`related_notice_id`)는 아직 찾지 못해 비어 있다.
- `notice.extractor_version` — 어떤 모델 · 프롬프트로 읽었는지. 프롬프트를 고친 뒤 다시 뽑을 행을 고른다.
- `notice.audience_scope` — 알림장은 같은 문장을 반 전체에 "개별 알림장" 으로 보낼 수 있다. 우리 아이에게 온 글이 우리 아이에 대한 글은 아니다.
- `notice_item.due_at` + `due_all_day` — 마감은 시각까지 있을 때도("14시까지") 날짜뿐일 때도("내일") 있다. 할 일의 날짜는 여기에만 있어서 화면의 `date` 도 여기서 나온다. 일정의 "9시까지 등원" 의 9시도 여기다.
- 칸으로 두지 않은 것 (11-04 명성님 리뷰) — `needs_review` · `review_reason` 은 확인 화면에서만 쓴다. 확인하지 않은 항목은 저장 API 가 받지 않아 표에서는 늘 비어 있었다. 원문 표현 `date_text` · `due_text` 는 화면에 나오지 않고, 원문은 `source_quote` 에 남는다.
- 확인 화면 항목의 `past` (#828) — 견줄 날이 모두 사진을 받은 날(한국 날짜)보다 앞이면 참이다. 일정은 화면이 캘린더에 넣는 날로 본다 — 시작을 읽었으면 시작 · 끝 중 늦은 것, 시작이 없으면 마감. 화면이 마감은 캘린더에 넣지 않아서, 시작이 있는데 마감까지 보면 지난 행사가 켜진 채로 시작한다 (#854 리뷰). 할 일 · 안내는 시작 · 끝 · 마감 중 가장 늦은 것 — 기간이 열렸어도 마감이 남았으면 아직 할 수 있다 (#903 리뷰). 하나도 못 읽었으면 거짓. 화면은 지난 일정의 체크를 켜 두지 않는 데 쓴다 — 오늘과 견주는 것은 날짜 계산이라 서버가 한다 (루트 §2 · `apps/web/CLAUDE.md` §4). `needs_review` 처럼 확인 화면에서만 쓰고 표에는 칸이 없다.
- `notice_item.notice_id` — 공지를 지우면 항목도 지운다(CASCADE). 공지 id 를 바꾸려 하면 막는다(RESTRICT).
- `notice_item.details` — 금액 · 장소 · 회신 수단 · 제출 서류처럼 **보여 주기만 하는 값**의 이름-값 목록이다. 기준은 하나다: 코드가 갈라지거나 정렬하는 값은 칸으로, 보여 주기만 하는 값은 `details` 로. 처음에는 `amount` · `amount_kind` · `reply_method` 칸이 있었지만, 금액은 항목의 2% 에만 채워졌고 반별 금액 · 장소 · 제출 서류를 담지 못했다.
  - 🚨 이름이 문서마다 제각각이다 (83건에 62종). 이 값으로 코드를 가르지 않는다.
  - 🚨 날짜 규칙을 지나지 않는다. 일정 · 할 일의 날짜가 여기로 새면 `needs_review` 로 올린다. 비가 올 때만 쓰는 연기일 같은 조건부 날짜는 여기가 맞다 — `starts_at` 에 넣으면 없는 일정이 생긴다.
  - 잃는 것: 금액이 글자라 합계를 내려면 다시 뽑아야 한다. 지금 계산하는 기능은 없다.
- `event.source_notice_item_id` (UNIQUE) — 공지 항목 하나는 일정 하나가 된다. 처음에는 `notice_item.event_id` 로 항목이 일정을 가리켰는데, 일정 쪽이 출처를 가리키는 기존 방향(`event.source_notice_id`)에 맞춰 뒤집었다 (11-04 명성님 리뷰). `event_item` 과 1:1 로 잇지 않은 이유 — `event_item` 은 준비물 한 줄이라 "가을 소풍" 항목 하나가 일정 1개 + 준비물 N개가 된다.
  - 사진 화면은 공지를 저장하기 **전에** 일정부터 넣을 수 있다. 그래서 일정을 만들 때가 아니라 공지 저장(commit) 때, 화면이 보낸 `event_id` 로 잇는다. 다른 아이의 일정 · 이미 이어진 일정은 잇지 않는다.
  - 일정을 지워도 항목은 남고, 공지를 지워도 일정은 남는다(SET NULL). 일정은 보호자가 확정한 것이라서다. 공지를 지울 때 일정까지 정리하는 것은 보호자 확인을 거쳐야 한다 (승인 게이트 ㉠) — 아직 공지를 지우는 기능이 없다.
  - 정정 공지가 고칠 일정을 찾는 길이기도 하다. 정정 공지 처리는 아직 없다.
- `source_notice_id` FK 7곳은 `NOT VALID` 로 걸었다. 기존 행을 검사하지 않아서 배포가 멈추지 않고, 새로 쓰는 값은 검사한다.

## 5. 날짜는 코드가 계산한다

모델은 날짜 표현을 **적힌 그대로** 옮기고, 계산은 `app/rules/notice_dates.py` 가 한다 (CLAUDE.md §2 · §3). 공지의 날짜는 대개 연도가 없다.

| 규칙 | 예 |
| --- | --- |
| 연도는 발행일, 없으면 받은 날에서 빌린다 | `11월 3일(화)` |
| 적힌 요일이 맞는 해를 고르되 기준일에서 300일 안에서만 찾는다 | 7월에 올린 연간계획의 `04.15.(수)` |
| 요일이 어긋나면 고치지 않고 되묻는다 | 원문 자체의 오타도 여기서 잡힌다 |
| 월간표는 기준 월이 있어야 달 없는 날짜를 읽는다 | `2일(수)` · 달력 칸의 `3` |
| 주 단위는 날짜가 아니다 | `11월 1주` |
| 흩어진 날짜 · 회차는 잇지 않고 되묻는다 | `19일 10:00~11:30, 27일` · `10시, 12시 30분` |
| 시각은 범위의 자기 쪽 날짜에 붙는다 | `10월 27일 10:00 ~ 11월 17일 18:00` |
| 끝이 열린 표현은 마감이 아니다 | `10월 1일 10:00 ~ 선착순 마감` |
| `까지` 만 있으면 끝이지 시작이 아니다 | `4월 30일까지 시행` |
| 일정의 날짜 + 시각 + `까지` 는 그날 하루 일정이고, 시각은 마감이다. 시작 시각을 지어내지 않는다 | `8/27(목) 9시까지 등원` → 8/27 종일 + 9:00 마감 |
| 할 일의 달 단위 표현은 그달 말일 마감이다. 일정이면 되묻는다 | `9월 내로` · `11월 말까지` |
| 할 일의 하루 날짜는 어느 칸에 적혔든 마감 하나로 저장한다. 기간이면 시작을 남긴다 | `내일` · `11월 6일 14시` |
| 시각 앞의 낱말로 오전 · 오후를 안다 | `저녁 7시` → 19:00 · `새벽 5시` → 05:00 · `밤 12시` → 23:59 |
| 오전 · 오후가 없으면 운영 시간(7:30 ~ 19:30) 안에서 한 가지로 읽힐 때만 받는다 | `3시까지` → 15:00 · `10시` → 10:00 |
| 7시대는 아침 일찍 등원(7시대)과 저녁(19시대)이 둘 다 있어 시각을 비우고 날짜만 남긴다. 일정 · 할 일이면 되묻는다. 범위의 끝이 분명하면 끝보다 이른 쪽으로 읽는다 | `7시 학부모 모임` · `7시 45분` → 되물음 · `7:30 ~ 19:30` → 07:30 ~ 19:30 |
| 끝 시각은 시작보다 늦은 쪽으로 읽는다 | `6시 30분 ~ 8시 30분` → 18:30 ~ 20:30 · `10시 ~ 7시` → 10:00 ~ 19:00 |

🚨 **조용히 틀린 날짜가 못 읽은 것보다 나쁘다.** 못 읽으면 보호자가 채우고, 틀리면 틀린 날에 알림이 울린다. 애매하면 값을 비우고 `needs_review` 로 묻는다.

**규칙은 금지 패턴만 막는다 (11-04 명성님 리뷰).** 위 규칙은 둘 중 하나다 — 적힌 글자에서 날짜를 계산하거나(연도 · 요일 · 말일), 있을 수 없는 읽기를 지운다(새벽 3시 · 시작보다 이른 끝 · 시작이 된 `까지`). 읽기가 둘 이상 남으면 고르지 않고 비운다. 그전에는 `9시까지` 를 행사 시작으로 넣는 짐작 규칙이 있었는데 뺐다. 저장해 둔 54회 답에 다시 돌리면 달라진 것은 유치원 소식지 한 판의 행사 3건뿐이고(9시 시작 → 종일 + 9시 마감), 그 문서의 캘린더 날짜가 세 판 모두 같아졌다(세 판 일치 16/18 → 17/18). 지어낸 문서 판정은 45/45 그대로다.

## 6. 개인정보

- 원본 이미지는 저장하지 않는다. 글자만 저장한다.
- 저장하는 글자 칸(`raw_text` · 제목 · 근거 문장 · `label` · 날짜 표현 · 준비물 · `details`)에서 사람 이름 · 다니는 기관 이름 · 전화번호를 가린다 (`mask_names`).
  - 기관은 어린이집 · 유치원 이름과 그 약칭만 가린다. 반 이름 · 행사 장소 · 외부 기관은 가리지 않는다 — 가리면 "어느 반이 얼마", "어디로 가는지" 가 사라진다 (11-02 PM, 시험 문서 항목 517건에서 제목의 `[기관]` 35건 → 13건).
  - 2글자 이름과 약칭은 뒤에 호칭 · 조사가 올 때만 가린다. 글자를 통째로 바꾸면 `하나씩` · `보라색` 이 깨지고, 약칭 `해님` 이 `해님반` 을 지운다.
  - 이메일 주소는 가리지 않는다 (11-02 PM). 제출처로 쓰이는 값이고 대개 기관 주소다. 처리방침에서 저장 항목으로 다룬다.
  - 🚨 **이름 찾기는 모델에 기댄다** — 모델이 놓친 이름은 남는다. 그래서 가린 글자도 공개 자료로 다루지 않는다.
  - 🚨 **가리기는 저장할 때만 일어난다.** 모델이 읽어야 이름을 찾으므로 Gemini 에는 이름이 든 사진이 그대로 간다. CLAUDE.md §2 "모델 입력에도 이름 대신 별명/ID" 와 어긋나므로 처리방침에서 다룬다.
- 로그에는 토큰 수만 남긴다. 실패 메시지에 메뉴 · 원문이 실릴 수 있어 예외 종류만 남긴다.
- 🚨 **픽스처에 실제 공지를 넣지 않는다.** 테스트의 공지 글은 전부 지어낸 것이다.

## 8. 아직 없는 것

- 활동 lane — 서버가 422 로 돌려보낸다
- 알림장의 아이 문장 → `observation_*`. 지금 commit 은 관찰을 만들지 않는다. 반 공통 문장을 구분하지 않고 넣으면 잘못 승격되므로 `audience_scope` · 문장 주체 판정이 먼저다. 우리 아이 이름도 `[이름]` 으로 가려져서 `[이름]는 [이름]와` 가 되므로, 경로를 만들 때 우리 아이를 구분하는 표시도 필요하다. 공개 자료에 알림장 실물이 없어서 지어낸 문서로만 시험했다
- 정정 공지를 앞 공지에 잇는 자동 판단 — 정정이라는 사실(`relation`)만 저장한다. 어느 공지 · 어느 일정을 고치는지 찾지 못해서, 보호자가 새 날짜를 일정으로 넣으면 옛 일정이 그대로 남는다
- HEIC 미리보기 — 서버는 읽지만, 안드로이드 Chrome · WebView 는 HEIC 를 `<img>` 로 그리지 못해 읽는 중 · 확인 화면의 사진 미리보기가 비어 보일 수 있다
- ~~업로드 본문 크기 제한~~ — 사진은 S3 로 가지만(§2), FastAPI 는 누가 보내든 본문을 먼저 끝까지 받는다. 그래서 Caddy 가 api 주소에서 16MB 로 자른다 (`request_body max_size`, §2 표 · `deploy/caddy/Caddyfile`)
- 화면에 보이는 값 — 서버는 `PhotoEntry` 로 `starts_at` · `ends_at` · `due_at` · `target_scope` · `details` · `source_quote` 를 보내지만 웹이 아직 그리지 않는다. 그래서 `9:30` 은 보호자가 다시 입력하고, `11/23 ~ 11/27` 은 첫날 하루 일정으로 들어가고, 금액 · 대상 · 회신 수단을 보호자가 확인할 수 없다. 웹 `photo-review.tsx` · `photo-entry-sheet.tsx` 를 고친다 (#611 과 같은 파일)
- ~~사진 시트의 알림 고르기~~ — 생겼다 (`apps/web/src/components/photo-entry-sheet.tsx` 의 `ReminderField`)
- 저장한 공지를 읽는 곳 — 화면 · Food · Growth · 추천 근거 어디에도 연결되지 않았다
- 여러 장 공지 — 업로드가 사진 한 장만 받아 2쪽짜리 공지는 공지 2건이 된다. 이미지가 있는 게시글의 최대 34% 가 2장 이상이다 (별개 사진이 섞인 상한값)
- 여러 쪽 PDF · HWP 업로드 — 서버 API 는 이미지만 받는다. 파일 읽기(`document_text.py`)는 있고 말뭉치 시험에 썼다
- 붙여넣은 텍스트 공지 — Memory Agent 경로 그대로다. `notice` 에 쓰지 않는다
