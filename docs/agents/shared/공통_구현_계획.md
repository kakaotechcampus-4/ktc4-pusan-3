## 1. 공통으로 두지 않은 것

**`execute_tool` 을 공통화하지 않았다.** 허용 목록·핸들러 표·컨텍스트 타입이 Agent 마다
달라서 제네릭으로 만들면 타입만 깊어지고 얻는 게 없다. 각 Agent 의 `registry.py` 가 자기
것을 갖는다 — [food/registry.py](../../../apps/api/app/agents/food/registry.py) 가 선례이고
모양은 이렇다.

```python
def tools_for(task_type, gate) -> tuple[str, ...]      # 빈 튜플이면 모델을 안 부른다
def specs_for(names) -> list[dict]                      # 모델에게 보낼 스펙
async def execute_tool(name, arguments, context, *, allowed) -> ToolResult
```

돌려주는 `ToolResult` 와 실패 코드만 공통이다. **같은 실패가 Agent 마다 다른 이름으로
로그에 남으면 집계가 안 된다.**

**`Operation` 도 Agent 마다 다르다.** Memory 는 `parse/create/query/update/delete`,
Food 는 `query/propose/report`. 공통 `ToolResult.operation` 은 `str | None` 이고, 좁히는
것은 각 Agent 의 `ok()`/`fail()` 래퍼다.

## 3. 공통 모듈이 강제하는 것

문서에 적힌 규칙 중 **코드가 막아 주는 것**만 적는다. 나머지는 각 Agent 가 지켜야 한다.

| 규칙 | 어디서 막나 |
| --- | --- |
| 월령을 `//30` 으로 세지 않는다 | `age.months_between()` — 달력 계산만 노출 |
| `date` 자리에 `datetime` 이 안 온다 | `age._require_plain_date()` — `TypeError` |
| 기피(−1)를 후보에서 지우지 않는다 | `rank_evidence()` 가 제거 목록을 반환하지 않는다 |
| `polarity IS NULL` 은 근거가 아니다 | `rank_evidence()` 가 빼고 `pick_followup()` 이 집는다 |
| 감쇠를 Agent 가 다시 세지 않는다 | `rank_evidence()` 가 유예일 인자를 받지 않는다. `archived` 제외만 |
| 아이 기록 0행이면 일반 추천 | `suggestion.build()` 가 `kind` 를 정한다 |
| 문서 행만으로 개인화가 안 된다 | `Ref.is_child_record` — 품질 지표가 아이 기록만 센다 |
| 기피를 인용했으면 이유에 밝힌다 | `build()` 가 라벨이 문장에 없으면 거절 |
| 추천은 최대 3개 · 0개는 실패가 아니다 | `check_count()` — 넘치면 거절, 모자라면(0개 포함) `exhausted=True` 일 때만 통과 |
| 다 못 채우면 개수 안내 | `count_notice()` — 문구는 `suggestion.readout.yaml` |
| 되묻기는 한 번에 하나 | `DomainAgentResult.__post_init__` |
| 복약 초안에 실제 알림 시각 필수 | `MedicationDraft.__post_init__` |
| 상수 문구는 키로 관리 | `ReadoutCatalog` — 없는 키는 즉시 `KeyError` |
| 0행이 "없음"인지 "모름"인지 가른다 | `Gate.allergy_filter_ready` (F-4) |

`build()` 의 기피 검사는 **라벨이 문장에 들어 있는가**까지만 본다. 문장 품질은 못 본다 —
라벨조차 안 나오면 확실히 말하지 않은 것이라는 하한만 건다.

## 4. 남은 공통 작업

### 4-1. `app/rules/term_match.py`

Food 의 알레르기 필터, Activity 의 `hazard_term`, Growth 의 활동 행 검사가 같은 매처를
쓴다. 구현이 두 벌이 되면 한쪽만 갱신된다.

알고리즘은 정해져 있다 — **공백 제거 부분 일치 + guards + 가장 엄한 판정 우선.**
guards 는 오탐 취소 목록이다("밀크티"는 밀이 아니다).
칸이 여럿이면(메뉴명 · 재료 하나하나, 활동 `content` · `materials`) 이어 붙이지 않고 `match_fields` 로
칸마다 따로 본다. 이어 붙이면 guard 가 칸 경계를 넘어 덮고(#258 — "통밀 크래커" + "크림치즈"),
어느 칸에도 없는 용어가 생긴다(Activity 3-5 — "작은" + "블록 담는 통"). `match_fields` 에서는 guard 가
한 칸 안의 띄어쓰기도 넘지 않는다. 별칭은 띄어쓰기는 넘지만 문장부호는 넘지 않고("소스 : 시금치" 는
"스시" 가 아니다), 보이지 않는 서식 문자(폭 없는 공백 · soft hyphen)는 없는 글자로 본다.
이름이 같은지 견줄 때(`normalize`)는 문장부호 · 기호도 지운다 — 훑을 때 남기는 글자와 같다.
행이 많으면 `TermMatcher` 로 별칭 색인을 한 번만 만든다.
보호자가 적은 알레르기 이름을 읽는 규칙도 공통이다 — `app/agents/common/allergy.py`(Food · Activity).

선행은 `hazard_term` 스키마다. [activity-agent-v1.md](../activity/activity-agent-v1.md) §3-5 에 있다
([README §5](../README.md#5-growth가-hazard_term에-요구하는-것)의 Growth 요구를 채운다).
Food 의 `allergen_term` 은 이미 `aliases`·`guards` 를 갖고 있어 그쪽 모양을 따르면 된다.

### 4-3. `pipeline` 이 채널을 처리하는 자리

`DomainAgentResult` 는 값만 정한다. 다섯 채널을 실제로 내보내는 것은 pipeline 이다.

| 채널 | pipeline 이 할 일 |
| --- | --- |
| `suggestions` | 주입된 writer 로 추천 행과 `suggestion_evidence` 행을 한 트랜잭션에서 INSERT · **commit 이 끝난 뒤에** 카드 화면 이벤트(id 포함). 저장에 실패하면 그 Agent 카드는 빼고 `partial` · 0개면 저장할 행 없이 그 Agent 묶음을 개수 안내와 함께 내보낸다 — 실패가 아니다 (K-12) |

| `event_requests` | Memory 일정 tool 을 코드로 호출 → 초안 payload |
| `needs_observation` | 화면이 한 줄로 묻는 이벤트 |
| `medication_drafts` | payload 로 내보내기만. 제출은 백엔드 |

`suggestion_evidence` 테이블과 INSERT 는 `c5a81f0d3b62` · `domains/suggestion/repository.py` 에 들어갔다 (2026-09-25). 남은 것은 문서 행 조회 tool 이다.

## 5. routing · pipeline 이 바뀌는 자리

routing 은 `Routing.domain_tasks` 로 공통 `DomainTask` 를 낸다. 유형별 묶기는 `agent × task_type` 당 하나,
상한(2)은 **agent 단위**로 센다. 라벨은 Supervisor 가 준 문자열 그대로 넘기고 enum 변환은 각 Agent 의
`task_type_of()` 가 한다. 라벨이 없는 Activity 는 `None` 이다.

pipeline 은 `_RUNNERS[agent]` 와 `handle_input` 이 받은 `contexts[agent]` 로 실행 함수와 context 를 찾는다.

1. **동시 실행** — 읽는 도메인 task 는 전부 동시에 돈다. Memory 다음 · 쓰는 task 다음이라는 순서는 유지한다(6번). 같은 Agent 의
   task 둘(식단 추천 + 영양소 분석)도 동시라서 context 마다 `for_task()` 를 두고 task 마다 run state 를 새로 받는다.
2. **부분 실패** — 한 Agent 가 예외를 내면 그 Agent 만 빠지고 `Partial(reason, succeeded, failed)` 이벤트가
   나간다. 도메인 Agent 가 전부 실패했고 저장·메모·안내도 없으면 부분 결과가 아니라 `Failed("llm_unavailable")` 다.
   Agent 예외 메시지는 로그에 남기지 않는다 (발화 조각이 섞일 수 있어 예외 종류만).
   `Partial` 은 도메인 단계가 다 끝나거나 20초가 된 뒤 **한 번** 나가고, 화면에는 `partial` 로 간다.
   서버는 `reason` 과 Agent 이름만 보내고 문구는 화면이 만든다(`unavailable` 과 같다). 끝 신호가 아니라 뒤에 `done` 이 온다.
3. **20초** — 입력부터 잰다(`RUN_DEADLINE_S`). Supervisor·Memory 는 끊지 않고, 둘이 쓴 만큼 도메인 몫이 준다.
   넘기면 도메인 Agent 만 끊고 `Partial("timeout_20s", ...)`.
4. **호출 예산** — 입력 run 당 최대 5회 · 도메인 Agent 당 1회 이내 (NF-01 재정의).
5. **배선 버그** — 표에 없는 agent 나 빠진 context 는 부분 실패로 숨기지 않고 예외로 올린다.
6. **쓰기 순서** — 같은 run 안에서 쓰는 task 가 읽는 task 보다 먼저 끝난다. 순서는 "기록 단계 → 쓰는
   도메인 task → 읽는 도메인 task" 다. 쓰는 라벨은 각 Agent registry 의 `WRITING_TASKS` 가 표시하고
   (지금은 `food:daycare_meal`), pipeline 은 `_WRITING_TASKS` 로 모은다. 쓰는 task 도 20초 안에서 센다.
   쓰는 task 가 실패하거나 끊겨도 읽는 task 는 돈다.
7. **commit 지점** — 러너가 넘긴 `commit` 을 Memory 가 끝난 직후 한 번 부른다. 세션과 commit 구현은 러너에
   있고 pipeline 은 기록 단계가 끝난 시점만 알린다. 트랜잭션은 Memory 의 쓰기만 묶는다. 되묻기 맥락은 commit 뒤 `PendingReply` 로 나가 러너가 프로세스 메모리에 둔다(10-05 트랜잭션 회의 · [memory-agent-v1.md](../memory-agent-v1.md) D12).
   `Saved` · `EventDrafts` · note · `PendingReply` 는 그 뒤에 나간다. commit 이
   예외를 내면 pipeline 은 잡지 않는다 — 확정된 게 없으니 러너가 `failed` 로 끝낸다. 도메인 쓰기 포트는
   호출마다 짧은 트랜잭션으로 바로 commit 하고, 조회 포트는 호출마다 짧은 세션으로 읽는다.
8. **commit 뒤에는 failed 가 없다** — `PipelineResult.committed` 가 참인 run 은 `done`(+ `partial`) 으로
   끝난다. `failed` 는 "저장 없음" 이라 화면이 원문을 돌려주는데, commit 뒤에 내면 다시 보낼 때 두 번
   저장된다. 도메인 쓰기는 entrypoint 가 보호자 말을 반영한 쓰기 포트(지금은 급식 수정 · 삭제)만 감싸
   (`run_writes.record_food_writes`) 포트 호출이 성공하고 돌아온 뒤에만 표시를 남기고, pipeline 은 그 표시로
   판단한다. 쓰기 전에 모델 호출이 실패하거나 시간을 넘긴 run 은 표시가 없어 `failed` 로 끝나고 원문이 입력창에
   돌아간다. 계산 중에 생기는 메뉴 카탈로그 저장은 감싸지 않는다 — 감싸면 질문만 한 run 이 모델
   실패에도 `done` 이 된다. 어떤 포트를 감싸는지는 `Agent_공통규약.md` §2 "쓰는 시점" 의 기준을 따른다.
   commit 응답을 기다리다 취소되면 들어갔어도 표시가 안 남는다. 다시 보내도 안전하게 하는 건 쓰기 쪽 몫이다
   — UPDATE 는 같은 갱신을 두 번 적용해도 같게, INSERT 는 도메인 값으로 만든 중복 방지키로 막는다.
9. **결과 순서** — 도메인 결과(`DomainRouted`)는 끝나는 대로 나간다. 쓰는 task 의 결과는
   읽는 task 가 시작하기 전에 나가고, 읽는 task 끼리는 끝난 순서다. 같은 틱에 같이 끝난 것만 task 순서다.
   `PipelineResult.domain` 은 그대로 task 순서다. 결과를 넘기는 콜백(화면 번역)이 터지면 부분 실패로
   숨기지 않고 남은 task 를 끊은 뒤 올린다. 화면도 카드 순서를 고정하지 않는다(#215) — 결과는 대화 아래에
   도착한 순서대로 블록으로 붙고, 이미 그린 블록을 다시 정렬하면 읽던 카드가 밀린다. 화면이 기대는 것은
   ① 결과마다 agent 가 실린다 ② `partial` 은 모든 결과 뒤에 한 번 온다 ③ 그 뒤에 `done` 이 온다, 셋뿐이다.
10. **단계별 시간** — `PipelineResult.times`(`StageTimes`)에 Supervisor(다시 나누기 포함) · 기록 단계(Memory +
   commit) · 도메인 단계를 시작할 때 남은 몫(`budget_ms`) · 쓰는 묶음 · 읽는 묶음의 ms 를 싣고 `_log` 가 찍는다.
   task 마다 `도메인 task ... result=… ms=…` 한 줄이 따로 남는다. 원문은 없다. 도메인 단계 최소 예산은
   이 값을 모은 뒤 정한다.

pipeline 은 결과에서 `DomainOutcome`(agent · task_type · status · model_calls)만 읽는다. mock 결과와
`DomainAgentResult` 가 같이 만족해서 Agent 가 실구현으로 바뀌어도 pipeline 은 그대로다.
새 Agent 를 붙일 때 고치는 곳은 `IMPLEMENTED_AGENTS` · `_RUNNERS` · entrypoint 의 contexts · 그 Agent context 의
`for_task()` · 결과의 `agent` 필드다. 쓰는 라벨이 있으면 그 Agent registry 의 `WRITING_TASKS` 와 pipeline 의
`_WRITING_TASKS` 도 고친다. 보호자 말을 반영하는 쓰기 포트가 있으면 entrypoint 에서 `run_writes` 래퍼로 감싼다.

채널별로 pipeline 이 무엇을 하는지는 §4-3 에 있다. 아직 구현하지 않았다.

## 6. `suggestion` 쓰기

- **`status` 는 Agent 가 건드리지 않는다.** 생성은 항상 `draft` · `expires_at=+24h`.
- **요청 1건당 최대 3개.** 출력 tool 이 개수를 검사한다 — 4개 이상이면 거절, 채울 수 있는데 덜 내도 거절. 근거 0행 general 추천도 같다.
- **필터 후 3개 미만이면 재호출 1회** — 안전 필터(알레르기·연령 금지식품·`hazard_term`)를 거른 뒤 후보가 3개 미만이면 해당 Agent 만 모델을 한 번 더 부른다. 기피는 필터가 아니라 근거라 재호출 사유가 아니다. 재호출 프롬프트에 걸러진 항목을 제외 목록으로 넣는다. 재호출 결과는 첫 호출에서 통과한 것 뒤에 빈자리만 채운다(같은 후보는 건너뛴다). 1회로 끝나고 그래도 부족하면 남은 만큼만 내고 개수 안내를 붙인다. 0개면 추천 없이 안내만 낸다 — `check_count(exhausted=True)` 가 0개도 예외 없이 통과시킨다 ([Tool_공통.md](Tool_공통.md) §5-2). `model_calls` 상한은 이 경우에만 Agent 당 2를 허용한다.
- **저장 뒤 화면 전환** — pipeline 이 `SuggestionWriter` 로 draft 저장(추천 행 + 근거 행, 한 트랜잭션)을 끝낸 **뒤에** 추천 카드 화면 이벤트를 내보낸다. 보여 주면서 동시에 저장을 요청하지 않는다 — 카드의 승인 · 거절 · 피드백은 저장된 행의 id 로 동작하고, 저장에 실패한 개인화 카드가 나가면 근거 0행 추천이 나간 셈이다. 저장에 실패하면 그 Agent 카드는 빼고 `partial` 로 둔다. 저장 구현(트랜잭션 · 제약)은 백엔드, 저장 → 카드 순서는 pipeline 몫이다. 카드 화면은 그 run 의 응답을 그대로 쓰므로 묶음 키가 필요 없다. 별도 목록 화면은 `expires_at > now()` 인 suggestion 전부를 조회한다.

- 근거는 `suggestion.source_refs`(jsonb) 가 아니라 **`suggestion_evidence` 테이블**이다. `PRIMARY KEY (suggestion_id, source_kind, source_id)` 에 `note` 가 붙는다 (2026-09-23 회의 확정. 함께 두었던 `source_updated_at` 은 2026-09-29 에 뺐다). `note` 는 NOT NULL 이다. 컬럼 이름이 `memory_*` 가 아닌 것은 가리키는 대상이 Memory 소유 테이블만이 아니어서다 — 문서 행과 `daycare_meal` 도 들어온다.
- `source_kind` 는 **두 무리**다. 아이 기록(`observation_*` 5종 · `profile_affinity` · `child_growth_log` · `notice` · `daycare_meal`)과 문서 행(`food_doc` · `growth_doc` · `activity_doc`). **품질 지표는 아이 기록만 센다** — 문서 행만 달고 나간 개인화 추천은 근거 0행과 같다.

```
① 공통 뼈대        ✅ 끝
② routing·pipeline  ✅ DomainTask · 실행 함수 표 · 동시 실행 · partial · 20초
   └ 채널 처리(§4-3)는 ③ 에서 결과가 실제로 나온 뒤
③ Food 실구현      이미 mock 이 있다. 포트·코드 tool·출력 검증을 채운다
   └ 선행: ② · suggestion/suggestion_evidence 마이그레이션 · daycare_meal · 영양 데이터
④ Growth           growth_doc 148행이 임계 경로다. 코드는 며칠, 콘텐츠는 몇 주
   └ 선행: ③ · child_growth_log · 도서 API 키
⑤ Health           안전에 가장 민감하고 외부 API 가 가장 많다. 뼈대가 굳은 뒤에
   └ 선행: ④ · 질병청·건보·E-Gen · medication 마이그레이션
⑥ Activity         담당자 일정에 따라. 공통 뼈대는 이미 쓸 수 있다
```

Activity 를 ③~⑤ 와 병렬로 해도 된다. 공통 모듈이 이미 있어 서로 기다릴 이유가 없다.

## 8. Agent별 구현 메모

각 Agent 는 **① mock → ② 읽기 tool → ③ 출력 tool + 코드 규칙** 순서다. Food 가 ①을 끝냈다.

### Food

- **선행**: ORM 어댑터 · `health_safety` 조회 · `daycare_meal` 적재(OCR + 대체식 교체) · 영양 데이터 소스 · 권장 섭취량 외부 소스(연령별 일반값 + 성별 없는 열량 계산식) · 알레르기 "없음 vs 모름" 구분(F-4)
- **코드가 막는 것**: 알레르기 필터 · 정확한 섭취량 생성 금지 · 근거 매핑
- **영양이 선호보다 앞선다**: 기피 affinity 가 있어도 부족한 식품군을 후보 풀에서 빼지 않는다. 기피는 풀을 줄이는 값이 아니라 `reason` 을 쓰는 값이다
- `child_growth_log` 는 권장 열량 계산 입력으로 읽는다(코드 계산). 측정이 없으면 연령별 일반값. **성별은 읽지 않는다**

### Activity (두 번째)

- **왜 두 번째인가**: 외부 API 가 날씨·장소 둘뿐이고 쓰기 계약이 `suggestion` 하나로 끝난다. 공통 뼈대 검증용이다
- **읽기 포트**: `observation_activity` · `profile_affinity(domain=activity)` · Calendar · Weather · Place
- **코드가 막는 것**: 중복 제거 · 나이/안전 필터 · **예약·결제 경로 없음**
- **읽지 않는 것**: `observation_education` · `observation_routine`

### Growth

- **핵심**: `observation_routine` · `observation_education` → `growth_doc` · 도서 API 연결 추천. `notice` 는 보조라 없어도 동작해야 한다
- **읽기 포트**: `observation_education` · `observation_routine` · `observation_activity`(참고) · `profile_affinity(domain ∈ education, activity)` — `routine` 은 승격 대상이 아니라 affinity 가 없다 · `child_growth_log` · `notice` · `growth_doc` · 도서 API. `domain` 을 복수로 받는다 — 포트 시그니처는 `domains: tuple[str, ...]`
- **`routine_coaching` 은 `trigger` 필수** — NULL 이면 역질의
- **`growth_review` 는 모델을 부르지 않는다** — 차분 + 템플릿, `model_calls=0`. 판정 요청("잘 크고 있어?")도 여기로 온다
- **코드가 막는 것**: `strength`·`assistance_level`·`completion_status` 의 점수 환산 금지 · 단발 관찰 승격 금지 · `polarity=-1` 을 "못하는 것"으로 해석 금지 · **백분위 판정 금지**
- 근거가 `observation_activity` 를 가리킬 수 있다 — 화면 문구가 "놀이 기록을 참고했어요"로 나와야 한다

### Health (마지막)

- **왜 마지막인가**: 안전에 가장 민감하고 외부 API 가 가장 많다(질병청·건보·E-Gen). 앞의 셋으로 뼈대가 굳은 뒤에 붙인다
- **경계**: 진단·처방 없음. 같은 증상 3회 반복이면 추천을 멈추고 "병원 확인이 필요해 보여요" + 정리된 기록만. 이 판정은 **규칙**이다
- **Supervisor 와의 분담**: 진단 문의는 `guarded/diagnosis` 로 걸러져 Health 까지 가지 않는다
- **`medication` 이 유일한 쓰기 라벨** — 생성·수정은 초안 payload(DB 저장 없음), 중단은 soft delete. 확인 모달에 실제 알림 시각 필수
- **성장 판정 없음**: 백분위·BMI 판정은 제거됐다. 체중과 관련한 식이·운동 조언은 어느 Agent 도 하지 않는다
