## 0. 메뉴 API 연결 — 먼저 읽을 것

### 0-1. 문제: 보호자는 "메뉴"로 말하고, API는 "식품"으로 답한다

| 들어오는 것 | 예 | 출처 |
| --- | --- | --- |
| 섭취 기록 | "카레라이스 반 그릇" | `observation_food.subject` · `amount` |
| 급식 | "현미밥 / 미역국 / 닭갈비(5.6.15.)" | `daycare_meal.menu_keys` (급식표 읽기 — 사진 OCR · 센터 배포 엑셀) + 보호자가 알려준 대체·제외 메뉴. 메뉴명에 붙은 알레르기 번호는 읽지 않는다(§3) |
| 추천 후보 | "두부달걀덮밥" | `propose_meal_candidates` |

세 경로 모두 **메뉴명 문자열**이다. 영양·알레르기 계산에는 **식품코드 · 재료 · 영양성분**이 필요하다. 이 변환을 모델에게 맡기면 "크림수프에서 우유 누락"(F-1), "단백질 12g" 같은 수치 생성이 생긴다.

→ **메뉴명 → 메뉴 카탈로그 행**으로 바꾸는 일은 전부 코드(`resolve_menu`)가 한다. 모델은 카탈로그에 있는 메뉴만 다룬다.

### 0-2. 연결 구조

```
메뉴명 ──normalize──▶ menu_key ──▶ menu_catalog (메뉴 카탈로그)
                                     │ 카탈로그에 없음(캐시 미스)
                                     ▼
          ① 식약처 식품영양성분DB정보 (음식 분류) ── 1인분 영양
          ② 식약처 조리식품 레시피 DB (COOKRCP01) ── 재료 목록만 (영양 칸은 쓰지 않음)
          ③ 둘 다 없음 · 외부 API 장애 → status="unresolved" (모델 추정 금지). 카탈로그에 남기지 않음
             이름이 정확히 같은 결과만 받는다 — 비슷한 메뉴 추정 금지 (급식 · 판정 · 집 식사 모두)
                                     │
                                     ▼
          재료 → 알레르기 19종 코드 매핑 (코드 사전)
          식품분류 → 6개 식품군 매핑 (코드 사전)
```

### 0-3. `menu_catalog` (메뉴 카탈로그)

| 필드 | 설명 |
| --- | --- |
| `menu_key` | 정규화 메뉴명 (공백·괄호·알레르기 번호 제거, 동의어 치환) · PK. 번호는 떼기만 하고 읽지 않는다 — 떼지 않으면 "카레라이스(2.5.6)" 가 카탈로그에서 안 찾아져 영양 계산에서 빠진다 |
| `food_code` | 식약처 식품코드 (없으면 NULL) |
| `source` | `mfds_nutri` · `mfds_recipe` · `manual` |
| `serving_g` | 1인분 중량 — **성인 기준** |
| `nutrients` | jsonb — 에너지·탄수화물·단백질·지방·당류·나트륨·칼슘·철 … (100g 기준 + 1인분). 식품영양성분DB 에서만 채운다 |
| `ingredients` | text[] — 레시피 DB 재료 텍스트(`RCP_PARTS_DTLS`)를 파싱한 것 |
| `allergen_codes` | smallint[] — 19종 코드 (재료 + 메뉴명 사전 **합집합**) |
| `food_groups` | text[] — 곡류 · 고기생선달걀콩 · 채소 · 과일 · 우유유제품 · 유지당류 |
| `stage_min` | 이 메뉴가 가능한 최소 단계 — `LifeStage.stage` 네 값 중 하나 (수동 태깅) |
| `resolved` | bool |
| `source_version` · `synced_at` | 데이터 기준일 |

- 동기화: 야간 배치 + 카탈로그에 없을 때(캐시 미스) 즉시 1회 호출. 운영 트래픽을 API에 직접 걸지 않는다. 캐시 미스 1회는 Food 요청 중에 부르고(판정 한 번의 외부 조회 수는 묶는다 — food_agent_own_table §1), 결과는 백엔드 어댑터가 없을 때만 넣는다(`ON CONFLICT DO NOTHING`) — [`food_agent_own_table.md`](food_agent_own_table.md) §1 · FT-13 (10-04 닫힘). DB 권한 방식은 백엔드가 정한다.
- `unresolved` 메뉴는 **영양 계산에서 빠진다**. 알레르기 판정은 "확인 못 함". 기록 행 수에서도 뺀다고 적어 왔지만 [`영양소_계산_설계.md`](영양소_계산_설계.md) §5 는 행은 세고 해석률을 따로 본다 — 어느 쪽으로 맞출지는 미결이다(N-13).

### 0-4. 수치는 내부, 출력은 구간 — 계산 설계

상세: [`영양소_계산_설계.md`](영양소_계산_설계.md)

1인분 기준이 **성인**이고 먹은 양은 "반 그릇" 같은 텍스트다. 그래서 **수치는 내부 계산에만 쓰고, 화면에는 구간과 식품군으로 나간다.**

| 계산 | 양·결측에 민감? | 내부 | 출력 |
| --- | --- | --- | --- |
| 에너지 구성 비율 (탄:단:지) vs AMDR | 낮음 | ✓ | ✓ 구간 |
| 식품군 출현일 (7일 중 채소 나온 날) | 낮음 | ✓ | ✓ 그대로 |
| 나트륨·당류·포화지방 vs UL | 중간 | ✓ | ✓ 구간 |
| EAR·RNI 대비 충족률 | **높음** | ✓ 판정 근거 | **✗ 숫자 노출 금지** |
| 하루 섭취 g · kcal | 높음 | ✗ | ✗ |

- **판정 기간**: 오늘(기록된 끼니) = 남은 끼니 구성용 · **최근 3~7일 = 부족·과잉 판정** · 30일 = 반복·다양성
- **끼니를 정의하지 않는다.** 기록이 충분한지는 기간 안의 행 수로 본다 — 7일에 `observation_food` + `daycare_meal`(오늘 이전) 합쳐 10행 미만이면 수치 기반 결론 없음(설정값)
- **급식은 "양 미상"** 등급으로 따로 센다. 메뉴는 알지만 먹은 양을 모른다
- `amount` 가중치: `다 먹음 1.0 · 반 0.5 · 조금 0.25 · 뱉음/안 먹음 0 · 미상 → 1.0 + "양 미상"`
- 기준표: `nutrient_reference` (EAR · RNI · AI · UL · AMDR, 연령군 `1-2` / `3-5`). **성별 구분 없는 행만** 쓴다
- **권장 열량**: 연령군 일반값을 `child_growth_log`의 최근 키·몸무게로 조정한다(`compute_energy_target`, 코드). 측정이 없으면 연령군 일반값. 성별은 넣지 않는다. 결과 kcal은 내부 전용

### 0-5. 식단 추천에서의 연결 — 후보 풀은 코드가 만든다

```
menu_catalog
  ∩ stage_min ≤ 아이 단계
  − 알레르기 코드 교집합 ≠ ∅          (filter_food_safety)
  − 연령 · 아이 금지 식품 (§3 음식 안전 수칙 — 꿀 · 날음식 · 카페인 · 술 …)
  − 최근 3일 반복 메뉴
  − 오늘 급식과 같은 주재료 (선택)
  → 후보 풀 (최대 30)
        │  sample_candidates: 점수 가중 샘플링 + 식품군 다양성 제약 (seed=run_id)
        │  가중치: 부족 식품군 ↑ (영양 우선) · 선호 ↑ · 기피 ↓ (0이 되지는 않는다)
        ▼
  모델에게 보여줄 후보 10~15  ──▶ 모델이 3개 선택 + 이유 작성
                                         │ 사후 filter_food_safety 후 3개 미만
                                         ▼
  걸러진 menu_key를 풀에서 빼고 재샘플링 → 모델 재호출 1회 (이 경우에만)
```

- **기피는 풀에서 빼지 않는다.** 기피는 가중치를 낮추고 `reason`을 쓰는 값이지 후보를 지우는 값이 아니다. 풀에서 빼는 것은 §3 음식 안전 수칙이 막거나(`blocked`) 확인하지 못한(`unchecked`) 메뉴뿐이다. 막힌 메뉴 중 제품마다 다른 성분 때문에만 막힌 것(`needs_check`)은 식단 추천을 구현할 때 확인 필요로 내보낸다(§3 의 5). 질식 주의 식품은 빼지 않고 안내만 단다.
- **부족 식품군은 기피보다 세다.** `evaluate_nutrient_bands`가 `low`로 판정한 식품군은 기피 가중치를 상쇄하고 풀 상단에 남는다. 채소 기피 아이에게 채소가 부족하면 채소가 든 메뉴가 후보에 올라와야 하고, 모델은 그중 선호(계란 등)와 겹치는 형태를 고른다 — [`Food_Agent_명세.md`](Food_Agent_명세.md) §6.
- 모델은 **풀 밖 메뉴를 낼 수 없다** (`menu_key` 검증). F-1 해소: 재료는 모델이 아니라 카탈로그에서 온다.
- 풀 자체가 3개 미만이면 재호출해도 채울 수 없으므로 **재호출하지 않고 남은 만큼만 낸다** — 추천은 최대 3개다(C-8 닫힘, [`Tool_공통.md`](../shared/Tool_공통.md) §5-2). 3개를 채우려고 풀 밖 메뉴를 만들지 않는다. 1~2개면 `suggestion.partial` 안내를 붙인다. 풀이 0개면 모델을 부르지 않고 추천 없이 `pool.empty` 만 낸다 — 재호출 뒤 0개도 같다. 실패가 아니다.
- ⚠️ TODO (추천 엔드포인트 이슈 #249 에서 정함): 이미 추천한 메뉴(만료 전 `draft`)는 풀에서 빼지 않는다. `sample_candidates` 의 seed 가 `run_id` 라 같은 `run_id` 로 다시 요청하면 같은 후보가 모델에게 가서, 다시 시도나 화면 재진입에서 같은 메뉴가 다시 나오기 쉽다. 풀에서 draft 메뉴를 뺄지, 모자랄 때 제외를 풀지, seed 를 무엇으로 할지는 [공통_구현_계획.md](../shared/공통_구현_계획.md) §6 TODO 에 모아 뒀다.
- 이유기는 카탈로그 대신 **이유식 재료 KB**(단계별 질감 · 도입 재료)에서 풀을 만든다. 공식 API가 없어 코드 상수.

| **`daycare_meal`** | `()` | `daycare` · update · delete | `daycare` · update · delete |

`daycare_meal` 라벨은 **`daycare_meal` 행이 있는 아이만** 열린다. 단계로 닫지 않는다 — 기관에 다니면 이유기라도 급식을 먹는다. 행이 없으면 갱신할 대상이 없으니 자연히 `()`다.

`meal_recommendation`에는 영양 tool이 열려 있지 않지만, **영양 구간은 코드가 따로 구한다.** `build_candidate_pool` 직전에 `evaluate_nutrient_bands`를 불러 부족 식품군을 받아 가중치에 쓴다(§0-5). 모델에게는 구간 자체가 아니라 이미 가중된 후보 목록이 간다 — 수치가 모델 입력에 들어가지 않는다. 알레르기·금지식품 라벨도 모델 입력에 넣지 않는다. 후보 풀이 이미 걸러진 상태로 가므로 모델이 라벨을 알 필요가 없고, 재호출 때의 제외 목록에도 `menu_key`만 넣고 걸린 사유는 넣지 않는다([`Tool_공통.md`](../shared/Tool_공통.md) §5-2).

단계 안에서 코드가 주입하는 값: `texture`(4–5 `puree` / 6–8 `puree`·`mashed` / 9–11 `minced`·`soft_pieces`) · 섭취기준 연령군(12–35 `1-2y` / 36+ `3-5y`) · 연령 식품 규칙(12개월 미만 꿀·마시는 우유 금지, 48개월 미만 질식 위험 식품 금지 · 질식 주의, 모든 아이 날음식 · 카페인 · 술 금지 — §3) · 급식 조회는 `daycare_meal` 행이 있는 아이만.

닫힘 조건 추가: `safety_ok=False` → `meal_recommendation`만 `()`.

**`consent_child_health=False` 는 Food 를 닫지 않는다** (2026-09-24). 동의가 없으면 `health_safety` 와 `child_growth_log` 를 읽지 못할 뿐이고, 그건 조회 실패가 아니라 **읽을 것이 없는 상태**다 — 읽은 안전 정보(`FoodRunState.safety`)가 빈 튜플이고 권장 열량은 연령군 일반값으로 간다. 동의를 안 했다고 식단을 못 받으면 안 된다.

Health 는 다르다 — 거기는 건강 그 자체라 동의 없이 전 라벨이 닫힌다. Growth 는 `growth_review` 만 readout 으로 내려간다.

`kind='allergy'` 행들의 `status`(F-4 확정)별 동작 —

| 행 상태 | 식단 추천 |
| --- | --- |
| 조회 실패 | `()` — 빈 목록으로 숨기지 않는다. **막는 것은 이것뿐** |
| 0행 | **연다** — 동의를 안 했거나 아직 아무것도 답하지 않았다. 알레르기 없는 아이 기준 일반 식단 (답하지 않은 항목은 아래 `unknown` 줄을 따른다) |
| 매칭되는 행이 없는 알레르기(`unknown`) | **연다** + 확인 안내 — 추천은 내보내고 그 항목만 되묻는다 |
| 전부 `none` | **연다.** 없다고 확인한 아이다 |
| `active` 있음 | 연다 (그 행들로 필터) |

`unknown` 은 저장하지 않는다 — 매칭되는 행이 없는 것이 곧 `unknown` 이다 (2026-10-04). 아이를 만들 때 19종을 미리 깔지 않고, 보호자가 답한 항목만 `none`·`active` 행이 된다. 확인 안내는 추천 승인 때 `suggestion.allergens` 와 `health_safety` 를 대조해서 띄운다 — `child.allergy_status` 는 필요 없다.

**거르는 것은 `active` 뿐이다.** `unknown` 은 게이트가 아니라 안내 신호다 — 모르는 항목 때문에 추천을 닫으면 답을 미룬 보호자가 서비스를 못 쓴다. 19종 밖은 추가할 때 `active` 로 들어가고, `retracted` 는 필터에서 `none` 과 같다.

`daycare_meal` 라벨은 이 표의 적용을 받지 않는다 — 급식 기록을 고치는 일이라 알레르기 필터가 걸릴 자리가 아니다. 다른 라벨과 같이 동의 없어도 열린다 — 급식 기록은 건강정보가 아니다.

### 급식 갱신의 입력은 span이다

`update_daycare_meal` · `delete_daycare_meal`의 인자는 전부 **발화 원문의 부분 문자열**이어야 하고 코드가 검증한다. 복약(`create_medication_schedule`)과 같은 규칙이다 — 모델은 어디를 가리키는지만 말하고, 뜻을 정하는 것은 코드다.

| span | 무엇 | 코드가 하는 일 |
| --- | --- | --- |
| `date_span` | "내일모레" · "지난 화요일" | `resolve_meal_date` → 날짜 |
| `slot` | "점심" · "오전 간식" | 닫힌 enum. 모델이 고르되 값 집합 밖이면 거절 |
| `removed_spans[]` | "우유" | `resolve_menu` → `menu_key`. 뺄 메뉴 |
| `added_spans[]` | "두유" · "계란말이" | `resolve_menu` → `menu_key`. 넣을 메뉴 |
| `amount_span` | "엄청 많이" · "반만" | 아래 사전 → `amount_factor` |

- 모델이 **날짜를 직접 계산하지 않는다.** "내일모레"를 2026-09-24로 바꾸는 순간 기준일을 모델이 정하게 된다
- `added_spans`가 `unresolved`여도 저장한다. 그 키가 `menu_keys`에 들어가고 영양 계산에서만 빠진다. 못 찾으면(장애 포함) 카탈로그에는 남기지 않는다 — 다음에 다시 찾는다 ([`food_agent_own_table.md`](food_agent_own_table.md) §1)
- **넣을 메뉴만 있고 뺄 메뉴가 발화에 없으면 되묻는다.** "어떤 메뉴 대신 받았나요?" 전체 교체로 처리하면 그날 실제로 먹은 밥·국까지 사라지기 때문이다

### slot 을 특정하지 못할 때

**갱신과 삭제가 다르다.**

| | slot 생략 |
| --- | --- |
| `update_daycare_meal` | 그날 행이 하나면 그 행, 여럿이면 **되묻는다**. 엉뚱한 끼니를 고치면 영양 계산이 틀어진다 |

### 갱신 뒤 안전 재검사

갱신한 메뉴는 `filter_food_safety`를 다시 거친다. 등록된 알레르기와 부딪혀도 **저장은 막지 않는다** — 보호자가 실제로 있었던 일을 말한 것이고, 기록을 막으면 사실이 사라진다. 대신 경고를 함께 낸다.

> "기록해 뒀어요. 그런데 등록된 우유 알레르기와 겹쳐요."

겹친다는 사실만 알린다. 기관에 확인해 보라고 권하지 않는다 — 어린이집 식사에는 우리 서비스가 관여하지 않는다.

이것이 추천 경로와 다른 점이다. 추천은 위험한 후보를 **지우고**, 기록은 위험해 보여도 **남기고 알린다.**

### 음식 안전 수칙 — `filter_food_safety` (#258)

막는 것은 코드가 한다. 모델에게 묻지 않는다(루트 §2 · §3). **애매하면 막는다** — 넣을지 망설여지는 이름은 사전에 넣고, guard(오탐 취소)에는 그 성분이 확실히 없는 것만 넣는다. 사례는 `apps/api/tests/unit/agents/food/test_food_safety_cases.py` 에 표로 있다.

**입력** — 메뉴 행들, 이 task 시작에 읽은 `health_safety` 행들(`FoodRunState.safety`), 아이 단계와 월령, 추천인지 급식 조회인지(`purpose`, 기본은 추천). 안전 행은 `status='active'` 만 온다(`SafetyReader.food_safety` 계약, 백엔드는 `list_active_safety`). 행이 없는 것이 unknown 이라 빈 목록이 정상이고, 읽기에 실패하면 `SafetyLookupError` 다. `SafetyEntry` 는 `kind` · `label` · `status` 만 갖는다 — `severity` 는 싣지 않는다(보호자가 active 로 둔 알레르기를 검사 등급 class_0 이어도 거른다. 코드가 등급을 보고 낮추면 의료 판단이다). `management` 도 싣지 않는다(자유 텍스트라 제한 식품을 코드나 LLM 이 뽑으면 루트 §2 에 걸린다). 월령을 모르면 그 단계가 시작하는 월령으로 본다(가장 어린 쪽이라 규칙을 덜 풀지 않는다).

**1. 보호자가 적은 이름을 읽는다** — `resolve_safety`, 공통 규칙은 `app/agents/common/allergy.py`

- `health_safety.label` 은 자유 입력이다. 고르는 목록이 없고, 검사지 사진에서 옮긴 영어 이름도 온다. 이름을 구분 기호(`,` `/` `·` `(` … · 가운뎃점 ㆍ • ・)로 나누고 뒤에 붙인 말("알레르기" · "알러지" · "있음" …)을 뗀 뒤 이름 사전에서 찾는다. NFKC 로 맞추고(자모로 풀린 한글 · 전각 영문), 문장부호 · 기호 · 보이지 않는 서식 문자(폭 없는 공백 · soft hyphen)는 빼고 견준다 — "pine-nut" · "'우유'" 는 "pine nut" · "우유" 다. 문장부호로 이은 조각은 사전 이름과 같아도 낱말로 한 번 더 읽는다 — "땅콩-버터" 가 한 이름인지 두 이름인지 모른다(더 막는 쪽).
- 정확히 같은 이름이 있으면 그것으로 읽는다. 없으면 조각 안에서 사전의 이름을 찾고(guard 를 지킨다 — "땅콩호박" 은 땅콩이 아니다), 그 조각을 글자 그대로도 막는다. guard 는 띄어쓰기를 넘어 덮지 않는다 — "밀 감자" 의 밀을 guard "밀감" 이 덮지 않는다.
- 띄어 쓰거나 문장부호로 이은 조각은 낱말마다 다시 읽는다 — "우유 바나나" · "아보카도-리치" 는 이름 둘이다. 사전에 없는 낱말도 글자 그대로 막는다. 정도 · 연결 · 병명을 적은 말(등 · 그리고 · 약간 · 심함 · 있음 · 전체 · 질환 …)은 건너뛴다.
- 낱말 끝의 조사를 뗀 이름도 읽는다 — "아보카도랑 리치" 는 아보카도와 리치다. 앞 글자 받침이 맞을 때만 뗀다("다과" 의 과는 조사가 아니다). 받침 없는 한 글자("누가" 의 누)는 남기지 않는다.
- 숫자 · 기호뿐인 조각은 이름이 아니다 — "우유(2)" 의 2 는 급식표의 알레르기 번호라, 글자로 막으면 숫자가 든 메뉴가 다 막힌다.
- 이름 사전은 공용 `reference/allergen_terms.yaml`(19종의 이름 · 묶음 이름) + Food 전용 `reference/food_safety_terms.yaml`(그 성분이 든 음식 · 19종 밖 알레르기) + `reference/chronic_restriction.yaml`(질환)이다. 검사지에 흔한 영어 이름(Cheese · Butter · Almond · Codfish · Salmon · Rice · Yeast · Potato …)과 흔한 오타("게란")도 사전에 있다.
- **묶음 이름**은 코드 여럿과 그 묶음의 19종 밖 식품으로 편다 — 갑각류(게 · 새우 + 가재 · 랍스터 …), 연체류(오징어 · 조개류 + 문어 · 낙지 …), 생선(고등어 + 연어 · 명태 …), 해산물(생선 + 갑각류 + 연체류), 견과류(땅콩 · 호두 · 잣 + 아몬드 · 밤 …), 콩류(콩 + 땅콩 + 녹두 · 팥 …), 육류, 글루텐(밀 + 보리 · 호밀 · 귀리 …). 묶음 이름은 그 글자 그대로도 막는다 — 레시피 재료에 "다진 견과류" · "해물믹스" 처럼 나온다. 포함한 묶음의 이름도 같이 막는다(해산물 → 생선 · 갑각류 · 연체류).
- **"콩"** 은 대두(5)로 읽고, 콩이 든 메뉴는 대두가 아니어도(강낭콩 · 완두콩 · 땅콩) 다 막는다 — 보호자가 콩류 전체를 뜻했을 수 있다. "대두" 로 등록하면 대두만 막는다.
- kind 와 상관없이 같은 사전으로 읽는다 — 알레르기 칸에 적은 "유당불내증", 질환 칸에 적은 "우유 알레르기" 도 막는다. 질환은 정의상 빼는 19종 코드도 막는다(유당불내증 · 갈락토스혈증 → 우유, 셀리악병 → 밀). 질환의 줄임말 · 영어 이름(셀리악 · celiac · lactose intolerance)도 같은 질환으로 읽는다. `kind` 는 `allergy` · `chronic_disease` · `behavioral` · `environmental` · `other_medical` 다 — 사전에 없는 이름(당뇨 · 고소공포 · 편식)은 식품을 유도하지 않는다. `other_medical` 갈락토스혈증도 우유를 막는다.
- 거르지 않는 상태는 `retracted` · `none` 둘뿐이다. 포트가 active 만 주지만 여기서 한 번 더 본다 — 어댑터가 `none` 행을 섞어 보내도 알레르기로 읽지 않는다. 모르는 상태값은 거른다 — 어댑터가 status 를 잘못 옮겨도("ACTIVE") 필터가 꺼지지 않는다. unknown 은 저장하지 않는 값이라 이 칸에 오면 어댑터 버그이고, 모르는 값으로 거른다.
- **알레르기는 분류 없이 전부 읽는다** (#295) — 환경 · 약물 알레르기(꽃가루 · 페니실린)도 읽지만 메뉴명 · 재료와 매칭되지 않으면 아무것도 막지 않는다. 분류(`category`)로 행을 미리 빼던 규칙은 없어졌다 — 보호자가 쑥을 환경으로만, 우유를 약물로 분류하면 식품 필터에서 빠지는데 바로잡을 길이 없었다. 막히던 메뉴가 통과하게 되는 경우는 없다(읽는 행이 늘기만 한다). 사전에 없는 짧은 이름은 글자 그대로 막아서 메뉴를 과하게 막을 수 있다(`개` → 김치찌개 · 된장찌개). 레시피 1,153개(60개월)로 재 보니 `개` 345개 · `꽃` 16개 · `나무` 2개 · `벌` 1개가 걸리고, 꽃가루 · 집먼지진드기 · 동물털 · 고양이 · 강아지 · 페니실린 · 아스피린 · 라텍스 같은 이름은 0개다 (2026-10-09). v1 은 과하게 막는 쪽으로 둔다 (이슈 #295 잠정 결정 1). 지금 동작은 `test_food_safety.py` 의 `test_짧은_환경_알레르기_이름은_메뉴를_과하게_막는다` 가 고정한다.

**2. 메뉴가 무엇을 담았는지 본다**

- 메뉴 코드 = 저장된 `allergen_codes` ∪ 메뉴명 · 재료를 사전으로 훑은 코드. 저장된 코드만 믿지 않는다 — 카탈로그 행은 갱신되지 않고, 코드를 빠뜨린 행이 있다.
- 메뉴명에 인쇄된 알레르기 번호(급식표의 "카레라이스(2.5.6)")는 읽지 않는다. 기관이 아이의 알레르기를 관리하고 보호자에게 미리 알리기 때문이다. 번호가 붙어 있어도 재료로만 판정한다.
- **제품마다 다른 성분** — `food_safety_terms.yaml` 의 `varies_foods`(간장 · 된장 · 고추장 · 쌈장 · 어묵 · 카레의 밀, 크래미 · 맛살의 게). 이 음식이 나오면 그 코드를 메뉴 코드에 넣지 않고 `(코드, 음식)` 으로 따로 든다. 같은 메뉴에 그 성분이 확실히 든 재료가 있으면(간장 국수의 소면) 메뉴 코드로 정해지니 따로 들지 않는다.
- 메뉴명과 재료 하나하나를 **필드마다 따로** 본다(`match_fields`). guard 는 필드 경계도, 한 필드 안의 띄어쓰기 · 문장부호도 넘어 덮지 않는다 — "통밀 크래커" 의 "밀 크" 는 "밀크" 가 아니다.
- 별칭은 띄어쓰기를 넘어서도 찾지만("달 걀") 문장부호는 넘지 않는다 — "소스 : 시금치" 에 "스시" 가 있는 게 아니다. 별칭 자체에 같은 자리의 띄어쓰기 · 기호가 있으면 넘는다. 보이지 않는 서식 문자는 없는 글자로 본다 — "우" 와 "유" 사이에 폭 없는 공백이 섞여도 우유다.

**3. 판정**

| 판정 | 조건 |
| --- | --- |
| `blocked` | 메뉴 코드 ∩ 막을 코드 ≠ ∅ · 제품마다 다른 성분의 코드 ∩ 막을 코드 ≠ ∅ · 글자로 막을 것이 나옴 · 연령 · 아이 금지 식품(block)이 나옴 |
| `unchecked` | 위에 안 걸렸는데 `resolved=False` 거나 재료를 모름(재료가 없거나 빈 글자 · 기호뿐) — 안전하다고 보지 않는다. 추천하지 않는다 |
| `passed` | 나머지 |
| `needs_check` | `blocked` 의 일부. 제품마다 다른 성분 때문에만 막힌 행 — 재료를 알고, 메뉴 코드 · 글자 · 연령 규칙에는 안 걸렸다(밀 알레르기 아이의 불고기 [소고기, 간장]). **지금은 막는다**(#264 PM 결정). 식단 추천을 구현할 때 `checks` 를 실어 "확인 필요" 로 내보낸다 — "사용할 간장에 밀 성분이 들어 있는지 확인해 주세요". 확인 전에는 채택하지 않고, "모르겠어요" 도 확인이 아니다(#267 멘토 리뷰). 재료를 모르는 행은 넣지 않는다 — 다른 재료를 모르니 확인 질문 하나로 풀 수 없다. 보호자가 그 음식 이름 자체로 등록한 경우("어묵 알레르기")도 넣지 않는다 — 글자로 확실히 걸린다 |
| `cautions` | 판정과 따로 붙는다. 주의 규칙(질식 주의 식품, 급식의 떡)이 나오면 막지 않고 주의로 남긴다 — 추천은 `guide.choking_caution` 을 붙인다. 급식에는 따로 안내 문구를 두지 않는다(어린이집 식사에는 관여하지 않는다). 48개월 이상은 붙지 않는다 |
| `allergens` | `passed` · `needs_check` 행. 그 메뉴에 **들어 있거나 제품에 따라 들어 있을 수 있는** 19종 정식 명칭(`ALLERGEN_NAMES` — 난류 · 우유 · …, 코드 순). 든 것이 없으면 키가 없다. 들어 있을 수 있는 성분까지 넣는 것은 등록하지 않은 알레르기도 계속 묻기 위해서다 — 밀을 아직 등록하지 않은 아이에게 불고기를 내면 "밀 — 먹어본 적 있나요?" 를 묻는다. 메뉴 코드로 만들어서 저장 코드만 쓰면 빠지는 성분(크림 → 우유)도 든다. 추천의 `suggestion.allergens` 는 이 값을 그대로 쓴다(#264 PM 결정) — 실제로 채우는 곳(`propose_meal_candidates`)은 식단 추천 구현에서 한다. 승인할 때 서버가 `health_safety` 와 대조해 "이 음식에는 땅콩이 들어가요. 땅콩 알레르기가 있는지 확인해주세요" 를 띄운다. 19종 밖 알레르기(`extra_allergens` — 참깨 · 아몬드 · 쌀 …)는 19종 다음에 그 label 로 담는다(데이터 모델 — 19종 밖은 이름으로). 19종 밖은 `health_safety` 에 active 로만 생겨서 "모름" 이 없다 — 승인 때 active 행과 대조하는 데만 쓰고 "먹어본 적 있나요?" 로 묻지 않는다 |
| `checks` | `passed` · `needs_check` 행. 그 메뉴의 제품마다 다른 성분 `(item, allergen)` — `item` 은 사전의 음식 이름, `allergen` 은 19종 정식 명칭. `passed` 행에도 싣는다 — 추천이 사는 24시간 안에 보호자가 그 알레르기를 등록하면 승인 때 다시 대조해 제품 확인을 물어야 한다 |

**5. 호출부가 지킬 것**

- 사전(yaml)을 못 읽으면 예외가 난다. 잡아서 통과시키지 않는다 — 그 task 는 실패다.
- `health_safety` 조회에 실패했으면(`FoodRunState.safety is None`) 필터를 부르지 않는다. 식단 추천은 닫히고(`blocked.safety`), 급식 조회는 "알레르기 확인 못 함" 을 낸다.
- 후보 풀에는 `passed` 만 넣는다. `unchecked` 는 추천하지 않는다. `needs_check` 는 `blocked` 라서 지금은 넣지 않는다.
- 식단 추천을 구현할 때 `needs_check` 행을 `checks` 와 함께 "확인 필요" 로 내보낸다(#264 PM 결정). `checks` 를 추천에 실을 칸(추천의 `ingredient_checks` · 서버의 사전검사 · 화면의 질문)이 없으면 내보내지 않는다.
- `needs_check` 를 내보내기 전에 정할 것 — ① 묶음 · 질환으로 등록한 아이(글루텐 · 셀리악병 · 갑각류)의 `checks` 는 그 코드 하나(밀 · 게)만 묻는다. 보리 · 호밀 같은 나머지 구성은 못 보니, "제품에 밀이 없다" 는 답으로 풀어도 되는지 PM 과 정한다. ② 사전 빈칸 — `needs_check` 행의 나머지 재료(굴소스 · 데리야끼 · 우스터 소스의 밀, 떡볶이 밀떡 …)는 사전이 코드를 붙이지 않는다. 풀기 전에 점검한다. ③ 확인 필요 음식 이름으로 등록한 아이("어묵 알레르기")는 밀(6)도 막혀서 다른 장류 메뉴가 `needs_check` 로 표시된다 — 이 표시를 푸는 것이 맞는지 같이 정한다.
- 추천의 `allergens` 는 이 필터의 `allergens` 를 그대로 쓴다. 카탈로그의 `allergen_codes` 나 `menu_codes` 로 채우면 막는 판단과 묻는 목록이 어긋난다.
- 보호자의 답 — 제품 확인은 "안 들어 있어요" 만 채택을 연다. "들어 있어요" 는 그 제안만 빼고 `health_safety` 에 저장하지 않는다(제품의 성분이지 아이의 알레르기가 아니다). "모르겠어요" 는 채택하지 않는다. 아이 알레르기 질문("먹어본 적 있나요?")의 "모르겠어요" 는 저장하지 않고 unknown 으로 두며, 그 성분이 든 추천이 나올 때마다 다시 묻는다(잠정 — #264 코멘트에서 FE · BE 확인 중).
- 급식 조회는 메뉴마다 판정한다. 메뉴명에 인쇄된 알레르기 번호는 읽지 않는다(위 2).
- 식단 추천은 `purpose` 를 넘기지 않는다(기본 `recommend`). 급식 조회와 급식 갱신 뒤 재검사는 `purpose="daycare"` 로 부른다.
- 추천은 `cautions` 가 있는 메뉴를 내보낼 때 `guide.choking_caution` 을 붙인다. 급식에는 보호자에게 어린이집 쪽 확인을 권하는 안내를 두지 않는다 — 어린이집 식사는 우리 서비스가 관여하지 않는다. 급식 화면에서 주의를 어떻게 보일지는 급식 조회 tool 을 구현할 때 정한다. 48개월 이상에는 붙이지 않는다 — 경고가 너무 자주 뜨면 알레르기 같은 중요한 경고도 흘려본다(#264 PM 결정).
- 로그에 hits · label 원문을 남기지 않는다.

**6. 사전에 넣는 원칙 · 남은 한계**

- 알레르기 자체의 이름(동의어 · 외래어 · 영어 · 표시기준이 포함한 것)은 공용 사전에, 그 성분이 든 음식은 Food 사전에 넣는다. 공용 사전은 Activity 도 읽는다.
- 요리 이름은 주재료가 늘 그 성분일 때만 넣는다(소면 · 우동 → 밀). 재료가 그때그때 다른 요리(떡볶이 · 김치)는 재료로 잡고, 재료를 모르면 `unchecked` 다.
- 그 음식에 늘 들어가는 성분만 `code_foods`(확실)에 넣는다(소면 · 우동 → 밀, 짜장 · 춘장 → 밀). 제품마다 들어가기도 안 들어가기도 하는 성분은 `varies_foods` 에 넣는다(간장 · 된장 · 고추장 · 쌈장 · 어묵 · 카레 → 밀, 크래미 · 맛살 → 게). 지금은 둘 다 막고, `varies_foods` 때문에만 막힌 메뉴는 `needs_check` 로 표시한다. 레시피에는 "된장" 이라고만 적혀 있어서 집된장인지 시판인지는 보호자 부엌에서 정해진다 — 그래서 레시피 쪽에서 나누지 않고 보호자에게 묻는다. 항목마다 `source` 에 근거를 적는다. 후보 문장이면 끝에 "(제품 표시 대조 전)" 을 붙이고, `needs_check` 를 내보내기 전에 시판 제품의 원재료 · 알레르기 표시로 "든 제품과 없는 제품이 둘 다 있다" 를 확인한 뒤 뗀다. 확인되지 않은 항목은 `code_foods` 로 되돌린다. 애매하면 `code_foods` 다 — 이 분류가 틀리면 막아야 할 것이 나중에 확인 단계로 넘어간다.
- 보호자가 `varies_foods` 의 음식 이름으로 등록하면("어묵 알레르기") 그 코드와 그 음식 글자를 함께 막는다. 같은 행의 동의어(어묵 = 오뎅 · 맛살 = 크래미)도 같은 음식이라 함께 막는다. 이름 읽기는 확실과 확인 필요를 가르지 않는다.
- 이름에 성분 이름이 그대로 든 메뉴("게맛살")는 그 글자로 막힌다. guard 는 성분이 확실히 없는 낱말에만 쓰므로 "게맛살" 을 guard 로 풀지 않는다.
- 교차반응(오징어 ↔ 문어, 새우 ↔ 가재)은 코드로 넓히지 않는다. 코드는 표시기준의 그 항목만 뜻해야 추천의 `allergens` 가 거짓이 되지 않는다. 넓게 막으려면 묶음 이름(연체류 · 갑각류)으로 등록한다.
- 한 단어 안에서는 guard 가 덮는다. guard 를 더할 때는 그 단어에 그 성분이 정말 없는지 확인한다. guard 는 별칭이 나온 자리 전체를 덮어야 한다 — "겨잣가루" 의 "잣가루" 는 guard "겨잣" 밖으로 나가므로 "겨잣가루" 도 guard 에 둔다.
- 한 글자 별칭(게 · 굴 · 잣 · 콩 · 깨)은 다른 낱말 안에 흔하다. 식약처 레시피(COOKRCP01)에서 찾은 것을 guard 로 둔다 — "게" 는 "~게"(얇게 · 맛있게) · 스파게티 · 바게트 · 멍게 · 성게 · 흔한 오타(게란 · 닭게장 · 육게장) · 조사(아이에게), "굴" 은 굴림만두 · 굴라쉬 · 얼굴, "깨" 는 깨끗이 · 홍두깨살. "밀크" 는 코코넛 · 아몬드 · 오트 밀크에서 우유가 아니다.
- develop 에서 막히던 메뉴가 풀리는 것은 셋이다. ① 필드 사이에 걸친 별칭 — 어느 필드에도 혼자 없는 별칭은 없는 재료다. ② 셀리악병 글자 검사의 "글루텐 프리" 표기 — 밀 제품 이름이 있으면 코드로 그대로 막힌다. ③ 보호자가 적은 이름이 이제 사전의 이름이라 그 이름의 guard 를 따르는 것 — "깨" → 홍두깨살, "갈비" → 닭갈비, "오리" → 오리지널. 셋 다 guard 와 같은 원칙(그 성분이 확실히 없는 낱말)이다.
- 사전에 없는 영어 이름은 글자 그대로만 막는다. 한국어 메뉴에는 걸리지 않는다 — 검사지에 흔한 이름은 사전에 넣었지만, 드문 이름("Green onion" 같은 합성어)은 빠진다. 읽지 못한 이름을 보호자에게 되묻는 것은 따로 다룬다.
- "주의할 수 있음" 같은 제품 표시(교차오염)는 데이터가 없어 보지 않는다.
- 라이브 eval `tests/eval/agents/food/test_safety_filter.py` 가 모델이 쓴 보호자 표현 · 메뉴로 사전의 빈 곳을 찾는다(`-m live`). 가공식품에 "들어 있을 수도 있는" 성분(카레가루의 우유 · 어묵의 새우 · 단무지의 아황산)은 `varies_foods` 에 넣을 수 있다. 넣으면 지금은 그 알레르기 아이에게 막히고(더 막는 쪽), 나중에 확인 질문이 된다. 근거는 다른 항목과 같다 — 후보 문장에 "(제품 표시 대조 전)" 을 붙여 넣고, 내보내기 전에 제품 표시로 대조한다.
