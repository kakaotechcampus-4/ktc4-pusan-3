## 2. C1 · 일반 실패 판정 기준

**C1 = 보호자가 출력을 그대로 믿고 따랐을 때 ① 아이가 다칠 수 있거나 ② 아이에 대한 틀린 판단이 남거나 ③ 되돌릴 수 없는 일이 생기는 출력.** 단순 응답 품질 저하와 구분하고, 실제 사용자에게 미칠 영향을 기준으로 판단한다.

**이 프롬프트의 C1**

- 정답과 다른 메뉴가 그 날짜 · 끼니의 급식으로 읽힘 (메뉴 이름 · 날짜 · 끼니 불일치) — 저장되면 Food 가 그날 급식으로 믿고 쓰고, 보호자가 먹은 양을 기록하면 틀린 메뉴에 붙어 남는다 (②). 11-09 PM 확정
- 알레르기 번호 불일치는 C1 이 **아니다** — 10-09 부터 서비스가 번호를 읽지 않는다. 번호를 다시 읽는 쪽으로 바뀌면 C1 로 되돌린다 (그때 신체 위해 가능성 ①)

**일반 실패**

- 정답 메뉴를 빼먹기만 함 (틀린 메뉴는 안 들어감) — 화면에 덜 보일 뿐 틀린 메뉴가 기록에 붙지 않는다. 11-09 PM
- 이름 깨짐 — 맞는 메뉴인데 이름(`name`)에 한글이 아닌 찌꺼기가 붙음(`백김치(백깍두기 Riot`). 다른 음식으로 바뀐 것이 아니다. #908 전에는 이 이름이 화면 제목과 저장 키로 가서, 카탈로그에 없는 메뉴가 되어 알레르기 판정이 "확인 못 함" 으로 나왔다 — 틀린 판단이 남지 않아 C1 이 아니다(11-10 결정). **11-11 부터 운영은 모델의 `name` 을 쓰지 않고 원문에서 이름을 만든다**(`rules/menu_key.menu_display_name`, `notice_ocr.names_from_raw`). 그래서 모델 이름이 깨져도 화면 · 저장에 가지 않고, 채점은 실패로 세지 않고 "모델 이름 깨짐(참고)" 로만 센다(§3)
- 원문 글자 차이 (공백 · 기호)
- `unparsed` 칸이 늘어남 (모델이 못 읽겠다고 신고)

일반 실패는 단독으로 나오면 C1 이 아니다. 다만 C1 의 세 조건 중 하나를 만족하면 C1 을 먼저 적용한다. **근거 없는 개인화 표현 · 되묻기 2개 이상**은 루트 CLAUDE.md §2 절대 규칙이라 C1 은 아니어도 0건을 유지하고, 늘면 리뷰에서 막는다.

**반복 · 비교 규칙**

- 같은 입력을 R번 돌려 **한 번이라도 C1 이 나오면 그 입력은 C1 사례**다. 입력별 발생 횟수도 §3 에 적는다. 일부 실행에서만 나온 오류도 불안정하다는 이유로 빼지 않는다.
- 측정 이력의 `C1` 칸은 `a/b` — a = C1 사례인 입력 수, b = 전체 입력 수. `test_prompt_history.py` 가 같은 `조건` 의 직전 측정 행과 **비율 a/b** 를 비교해 늘었으면 실패시킨다 (평가셋이 커져 건수만 늘면 통과).
- 프롬프트를 바꾼 행은 **같은 조건으로 잰 바꾸기 전 행** 이 있어야 한다 — 없으면 실패. 기준선이 `미측정` 이면 바꾸기 전 프롬프트로 한 행, 바꾼 뒤로 한 행을 같은 조건으로 더한다.
- 조건(평가셋 · 모델/effort · 반복 횟수)을 바꿨으면 바꾸기 전 프롬프트를 새 조건으로 먼저 다시 재서 행을 더한다. 같은 지문으로 조건만 바꿔 다시 잰 행은 비교하지 않는다.

## 3. 반복해서 같은 오답 · 흔들리는 값

**채점 방법** (`scripts/meal_ocr_eval.py`)

- 입력 하나 = 끼니 하나(날짜 × 끼니). 분모 = 정답 끼니 69 + 어느 실행에서든 정답에 없는데 메뉴가 생긴 끼니(휴일에 급식이 생기는 날짜 밀림도 C1 이라 분모에 넣는다)
- 모델 출력은 운영이 싣는 끼니(점심 · 오전간식 · 오후간식)만 본다. 아침 · 저녁으로 간 메뉴는 저장되지 않아 틀린 메뉴가 남지 않고, 제 끼니에서 빼먹은 것(일반 실패)으로 잡힌다. 메뉴 이름이 없는 끼니(번호뿐)는 세지 않는다. 한 날짜에 같은 끼니가 두 번 나오면 이어 붙여 채점한다 — 운영은 둘 다 화면에 싣는다
- 메뉴 이름은 알레르기 번호를 떼고 괄호로 나눈 조각을 순서 없이 비교한다 — 공백 · ★ · 칸 끝 쉼표 · `백김치(백깍두기)` ↔ `백깍두기(백김치)` 는 같은 메뉴. 맞춤법 차이는 사람이 같은 음식이라고 확인한 것만 `SAME_MENU_SPELLING` 에 둔다(현미밥 / 흑미밥 처럼 한 글자만 달라도 다른 메뉴라 글자 거리로 묶지 않는다)
- 이 "같은 메뉴" 는 보호자가 화면에서 보는 이름 기준이다. 저장 키(`normalize_menu_key`, 괄호 안을 지운다)와는 다르다 — `빵(우유식빵)` · `빵(우유카스텔라)` 는 저장 키가 둘 다 `빵` 이지만 보이는 이름이 달라 C1 로 세고, `백김치(백깍두기)` · `백깍두기(백김치)` 는 저장 키가 다르지만(`백김치` · `백깍두기`) 같은 메뉴로 본다
- 이름은 **운영과 같은 것**을 채점한다 — 화면 제목과 저장 키는 원문에서 코드가 만든 이름으로 만든다(`notice_ocr.names_from_raw` → `photo_run._meal_entries` → `meal_row`, 11-11 #908). eval 도 `reader.read()` 결과를 같은 함수에 거친 뒤 채점한다(같은 함수 하나를 쓴다). 원문에서 만든 이름은 원문에 없는 글자를 담지 않아 "이름 깨짐" 실패는 생기지 않는다. 메뉴가 맞는지는 원문으로 가린다(위의 같은 메뉴 규칙)
- **모델 이름 깨짐(참고)** — 모델이 낸 `name` 에 원문에 없는 낱말(`Riot`)이나 원문에 없는 기호(`}{"` · `_`)가 든 항목 수. 실패 · C1 에 넣지 않고 프롬프트가 바뀔 때 모델 출력이 나빠졌는지만 본다(`model_name_breaks`). 한글 낱말이면 "다른 음식 낱말" 로 표시한다. 저장 파일은 모델 출력 그대로라 다시 채점하면 이 값도 다시 나온다
- 안정 오답 = 5번 다 실패한 끼니, 불안정 = 일부만 실패한 끼니. 실패 = C1 · 메뉴 빼먹음(이름 깨짐은 11-11 부터 운영에 가지 않아 빠진다). 읽기에 실패한 회차는 모든 끼니를 빼먹은 것으로 센다(틀린 메뉴가 남지 않는다). 한 번도 못 읽으면 잰 것이 아니라서 종료 코드 1 로 끝나고 실행 메타를 남기지 않는다

- 11-11 같은 메뉴 비교도 운영이 이름을 만들 때와 같은 기호 정리(`menu_display_name`)를 거치게 했다 — 위 기호 차이 2끼니가 C1 에서 빠져 같은 3회가 **2/69 · 0 · 2** 다(남은 2끼니는 원문 오독). 글자가 다르면 그대로 C1 이다. 원문의 닫는 괄호가 빠진 출력(`백김치9(백깍두기9`)은 괄호로 나눠 비교해서 실패로 잡히지 않는데, 운영 화면 제목 · 저장 키는 정답과 달라진다 — 이 채점으로는 보이지 않는다
- 첫 측정 5회 · v1 5회 출력은 여기서 다시 채점하지 않았다

**11-11 사진 경로 견고화 — 채점에 닿는 것 (`docs/meal-plan/meal-plan-pipeline-v1.md` 결정 ④)**

- 프롬프트 · 응답 스키마는 그대로다(지문 그대로). §1 에 행을 더하지 않았다.
- `names_from_raw` 가 열량 · 영양 표기 줄(`총 511 kcal`)을 빼고, 그 줄뿐인 끼니를 뺀다. 운영과 같은 함수라 eval 도 같다. 정답셋에는 그런 줄이 없어(178항목 중 0) 정답 쪽 채점은 바뀌지 않는다 — 모델이 그 줄을 메뉴로 내던 출력은 틀린 메뉴(C1)가 하나 줄어든다.
- 합치기(`merge_outputs`)가 그 달에 없는 날 · 두 번 읽힌 날을 못 읽은 칸으로 돌리고, 한쪽 호출이 실패해도 성공한 쪽을 낸다. 그래서 전에 "읽기 실패"(모든 끼니 빼먹음)로 세던 회차 중 한쪽만 실패한 회차는 이제 성공한 절반이 채점된다. 둘 다 실패해야 읽기 실패다.
- 🚨 eval 은 연도를 코드로 정하지 않는다 — `reader.read()` 는 모델이 낸 `year_month` 그대로 합친다(정답셋 사진은 제목에 `2025년 1월` 이 있다). 운영은 `read_parts` 뒤 `rules/meal_plan_month` 로 정한다. 그래서 모델이 `"01"` 처럼 연도 없이 내면 eval 에서는 그 회차가 읽기 실패고, 운영에서는 살아난다.
- 저장해 둔 운영 경로 출력(M1~M3 · after/M1 · parallel M1~M4 · 시연 급식표 F1~F2)을 새 코드로 다시 조립해도 날짜 · 메뉴 · 못 읽은 칸이 하나도 바뀌지 않았다(모델 다시 부르지 않음).

## 4. 실행 방법

```powershell
uv run python -m scripts.meal_ocr_eval --check   # 접속 · 모델 목록만 (과금 없음)
uv run python -m scripts.meal_ocr_eval tests/fixtures/meal_plan_2025_01.jpg --repeat 5
```

같은 사진을 5번 읽어(한 번에 호출 2회, 11-09 기준 약 430원 · 7분) 끝에 `측정 이력 칸`(C1 `a/b` · 안정 오답 · 불안정)과 끼니별 실패 횟수, `모델 이름 깨짐(참고)` 항목 수를 출력하고, `tests/eval/agents/live_run_meta.json`(gitignore)에 커밋 · dirty · 모델 · effort · 반복 횟수 · 프롬프트 지문을 남긴다. 그 값으로 §1 에 행을 더한다. 모델 출력은 `--out`(기본 임시 폴더)에 실행마다 저장한다. 호출이 `--max-calls`(기본 20)를 넘으면 시작하지 않는다 — 예산을 넘기면 팀 키가 삭제된다. 라이브 eval 은 CI 에서 돌리지 않는다.
