문서 목적: 사진 입력의 기본 모델을 정한 근거(실측)와, 채점 기준 · 정답셋 · 실행 방법을 고정한다.

## 1. 채점 — 무엇을 맞아야 하나

정본: [`apps/api/scripts/meal_ocr_eval.py`](../../apps/api/scripts/meal_ocr_eval.py)

```
uv run python -m scripts.meal_ocr_eval --check                                  # 접속 · 모델 목록 (과금 없음)
uv run python -m scripts.meal_ocr_eval tests/fixtures/meal_plan_2025_01.jpg     # 기본 모델로 채점
uv run python -m scripts.meal_ocr_eval IMAGE --model claude-opus-5 --base-url … # 비교
```

| 지표 | 뜻 | 왜 |
| --- | --- | --- |
| **메뉴 단위 알레르기 번호 일치** | 정답의 메뉴마다 `parse_allergens(raw).codes` 가 같은 메뉴가 모델 출력의 같은 끼니에 있는가 | **제일 중요.** 저장은 메뉴 1개 = 1행이라 이 단위로 맞아야 한다 |
| 끼니별 번호 합집합 일치 | 끼니 안 번호를 합쳐서 비교 | 한 메뉴에서 빠진 번호를 옆 메뉴가 가리면 못 잡는다 — 참고용 |
| 원문 글자 그대로 · 정규화(공백 · ★ · 괄호 · 잼/쨈 무시) | `raw` 문자열 비교 | 참고용. 글자가 달라도 번호가 맞으면 서비스엔 문제없고, 그 반대는 문제다 |
| 범위 밖 번호 · `unparsed` | 19종 밖 숫자 · 모델이 못 읽었다고 한 칸 | 검수 신호가 제대로 나오는지 |

정답셋: [`apps/api/tests/fixtures/meal_plan_2025_01.json`](../../apps/api/tests/fixtures/meal_plan_2025_01.json) — 지자체 어린이급식관리지원센터 공개 배포본 2025-01 ③형(만 1~2세) 1장, 27일 · 178항목, 기관명 가림, 사람이 고해상도 원본과 대조해 확정. 사진은 같은 폴더의 `.jpg` (992×1403).

## 2. 결과

호출은 1~15일 · 16~31일 **2분할**(게이트웨이 출력 상한 6,000 토큰), 추론 강도 medium.

| 날짜 | 모델 | 메뉴 단위 번호 일치 | 끼니 합집합 | 원문(정규화) | 비용/회 | 시간 |
| --- | --- | --- | --- | --- | --- | --- |
| 09-09 | claude-opus-5 | 171/178 (96%) | 62/69 (90%) | 87% | 374원 | 104초 |
| 09-09 | gemini-3.1-pro-preview ×3 | 177 · 178 · 177 (99~100%) | 69/69 ×3 | 90 · 98 · 97% | 167원 | 70초 |
| **09-16** | **gemini-3.1-pro-preview** (새 계약 #65 · `dinner` · 원문자 명시) | **178/178 (100%)** | **69/69** | 97% | 약 160원 | 74초 |

**오류의 성격이 다르다.**

- Opus 5 의 틀린 7개 중 4개는 **없는 번호를 만들어 낸 것** (`&잼` → 8, `17` → 13, 씨리얼에 1 추가). 고등어(7) 누락 1건, 오후간식 행을 옆 칸과 섞은 것 1건. 검수 표시 없이 나온 것이 위험하다.
- Gemini 는 번호를 지어내거나 빠뜨린 경우 0건. 09-16 실측에서 원문이 다른 7개는 전부 철자(`물만두국`/`물만둣국`, `샤인머스켓`/`샤인머스캣`, `우유식빵`/`우유모닝롤`)이고 번호는 같다. `unparsed` 4칸은 전부 날짜 없는 견본 열(♥생일식단♥)을 제대로 걸러낸 것이다.

→ **기본 모델은 `gemini-3.1-pro-preview`** (`MEAL_OCR_MODEL` 기본값). Opus 5 엔드포인트는 `.env` 주석에 비교용으로 둔다.

## 3. 게이트웨이(Elice MLAPI)에서 실측한 것

- 엔드포인트가 **모델마다 다르다.** `--base-url` 로 바꿔 끼운다.
- 출력 **6,000 토큰 상한**은 게이트웨이 공통. `max_completion_tokens` 를 더 주어도 무시된다. 한 달치 JSON 은 7,000 이상이라 2분할이 필수.
- 응답을 `{"MealPlanJSON": {...}}` 처럼 스키마 이름으로 한 겹 감싸는 경우가 있다. `parse_output` 이 벗긴다.
- 프롬프트 캐시가 자동 적용된다. Opus 는 첫 호출에 쓰기 할증 1.25배, Gemini 는 할증 없음. 09-16 실측에서는 캐시 적중 0 (분할 호출 사이 간격이 짧아도 적중하지 않았다 — 원인 미확인).
- 5회 시도 중 원인 미확인 일시 오류 1회. 재시도 정책은 아직 없다(SDK 기본 1회).

## 4. 후보 방식 — 범용 VLM 만이 아니다

| | 방식 | 장점 | 단점 | 우리 조건에서 |
| --- | --- | --- | --- | --- |
| **A** | 범용 VLM + Structured Output (현재) | 우리 스키마 직접 강제 · 인프라 0 · MLAPI 크레딧 안 | 확신도 없음 — 모델 자기 신고(`unparsed`)에 의존 | 1장 기준 100%. 다른 양식 검증 필요 |
| **A+** | A 를 두 모델로 돌려 불일치만 검수 | 확신도 대용 | 장당 비용 2배(약 550원) | 인프라 없이 되는 유일한 확신도 |
| **A′** | Mistral OCR 4 | 단어 · 페이지 확신도 + 위치 | 출력이 문서 구조라 우리 스키마로 옮기는 단계가 다시 필요 | MLAPI 라이브러리에 있어야 크레딧 안 |
| **B** | PaddleOCR-VL-1.6 셀프호스팅 | 공개 벤치마크 최고 · CJK 강함 · 이미지가 밖으로 안 나감 | 서빙 서버 필요 · 역시 스키마 정리 단계 필요 | 루트 §7 "인프라 하나" 와 충돌. A 가 무너질 때의 대안 |

벤치마크로 고르지 않는다 — Mistral 이 OCR 4 발표문에서 "자기 문서로 직접 평가한 뒤 도입하라" 고 권고했고([mistral.ai/news/ocr-4](https://mistral.ai/news/ocr-4/)), §2 가 같은 얘기다(일반 지능 지수는 Opus 가 높았지만 한국어 급식표는 Gemini 가 정확했다).

**센터 배포 엑셀 · 한글은 이 비교 대상이 아니다.** 표 안이 텍스트라 OCR 없이 읽는다 (파이프라인 문서 §1).
