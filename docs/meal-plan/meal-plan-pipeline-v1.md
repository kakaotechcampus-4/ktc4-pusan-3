# 급식표 구조화 파이프라인 v1

문서 목적: 급식표 입력(사진 · 엑셀 · 한글)이 모이는 공통 JSON 과 읽기 인터페이스를 고정하고, 저장 이전 단계의 결정을 남긴다.

기준 브랜치: `feat/be-16-meal-plan-schema`
작성일: 2026-09-16
담당: 박재형
선행 문서: [`docs/overview/tech-spec.md`](../overview/tech-spec.md) (§7 외부소스 테이블 자리) · 루트 [`CLAUDE.md`](../../CLAUDE.md) §2 §3

이슈 #16 (파이프라인) · #63 (엑셀 · 한글 입력). 2026-09-08 초안(#21)을 다섯 PR 로 나누며 다시 썼다.

---

## 1. 흐름

```
사진(OCR)  ┐
엑셀       ├─→  MealPlanJSON  ─→  저장 (`daycare_meal`, 아이 기준)
한글       ┘     §3                메뉴는 name 으로 — 알레르기 번호는 읽지 않는다 (결정 ②)
```

입력이 무엇이든 **읽기 코드는 `MealPlanJSON` 까지만** 낸다. 그 뒤(저장 · 검수)는 입력원과 무관하다.

| 입력 | 어디서 오나 | 읽는 방법 | 못 읽는 칸 |
| --- | --- | --- | --- |
| `image` | 보호자가 찍은 사진 | OCR (Gemini) → [`image_ocr.py`](../../apps/api/app/providers/meal_plan/image_ocr.py) | 생긴다 → 검수 (실측: 178항목 · 번호 일치 100% · [모델 비교](./ocr-model-eval-v1.md)) |
| `xlsx` | 급식관리지원센터 배포 엑셀 (6종 시트) | 셀을 그대로 읽는다 (openpyxl) → [`xlsx.py`](../../apps/api/app/providers/meal_plan/xlsx.py) | 거의 없다 (실측: 6시트 · 868항목 · 0) |
| `hwp` | 센터 배포 한글 | 표 안 텍스트를 읽는다 (라이브러리 미정, §6) | 거의 없다 |

센터 배포본은 표 안이 전부 텍스트라 OCR 이 필요 없다 (실측: 원문자 769개가 텍스트로 들어 있음).

**실제 대상 기관은 부산대 병설유치원이고, 급식표를 아직 받지 못했다.** 위 표의 `xlsx` · `hwp` 와 §3 의 `meal_type` 은 급식관리지원센터 배포본으로 실측한 것이다. 유치원 급식표 형식을 확인하면 입력 종류와 끼니 칸을 조정한다.

## 2. 결정

### ① 저장 기준(아이 / 기관)은 미정 — 우선 아이 기준으로 구현한다

같은 급식표를 보는 아이가 많아 기관 기준이 호출 · 저장 · 검수 모두 유리하지만, 기관 정보를 다루는 것이 개인정보 범위(루트 §2 "프로필 질문을 늘리지 말 것")와 부딪힌다. 결정은 회의안건 1-2. 그 전까지는 아이 기준으로 만들고, JSON 의 `institution_name` 은 급식표에 찍혀 있을 때만 채우는 **선택값**으로 둔다 — 기관 기준으로 바꿀 때 쓸 수 있게 버리지 않는다.

### ② 알레르기 번호는 읽지 않는다 (10-09 갱신)

처음에는 "모델은 번호를 만지지 않고, 규칙(`app/rules/allergen.py`)이 `raw` 에서 뽑는다" 였다. **10-09 에 번호 자체를 읽지 않기로 바꿨다** — 기관이 아이의 알레르기를 관리하고 보호자에게 미리 알린다. 급식의 위험 식품 표시는 Food 가 메뉴 이름 · 재료로 한다([`Food_Tool_명세.md`](../agents/food/Food_Tool_명세.md) §3).

```
읽기 코드  →  { name, raw }              표 읽기 · 메뉴명 분리. name 에는 번호 · 기호가 없다
```

- `allergen_codes` 는 JSON 에 **없다.** 모델이 그 키를 내면 검증에서 거절된다 (`extra="forbid"`).
- `raw` 는 번호까지 원문 그대로 남긴다 — 보호자가 종이 원본과 대조하는 검수용이다.
- **`name` 은 번호 · 기호를 뺀 이름이어야 한다.** 메뉴 카탈로그 조회와 영양 계산이 이 이름을 쓴다. 번호가 남으면 카탈로그에서 안 찾아져 영양 계산에서 빠진다.

### ③ 못 읽은 칸은 지어내지 않고, 그 칸만 비운다

**못 읽은 칸은 메뉴 이름을 못 읽은 칸이다.** 이름은 확실한데 번호만 흐린 칸은 `unparsed` 로 보내지 않는다 — 번호를 쓰지 않으니, 그 칸을 버리면 멀쩡한 메뉴가 영양 계산에서 빠지기만 한다(10-09).

`unparsed` 가 비어 있지 않으면 사람이 봐야 하는 급식표다. 검수는 **사진을 올린 보호자가 그 자리에서** 한다 (종이 원본을 가진 사람이 그 보호자뿐이다). 보호자가 확인을 안 눌러도 급식표 전체를 버리지 않고 **못 읽은 칸만 "확인 안 됨"** 으로 두고 나머지는 쓴다 — 급식표는 아이 알레르기 정보 자체가 아니라 "그날 뭐 나오나" 참고 자료라 한 칸 때문에 한 달치를 버리는 것은 과하다. "확인 안 됨" 은 빈칸(메뉴 없음)과 구분되는 별도 상태여야 하며, 이 표시는 저장 단계(칸 단위)의 몫이다.

이 확인은 되돌릴 수 없는 행동의 승인이 아니라 "읽은 게 맞나" 확인이라, 루트 §2 의 승인 게이트 2곳에 더하는 것이 아니다.

### ④ 사진 급식표 — 연도는 코드가 정하고, 한 칸 때문에 표를 버리지 않는다 (11-11)

2026-11-11 운영 장애에서 정했다. 연도 없는 급식표(`[11]월 급식계획`)를 읽어 화면에 "잘 읽었어요 24건" 이 떴는데 저장이 400 으로 막혔다. 원인은 셋이었다 — 모델이 지어낸 연도, 열량 줄이 메뉴가 된 것, 화면에 나간 항목을 저장이 거절한 것.

**연도는 모델에게 묻지 않는다** (루트 §2 · §3 날짜 계산). [`rules/meal_plan_month.py`](../../apps/api/app/rules/meal_plan_month.py) 가 정하고 [`agents/notice_ocr.read_photo`](../../apps/api/app/agents/notice_ocr.py) 가 부른다.

- **월**은 모델이 읽은 `year_month` 에서 모양을 가리지 않고 읽는다 — `11` · `11월` · `2026.11` · `26-11` 모두 11월. 형식이 틀렸다고 표를 버리지 않는다.
- **연도** — PM 결정(11-11): 연도가 비어 있으면 조용히 채우지 않는다.

| 경우 | 연도 | 화면 |
| --- | --- | --- |
| ① 원문(공지 읽기의 옮겨 적은 글)에 연도가 **그 달과 붙어** 적혀 있고 모델 연도와 같다(또는 모델이 연도를 안 냈다) — `2025년 1월` · `2025.01` · `25년 1월` | 그 연도 (`written`) | 알리지 않는다 |
| ② 원문에 연도가 없고 그 달이 받은 날(한국 날짜)의 **지난달 · 이번 달 · 다음 달** | 코드가 정한다 (`guessed`). 12월에 받은 1월은 다음 해, 1월에 받은 12월은 지난해 | 🚨 추정 안내를 그릴 통로가 지금 웹에 없다 — 서버 로그 WARNING 한 줄만(아래) |
| ③ 원문에 연도가 없고 그 밖의 달 (11월에 받은 3월) | 정하지 않는다 (`unknown`) | 급식을 내보내지 않고 "급식표에 연도가 적혀 있지 않아 언제 것인지 알 수 없어요" 한 줄(표를 못 읽었을 때와 같은 통로) |
| ④ 원문의 연도가 모델과 다르거나, 그 달의 연도가 원문에 여럿 | 원문의 연도 중 받은 날에 가장 가까운 것 (`written_other`). 똑같이 가까운 것이 둘이면 ③ | ②와 같다 |

- `2025학년도 1월` 은 연도가 아니다 — 그 1월은 2026년이다. 그래서 연도는 그 달과 붙어 있을 때만 본다.
- 공지 날짜 규칙(`notice_dates._nearest`, 60일)을 쓰지 않는다 — 11월에 받은 3월 급식표가 "내년 3월", 1월에 받은 12월 급식표가 11개월 뒤가 된다.
- 두 호출(1~15일 · 16~31일)의 월이 서로 다르거나 월을 못 읽으면 표를 못 읽은 것이다 — 어느 달인지 모르면 날짜를 하나도 쓸 수 없다. 공지 항목은 산다. 한쪽 월만 읽었으면 그 월이다.
- ②의 안내 통로 — 지금 화면에서 저장되지 않는 줄은 "확인이 필요해요" 항목뿐인데, 거기 넣으면 "확인 안 한 것 1건은 저장하지 않아요" 로 세어지고, 보호자가 확인을 누르면 "확인한 것" 에 들어가 저장되지 않는 줄이 저장되는 것처럼 세어진다. 그래서 넣지 않았다. 웹에 `parsed` 의 안내 칸(예: `notices: string[]`)과 그것을 그릴 자리가 필요하다.
- **한계** — 표의 요일로 검산하지 않는다. 표 읽기 출력에는 `day`(숫자)만 있고 요일이 없다(프롬프트 · 응답 스키마를 바꾸지 않고는 얻을 수 없다). 사진에 적힌 연도 자체가 틀린 급식표, 모델이 날짜 칸을 밀어 읽은 표는 막지 못한다.

**메뉴가 아닌 줄은 메뉴로 만들지 않는다.** 열량 · 영양 표기 줄(`총 511 kcal` · `462/17`)은 [`rules/menu_key.is_nutrition_line`](../../apps/api/app/rules/menu_key.py) 이 가르고 `names_from_raw` 가 뺀다. 보수적이다 — 열량 · 영양 낱말 · 단위와 숫자 · 기호를 지우고 글자가 하나도 안 남을 때만이고, 정답셋 두 벌(178 · 156항목)의 메뉴는 하나도 걸리지 않는다. 그 줄뿐인 끼니는 급식이 없는 칸이다(확인 항목도 만들지 않는다). 번호만 읽힌 칸(`2` · `5,6`)은 열량 줄이 아니라 이름을 못 읽은 칸으로 확인을 받는다.

**한 군데가 어긋났다고 표 전체를 버리지 않는다** (결정 ③의 사진판). 걸린 부분만 못 읽은 칸(`unparsed`)으로 돌리고 나머지 급식은 산다.

| 어긋난 것 | 전 | 지금 |
| --- | --- | --- |
| 그 달에 없는 날(2월 30일) | 한 달 표 전체 실패 | 그 날만 원문과 함께 못 읽은 칸 |
| 같은 날 두 번 | 앞 것을 남기고 뒤 것은 날짜만 신고 | 앞 것을 남기고 뒤 것은 원문과 함께 못 읽은 칸 |
| 1~31 밖의 날(0 · 32) | 그 호출(15일치) 전체 실패 | 그 날만 못 읽은 칸 |
| 두 호출 중 한쪽 실패(시간 초과 · 잘림 · 형식 · 기한) | 성공한 쪽까지 버림 | 성공한 쪽은 살고 "16일~30일 급식은 읽지 못했어요" 하나 |
| 한 호출이 정상 종료했지만 그 구간을 대부분 빠뜨림(아래) | 아무 표시 없이 읽은 것만 저장 | 읽은 급식은 그대로 저장 대상이고 "16일~30일 급식 중 일부만 읽었어요" 하나 |
| 한 날에 같은 끼니 두 번 | 같은 항목 id 둘 → 저장 422 | 앞 것을 남기고 뒤 것은 못 읽은 칸 |

**한 구간이 조용히 덜 읽히면 한 줄로 알린다** (11-11 실측 — 뒤 호출이 16일 하나만 내고 정상 종료해 21일치 중 11일치만 저장됐다). 구간(1~15일 · 16~말일)의 읽은 날(메뉴 · 휴일 표시 `note` · 날짜 붙은 못 읽은 칸이 있는 날)이 그 달 달력의 평일(월~금, 공휴일은 따지지 않는다) 수의 절반에 못 미치고, **다른 구간은 평일의 3/4 이상 읽혔을 때만**(한 주치 · 두 주치 식단표에서 뜨지 않게) 못 읽은 칸 하나를 더한다 — 그 구간에서 하나도 못 찾았으면 "…급식은 찾지 못했어요. 사진에 이 날짜가 있는지 확인해 주세요."(보름치 급식표일 수 있다). 호출이 실패한 구간은 겹쳐 내지 않는다. 세기는 [`rules/meal_plan_coverage.py`](../../apps/api/app/rules/meal_plan_coverage.py), 서버 로그는 WARNING 한 줄(run id · 구간 · 읽은 날 수 · 평일 수만). 한 구간에서 며칠만 빠진 것은 잡지 못하고, 휴일을 적지 않은 방학 달 · 보름치 표의 빈 구간에는 알린다.

못 읽은 칸은 이유 앞에 어느 날 어느 끼니인지 붙인다(`11월 9일 오후 간식 — …`, 그 달에 있는 날만). 날짜 칸은 비운다 — 저장하지 않는 칸이다. 표 전체가 실패하는 것은 월을 쓸 수 없을 때, 연도를 정하지 않을 때(위 ③), 두 호출이 모두 실패했을 때뿐이다.

**화면에 나가는 항목은 저장 검증을 반드시 통과한다.** 읽은 항목은 확인 화면으로 가기 직전에 저장과 **같은 스키마**(`PhotoEntry`)로 검사한다(`photo_run._servable`). 규칙을 두 벌 두지 않는다.

- 날짜가 저장 범위(앞뒤 3년) 밖 → 날짜를 비우고 확인 필요. 급식은 읽지 못한 칸으로 돌린다 — 날짜를 비운 급식을 확인하면 commit 이 run 의 날짜(범위 밖)로 저장하기 때문이다.
- 제목이 비면 확인 필요, 길면 자르고 확인 필요(급식은 메뉴 경계에서 자른다 — 반쪽 이름이 저장 키가 되지 않게). 준비물은 빈 것을 조용히 빼고, 길거나 많으면 줄이고 확인 필요.
- 제목에서 저장 키가 하나도 안 나오는 끼니(`(자율배식)` · `(국내산)` 만 있는 칸, 결정 ⑤)는 원문과 함께 읽지 못한 칸으로 돌린다 — 그대로 내보내면 commit 이 "메뉴를 적어 주세요"(422)로 막힌다.
- 그래도 걸리면 "읽지 못한 항목" 으로만 보이고 저장 대상에서 빠진다. 확인한 항목이 한 번에 저장할 수 있는 수(200)를 넘으면 넘는 것은 확인 필요로 돌린다.
- 확인 필요 항목은 보호자가 시트에서 확인하기 전에는 저장 대상이 아니다(웹 `photo-review.tsx` 가 `needs_review` 인 항목을 빼고 보낸다). 걸리면 서버 로그에 WARNING 한 줄 — 항목 id 와 칸 이름만, 원문 · 제목 글자는 남기지 않는다(루트 §2 개인정보).

### ⑤ 급식표 저장 키에 괄호 안 음식 이름을 하나 더 싣는다 (11-11, #908)

`normalize_menu_key` 는 괄호 안을 통째로 지운다. 그래서 `떡(꿀설기)` 의 저장 키(`daycare_meal.menu_keys`)가 `떡` 하나뿐이었고, 급식 알레르기 · 월령 판정(`agents/food/tools/menu.py` 의 `lookup_daycare_menu`)이 "꿀" 을 못 봐서 8개월 아기에게 "차단" 이 아니라 "확인 못 함" 이 나왔다. `빵(우유카스텔라)` 도 우유 알레르기 아이에게 "확인 못 함" 이었다.

- **급식표 저장에서만 키를 더한다.** [`rules/menu_key.meal_menu_keys`](../../apps/api/app/rules/menu_key.py) 가 제목을 괄호 구간 밖 쉼표에서만 메뉴로 나누고(`샐러드(사과, 배)` 는 한 메뉴), 메뉴마다 괄호 밖 키(예전과 같은 `normalize_menu_key(메뉴)`)를 먼저, 이어서 괄호 안을 `,` `/` `·` `&` `+` "또는" 에서 나눈 음식 이름을 키로 싣는다. `떡(꿀설기)` → `떡` · `꿀설기`. 부르는 곳은 `photo_run.meal_row` 한 곳이다.
- **`normalize_menu_key` 는 바꾸지 않는다.** Food Agent 여러 곳이 같은 함수로 급식표 · 보호자 말 · 영양DB 의 키를 맞춘다. 괄호 밖 키가 그대로라 카탈로그 · 영양 계산이 찾던 키도 그대로다. 괄호 없는 제목의 키는 예전과 같다(테스트로 대조) — 다만 겹친 키는 한 번만 싣고, NFKC 를 먼저 하므로 전각 쉼표(`，`)도 메뉴를 나눈다.
- **괄호 안에서 빼는 것은 음식이 아닌 것이 분명한 조각뿐이다** — 원산지만인 것(`국내산` · `국내산/미국산`), 분량(`1/2` · `200ml` · `반공기`), 크기 · 표시 낱말과 정확히 같은 것(`소` · `자율배식` · 조리법을 바꿔 적은 `군` · `구운` 등). 원산지는 "원산지" 낱말과 조각 **끝에** 붙은 아는 원산지 낱말만 떼고 음식 이름은 남긴다 — `땅콩:국내산` → `땅콩`, `쌀:국내산` → `쌀`, `원산지: 새우 수입산` → `새우`. 가운데는 건드리지 않고(`된장국산적`), 모르는 나라(`땅콩세네갈산`)는 떼지 못해 통째로 남는다. 🚨 **애매하면 남긴다.** 남기면 "확인 못 함" 으로 한 번 더 보게 되고, 지우면 알레르기를 놓친다. `꿀` · `잣` 같은 한 글자 음식은 남는다.
- **괄호 구간은 `normalize_menu_key` 가 지우는 구간과 같은 정규식(`_BRACKETS`)으로 정한다.** 그래서 괄호 밖 키에서 지워진 글자는 괄호 안 조각으로 가고, 거른 조각(원산지 · 분량 · 표시 낱말) 말고는 어느 키에도 안 남는 글자가 없다(무작위 제목 테스트로 본다). 안 닫힌 괄호 · 짝 없는 닫는 괄호는 정규식에 안 걸려 예전처럼 괄호 밖 키에 남는다(`빵(우유카스텔라` → `빵우유카스텔라`). 괄호가 어긋나도(보호자가 화면에서 제목을 고칠 수 있다) 예외를 내지 않는다.

**남은 것**

- **영양 분석이 한 번 더 센다.** Food Agent 는 저장된 급식을 읽는다(#961). 영양 합계(`agents/food/nutrition_eval.py` 의 `daily_totals`)는 저장 키 하나를 메뉴 하나로 세므로, `떡` 과 `꿀설기` 가 둘 다 해석되면 같은 떡이 두 번 들어간다(대체 메뉴 `백김치(백깍두기)` 는 둘 중 하나만 나오는데 둘 다 센다). 괄호 안 키가 해석되지 않으면 합계에는 안 들어가지만 메뉴 수에는 들어가 해석률(`MIN_RESOLUTION_RATIO`)이 내려간다. 괄호 안 키를 영양에서 어떻게 셀지는 아직 정하지 않았다.
- **채팅으로 급식을 고치는 길은 아직 괄호 안이 빠진다.** `agents/food/tools/menu.py` 의 `_menu_keys` 는 `normalize_menu_key` 만 써서, 보호자가 채팅으로 `떡(꿀설기)` 를 더하면 키가 `떡` 하나다.
- **채팅으로 급식을 빼는 길도 괄호 안 키를 모른다.** 같은 파일의 갱신은 `menu_keys - removed + added` 라서, 보호자가 "떡 대신 죽" 이라고 하면 `떡` 만 빠지고 `꿀설기` 가 남는다. 아직 정하지 않았다.
- **키를 그대로 이어 보여 주는 화면에서는 괄호 안 이름이 따로 선 메뉴처럼 보인다** — 홈 "오늘" 줄 · 급식 조회 문구에 `떡, 꿀설기` · `백김치, 백깍두기`(대체 메뉴 둘이 다 나온 것처럼 보임). 표시용 이름을 따로 저장하기 전까지의 한계다.

## 3. `MealPlanJSON` — 정본은 [`apps/api/app/providers/meal_plan/schema.py`](../../apps/api/app/providers/meal_plan/schema.py)

급식표 1장 = 한 달치.

```json
{
  "source": "xlsx",
  "year_month": "2026-09",
  "institution_name": null,
  "days": [
    { "day": 1, "meals": [], "note": "휴일" },
    {
      "day": 2,
      "meals": [
        { "meal_type": "snack_am", "items": [ { "name": "달걀채소죽", "raw": "달걀채소죽:①" } ] },
        { "meal_type": "lunch",    "items": [ { "name": "보리밥",     "raw": "보리밥" },
                                              { "name": "애호박국",   "raw": "애호박국:⑤⑥" } ] }
      ]
    }
  ],
  "unparsed": [ { "day": 4, "meal_type": "snack_pm", "raw": "빵(찐", "why": "메뉴 이름이 잘림" } ],
  "notes": null
}
```

| 필드 | 규칙 |
| --- | --- |
| `source` | `image` / `xlsx` / `hwp`. **읽기 코드가 채운다.** 뒤 단계가 검수 필요 여부를 판단하는 근거 |
| `year_month` | `YYYY-MM` 만. 사진은 모델이 낸 값이 아니라 코드가 정한 연월이다(결정 ④) |
| `institution_name` | 선택값. 급식표에 찍혀 있으면 그대로, 없으면 `null` (결정 ①) |
| `days[].day` | 1~31 이고 **그 달에 있는 날**이어야 한다. 같은 날이 두 번 나오면 거절. 날짜 계산은 `date_of(day)`. 사진은 합치기(`merge_outputs`)가 걸리는 날을 먼저 못 읽은 칸으로 돌려서 표 전체가 거절되지 않는다(결정 ④) |
| `meal_type` | `breakfast` / `snack_am` / `lunch` / `snack_pm` / `dinner`. 센터 급식표 실측(오전간식 · 점심 · 오후간식, 석식형은 저녁) |
| `items[].raw` | 원문 그대로. 번호 · 기호 보존. 검수용이고, 번호는 읽지 않는다(결정 ②) |
| `items[].name` | `raw` 에서 번호 · 기호를 뺀 메뉴 이름. 메뉴 카탈로그 · 영양 계산이 쓰는 값 |
| `unparsed[]` | 메뉴 이름을 못 읽은 칸. `why` 필수. 지어내지 않고 여기로. 번호만 흐린 칸은 아니다(결정 ③) |
| `allergen_codes` | **없다.** 결정 ② |

## 4. 읽기 인터페이스 — [`base.py`](../../apps/api/app/providers/meal_plan/base.py)

```python
class MealPlanReader(Protocol):
    source: MealPlanSource
    def read(self, data: bytes, *, mime_type: str) -> MealPlanJSON: ...
```

```
app/providers/meal_plan/
├── schema.py      MealPlanJSON · MealPlanSource · MealType
├── base.py        MealPlanReader
├── image_ocr.py   (4/5 · #67) Gemini OCR — ImageOcrMealPlanReader · 설정 MEAL_OCR_* · 2분할 호출
│                  read_parts(호출별 결과 · 실패한 범위) → 연월은 부르는 쪽이 정해 merge_outputs 에 준다
├── xlsx.py        (3/5 · #63) 센터 엑셀 — XlsxMealPlanReader(sheet=None) · list_menu_sheets()
└── hwp.py         (#63) 센터 한글 — 아직 없다 (라이브러리 미정, §6)
```

**엑셀 읽기의 규칙** (`xlsx.py` 머리 주석에 시트 배치가 있다)

- 시트 하나 = 급식표 하나. 6종 시트 중 어느 것을 읽을지는 호출 쪽이 `sheet` 로 고른다 (기관이 고른 유형). 안 주면 급식표로 보이는 첫 시트.
- `복숭아/치즈:⑪/②` 처럼 이름과 번호가 같은 개수로 갈리면 항목 둘로 나눈다(`복숭아:⑪` · `치즈:②`). 개수가 다르면(`찐고구마/우유:②`) 나누지 않는다 — 어느 번호가 어느 것인지 지어내지 않는다.
- `24:추석연휴` 는 24일 + 메모. 열 머리가 숫자가 아니면(생일식단 · 현장학습식단 견본 열) 날이 아니다.
- 빈 칸 · `0` 은 메뉴 없음. `#REF!` 같은 엑셀 오류값은 `unparsed`.
- 각주(`※알레르기 유발식품 …`)부터는 읽지 않는다.

## 6. 열린 질문

- **`meal_type` 과 Food Agent 의 `MealSlot`.** Agent 쪽은 `snack` 하나인데 급식표는 오전 · 오후 간식이 갈린다. 저장은 다섯으로 두고 조회 때 `snack` 으로 합칠지, Agent 쪽을 나눌지 — 이시하 (2/5 PR 질문).

- **한글 라이브러리.** `pyhwp` 는 AGPL 이다. 채택 여부, 대안(센터에 엑셀 요청 · 다른 변환 경로) — #63 에서 정한다.
- **기관명 · 원본 보관.** `institution_name` 과 원본 이미지를 저장할지, 얼마나 둘지 — 회의안건 0-1 · 0-2.
