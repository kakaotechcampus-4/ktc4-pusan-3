# Idempotency-Key v1

문서 목적: 되돌릴 수 없는 엔드포인트 5개에서 **같은 요청이 두 번 실행되지 않는다**를 계약으로 고정한다. 클라이언트가 무엇을 보장하고, 서버가 무엇을 보장해야 하는지를 나눈다.

기준 브랜치: `refactor/fe-29-idempotency-enforcement`
작성일: 2026-09-11
담당: 고태영 (클라이언트 절반) · **서버 절반은 백엔드 이슈** (김명성)
선행 문서: [`docs/api/api-interface-v1.html`](./api-interface-v1.html) §01 공통 규약 — 그 문서의 "Idempotency-Key" 절을 **대체하지 않고 채운다**

> 이 문서는 [#29](https://github.com/kakaotechcampus-4/ktc4-pusan-3/pull/29) 멘토 리뷰(질문 4)에서 나온 지적을 반영한 것이다.
> 원문 요지 — *"두 장치 모두 도움이 되지만 현재 구성만으로 충분하다고 보기는 어렵다. 특히 **경고와 강제는 구분**하면 좋겠다. 클라이언트에서는 중요한 작업별 함수에 키를 필수 인자로 두고, **서버에서도 누락을 거부하며 중복 실행을 막는 동작을 보장**하는 방향을 권한다."*

## 1. 왜 다시 보는가

이전 구조는 **정규식 목록 + dev 콘솔 경고** 하나였다. 세 군데가 비어 있었다.

**① 경고는 강제가 아니다.** `process.env.NODE_ENV !== "production"` 안에 있어서 운영에서는 실행되지 않았다. 실행되더라도 요청은 그대로 나갔다. 즉 중복 실행을 막는 장치가 "서버가 400 을 주기를 기대하는 것" 하나뿐이었고, **그 서버는 아직 없다.**

**② 목록을 사람이 관리했다.** 새 엔드포인트를 추가하면서 정규식을 추가하지 않으면 아무 일도 일어나지 않는다. 조용히 빠진다.

**③ 목이 키를 보지 않았다.** 특히 `POST /events/{eid}/confirm` 은 같은 이벤트가 다시 오면 **무조건 409** 였다. 그래서 아래 둘이 화면에서 구분되지 않았다.

| 실제로 일어난 일 | 무엇이어야 하나 | 이전 목 |
| --- | --- | --- |
| 확정은 성공했는데 응답을 못 받아 **같은 키로 재시도** | 처음 응답 재생 (성공) | 409 — 실패처럼 보인다 |
| 이미 확정된 일정을 **새 요청으로 또 확정** | `409 already_confirmed` | 409 — 구분 불가 |

부모 입장에서 첫 줄은 "일정이 안 들어갔나?" 이고 둘째 줄은 "이미 들어가 있어요" 다. 같은 화면을 그리면 안 된다.

## 2. 클라이언트가 보장하는 것

세 겹이다. 아래로 갈수록 늦게 잡히고, 위에서 잡히면 아래는 필요 없다.

### 2-1. 타입 — 키가 필수 인자다

`api.post(path, body, { idempotencyKey })` 의 `idempotencyKey` 는 **선택** 인자다. 빠뜨려도 컴파일된다. 그래서 되돌릴 수 없는 5개는 전용 함수로만 부른다.

```ts
// apps/web/src/lib/api/operations.ts
export function confirmEvent(
  eventId: string,
  idempotencyKey: IdempotencyKey,   // ← 선택이 아니다
): Promise<{ event: CalendarEvent; suggestion_status: SuggestionStatus }>;
```

`IdempotencyKey` 는 브랜드 타입이라 아무 문자열이나 넘어가지 않는다. 경로도 `idempotentPath` 표에서만 만든다 — **표를 거치지 않고 이 5개를 부를 방법이 없다.** 리뷰에서 지적된 "새로운 API 를 정규식 목록에 추가하지 않을 가능성" 이 여기서 닫힌다. 표에 줄을 더하지 않으면 경로 자체가 없다.

### 2-2. 런타임 — 요청이 나가지 않는다

```ts
// apps/web/src/lib/api/client.ts — 환경 구분 없음
if (method === "POST" && !idempotencyKey && requiresIdempotencyKey(path)) {
  throw new IdempotencyKeyRequiredError(path);
}
```

정규식은 `idempotentPath` 의 빌더에서 생성한다(`pathPattern`). 목록을 손으로 두 번 쓰지 않는다.

### 2-3. 키 수명 — 재시도는 같은 키

🚨 **여기가 가장 조용히 깨지는 곳이다.** 리뷰 원문: *"키는 같은 사용자 동작의 재시도에서 재사용해야 한다. 재시도마다 새 키를 만들면 중복 방지가 되지 않는다."*

`mutationFn: () => confirmEvent(id, newIdempotencyKey())` 는 타입도 통과하고 린트도 통과하지만 **키를 붙인 의미가 없다.** 그래서 키를 들고 있는 훅을 둔다.

```tsx
const idem = useIdempotencyKey();
const mutation = useMutation({
  mutationFn: () => confirmEvent(eventId, idem.current()),  // 재시도해도 같은 키
  onSuccess: () => { idem.rotate(); },                      // 성공한 뒤에만 다음 키
});
```

`rotate()` 를 실패 경로에서 부르지 않는다. 그게 재시도다.

## 3. 서버가 보장해야 하는 것

**이 절이 백엔드 작업 범위다.** 지금은 목이 대신 지키고 있다 (§6).

### 3-1. 판정 순서

```
① Idempotency-Key 헤더가 있나           없으면 → 400 idempotency_key_required
② 이 키로 저장된 응답이 있나
   ├ 있고 요청 지문이 같다              → 저장된 응답 재생 (핸들러 실행 안 함)
   └ 있고 요청 지문이 다르다            → 422 idempotency_key_reuse
③ 이 키가 처리 중인가                   → 409 idempotency_in_progress
④ 처리한다 → 2xx 면 응답을 저장한다
```

인증·동의 검사보다 **먼저** 한다. 키 없는 요청은 처리 자체를 시작하지 않는다.

### 3-2. 요청 지문 (fingerprint)

`method + 경로 + 요청 본문`. 본문 해시로 저장해도 된다.

🚨 `multipart/form-data`(`/photos`)는 **원문을 그대로 쓸 수 없다.** boundary 가 요청마다 새로 생성돼 같은 파일을 다시 올려도 바이트가 달라진다. 파트 이름 · 파일명 · 크기로 지문을 만든다.

### 3-3. 동시 요청

키를 **처리 시작 전에** 기록하고, 그 기록이 유일성 제약을 위반하면 `409 idempotency_in_progress` 를 준다.

```sql
-- 예시. 테이블 설계는 백엔드 몫이다.
UNIQUE (parent_id, method, path, key)
```

"두 번째 요청을 기다렸다가 같은 응답을 주는" 방식도 성립하지만, 409 를 고른 이유는 구현과 검증이 단순해서다 — 목·서버 양쪽에서 "핸들러가 정확히 한 번 실행됐다"를 그대로 확인할 수 있다.

### 3-4. 무엇을 저장하나 — **2xx 만**

| 응답 | 저장 | 왜 |
| --- | --- | --- |
| 2xx | ✅ | 실제로 처리가 끝났다. 재시도는 이걸 받아야 한다 |
| 403 `consent_required` | ❌ | **저장이 아예 안 된 상태**다. 캐시하면 "동의하고 다시 누른" 흐름이 영원히 같은 403 을 받는다 |
| 409 `already_confirmed` | ❌ | 상태가 바뀌지 않았다. 같은 키로 다시 시도해도 같은 답이다 |
| 422 · 401 | ❌ | 처리되지 않았다 |
| 5xx | ❌ | 🚨 재시도가 **필요한** 경우다. 저장하면 복구 경로가 막힌다 |

부작용: 재사용 거부(③)는 **성공을 한 번 저장한 뒤부터** 걸린다. 실패한 요청의 키를 다른 본문으로 돌려쓰는 것은 막지 않는다 — 그 경우 아직 아무것도 실행되지 않았으므로 중복 실행이 아니다.

### 3-5. 키 스코프 · 보관

- 키는 **보호자 단위**다. 저장 키에 `parent_id` 를 포함한다 — 다른 보호자의 키와 충돌하거나 남의 응답을 재생받는 일이 없어야 한다.
- 보관 **24시간** 제안. draft 만료(NF-07)와 같은 창이라, 만료된 draft 를 확정하려는 재시도가 캐시에 걸려 성공처럼 보이는 상황이 없다.
- 🚨 저장하는 것은 **응답 본문**이다. 로그에는 원문 대신 `memory_id` (CLAUDE.md §2 개인정보). 재생용 저장소도 로그가 아니므로 같은 원칙을 적용할 것 — 보관 기간이 끝나면 지운다.

## 4. 화면이 이 계약에 기대는 것

| 상황 | 서버 응답 | 화면 |
| --- | --- | --- |
| 확정 성공 | 200 | 확정 화면 |
| 응답 못 받고 재시도 | 200 (재생) | 확정 화면 — **에러를 보여주지 않는다** |
| 이미 확정된 일정을 새로 확정 | 409 `already_confirmed` | "이미 등록된 일정이에요" |
| 처리 중 다시 누름 | 409 `idempotency_in_progress` | 진행 상태 유지 · 버튼 잠금 |
| 키 재사용 (다른 본문) | 422 `idempotency_key_reuse` | **버그다.** 화면에 그리지 않는다 — 키 수명 관리가 깨진 것 |
| 동의 없음 | 403 `consent_required` | 동의 화면으로 (deeplink) · 같은 키로 재시도 가능 |

🚨 승인 게이트에 **낙관적 업데이트를 쓰지 않는다** (`apps/web/CLAUDE.md` §3). 재생 응답도 서버가 준 것이므로 규칙은 그대로다.

## 5. 계약서에 신설 제안하는 것

계약서 §01 은 *"헤더가 없으면 400"* 까지만 정하고 **코드명이 없다.** 아래 4개를 v1.1 에 넣을 것을 제안한다.

| 코드 | HTTP | 언제 | 상태 |
| --- | --- | --- | --- |
| `idempotency_key_required` | 400 | 되돌릴 수 없는 POST 인데 헤더가 없다 | 신설 |
| `idempotency_key_reuse` | 422 | 같은 키인데 요청 지문이 다르다 | 신설 |
| `idempotency_in_progress` | 409 | 같은 키가 아직 처리 중이다 | 신설 |
| `already_exists` | 409 | `health_safety` `UNIQUE(child_id, type, label)` 재등록 | 신설 — 계약서 본문에 **"409" 만 있고 코드가 없다** |

넷 다 [`apps/web/src/lib/api/errors.ts`](../../apps/web/src/lib/api/errors.ts) 에 이미 들어가 있다(주석으로 제안임을 표시). **확정 전까지 서버와 다를 수 있는 부분이다.**

## 6. 지금 이게 지켜지는지 확인하는 방법

### 6-1. 목이 서버 절반을 대신한다

[`apps/web/src/mocks/handlers/idempotency.ts`](../../apps/web/src/mocks/handlers/idempotency.ts) 의 `withIdempotency()` 가 §3 의 ①~④ 를 그대로 구현하고, 되돌릴 수 없는 5개 핸들러에 걸려 있다.

### 6-2. 타입 검사로는 안 되는 것

리뷰 원문: *"필드 모양이 맞는 것과 API 의 동작이 계약에 맞는 것은 별개다. 타입만으로는 동의 거부, 중복 처리, 상태 전이, SSE 이벤트 순서까지 확인할 수 없다."*

그래서 **시드의 타입 강제는 그대로 두고**, 동작을 거는 회귀 테스트를 따로 넣었다 (Vitest + `msw/node`, 브라우저 워커와 **같은 핸들러**를 쓴다).

```bash
cd apps/web && pnpm test
```

| 테스트 | 무엇을 건다 |
| --- | --- |
| 키 누락 | `idempotentPath` 표의 **5개 전부** 400 — 표에 줄을 더하고 목을 안 고치면 깨진다 |
| 같은 키 · 같은 요청 | 같은 응답 · 핸들러 1회 |
| 같은 키 · 다른 요청 | 422 |
| 같은 키 · 다른 엔드포인트 | 422 |
| 동시 요청 3건 | 1건 성공 · 2건 409 |
| 재시도 vs 이미 확정 | 같은 키 → 200 재생 / 새 키 → 409 `already_confirmed` (게이트 ㉠·㉡ 둘 다) |
| 동의 거부 | 403 + deeplink · **같은 키로 재시도하면 통과** |
| SSE 순서 | `saved` 가 `promoted` 보다 먼저 · `failed` 는 `raw_text` 를 돌려주고 `saved` 없이 끝난다 |
| 클라이언트 | 키 없이 부르면 **`fetch` 가 호출되지 않는다** |

### 6-3. 백엔드가 붙은 뒤

같은 케이스를 **실서버에도** 걸어야 한다 (리뷰: *"목과 실제 API 양쪽에서 확인"*). 목 테스트는 화면 회귀용으로 남기고, 서버 쪽은 `apps/api/tests/` 에 같은 표를 만든다. 목이 통과한다고 서버가 통과하는 게 아니다.
