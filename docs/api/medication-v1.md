선행: [`medication-tables-v1.md`](../medication/medication-tables-v1.md) (두 표 · §5 API 가 막을 것) · `docs/web/medication-v1.md` (#563 잠정 계약)

## 1. 프론트에 요청하는 변경


|       | 지금 (#563)                                             | 바꿔 주세요                                                                    |
| ----- | ----------------------------------------------------- | ------------------------------------------------------------------------- |
| 코스 경로 | `/children/{cid}/medications` · `…/medications/{sid}` | `/children/{cid}/medication-courses` · `…/medication-courses/{course_id}` |
| 회차 체크 | `PUT …/medication-doses/{did}/check`                  | `PATCH …/medication-doses/{dose_id}` (본문 `{ checked }` 그대로)               |


- **이유** — `medications` 는 "약 목록"으로 읽히지만 실제로는 복약 코스(약 1종의 복용 계획)다. 응답 키 `courses` · 타입 `MedicationCourse` 와도 맞춘다. 체크는 준비물 체크(`PATCH …/event-items/{iid}` + `{ is_prepared }`)와 같은 모양으로 한다.
- **고칠 곳** (#563 브랜치 기준 `git grep`) — GET 은 `home/page.tsx` · `profile/medications/page.tsx` · `profile/page.tsx` **세 곳에 따로** 적혀 있다. POST · PATCH 는 `lib/api/idempotency.ts` 두 줄, 체크는 `components/medication-dose-check.tsx`, 그리고 목 핸들러 · `mocks/contract.test.ts` · `idempotency.test.ts` · `e2e/medication.spec.ts` 의 경로 문자열.
- **바뀌지 않는 것** — 화면 URL(`/child/{id}/profile/medications`), 에러 처리(체크 실패는 코드와 무관하게 토스트), `checkable` 칸.

## 2. 용어

```
아이 (cid) ─ 코스 (course_id) ─ 회차 (dose_id)
```

- **코스** = 약 **1종**의 복용 계획. 예: "아목시실린 5ml, 10/27~10/29, 하루 3번 식후 30분". 약이 3종이면 코스 3건이고, **동봉된 약도 코스 · 회차가 약마다 따로** 생긴다. DB 표 이름은 `medication_schedule` 이고 같은 것이다 (요청 본문의 `schedule` 칸도 코스의 칸을 뜻한다).
- **회차** = 먹일 때마다 1행. 3일 × 하루 3번 = 9행. 체크 칸(`checked_at`)이 곧 복용 기록이다.

## 3. API 4개


| 하는 일          | 요청                                                     | 키     | 성공                         |
| ------------- | ------------------------------------------------------ | ----- | -------------------------- |
| 코스 등록 (게이트 ㉡) | `POST /children/{cid}/medication-courses`              | 필수    | 201 `{ course }`           |
| 코스 수정 (게이트 ㉡) | `PATCH /children/{cid}/medication-courses/{course_id}` | 필수    | 200 `{ course }`           |
| 진행 중 코스 조회    | `GET /children/{cid}/medication-courses`               | 없음    | 200 `{ today, courses[] }` |
| 회차 체크 · 해제    | `PATCH /children/{cid}/medication-doses/{dose_id}`     | 받지 않음 | 200 회차                     |


삭제(중단) API 는 **이번 범위에 없다** (중단은 Agent 가 되묻기 뒤에 처리).

## 4. 요청 · 응답 칸

### 등록 · 수정 요청

수정은 `source` 가 없고, 보호자가 확인한 **최종 상태 전체**를 보낸다. 길이는 글자 수(한글 1자 = 1)다.


| 칸                                | 형식                                                                       | 비고                                                                                          |
| -------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| `schedule.title`                 | 문자열, 필수                                                                  | 1\~200자. 공백만이면 400. **저장은 받은 그대로** (앞뒤 공백을 서버가 제거하지 않음)                                     |
| `schedule.dosage`                | 문자열 또는 `null`                                                            | 200자 이하                                                                                     |
| `schedule.indication_text`       | 문자열 또는 `null`                                                            | 500자 이하                                                                                     |
| `schedule.note`                  | 문자열 또는 `null`                                                            | 1000자 이하                                                                                    |
| `schedule.storage`               | `"room"` | `"fridge"` | `null`                                           |                                                                                             |
| `schedule.med_form`              | `"liquid"` | `"powder"` | `"tablet"` | `"ointment"` | `"drops"` | `null` |                                                                                             |
| `schedule.symptom_codes`         | 문자열 배열                                                                   | 화면이 고치지 않고 초안 값을 그대로 보낸다. 사전에 없는 **새** 코드는 400                                              |
| `schedule.starts_on` · `ends_on` | `YYYY-MM-DD`, 필수                                                         | 끝 &lt; 시작이면 400. **기간은 최대 90일** (끝 − 시작 + 1 ≤ 90). 무기한 없음. 시작일이 과거여도 되지만 지난 날짜의 회차는 만들지 않는다 |
| `doses[]`                        | 1\~24개                                                                   | 하루 시각 패턴(날짜 없음). 서버가 기간의 날마다 펼친다                                                            |
| `doses[].timing_anchor`          | `fixed` | `wake_up` | `breakfast` | `lunch` | `dinner` | `bedtime`       |                                                                                             |
| `doses[].offset_minutes`         | 정수 −120 \~ 180                                                           | `fixed` 면 0                                                                                 |
| `doses[].fixed_time`             | `"HH:MM"` 또는 `null`                                                      | `fixed` 일 때만 값이 있어야 한다                                                                      |
| `source` (등록만)                   | `"utterance"` | `"prescription_ocr"`                                     |                                                                                             |


- 선택 칸(`dosage` · `indication_text` · `note`)의 **빈 문자열은 `null` 로 저장**한다 (알레르기 등록의 "빈 메모는 null 로"와 같다).
- 보내지 않는 칸: `scheduled_time` · `draft_id` · `notice_times` · `missing` · `before` (보내면 400).

### 응답 `course`


| 칸                                                                          | 형식                                                     |
| -------------------------------------------------------------------------- | ------------------------------------------------------ |
| `id`                                                                       | 코스 id                                                  |
| `title` · `dosage`                                                         | 문자열 · 문자열/`null`                                       |
| `starts_on` · `ends_on`                                                    | `YYYY-MM-DD`                                           |
| `notice_times`                                                             | 하루에 울릴 시각 `["08:30","12:30","19:30"]`, 오름차순            |
| `doses[]`                                                                  | **오늘까지**의 회차, (날짜, 시각) 순                               |
| `doses[].id` · `dose_date` · `scheduled_time` · `checked_at` · `checkable` | 회차 id · `YYYY-MM-DD` · `"HH:MM"` · 시각/`null` · boolean |


`note` · `storage` · `med_form` · `indication_text` · `symptom_codes` 와 시각 패턴(`timing_anchor` 등)은 **저장은 하지만 응답에 주지 않는다** (수정 화면은 Agent 초안의 `before` 를 쓴다).

## 5. 성공하면 / 실패하면

### 등록


| 상황                                                                                                                          | 응답                                                                        |
| --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| "하루 세 번 식후" 3일                                                                                                              | **201** `{ course }`, 회차 9행, `course.doses` 는 오늘까지                        |
| 같은 키로 다시                                                                                                                    | 201, 처음 응답 그대로 (행이 늘지 않음)                                                 |
| 키 없음                                                                                                                        | 400 `idempotency_key_required`                                            |
| 입력 오류 (빈 약 이름 · 시작/끝 없음 · 뒤바뀜 · **기간 90일 초과** · `doses` 비어 있음 또는 **24개 초과** · 같은 시각 중복 · 사전에 없는 증상 코드 · 목록 밖 값 · **길이 초과**) | 400 `validation_failed` + `error.detail.fields` (예: `["schedule.title"]`) |
| 동의 없음                                                                                                                       | 403 `consent_required`                                                    |


### 수정


| 상황                           | 응답                                                                           |
| ---------------------------- | ---------------------------------------------------------------------------- |
| 정상                           | **200** `{ course }`                                                         |
| 같은 키로 다시                     | 200, 처음 응답 그대로                                                               |
| 없는 코스 · 남의 아이 코스 · **멈춘 코스** | **404** `not_found`                                                          |
| 체크된 회차가 **새 기간 밖**에 남게 되는 수정 | 400 `validation_failed` (`fields`: `schedule.starts_on`, `schedule.ends_on`) |
| 그 밖의 400 · 403               | 등록과 같음 (길이 · 기간 상한도 같다)                                                      |


수정 때 서버는 **체크된 회차와 이미 지난 회차를 그대로 두고, 미체크이면서 예정 시각이 지금 이후인 회차만** 지우고 다시 만든다. 다시 만든 회차는 `id` 가 바뀌므로 화면은 응답의 `course` 로 갱신한다.

### 조회

`today` 는 서버의 KST 오늘이다 (화면은 오늘을 따로 구하지 않는다).


| 상황                | 응답                                 |
| ----------------- | ---------------------------------- |
| 진행 중 코스가 있다       | 코스마다 `notice_times` 와 **오늘까지**의 회차 |
| 없다                | 200 `{ today, courses: [] }`       |
| 멈춘 · 끝난 · 시작 전 코스 | 싣지 않음 (한계는 8절)                     |
| 동의 없음             | 그래도 200 (조회는 동의를 보지 않음)            |


`checkable` 은 `dose_date ≤ 오늘` 이라 싣는 회차는 모두 `true` 다 (화면이 `false` 도 처리하므로 그대로 두면 된다).

### 체크

본문 `{ "checked": true | false }`. 게이트가 아니고, 같은 상태를 두 번 보내도 결과가 같다.


| 상황                           | 응답                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------- |
| 체크 / 해제                      | **200** `{ id, dose_date, scheduled_time, checked_at, checkable }` (해제는 `checked_at: null`) |
| 이미 체크된 회차에 `true` 를 또        | 200, **처음 체크 시각 유지**                                                                        |
| **내일 이후 날짜의 회차**             | **422** `dose_not_due`                                                                      |
| 없는 회차 · 남의 아이 것 · 멈춘 코스의 회차  | 404 `not_found`                                                                             |
| 동의 없음                        | 403 `consent_required`                                                                      |
| `checked` 가 없거나 boolean 이 아님 | 400 `validation_failed`                                                                     |


### 공통

- 에러 모양은 `{ "error": { "code", "message", "detail" } }`. 내 아이가 아니면 403 `child_access_denied`. 경로 uuid 형식 오류는 422.
- 쓰기 검사 순서: 접근 → 본문 형식 → 키 → 같은 키 재생 → 동의 → 대상 조회 → 내용 검증 → 저장. 앞에서 걸리면 쓰기는 0건이다.
- 건강정보 동의(`child_health`)는 **쓰기에서만** 확인한다.
- 같은 키 · **다른 본문**(422 `idempotency_key_reuse`)과 처리 중(409 `idempotency_in_progress`)은 서버가 **아직 내지 않는다**. 같은 내용 · 다른 키는 막지 않아 코스가 둘 생길 수 있다.

## 8. 확정한 것과 남은 것

### 확정 (4 · 5절에 반영)


|              | 결정                                                                               | 이유                                                                                                                                    |
| ------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 길이 상한        | `title` 200 · `dosage` 200 · `indication_text` 500 · `note` 1000 · 하루 `doses` 24 | 정상 입력이 거절되지 않게 넉넉히. `title` 은 일정 제출과 같고, `note` 는 일기 본문 1000자 선례(#549). `dosage` · `indication_text` · `doses` 값은 선례가 없는 제안값          |
| 기간           | 최대 90일, 과거 시작일 허용(지난 회차는 만들지 않음)                                                 | 코스는 처방 1건에 가깝다. 확인한 범위에서 급성 질환은 5~~10일, 오래 먹는 약도 1~~3개월 단위로 처방한다(9절). 올리는 것은 쉽고 줄이는 것은 저장된 데이터와 부딪혀 어렵다. **일반 약의 처방 일수 상한은 확인하지 못했다** |
| 끝난 · 시작 전 코스 | 이번에는 **진행 중만** 싣는다                                                               | 어떻게 보여 줄지는 프론트 화면 결정이 먼저라 후속. 한계는 아래                                                                                                  |
| 약 이름         | 받은 그대로 저장                                                                        | Agent 가 발화에서 뽑고 서버가 원문과 같은지 검증한 값이고, Agent 의 이름 비교는 공백을 정규화한다                                                                         |
| 선택 칸의 빈 문자열  | `null` 로 저장                                                                      | 알레르기 등록 선례                                                                                                                            |


### 알려진 한계

- **시작 전 코스** — 내일부터 먹는 약을 오늘 등록하면 시작일 전까지 목록에 안 보이고 수정도 못 한다. 보호자가 등록이 안 됐다고 생각해 다시 등록하면 코스가 둘 생긴다 (서버가 같은 내용을 막지 않는다).
- **끝난 코스** — 마지막 날이 지나면 목록에서 사라져서 마지막 회차를 늦게 체크할 수 없다.
- **긴 코스** — 조회가 오늘까지의 회차를 전부 주므로 90일 × 하루 3번이면 한 코스에 270개까지 늘어난다.

### 남은 것 (후속 · 합의)


|                 | 내용                      | 방향                                                     |
| --------------- | ----------------------- | ------------------------------------------------------ |
| 삭제(중단)          | 보호자 화면의 중단 API          | 이번 범위 제외. 게이트 ㉡ 논의(프론트 문서 §6-7)와 함께 후속                 |
| 동봉된 약 묶음        | 한 번에 체크하는 묶음 개념         | 이번엔 약마다 체크. 묶음은 처방전 경로(`source_draft_id`)와 함께 후속       |
| 90일을 넘는 코스      | 장기 복용 약을 한 코스로 등록해야 하는지 | 지금은 처방을 갱신할 때 새 코스로 이어서 등록. 필요하면 상한을 올리고 조회의 날짜 범위를 검토 |
| 끝난 · 시작 전 코스    | 목록에 보여 주는 방식            | **후속 이슈. 의견 요청** (아래 1)                                |
| 체크 · 확정한 보호자 기록 | 누가 체크 · 확정했는지           | **후속. 의견 요청** (아래 2)                                   |


### 의견을 구하는 것

**1. 끝난 · 시작 전 코스를 목록에 어떻게 보여 줄지** (프론트 · PM)

- 시작 전 — 내일부터 먹는 약을 오늘 등록하면 시작일 전까지 목록에 안 보이고 수정도 못 한다. 보호자가 등록이 안 된 줄 알고 다시 등록하면 코스가 둘 생긴다.
- 끝난 — 마지막 날이 지나면 목록에서 사라져서 마지막 회차를 늦게 체크할 수 없다 (병원에 가져갈 복용 기록에 구멍이 난다).
- 지금은 진행 중만 싣는다. 시작 전 · 최근 끝난 코스도 싣는다면 화면이 구분할 표시가 필요하고, 서버의 "진행 중" 판정을 한 곳에 두는 원칙(#579 리뷰)과 부딪히므로 별도 이슈에서 같이 정하고 싶다.
- 묻는 것: (a) 시작 전 · 끝난 코스를 화면에 보여야 하나? (b) 보여야 한다면 어떻게? (구분 표시, 지난 복약 보기 등)

**2. 체크 · 확정한 보호자를 기록할지** (AI · PM)

- `medication_dose` 에는 `checked_at` 만 있고 누가 체크했는지가 없다. 코스의 `created_by` 도 `agent` / `caregiver` 뿐이라 어느 보호자가 확정했는지 모른다. 알레르기 `health_safety` 는 보호자 id 를 남기고 응답에 닉네임을 준다.
- 같은 아이를 여러 보호자가 돌볼 때 필요할 수 있다. 필요하면 컬럼 추가(마이그레이션)와 응답 칸 추가(프론트 타입)가 따른다.
- 묻는 것: 복약 체크와 코스 확정에도 "누가"를 남겨야 하나? 남긴다면 화면에 보여 주나?

## 미검증

- 응답 예시는 구현 전 설계이고, 서버 스키마 이름은 제안이다.
- 요청에는 있고 응답에는 없는 칸(`note` 등)이 웹 contract 대조에서 어떻게 판정되는지는 `compare.ts` 전체를 읽지 않아 모른다.
- 길이 상한 중 `dosage` · `indication_text` · `doses` 값은 선례 없는 제안값이다. 기간 상한 90일은 확인한 범위(9절)에 근거한 제안이고, **일반 약의 처방 일수 상한은 확인하지 못했다.**
- 프론트 쪽 내용은 #563 브랜치(머지 전) 기준이다.
