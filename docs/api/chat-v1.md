# 지난 대화 다시 보기 — 저장 방식 · 날짜 · 조회 (#228)

필드 정의는 Swagger(`/docs` 의 `GET /children/{cid}/chat` · `GET /children/{cid}/calendar/{date}` 의 `chat_count`)가
정본이다. 여기는 Swagger 가 담지 못하는 흐름과 이유만 둔다. 결정 과정은 #228 의 10-06 · 10-15 댓글과 이 문서를 올린 PR 본문(10-16 결정).

앱을 다시 켜도 그날과 지난 날의 대화를 다시 볼 수 있게, run 하나를 대화 한 턴(`chat_turn` 한 행)으로 남긴다.
한 턴은 보호자 입력 하나와 그 run 의 답 전체다.

## 1. 누가 보고 언제 지우나

- **쓴 보호자 본인만 본다.** 일기처럼 개인 기록이다 — 같은 아이와 연결된 다른 보호자에게도 보이지 않는다
  (403 이 아니라 없는 것처럼).
- **지우는 때** — 탈퇴 · 아이 삭제는 FK CASCADE, 연결 끊기는 `unlink_parent` 가 직접 지운다(보호자 행이 남아
  CASCADE 가 움직이지 않는다). 기간 만료 배치는 없다. 기준은 [`safety/retention-v1.md`](../safety/retention-v1.md).
- 🚨 **연결 끊기와 run 끝이 겹치면** 끊은 뒤에 쓴 대화가 끊긴 보호자에게 남는다 — run 은 접수 뒤 최대 60초를
  뒤에서 돈다. 그래서 쓸 때 일기(#427)와 같은 순서로 보호자 → 아이 → 연결 행을 `FOR KEY SHARE` 로 잡고 연결을
  확인한다(`domains/chat/repository.py` 의 `add_turn`). 끊기가 먼저면 쓰지 않고, 쓰기가 먼저면 끊기가 기다렸다가
  같이 지운다.

## 2. 무엇을 어떻게 남기나

러너가 **화면으로 번역하기 전의 서버 이벤트**를 하나씩 받아 모으고(`api/runs/chat_record.py`), 끝 신호를 내고
채널을 닫은 뒤 한 번 쓴다. `Saved` 는 화면에는 관찰 내용으로 나가지만(#471) 여기서는 id 만 담는다.

| 저장 방식 | 이벤트 | 이유 |
| --- | --- | --- |
| **문장 그대로** | `note` · `guidance` · `unavailable` · `partial` · 끝 상태(`done`) · `agent_result`(추천 id 외 전부 — readout 문장 · 되묻기 · 묶음 이유 등) · 일정 초안 내용 | 그 순간 오간 말이라 나중에 바뀌지 않는다 |
| **`{kind, id}` 만** | `saved` 의 관찰 · `agent_result` 의 추천 id | 나중에 바뀐다 — 관찰과 추천은 조회할 때 지금 상태로 채운다(3절) |
| **남기지 않음** | `step` · 되묻기 조각 원문(`PendingReply`) · 05 보관함 맥락 · 로그용 이벤트 | 진행 중에만 의미가 있거나 원문 조각이다. 화면 전용인 `ping`(연결 유지) · `offer` 는 서버 이벤트가 아니라 애초에 오지 않는다 |

- **`done` 으로 끝난 run 만 남긴다.** `failed` 는 저장된 것도 보여 준 결과도 없는 run 이고, 원문은 입력창으로
  돌아가 보호자가 다시 보낸다. 실패한 키는 풀려서 다시 보내면 **새 run** 이 되므로, 실패한 run 까지 남기면 같은
  말풍선이 두 번 생긴다. 저장한 뒤 끊긴 run(`done` 의 `completed: false`)은 저장된 관찰이나 추천이 있으니 남긴다 —
  이 끝 신호는 러너가 직접 붙이기도 해서 이벤트가 아니라 채널에 실제로 나간 마지막 신호에서 읽는다.
- **끝 신호 뒤의 이벤트는 남기지 않는다.** 채널이 버려서 화면에 안 나간 것이다.
- **readout 은 기록 값이 들어 있어도 문장 그대로다.** 알레르기 확인 문구의 알레르기 이름, 성장 추이의 키 ·
  몸무게도 그렇다. 입력 원문과 Memory 의 답(`note`)도 관찰 내용을 담는다 — 보호자가 기록을 지우거나 고쳐도 지난
  대화의 **말풍선은 그날 오간 말 그대로** 둔다. 지난 대화까지 최신으로 맞추지 않는다(10-16).
- **일정 초안은 id 대신 내용을 담는다.** 초안은 DB 에 쓰지 않아서(9/17) id 로 지금 상태를 찾을 곳이 없다.
  지난 대화에서는 "넣기" 없이 읽기 전용으로만 그린다 — 넣은 초안에 넣기가 다시 서지 않는다.
- **대화 기록 때문에 run 이 끊기거나 실패로 보이지 않는다.** 옮기기 · 쓰기가 실패하면 로그만(원문 없이 run_id
  와 예외 종류) 남긴다.
- 저장 모양은 `api/chat_replies.py` 가 정한다. 🚨 저장한 행은 고치지 않으니 칸을 빼거나 뜻을 바꾸지 않는다 —
  늘릴 때는 기본값이 있는 칸으로 늘린다. pipeline 에 이벤트가 새로 생기면
  `apps/api/tests/unit/api/test_chat_record.py` 가 실패해 남길지 정하라고 한다.

## 3. 조회 — 지금 상태로 채우기

- **관찰** — `saved` 의 id 를 지금 상태로 읽어, run 화면의 `saved`(#471 · `apps/web/src/lib/api/sse.ts` 의
  `SavedEvent`)와 같은 `observations` 칸에 같은 변환(`app/api/v1/observation_outs.py`)으로 싣는다. 그 자리에서
  "저장됨" 으로 본 카드가 지난 대화에서도 같다 — **건강 기록도 run 화면처럼 건강 모양으로 싣는다**(기록 탭 ·
  캘린더는 지금처럼 건강을 빼지만, 지난 대화는 그날 화면을 다시 보여 주는 곳이다 · 10-16). 보호자가 지운 기록은
  내용 없이 `deleted` 에 id 만 둔다 — 지운 기록이 지난 대화에서 되살아나지 않는다.
- **추천** — `suggestion_ids` 는 그때 그대로 두고, 지금 상태를 `suggestions`(`{id, status}`)에 더한다(#500 리뷰).
  화면이 `status` 로 "후보 보기" 를 세울지 가른다 — `draft` 는 아직 고를 수 있고, `approved` 는 05 에서 그대로
  보인다. 둘 다 없는 턴에서 누르면 05 가 "이어서 할 수 없어요" 만 내는 막다른 길이 된다. 채택 자체는 여전히 05 추천 받기
  ([`suggestions-v1.md`](suggestions-v1.md))가 그 run 의 추천을 지금 상태로 거른다(`list_run_suggestions`).
  - 🚨 **만료는 상태 칸에 써지지 않는다.** 24시간이 지나도 `status` 는 `draft` 로 남고, 05 도 `expires_at` 으로
    가른다. 그래서 조회가 `expires_at` 이 지난 `draft` 를 `expired` 로 바꿔 내보낸다 — DB 값 그대로 내보내면
    며칠 지난 추천이 고를 수 있는 것처럼 보인다.
  - `suggestion_ids` 의 뜻을 바꾸지 않은 것은 화면이 지난 턴을 run 화면과 같은 리듀서에 흘리기 때문이다(`saved`
    가 `refs` 대신 `observations` 를 싣는 것과 같은 방식). 행을 찾지 못한 id 는 `suggestions` 에서 빠진다.
- **되묻기** — `reply_open` 은 그 턴의 질문 맥락이 서버 메모리(`pending_reply`)에 아직 있는지다(#500 리뷰). 앱을
  다시 켜도 15분 안이고 아직 답하지 않았으면 화면이 답할 자리를 연다. 만료 · 이미 답함 · 서버 재시작을 가르지
  않는다 — 접수 창구의 400 `reply_context_unavailable` 과 같은 이유다(어느 run 이 있는지 드러나지 않게).
  받은 순간의 값이라 그 뒤에 닫힐 수 있고, 그때 답하면 400 이다. 400 은 하루 한도를 깎지 않는다(맥락 확인이
  한도보다 앞).

## 4. 날짜와 커서

- **날짜는 입력을 접수한 순간의 KST 날짜다.** run 이 끝나 행을 쓰는 시각이 아니다. 되묻기에 답한 run 은 **질문한
  날**에 붙는다 — 자정을 넘겨 답해도(#226 과 같은 규칙). 질문 행이 아직 없으면 접수한 날이다 — 질문 행은 질문한 run 이 끝나야 쓰이는데, 되묻기 질문은 run 도중에 나가서
  그 run 이 끝나기 전에 답이 올 수 있다.
  그래서 `reply_to` 는 FK 가 아니다.
- **하루 단위로 준다.** 대화 화면은 날짜 구분선 단위로 그리고, 캘린더 하루 화면이 그 날짜로 연다. `date` 를 빼면
  오늘이다.
- **커서는 둘이다.** 하루 안에서는 최근 턴부터 `limit` 개를 끊어 오래된 순으로 주고, 더 이른 턴은 `next_cursor`
  로 잇는다. 그날을 다 받으면 `prev_date`(대화가 있었던 바로 앞 날)로 전날을 부른다 — 대화 없는 날은 건너뛴다.
  입력 한도(`INPUT_DAILY_LIMIT`, 지금 하루 5회)가 `limit` 보다 작아서 지금은 `next_cursor` 가 거의 null 이지만, 한도가 늘어도 계약이 바뀌지 않게 처음부터 둔다.
- **`next_date` 는 `prev_date` 와 대칭이다**(대화가 있었던 바로 뒤 날 · #500 리뷰). 캘린더에서 지난 날을 바로 열고
  아래로 내리며 다음 날을 붙인다. 오늘부터 그날까지 하루씩 이어 받으면 요청 수가 그 사이 대화한 날 수만큼 늘고,
  입력 한도가 늘면 하루가 여러 장이 돼 더 는다. 다음 날 쪽에는 "그날 안의 더 늦은 턴" 커서가 따로 필요 없다 —
  날짜만 주고 부르면 그날의 가장 늦은 부분부터 오기 때문이다.
- 🚨 **`next_cursor` 는 자기 날짜를 품는다.** 날짜 없는 커서를 자정이 지난 뒤 보내면 새 날에 적용돼 빈 목록과
  `prev_date`=어제가 나가고, 화면이 어제를 처음부터 다시 그려 이미 보이는 턴이 두 번 생긴다. 커서가 오면 그
  날짜로 읽고, `date` 가 함께 와서 다르면 400 이다.
- 캘린더 하루 보기의 `chat_count` 는 그날 **내** 대화 수다(일기처럼 남의 것은 세지 않는다). 달 보기에는 없다.

## 5. 하지 않는 것 · 남은 것

- **되묻기 맥락은 DB 로 옮기지 않는다**(10-06 댓글의 숙제). 지금처럼 서버 메모리에 15분만 둔다 — 조각 원문을
  남기지 않는 것이 이 기능의 완료 기준이고, 처리방침에도 "15분 동안 서버 메모리에만" 이라고 적혀 있다.
- **보호자가 대화를 직접 지우는 기능은 없다.** 요구가 생기면 턴 단위로 더한다.
- **성장 추이(`growth_delta`)를 근거 id 로 다시 그리는 것은 후속이다.** 키 · 몸무게를 고치거나 지우면 지난 대화의
  숫자도 바뀌게 하려면, Agent 쪽에 근거 기록으로 문장을 다시 계산하는 진입점 함수가 있어야 한다. Growth 가 run
  에 붙은 뒤(#446) 건의하고, 그 함수가 생기면 `StoredReadout` 에 근거 칸을 더한다. 그 전까지는 문장 그대로다.
- **웹** — 웹 타입 · 목 서버의 `chat_count`, 대화 run 이 끝난 뒤 그 턴의 날짜(되묻기 답이면 질문한 날) `calendarDay` 캐시 무효화, 위로 올려 전날
  불러오기 · 캘린더 입구 · 앱 재시작 때 다시 그리기는 FE 몫이다(#228 FE 범위).
