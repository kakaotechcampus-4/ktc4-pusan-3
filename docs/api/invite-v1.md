## 2. 왜 링크가 아닌가

**⚠️ 먼저 정정** — "링크는 카카오 OAuth 왕복을 못 넘긴다" 는 **사실이 아니다.** 프론트는 이미 `bind`·`provider`·`consent_code` 를 `sessionStorage` 로 왕복시키고 있어서(`auth-kakao-v1.md` §5-6) 토큰 한 줄 더 넣는 것은 된다. 그 이유로 코드를 고른 게 아니다.

**① 진입 브라우저를 통제할 수 없다.** 카톡으로 보낸 링크는 **인앱 브라우저**에서 열린다. 거기서 카카오 로그인이 카카오톡 앱으로 넘어갔다 돌아오면 같은 탭 세션이라는 보장이 없고, `sessionStorage` 가 날아가면 **초대 토큰만이 아니라 `bind` 까지 잃는다** — 그러면 초대가 아니라 **로그인 자체가 깨진다** (`bind` 가 없으면 1회용 코드를 세션으로 바꿀 수 없다).

**② 앱 딥링크 설정이 필요해진다.** `https://` 링크를 눌러 `apps/mobile` 웹뷰 셸로 들여보내려면 universal link / app link(`apple-app-site-association` · `assetlinks.json` · 도메인 검증)를 세워야 한다. 10주 안에 넣을 물건이 아니다.

**③ 입력 화면 하나를 두 곳에서 쓴다.** 초대를 받는 사람이 신규 가입자라는 보장이 없다 — 이미 쓰고 있는데 아이가 없는 보호자도 있다. 링크였다면 로그인/비로그인 두 갈래를 다 처리해야 한다. 코드는 **로그인을 끝낸 뒤 입력**하므로 왕복에 실어 보낼 상태가 하나도 없다.

> 🔶 **링크는 나중에 코드의 상위 호환으로 붙일 수 있다** — `/i/{code}` 가 코드 입력칸을 프리필하는 편의 기능이 되고, 아래 엔드포인트는 그대로다. 지금 코드로 고정하는 것이 그 길을 막지 않는다.

## 3. 엔드포인트

경로·시간 표기는 [계약서 §01](./api-interface-v1.html)을 따른다. **세 개 모두 `Bearer` 를 요구한다** — 무인증 예외 5개(`auth-kakao-v1.md` §3)를 늘리지 않는다.

### 3-1. `POST /children/{cid}/invites` — 발행 (owner 전용)

**요청 `{}`**

🚨 **`relation` 을 받지 않는다.** 아이와 어떤 사이인지는 **받는 쪽이 자기 입으로 말할 값**이다 — 보내는 사람이 미리 찍으면 잘못 찍었을 때 받는 쪽이 자기 프로필을 고치러 가야 하고, 그 값은 기록마다 "누가 적었나" 로 남는다 (#89 → #96).

```json
// 응답 201
{ "invite_code": "MKGRAND1", "expires_at": "2026-09-23T00:00:00+09:00" }
```

부를 때마다 **새 코드**다. 여러 명을 초대하려면 그만큼 발행한다.

- **owner 만 발행한다.** 아이에 연결되지 않은 보호자는 `403 child_access_denied`, 연결됐지만 owner 가 아닌 보호자는 `403 owner_only` 다. 화면이 이 버튼을 member 에게도 보여 주므로, 왜 안 되는지를 코드로 가른다.
- 코드가 이미 저장된 코드와 우연히 같으면 유니크 위반으로 `500` 이다. 저장되는 것이 없고 다시 누르면 새 코드로 성공한다. 누적 100만 건 근처에서야 의미가 생겨 재시도는 넣지 않았다.

### 3-2. `GET /invites/{code}` — 수락 전 확인

받는 사람이 **어느 아이에 붙는지 보지 못한 채로 연결되는 것**을 막는다. 코드는 카톡으로 오가는 여덟 글자라 잘못 받아 적거나 남에게 갈 코드를 받을 수 있는데, 붙고 나면 되돌리는 길이 "설정에서 연결 끊기" 뿐이고 **그 사이에 아이의 기록과 건강 정보를 다 본다.** 되돌릴 수 없는 것은 아니지만 **보고 나서 되돌릴 수는 없다.**

```json
// 응답 200
{
  "child": { "nickname": "…", "age_display": "만 4세" },
  "invited_by": { "nickname": "…" },
  "expires_at": "2026-09-23T00:00:00+09:00"
}
```

- 🚨 **코드를 소비하지 않는다.** 확인만 하고 그만둔 사람의 코드가 닫히면 1회용이라 다시 받아야 한다. 소비는 §3-3 하나만 한다.
- 🚨 **건강·알레르기를 내리지 않는다.** 아직 `parent_child` 행이 없는 사람이고, 코드만 알면 누구나 부를 수 있는 창구다 — 별명·나이와 초대한 보호자 별명까지다 (NF-04 최소 수집).
- 🚨 **§4 의 시도 제한에 함께 걸린다.** 코드를 소비하지 않고 계정 상태도 보지 않아서 **수락보다 더 좋은 추측 도구**다. 여기만 열려 있으면 제한이 있으나 마나다.
- **확인 순서는 제한 → 아이 보유 → 코드다.** 이미 아이가 있는 보호자는 코드를 보기 전에 `409 child_already_exists` 로 돌려보낸다. 코드가 맞든 틀리든 같은 409 라 코드의 유효 여부를 알려 주지 않고, 그래서 실패로 세지 않는다.
- 🚨 **아이 보유는 `parent_child` 행으로 센다 — 삭제(soft delete)된 아이와의 연결도 포함이다.** 수락의 `parent_id` 유니크 제약과 같은 기준이어야 한다. `deleted_at` 이 찍힌 아이를 건너뛰면 확인은 200 으로 아이를 보여 주고 수락은 매번 409 가 된다.
- 삭제(soft delete)된 아이에 대한 초대는 `404 invite_not_found` 다.

### 3-3. `POST /invites/{code}/accept` — 수락

```json
// 요청 — relation 은 선택. 안 고르면 필드를 빼고 보낸다
{ "relation": "sitter" }
```

```json
// 응답 200
{ "child_id": "c1", "nickname": "…", "age_display": "만 4세", "role": "member" }
```

`parent_child` 행 생성 + `invite.used_at` · `used_by` 기록. 🚨 **승인 대기 상태가 없다** — 수락하면 바로 연결된다 (계약서 §04 `GET /me`).

화면이 수락 뒤 그 아이 홈으로 가야 해서 응답에 `child_id` 를 싣는다.

- 🚨 **코드는 조건부 `UPDATE` 한 번으로 소비한다** — `UPDATE invite SET used_at = now(), used_by = … WHERE code_hash = … AND used_at IS NULL AND expires_at > now() RETURNING …`. 만료 · 사용 여부를 **수락 시점에 다시** 보고, 같은 코드로 동시에 와도 한쪽만 행을 받는다. 0행이면 다시 읽어 `404` · `409 invite_used` · `410` 을 가른다.
- 🚨 **`parent_child` 생성과 코드 소비는 한 트랜잭션이다.** `parent_id` 유니크 위반이면(확인과 연결 사이에 이 보호자에게 아이가 생긴 경우) 롤백하고 `409 child_already_exists` 다. **코드는 소비되지 않고** 다른 보호자가 쓸 수 있다.
- `relation` 을 안 고르면 `other` 로 저장한다 (§7 결정 04).

## 4. 코드 형식과 시도 제한

**Crockford Base32** — `0123456789ABCDEFGHJKMNPQRSTVWXYZ`. 사람이 옮겨 적다 헷갈리는 `I` · `L` · `O` · `U` 가 빠져 있다.

- 화면은 `ABCD-1234` 로 끊어 보여주고, **보낼 때는 정규화한 값**이다. 하이픈이 섞여 나가면 서버에서 없는 코드가 된다.
- 정규화는 대문자화 + 하이픈·공백 제거 + 혼동 문자 **치환**(`O`→`0`, `I`·`L`→`1`). 버리지 않고 옮긴다 — 0 을 O 로 받아 적은 사람에게 틀렸다고 말하지 않는다.
- 서버는 정규화한 값을 **해시로** 저장한다 (`session` · `auth_handoff` 와 같은 원칙 · `auth-kakao-v1.md` §7-4). 정규화한 결과가 8자가 아니면 조회하지 않고 없는 코드다.
- 🚨 **코드는 `secrets` 로 만든다.** `random` 은 예측할 수 있어 40비트를 더 줄인다.
- 클라이언트 쪽 절반은 [`apps/web/src/lib/invite-code.ts`](../../apps/web/src/lib/invite-code.ts) 다.

### 🚨 시도 제한 — 이 선택의 전제다

8자는 **40비트**라 제한이 없으면 긁을 수 있다. 링크(128비트 토큰)에는 없던 요구사항이고, **이게 없으면 코드로 바꾼 것이 그대로 취약점이 된다.**

| 기준 | 키 | 한도 |
| --- | --- | --- |
| 계정 | `parent_id` | 실패 5회 / 1시간 (프론트 목과 같은 값) |
| IP | 클라이언트 IP (IPv6 는 /64) | 실패 30회 / 1시간 |

- 둘 중 하나라도 넘으면 `429 too_many_attempts`. 계정만 세면 계정을 여러 개 만들어 돌 수 있어서 IP 를 함께 본다 ([#150 멘토 답변](https://github.com/kakaotechcampus-4/ktc4-pusan-3/pull/150#issuecomment-5857345738)).
- 🚨 **§3-2 와 §3-3 이 같은 통을 쓴다.** 확인 쪽이 더 좋은 추측 도구라, 따로 세면 막은 것이 아니다.
- **실패로 세는 것은 `invite_not_found` · `invite_used` · `invite_expired`** 다. 만료 · 사용된 코드도 "그 코드가 있었다" 를 알려 준다. `child_already_exists` 와 성공은 세지 않는다. 실패마다 원문 코드 없이 `parent_id` 와 사유만 로그로 남긴다.
- 🚨 **실패를 먼저 잡아 두고, 실패가 아니면 돌려준다.** 끝난 뒤에 세면 한꺼번에 보낸 요청이 전부 검사를 통과한 뒤 DB 를 기다리는 동안 한도를 넘는다. 검사와 기록 사이에 await 가 없다.
- 카운터는 **프로세스 메모리**다 (api 는 `--workers 1` 전제 · #134). 재시작하면 비워진다.

#### IP 를 얻는 법 — 배포에서 중요

- 지금은 `request.client.host` 를 그대로 쓰고 `X-Forwarded-For` 는 믿지 않는다. 헤더를 믿으면 위조로 IP 제한이 풀린다.
- 🚨 **api 를 nginx 뒤로 넣으면** uvicorn 을 `--proxy-headers --forwarded-allow-ips=<nginx 주소>` 로 띄워야 한다. 안 하면 모든 요청이 nginx IP 한 버킷에 몰려 **실패 30회면 전원이 429** 가 되고, 계정 6개로 일부러 그 상태를 만들 수도 있다. `--forwarded-allow-ips="*"` 는 금지 — 위조가 다시 열린다.

## 5. 에러

프론트가 제안한 이름을 그대로 쓴다 (§7 결정 03). `owner_only` 만 서버 구현에서 새로 생겼다.

| 코드 | 상태 | 언제 | 화면이 하는 말 |
| --- | --- | --- | --- |
| `invite_not_found` | 404 | 없는 코드 | 받은 코드를 다시 확인해 주세요 |
| `invite_used` | 409 | 이미 쓴 코드 | 초대한 분에게 새 코드를 받아 주세요 |
| `child_already_exists` | 409 | 이미 아이가 있는 보호자가 수락 | 한 보호자는 아이 한 명만 등록할 수 있어요 |
| `invite_expired` | 410 | 기한 만료 | 초대한 분에게 새 코드를 받아 주세요 |
| `too_many_attempts` | 429 | §4 시도 제한 | 잠시 후에 다시 시도해 주세요 |
| `child_access_denied` | 403 | 연결되지 않은 아이에 코드 발행 (계약서 §01 공통) | — |
| `owner_only` | 403 | 연결된 member 가 코드 발행 (§3-1) | 🔶 화면 문구 · 버튼 노출은 프론트가 정한다 |

🚨 **중복 등록은 §3-2(확인) 에서 먼저 막는다.** 수락에서야 막으면 **연결되지 않을 아이의 별명·나이를 보여준 뒤에** 거절하는 꼴이 된다.

### 남은 질문

- **아이 삭제를 soft delete 로 하면 그 보호자는 아이 재등록도 초대 수락도 못 한다.** 아이 삭제 경로가 둘 있다.
  - `purge_child()` (`domains/consent/retention.py` · #47) — 동의 증빙을 옮기고 child 를 **hard delete** 한다. `parent_child` 는 CASCADE 로 함께 지워져 문제가 없다. 삭제 정책 정본 §9 의 "MVP 는 복구 없는 hard delete" 와 맞는 쪽이다.
  - `archive_child()` (`domains/child/repository.py` · #130) — `child.deleted_at` 만 채우는 soft delete 다. `parent_child` 행이 남아 `parent_id` 유니크 제약에 계속 걸린다.
  - 아이 삭제 API 는 아직 없어 실제로 일어나지 않는다. 그 API 가 어느 경로를 쓸지 정할 때 함께 닫는다.
