## 1. 프로세스 메모리 상태 — Redis 로 갔다가 PostgreSQL 로

**문제** — api 는 `--workers 1` 전제(#134)로 몇몇 상태를 프로세스 메모리에 둡니다. 되묻기 맥락, 05 다시 시도 맥락, 사진 읽은 결과, run 채널(SSE 이벤트 목록), 보호자별 하루 입력 횟수, 초대 코드 실패 횟수입니다. 워커를 늘리면 되묻기 답이 맥락이 없는 다른 워커로 가고, 한도는 워커 수만큼 느슨해집니다. 재배포하면 이 상태가 전부 사라지는 것도 같은 뿌리입니다.

**처음 생각한 것 / 비교**

처음에는 하나씩 Redis 로 옮길 생각이었습니다. idempotency 키부터 Redis 로 옮겼고(#280), run 채널은 "서버 2대 이슈에서 `redis.asyncio` 와 같이" 보기로 미뤘습니다. 나머지를 옮길 차례가 되자 저장소를 다시 비교했습니다(#877). 옮길 대상은 아래와 같습니다.

| 위치 | 들고 있는 것 | 보관 | 워커 2개일 때 생기는 일 |
| --- | --- | --- | --- |
| `runs/pending_reply.py` | 되묻기 맥락 (원문 포함, "사용 중" 표시) | 15분 | 답이 다른 워커로 가면 맥락 없이 처리 |
| `runs/suggestion_retry.py` | 05 다시 시도 맥락 (원문 포함) · 0개 · 닫힘 기록 | 15분 / 24시간 | "이어서 할 수 없다" 로 빠짐 |
| `runs/photo_run.py` | 사진 읽은 결과 (공지 원문 포함) | 30분 | commit 요청이 다른 워커로 가면 결과 없음 |
| `runs/registry.py` | run 채널 — SSE 이벤트 append-only 목록 | 끝난 뒤 5분 | POST 받은 워커 ≠ SSE 연 워커면 화면이 이벤트를 못 받음 |
| `api/quota.py` | 보호자별 하루 입력 횟수 | 하루 | 한도가 워커 수만큼 늘어남 |
| `api/invite_attempts.py` | 초대 코드 실패 횟수 (계정 5 · IP 30 / 1시간) | 1시간 | 대입 공격 제한이 워커 수만큼 느슨해짐 |

이 대상은 "꺼내서 처리하는 작업 큐" 가 아니라 **만료가 있는 공유 보관함 + 카운터 + 이벤트 전달**입니다. 두 저장소를 이렇게 비교했습니다.

| 기준 | Redis | PostgreSQL |
| --- | --- | --- |
| 장애 영향 | 새 장애 지점이 넓어진다. 지금은 Redis 가 죽으면 idempotency 만 503. 옮기면 되묻기 · SSE · 한도까지 같이 멈춘다 | 새 장애 지점이 없다. DB 가 죽으면 어차피 서비스가 멈춘다 |
| 클라이언트 | 지금 `redis-py` 동기 클라이언트 + 차단기(1초 · 10초). `redis.asyncio` 전환이 따라온다 | asyncpg 비동기 세션을 이미 쓴다 |
| 만료 · 원문 삭제 | TTL 로 제때 지워진다 | 읽을 때 `expires_at` 로 거르고, 실제 삭제는 따로 돌린다. WAL · 백업에 남는다 |
| 같은 트랜잭션 | 안 된다 | 된다. 관찰 저장과 맥락 삭제를 한 commit 으로 묶는다 |
| "사용 중" 표시 | `SET NX` · Lua | `UPDATE ... WHERE in_use = false RETURNING` 한 줄 |
| 카운터 | `INCR` + `EXPIRE`, ZSET — 딱 맞는 도구 | upsert 한 줄 · 행 개수 집계. 이 트래픽엔 충분 |
| SSE 이벤트 전달 | Streams(`XADD` / `XREAD`)가 그대로 맞는다 | 이벤트 테이블 + 짧은 주기 읽기 |
| 테스트 | CI 에서 Redis 경로가 안 돈다. fakeredis 나 CI Redis 가 필요하다 | `db_client` fixture 그대로 |

선택지는 A(전부 PostgreSQL) · B(전부 Redis) · C(보관함은 PostgreSQL, 카운터 · SSE 는 Redis) 셋이었습니다.

**흐름**

- **#280 — idempotency 만 먼저 Redis 로.** 재배포하면 키가 사라져 배포 직전 요청의 재시도가 새 요청이 되는 문제였습니다. `REDIS_URL` 이 없으면 dict 로 폴백하게 했습니다. 실패한 run 의 키를 지우려고 역인덱스 `idem-run:{run_id}` 를 하나 더 둡니다.
- 리뷰어가 두 가지를 짚었습니다. 첫째, 본문의 "Redis 모드 6건 통과" 가 바뀐 파일에 없어서 다음에 누가 고쳐도 Redis 쪽이 깨졌는지 알 수 없다는 것입니다. 작성자는 `fakeredis` 를 dev 의존성으로 넣고 `tests/unit/api/test_idempotency_redis.py` 6건을 더했습니다. 둘째, `clear()` 의 `flushdb` 는 Redis DB 전체를 비워서 `.env` 에 `REDIS_URL` 을 넣은 사람이 `make test` 하면 로컬 Redis 가 통째로 비워진다는 것입니다. SCAN + DEL 로 `idem:*` · `idem-run:*` 만 지우게 바꿨습니다.
- 리뷰어는 "재시작 뒤 키는 Redis 에 24시간 남고 run 채널은 사라진다" 도 확인했습니다. 같은 화면에서 다시 시도하면 죽은 run_id 를 받지만, 전에는 새 run 을 만들어 중복 저장될 수 있었으니 이쪽이 더 안전하다고 봤습니다. 고치지 않고 docstring 에 한 줄 남겼습니다.
- run 채널은 이때 옮기지 않았습니다. 작성자 답은 "쓰기(sync publish) · 읽기(async subscribe) · 알림(`asyncio.Event` → Pub/Sub) 세 경로가 동시에 맞아야 해서 key-value 교체가 아니다" 였습니다. 서버 1대인 동안은 메모리에 두기로 했습니다.
- **#877 — 나머지를 옮길 때 다시 비교.** 작성자는 A 를 골랐습니다. 지금 트래픽에선 Redis 의 속도 이점이 드러나지 않고, 비동기 클라이언트와 별도 예외 처리를 더하는 것보다 테이블이 깔끔하다고 봤습니다. 리뷰어(PM)도 동의하며, Rails 8 이 캐시 · 큐 · 실시간 전달 기본값을 Redis 에서 DB 로 바꾼 사례(Solid Cache · Queue · Cable)를 들었습니다.
- 리뷰어가 트레이드오프 표에 세 가지를 더하라고 했습니다.
    - **백업** — `backup.sh` 가 매일 `pg_dump` 로 DB 전체를 올려 30일 남깁니다. 그대로 두면 15분~24시간짜리 원문이 백업에 30일 남습니다. 복원해도 이미 만료라 쓸 데가 없어서 `--exclude-table-data` 로 내용을 뺍니다.
    - **삭제** — `retention-v1.md` 가 탈퇴 · 연결 끊기 · 아이 삭제 때 "지체 없이" 지운다고 약속합니다. 탈퇴 · 아이 삭제는 FK `ON DELETE CASCADE` 로, 연결 끊기는 보호자 · 아이가 둘 다 남아 CASCADE 가 안 걸리므로 직접 `DELETE` 합니다.
    - **run 채널** — `LISTEN/NOTIFY` 는 워커마다 전용 연결이 필요하고 내용이 8,000바이트까지입니다. 짧은 주기로 읽는 방식부터 갑니다.
- CASCADE 를 걸면서 같이 챙길 것도 정했습니다. 지운 아이 앞으로 늦게 온 저장은 FK 오류가 나는데 러너가 조용히 버립니다. 보관함 쓰기는 짧은 트랜잭션으로 따로 끝내 아이 삭제의 `FOR UPDATE` 가 오래 기다리지 않게 합니다.
- **처리방침과 부딪혔습니다.** `chat-v1.md` §5 는 10-06 에 "되묻기 맥락은 DB 로 옮기지 않는다" 로 정했고, 처리방침은 이 맥락을 "서버 메모리에만" 둔다고 적었습니다. PM 이 뒤집기로 했습니다. 10-06 에 다시 볼 조건으로 정했던 "서버 2대 이상 · #228 로 원문이 DB 에 남을 때" 가 둘 다 해당하고, 백업에서도 빼기 때문입니다.
- PM 은 하나를 더 짚었습니다. 본문에 "삭제 시점은 그대로" 와 "실제 삭제는 정리 배치(하루 1회)" 가 같이 있는데, 하루 1회면 처리방침의 "15분 안에 지웁니다" 가 안 맞습니다. 짧은 주기로 `expires_at` 지난 행을 지우는 쪽으로 정했습니다. 리뷰어는 5분 크론을 제안했고, 구현은 api lifespan 의 루프가 1분마다 지웁니다(`api/runs/hold_purge.py`).
- **#899 — 1~4단계 구현.** 단계마다 "테스트 먼저(실패) → 구현(통과)" 두 커밋으로 올렸습니다.

| 단계 | 옮긴 것 | 표 (전부 UNLOGGED · 백업에서 내용 제외) |
| --- | --- | --- |
| 1 | 되묻기 맥락 `pending_reply` | `run_hold` (kind=pending_reply) |
| 2 | 05 다시 시도 `suggestion_retry` · 사진 결과 `photo_run` | `run_hold` (kind 추가) |
| 3 | 하루 입력 한도 `quota` · 초대 시도 제한 `invite_attempts` | `rate_event` |
| 4 | run 채널(SSE) — 메모리 채널은 그대로, 표에 미러 | `run_channel` · `run_event` |

- 1단계 리뷰에서 리뷰어가 머지 전 문제 하나를 찾았습니다. `claim` 이 `in_use=true` 를 커밋한 뒤 `validate_python(payload)` 를 `try` 없이 부릅니다. 질문이 나간 뒤 `PendingMemoryContext` 모양을 바꾼 코드가 배포되면 `ValidationError` 의 `input_value` 에 원문 조각이 담겨 로그로 가고, `in_use=true` 로 남아 그 질문이 15분 막힙니다. 메모리일 때는 배포하면 맥락이 같이 사라져서 없던 길입니다. 작성자는 못 읽으면 예외 종류만 남기고 행을 지운 뒤 `None` 을 돌려주게 했습니다. 05 다시 시도(`RetryTask`) · 사진 run(`PhotoRun`)도 같은 구조라 같이 막았습니다.
- 같은 리뷰의 나머지 셋도 반영했습니다.
    - 정리 코드(`release` · `drop`)가 DB 호출이 되면서 실패할 수 있게 됐고, 그러면 원래 나갈 429 가 500 으로 바뀝니다. 정리 한 걸음을 `tidy` 로 감싸 원래 응답이 그대로 나가게 했습니다.
    - `run_hold` 의 FK 검사가 아이 → 보호자 순으로 `FOR KEY SHARE` 를 잡아, 보호자 → 아이 순으로 잠그는 탈퇴와 교착할 수 있었습니다. 마이그레이션에서 보호자 FK 를 먼저 만들고, `pg_trigger` 로 순서를 보는 테스트를 넣었습니다.
    - `create_input` 설명문 순서를 바뀐 순서(찜하기 → 한도 → 채널 열기 → 키 기억 → 러너)로 고쳤습니다.
- 2~4단계를 이어 올리며 작성자가 자체 리뷰 · 적대 검증으로 찾은 것도 고쳤습니다.
    - 202 를 준 직후 다른 워커에서 SSE 를 열면 404 → 채널 행을 표에 쓴 뒤에 202
    - 미러 쓰기가 한 번 실패하면 다른 워커 화면이 10분 붙잡힘 → 끝 신호 · 닫힘만 따로 다시 씀
    - 사진 저장과 아이 삭제가 겹치면 교착(연결 둘로 3/3 재현, 아이 삭제 500) → 저장이 아이 행을 먼저 잠금
    - 연결을 끊은 뒤 늦게 끝난 run 이 끊긴 보호자 앞으로 원문을 남김(메모리 때부터 있던 틈) → 지금 이어진 보호자 · 아이에게만 보관
    - 초대 수락이 커밋된 뒤 시도 카운터 돌려주기가 실패하면 500 → 돌려주기 실패가 응답을 덮지 않음
- 재리뷰에서 리뷰어가 셋을 더 짚었고 모두 반영했습니다.
    - 못 읽은 행을 `except` 안에서 지우다 DB 오류가 나면, 새 예외의 `__context__` 에 `ValidationError` 가 붙어 원문 조각이 다시 로그로 갑니다. `drop` 도 `tidy` 로 감쌌습니다.
    - 한도 표의 보호자 id 통이 탈퇴 뒤에도 이틀 남습니다. 설명문은 "탈퇴 · 재가입 우회를 막으려고" 였지만 재가입하면 새 id 라 옛 통은 막는 게 없었습니다. 탈퇴 트랜잭션에서 그 보호자의 두 통을 `delete_events_with_prefix` 로 지우고, `retention-v1.md` 에 `rate_event` 줄을 더했습니다.
    - 돌리던 워커가 죽으면 다른 워커에 붙은 화면이 `OPEN_TTL` 10분 동안 "처리 중" 입니다. `stream_remote` 가 열린 지 90초(러너 60초 + 여유)가 지나도 안 닫혔으면 읽기를 끝내게 했습니다.

**결정**

- 전부 PostgreSQL(A)로 옮깁니다. 새 장애 지점과 동기 클라이언트 문제를 늘리지 않는 쪽입니다. idempotency 는 이미 Redis 라 그대로 둡니다.

## 2. 재배포 drain — 단일 컨테이너 + Caddy 대기 vs blue/green

**문제** — 재배포 때 옛 api 컨테이너는 SIGTERM 을 받고 Docker 기본 10초 뒤 SIGKILL 로 끝납니다. run 은 HTTP 요청이 아니라 백그라운드 태스크(`runs/runner.py` `start()`)라 uvicorn 이 기다리지 않고, 최대 60초(`RUN_DEADLINE_SECONDS`)까지 돕니다. 화면이 SSE 로 붙어 있지 않은 run 은 SIGTERM 순간 흔적 없이 사라졌습니다 — failed 도 안 나가고 Idempotency 키도 안 풀렸습니다. 문제가 난 적은 없지만, 옛 서버가 이미 받은 일을 끝까지 처리하고 내려가는 **drain** 을 넣기로 했습니다.

drain 을 넣으면 두 번째 질문이 생깁니다. drain 하는 동안 들어오는 **새 요청**을 어떻게 받을지입니다. api 는 컨테이너 이름(`ktc4-api`)과 edge 고정 IP(`172.30.0.20`, IMDS 방화벽용)가 고정이라 한 번에 하나만 뜹니다. compose `up` 은 옛 것을 멈춘 뒤 새 것을 띄우므로, drain 시간만큼 새 서버가 늦게 뜹니다. drain 자체는 #882 · #897 에서, 새 요청 받기는 #883 · #921 에서 다뤘습니다.

**처음 생각한 것 / 비교**

| | A. 단일 컨테이너 drain + Caddy 대기 | B. blue/green |
| --- | --- | --- |
| 새 요청 | Caddy 가 붙잡고 있다가 새 서버가 뜨면 보낸다 — 최대 drain + 기동 대기 | drain 중에도 새 서버가 바로 받는다 |
| 바꿀 것 | compose · Dockerfile · lifespan · Caddyfile 몇 줄 | api 두 벌, 방화벽 허용 IP 둘, Caddy 업스트림 전환 단계, `deploy.sh` 순서 |
| 메모리 | 지금과 같음 | drain 동안 api(+web) 한 벌 더 — 4GB 에 dev · prod 가 같이 떠 있어 실측 필요 |
| 남는 함정 | 대기 중 화면의 20초 무응답 타이머에 걸릴 수 있다 | drain 중 옛 run 의 SSE 를 다시 연결하면 새 서버로 가서 404 (run 은 프로세스 메모리, #134) |

작성자는 A 로 가되, 실측에서 여유가 충분하면 B 를 다시 보려고 했습니다.

**흐름**

- **메모리 실측(#883).** 추정 대신 커널이 기록한 최고치를 봤습니다. 서버는 cgroup v2 라 컨테이너마다 시작 이후 최고 사용량이 `memory.peak` 에 남습니다. 판정식은 "(지금 모든 컨테이너 peak 합) + (api peak) + (web peak) + OS 여유 ~400MB < 메모리 전체" 입니다. 빌드는 `flock` 으로 `up` 과 겹치지 않아 합에 넣지 않습니다.

| 컨테이너 | peak |
| --- | --- |
| ktc4-api | 366MB |
| ktc4-web | 119MB |
| ktc4-postgres-deploy | 126MB |
| ktc4-caddy | 59MB |
| ktc4-redis-deploy | 11MB |
| ktc4-dev-api | 218MB |
| ktc4-dev-web | 77MB |
| ktc4-dev-postgres-deploy | 157MB |
| ktc4-dev-redis-deploy | 12MB |
| **합** | **1,145MB** |

- `free -m` 은 total 3,832 · used 2,063 · available 1,768 · swap used 745 / 2,047 이었습니다. 판정식은 1,145 + 366 + 119 + 400 = 약 2,030MB < 3,832MB 라, **메모리만 보면 B 도 가능**했습니다.
- 실측에서 걸리는 점도 나왔습니다.
    - `dockerd` RSS 가 약 960MB(전체 25%)입니다. 빌드(BuildKit)가 dockerd 안에서 돌아 배포마다 부푸는 것으로 추정했고, 누수인지는 한 번으로 구분하지 못해 따로 보기로 했습니다.
    - prod api 대부분이 swap 에 있었습니다. 프로세스 RSS 34MB 인데 peak 은 366MB 입니다. 빌드 중 메모리 압박에 밀려난 것으로 보여, 배포 뒤 첫 요청들이 느릴 수 있습니다.
    - dev 재배포 로그를 보니 옛 api 종료(22:42:50) → 새 api 시작(22:43:06)으로, 지금도 **약 16초 api 가 없는 구간**이 있었습니다. 그 사이 요청은 502 입니다.
- 리뷰어(PM)가 판정식의 "OS 여유 400MB" 를 올려 잡아야 한다고 짚었습니다. used 2,063MB 에서 컨테이너 사용량 합(약 440MB)을 빼면 컨테이너 밖이 약 1,600MB(그중 dockerd 960MB)입니다. 이 값으로 다시 계산하면 1,145 + 366 + 119 + 1,600 = 약 3,230MB 라 들어가긴 하지만, 여유가 식보다 얇고 swap 은 이미 745MB 를 쓰고 있었습니다.
- **PM 결정 — A.** drain 동안 새 요청이 1분 남짓 기다리는 것은 괜찮다고 봤습니다. 그만큼 기다리는 건 배포 순간에 run 이 막 시작한 경우뿐입니다. 돌던 run 이 없으면 drain 이 바로 끝나게 해 달라고 했습니다. 그러면 공백은 지금(약 16초)과 같고, 그 16초도 502 대신 조금 늦은 응답이 됩니다. B 는 메모리상 가능해도 방화벽 IP · Caddy 전환 · `deploy.sh` 순서를 같이 고쳐야 해서, 수십 초 대기를 없애는 것에 비해 운영 배포 경로를 건드리는 양이 크다고 봤습니다.
- **화면 20초 타이머는 FE 코드로 확인했습니다.** 표의 A 함정은 Caddy 가 붙잡고 있는 동안에는 해당하지 않았습니다.
    - 20초 타이머는 입력을 보낼 때가 아니라 202 로 `run_id` 를 받고 SSE 를 구독할 때 걸립니다(`use-run-stream.ts` 의 `subscribeRun`). 입력 `POST` 에는 웹 쪽 시간 제한이 없습니다.
    - 그래서 대기 중에는 "시작하고 있어요" 진행 표시가 그대로 돌고 입력창은 잠겨 있습니다(`chat-thread.tsx` 의 `SENDING`, `conversation.ts` 의 `isBusy`). 실패 화면으로 넘어가지 않으니 다시 보내 겹칠 일도 없습니다.
    - 20초 카드가 뜰 수 있는 건 옛 api 가 202 를 준 직후에 종료 신호가 온 경우입니다. 이때 다시 시도는 같은 Idempotency-Key 로 나가고, 키가 Redis 에 있어 api 가 바뀌어도 두 번 저장되지 않습니다.
- **drain 구현(#897).** 종료 순서를 이렇게 잡았습니다.

```
SIGTERM ─ uvicorn: 새 연결 거부 → 열린 요청 · SSE 대기 (상한 70s, --timeout-graceful-shutdown)
        ─ lifespan: 남은 run → 표 미러 → Curator 대기 (상한 30s, main.DRAIN_SECONDS — 넘기면 취소)
        ─ lifespan: LLM 사용량 마지막 flush · 클라이언트 닫기 → 종료
120s    ─ 그래도 안 끝나면 SIGKILL (api stop_grace_period)
```

- uvicorn 상한을 run 마감(60초)보다 긴 70초로 잡은 이유는 실측입니다. 상한에 걸려 끊긴 SSE 는 uvicorn 이 ERROR traceback 을 찍었고, api ERROR 는 Discord 로 갑니다. 짧게 두면 배포마다 알림이 울립니다. 리뷰어도 "진짜 오류 알림이 무뎌지는 쪽이 더 손해" 라며 동의했습니다.
- 상한을 넘긴 run 은 명시적으로 취소합니다. 그냥 두면 uvicorn 이 정리 뒤 SIGTERM 을 다시 일으켜 프로세스와 함께 사라지고, asyncio 취소 처리도 돌지 않았습니다(실측). 취소하고 기다려 러너 `finally`(failed · 키 놓기 · 채널 닫기)를 거치게 했습니다.
- run 과 Curator 를 단계로 나눈 것은 run 이 끝나면서 Curator 를 띄우기 때문입니다. 한 번에 모으면 drain 중에 새로 뜬 Curator 를 놓칩니다. `drain_background()` 는 사용량 writer 를 멈추기 **전에** 불러, run · Curator 의 사용량도 마지막 flush 에 실리게 했습니다.
- PR #899 가 먼저 머지되며 run 채널마다 이벤트를 표에 옮겨 쓰는 미러 태스크(`RunChannel._writer`)가 생겼습니다. 작성자가 "drain 이 run 태스크만 기다리고 미러는 안 기다린다" 를 먼저 질문했고, 리뷰어가 따라가 보니 끝이 더 나빴습니다. 러너는 `channel.close()` 로 끝 신호를 줄 세우기만 하고 표에는 미러가 나중에 씁니다. 안 기다리면 끝 신호가 표에 안 남아, 앱을 내려 뒀던 보호자가 새 api 에서 같은 Idempotency-Key 로 다시 누를 때 표의 빈 `ended_with` 를 보고 옛 run_id 를 재생합니다. 화면은 ping 만 받다가 90초(`STALE_AFTER`) 뒤 "확인하지 못했어요" 로 떨어집니다.
- 그래서 `registry.running_mirrors()` 를 더해 drain 단계를 run → mirror → curator 로 뒀습니다. **닫힌 채널의 미러만** 봅니다. 안 닫힌 채널의 미러는 끝날 일이 없어서, 넣으면 drain 30초를 매번 다 씁니다.
- 리뷰에서 같이 고친 것이 둘 더 있습니다.
    - 취소 정리 5초가 단계마다 붙으면 최악이 70 + 30 + 15 + 5 = 120초로 `stop_grace_period` 와 같아집니다. `deadline + 5` 기준으로 바꿔 drain 전체에서 5초만 쓰게 했습니다.
    - `with suppress(Exception)` 로 drain 실패가 로그 없이 지나가서, 망가진 drain 과 잘 된 drain 이 똑같아 보였습니다. `log.warning("drain 이 %s 로 중간에 멈췄다", ...)` 로 남깁니다(WARNING 이라 Discord 는 안 울립니다).
- `deploy.sh` 의 `up --wait-timeout` 은 240 → 360(기동 240 + 옛 api 유예 120)으로 올렸습니다. 옛 api 를 멈추는 데 최대 120초가 한 `up` 안에 들어가서, 240 이면 swap 을 쓰는 느린 기동(#747 에서 2분 20초)과 겹칠 때 멀쩡한 배포가 롤백될 수 있었습니다. 늘려서 잃는 건 "진짜 실패한 배포를 알아채는 게 그만큼 늦어지는 것" 뿐이라고 봤습니다.
- web 에는 `stop_grace_period` 를 넣지 않았습니다. run 같은 긴 작업을 들고 있지 않아 기본 10초면 충분합니다.
- **새 요청 붙잡기(#921).** `deploy/caddy/Caddyfile` 한 파일입니다. prod · dev 의 web · api `reverse_proxy` 네 곳에 이 블록을 넣었습니다.

```
(wait_upstream) {
	lb_try_duration 150s   # drain 최대 ~110s(#882) + 기동 ~16s + 여유
	request_buffers 1MB    # 없으면 재시도한 POST 가 본문 없이 502
}
```

- Caddy 2.10.0 로컬 실측에서 `request_buffers` 가 왜 필요한지 나왔습니다. Caddy 재시도는 첫 시도에서 POST 본문을 읽어 써 버립니다. 버퍼가 없으면 재시도한 POST 가 `invalid Read on closed Body` 로 502 입니다.

| 상황 | 결과 |
| --- | --- |
| upstream 컨테이너 없음 → 5초 뒤 기동, GET | 200 (6.3s 대기) |
| 같은 상황, 작은 POST + `request_buffers 1MB` | 200, 본문 그대로 |
| 컨테이너는 있고 포트 닫힘(drain 중) → 다시 열림, 작은 POST | 200 |
| `request_buffers` 없이 POST | 502 `invalid Read on closed Body` |
| 버퍼보다 큰 POST(2MB) | 502 (지금과 같음) |
| 상한 안에 안 뜸 | 상한 뒤 502 |

- 재시도는 **연결 자체가 안 된 요청만** 합니다(Caddy 기본). upstream 이 받은 POST 는 다시 보내지 않아 두 번 처리되지 않습니다.
- 작성자가 물은 두 가지에 리뷰어가 답했습니다.
    - **api 가 진짜 죽었을 때도 150초 기다립니다.** Caddy 는 배포 중인지 장애인지 구분하지 못합니다. 리뷰어는 괜찮다고 봤습니다. 장애 감지는 `health-alert.sh` 가 컨테이너에 직접 물어서 늦어지지 않고, 컨테이너가 죽었다가 `restart: unless-stopped` 로 다시 뜨는 흔한 장애에서는 오히려 화면이 502 대신 기다렸다가 성공합니다.
    - **버퍼 1MB.** 버퍼보다 큰 본문은 배포 중 재시도가 안 되고 502 입니다. 큰 본문은 사진(최대 15MB)뿐이고 운영은 사진이 S3 로 바로 올라갑니다. 16MB 로 올리면 배포 중 들어온 요청마다 그만큼 Caddy 메모리를 잡아 4GB 서버에서 더 위험해서 1MB 를 유지했습니다.

**결정**

- A — 컨테이너 하나 + Caddy 대기. B 는 메모리상 가능하지만 api 두 벌 · IMDS 방화벽 · Caddy 전환 · `deploy.sh` 변경이 커서 보류했고, 필요해지면 다시 엽니다.
- 시간 예산은 uvicorn 70초 + lifespan 30초 + 취소 정리 5초 + 마지막 flush 5초 = 110초 < `stop_grace_period` 120초 입니다. 이 합계를 Dockerfile · `main.py` · compose · `deploy-v1.md` 네 곳에 같이 적었습니다.
- Caddy 대기 상한 150초는 이 drain 예산(110초)을 전제로 잡은 값입니다. 150초는 run 이 돌던 중에 배포가 겹친 최악값이고, 평소 배포는 기동 시간(~16초)만큼만 기다립니다.

**결과**

- 실제 api 이미지로 `docker stop` 하면 남은 일이 없을 때 즉시 exit 143 으로 내려갑니다. 기동은 8초입니다.
- dev 리허설(11-11, api 만 교체)에서 두 경우 모두 ERROR · Killed 없이 끝났습니다.
    - 화면을 연 채 run 중 교체 → uvicorn 이 SSE 가 닫힐 때까지 6초 기다린 뒤 종료, 화면에 결과가 끝까지 나옴
    - 탭을 닫고 run 중 교체 → 열린 연결이 없어 바로 lifespan 으로 넘어가 drain 이 run 을 기다린 뒤 7초 만에 종료, 다시 들어갔을 때 결과가 남아 있음
- 그 배포 자체는 기동 → 성공 20초로 `--wait-timeout 360` 에 여유가 컸습니다.

**남은 것**

- `deploy-v1.md` §drain 에 "알려진 문제" 표로 남긴 것입니다. 전부 재배포하는 순간에 일이 돌고 있을 때만 생기고, drain 이 없던 때(10초 뒤 SIGKILL)보다 나빠지는 것은 없습니다.

| 언제 | 무엇이 | 왜 |
| --- | --- | --- |
| 사진을 읽는 중에 배포 | 70s 에서 uvicorn 이 ERROR 를 찍어 Discord 가 한 번 울린다. 옛 api 가 120s SIGKILL 까지 갈 수 있다(Caddy 가 150s 붙잡아 502 는 아니다) | 사진 run 에는 60s 마감이 없다(모델 상한 식단표 300s · 공지 120s). 취소해도 `asyncio.to_thread` 의 스레드는 안 멈춘다 |
| drain 이 run 을 30s 에서 취소할 때, 마침 Memory commit 직후 | 저장은 됐는데 failed 로 닫고 키를 놓는다. 같은 키로 다시 누르면 두 번 저장된다 | `await session.commit()` 과 `memory_committed = True` 사이에서 취소가 걸릴 수 있다 |
| drain 이 run 을 취소할 때 | 관찰은 저장됐어도 지난 대화에 그 입력이 안 남는다 | 대화 기록(`on_end`)이 러너 `finally` 밖이다 |
| 늦은 run 이 하나라도 있을 때 | Curator 는 바로 취소된다. 다음 실행이 `list_unlinked` 로 다시 집어 잃는 건 없다 | run 단계가 30s 를 다 써서 Curator 단계에 남은 시간이 0 이다 |
| 화면이 안 붙은 run 만 있을 때 | run 마감은 60s 인데 30s 에서 끊긴다 | uvicorn 단계를 건너뛰고 lifespan 의 30s 만 남는다 |
| run 이 자기 60s 마감에 걸린 직후 | 되묻기 맥락 저장이 끝나기 전에 내려가면 새 api 에서 이어서 못 한다 | 러너가 shield 로 돌려 둔 저장(`saving`)은 drain 이 모르는 태스크다 |

- `health-alert.sh` 가 배포 잠금을 보지 않아, drain 으로 옛 api 가 길게 내려가는 동안 🔴 → 🟢 알림이 한 쌍 갈 수 있습니다. 거슬리면 따로 이슈로 뺍니다.
- `dockerd` RSS 추세와 prod api 가 swap 에 밀려나는 것은 #883 범위 밖으로 따로 봅니다.
- Caddy 는 prod checkout 의 Caddyfile 을 읽어, dev 에도 main 배포가 성공한 뒤에 반영됩니다.

## 3. 기억 감쇠가 동작하지 않음 — 그리고 드러난 경합 · 교착

**문제** — 기억(`profile_affinity`)의 상태는 "오늘 기준 최근 N일" 로 정해집니다. 14일 안에 관찰된 날 수(O), 21일 안의 wrong 수(W), 마지막 관찰 뒤 21일이 기준입니다. 그런데 상태를 다시 계산하는 `recompute_profile` 은 관찰이 붙거나 고쳐질 때와 Correction 때만 불렸습니다. **새 기록이 없으면 날짜가 지나도 상태가 그대로였습니다.** 확인됨이 14일 창을 벗어나도 후보로 내려가지 않았고, wrong 이 21일 창을 벗어나도 다시 확인됨으로 올라가지 않았습니다. 이것이 감쇠가 동작하지 않은 원인입니다(#636).

**처음 생각한 것 / 비교**

| 고민 | 고른 것 | 버린 것 · 이유 |
| --- | --- | --- |
| 배치 대상 범위 | 지워지지 않은 아이의 archived 가 아닌 기억 전부를 순회 | "막 창을 벗어난 것" 만 고르는 쿼리 3개 + 인덱스. 아이당 기억이 수십 개라 전체 순회로 충분하다고 봤다(`# ponytail:` 주석에 확장 경로) |
| 잠금 위치 | 모든 경로가 지나는 `recompute_profile` 에 행 잠금 | 배치에서만 잠그기. lost update 는 Curator · Correction 사이에서도 일어난다 |
| 기준일 | KST 날짜 | 서버 시계(UTC). cron 이 도는 UTC 20시에는 UTC 날짜가 KST 보다 하루 늦다 |
| 화면이 낡은 상태를 보는 문제 | 배치로 저장값을 맞춘다 | 읽을 때마다 다시 계산. 기억마다 O · W 집계 쿼리가 붙어 목록 API 가 무거워지고, 화면 · Agent · 배치 세 곳이 각자 상태를 계산하게 된다 |

**흐름**

- **하루 한 번 배치를 붙였습니다(#715).** `app/workers/profile_recompute.py` 를 서버 cron 이 KST 05시에 부릅니다. 아이마다 잠그고 아이마다 커밋해서, 한 아이가 실패해도 나머지는 반영됩니다. 로그에는 건수만 남고, 실패는 ERROR 로 Discord 에 갑니다.
- **배치를 붙이며 기존 경합 2건을 재현했습니다.** 배치가 다른 경로와 동시에 같은 기억을 건드리게 되면서 드러났습니다.
    - **lost update** — `recompute_profile` 이 잠그지 않은 값을 읽고 써서, 동시에 들어온 Correction 의 strength 감소를 덮어썼습니다(재현에서 0.46 → 0.495). 행 잠금(`with_for_update`)을 걸고 `populate_existing` 으로 DB 값을 다시 읽게 고쳤습니다.
    - **교착** — Memory 의 관찰 수정 · 삭제와 Curator 가 기억 둘을 반대 순서로 잠그면 `DeadlockDetected` 가 났습니다. Memory 수정 · 삭제가 맨 앞에서 Curator 와 같은 아이 잠금(`lock_child_memory`)을 잡게 했습니다. 새 기록 저장은 잡지 않습니다. Curator 의 아이 잠금도 `lock_child_memory` 한 곳으로 모았습니다(동작 변화 없음).
- 작성자는 리뷰에서 두 가지를 물었습니다.
- **질문 1 — 관찰을 고치거나 지우는 run 이 직전 입력의 Curator 를 기다리는 지연.** Curator 는 아이 잠금을 잡은 **뒤에** 임베딩과 동일성 판정 LLM 을 부릅니다. 그래서 Memory 가 Curator 를 기다린 만큼 20초 예산(`agents/pipeline.py` `RUN_DEADLINE_S`)에서 도메인 Agent 몫이 줄고, 혼합형 입력에서 `partial(timeout_20s)` 가 날 가능성이 커집니다. 기록만 하는 입력은 영향이 없습니다. 잠정 결론은 "교착으로 run 이 죽는 것보다 낫다" 였지만, 실제 Curator 소요 시간은 재지 않았습니다.
- 리뷰어(Agent 담당)는 잴 수단부터 없다고 짚었습니다. 임베딩 · judge 호출별 `latency_ms` 만 있고 `child_id` 가 없어 실행 단위로 묶이지 않습니다. 잠금을 쥔 시간 · 기다린 시간을 상시 로그로 남기자고 제안했고, 작성자가 이 PR 에 넣었습니다. 원문 없이 `child_id` 와 밀리초만 남깁니다.

```
curator 아이 잠금 child_id=<id> wait_ms=<ms> held_ms=<ms>   ← 커밋 · 롤백까지 쥔 시간
Memory 아이 잠금 child_id=<id> wait_ms=<ms>               ← 관찰 수정 · 삭제가 기다린 시간
```

- 같은 run 의 두 번째 수정부터는 이미 잠금을 쥐고 있어 `wait_ms=0` 으로 찍힙니다. 그래서 0 이 아닌 줄만 보면 20초 예산에서 빠진 몫이 됩니다. 이 로그가 실제로 찍히는지 테스트(`test_trigger_curator_background.py` · `test_profile_recompute_concurrency.py`)로 고정했고, 리뷰어는 타이밍에 기대는 테스트라 여러 차례 반복해 흔들리지 않는 것과 로그를 빼면 실패하는 것을 확인했습니다.
- 같은 리뷰어가 하나를 더 물었습니다. 화면 API 는 저장된 state 를 그대로 내보내서(`GET /children/{cid}/affinities`), crontab 이 등록되지 않으면 오랜만에 들어온 사용자에게 강등됐어야 할 기억이 확정으로 남습니다. 작성자는 사실임을 확인했습니다. 그래도 읽을 때 다시 계산하지 않고 배치를 유지하되, "cron 을 사람이 손으로 등록하는 것" 이 진짜 위험이라 보고 배포 때 cron 줄을 자동 등록하는 일을 #718 로 뺐습니다.
- **질문 2 — 기록 정정과 run 사이의 교착을 재시도 없이 남겨도 되는가.** 작성자가 재현한 조건은 이렇습니다. 한 run 이 같은 기억 A 에 묶인 관찰 X, Y 를 차례로 고치는 사이, 다른 보호자가 Y 를 "잘못된 기록" 으로 정정할 때입니다.
    - run: 아이 잠금 → 관찰 X → 기억 A → (관찰 Y 대기)
    - 정정: 관찰 Y → (기억 A 대기)
- 작성자 재현에서는 정정 쪽이 끊겼습니다. 정정도 아이 잠금을 잡으면 막히지만, 그러면 정정이 run 전체(수 초~수십 초)를 기다리게 됩니다. 그래서 잠정 결론은 "조건이 매우 좁으니 그대로 두고, 끊긴 요청은 다시 누르면 된다" 였습니다. 기억 정정은 기억 행 하나만 잠가 교착이 생길 수 없다는 것도 같은 방식으로 확인했습니다.
- **리뷰어(eval 담당)가 이 판단을 반박했습니다.** 재시도를 안 넣는 데는 동의하지만, "다시 누르면 된다" 는 정정 쪽이 끊길 때만 맞다는 것입니다. 두 순서를 각각 만들어 5번씩 돌렸고 5번 모두 같은 결과였습니다. run 은 `DbMemoryStore.delete_observation` 을, 정정은 라우터와 같은 순서(`find_observation(for_update=True)` → `handle_observation_correction`)를 썼습니다.

| 순서 | 끊긴 쪽 |
| --- | --- |
| 정정이 Y 를 잡고 A 를 먼저 기다린 뒤 run 이 Y 를 기다림 | 정정 (작성자가 재현한 경우) |
| run 이 Y 를 먼저 기다린 뒤 정정이 A 를 기다림 | **run** |

- Postgres 는 먼저 기다리기 시작해 `deadlock_timeout`(1초)이 먼저 지난 쪽이 교착을 찾고 자기를 끊습니다. 그래서 둘 다 일어납니다.
- run 이 끊기면 피해가 다릅니다. `update_observation` · `delete_observation` 의 DB 오류는 Memory 도구에서 잡히지 않고 올라가고, 기록 단계 전체가 한 트랜잭션이라 **같은 입력으로 새로 만든 관찰까지 함께 롤백**됩니다. 보호자에게는 "말한 게 저장이 안 됐다" 로 보입니다. 정정이 끊기는 쪽은 500 "잠시 후 다시 시도해 주세요" 로 끝나니 괜찮습니다.
- 리뷰어는 기다리는 시간을 늘리지 않고 고치는 방법도 냈습니다. 교착의 원인은 run 이 관찰 X 를 고친 **바로 뒤에** `_refresh_profile` 로 기억 A 를 잠가 "관찰 → 기억 → 관찰" 순서가 섞이는 것입니다. Curator 는 이미 관찰을 다 고친 뒤 `recompute_after_linking` 으로 기억을 마지막에 몰아 계산해서 정정과 이 교착이 없습니다. run 도 바뀐 `affinity_id` 만 모아 두고 러너의 `commit()` 직전에 id 순으로 refresh 하면, 잠금 순서가 run 은 "아이 잠금 → X, Y → A", 정정은 "Y → A" 가 되어 순환이 없어집니다. 리뷰어는 run 이 끊겼던 순서를 이 잠금 순서로 흉내 내 둘 다 끝까지 가는 것을 확인했습니다(실제 `DbMemoryStore` 를 고친 것은 아님).
- 작성자는 놓친 것을 인정하고, 이 PR 에 더하지 않고 후속 #717 로 뺐습니다. PR 본문의 "다시 누르면 됩니다" 옆에 run 쪽도 끊길 수 있다는 점을 적었습니다.

**결정**

- 감쇠는 하루 한 번 배치(KST 05시)로 저장값을 맞춥니다. 읽을 때 다시 계산하지 않습니다.
- 모든 재계산 경로가 지나는 `recompute_profile` 에 행 잠금을 겁니다. Memory 의 관찰 수정 · 삭제는 Curator 와 같은 아이 잠금을 먼저 잡습니다.
- 그 대가인 Curator 대기 지연은 감수하고, `held_ms` · `wait_ms` 로그로 배포 후 수치를 봅니다.
- 정정과 run 의 교착은 재시도로 덮지 않고, run 의 기억 재계산을 commit 직전으로 미뤄 순환 자체를 없앱니다(#717). 정정 쪽에 아이 잠금을 거는 것은 정정이 run 전체를 기다리게 돼서 뺐습니다. `_lock_child` 는 그대로 둡니다 — Curator 와 run 이 관찰 둘을 반대로 잠그는 경우는 순서 바꾸기만으로 막히지 않습니다.
- 보호자가 "아니에요" 라고 한 기억도 그 뒤 14일 안에 관찰이 3일 이상 쌓이면 다시 확인됨으로 올라갑니다. W 는 21일 창에서만 세기 때문이고, **의도된 동작**입니다. 새 증거가 계속 쌓이면 오래된 부정보다 증거를 따르고, 관찰이 끊기면 결국 archived 로 갑니다. 정정 때 깎인 strength(×0.93)는 그대로 남아 추천 순위에서 뒤로 밀립니다.

**결과**

- PR #715 는 커밋 5개로 나눴고, 각 커밋에서 ruff 와 전체 테스트가 통과했습니다(마지막 커밋 9,516 passed). 변이 테스트는 24/24 를 잡았습니다.

## 4. 깨진 idempotency 재생 값 — 24시간 막힘을 재시도 한 번으로

**문제** — `recall` 은 Redis 에 기억해 둔 재생 값을 `json.loads` 로 바로 읽었습니다(`app/api/idempotency.py:83`). 값이 깨져 있으면 `JSONDecodeError` 가 그대로 올라가고, 마지막 그물(`app/api/errors.py:199-209`)이 500 `internal_error` 를 냈습니다. 키 TTL 이 24시간(`_TTL_SECONDS`)이고 화면은 같은 키로 다시 보내므로, 그 보호자는 24시간 동안 같은 키 재시도마다 500 을 받습니다. 장애 점검(`eval/faults.md` F7 · IDEM-C, #777)에서 나왔고, 11-10 채점에서도 그대로 유효했습니다.

`recall` 을 부르는 창구는 라우터 7개 16곳입니다 — `children` · `delete_proposals` · `health_safety` · `medications` · `observations` · `photos` · `suggestions`. 온보딩 제출 · 한 줄 입력 · 추천 승인이 모두 들어갑니다. 깨진 값이 생기는 길은 값 형식을 바꾼 배포 · 수동 편집 · 다른 프로그램이 같은 키 이름을 쓴 경우입니다. 흔하지 않지만, 생기면 24시간 막힙니다.

**처음 생각한 것 / 비교**

이슈는 두 안을 놓고 시작했습니다. 어느 쪽이든 깨진 값으로는 처음 요청이 저장까지 끝냈는지 알 수 없습니다.

| | 1. 503 + 키 지우기 | 2. 키 지우고 바로 새 요청으로 |
| --- | --- | --- |
| 이번 요청 | 503 `temporarily_unavailable` (Redis 장애와 같은 답) | 그대로 처리 |
| 다음 재시도 | 새 요청 | — |
| 두 번 저장 | 생길 수 있음 (503 뒤 다시 누르면 새 요청) | 생길 수 있음 |
| 보호자 부담 | 한 번 더 누름 | 없음 |

**흐름**

- 이슈 — 깨진 값을 어떻게 답할지 정하고 `recall` 에 반영하는 것으로 범위를 잡았습니다. 로그에는 지금처럼 키 대신 오류 종류만 남깁니다. 완료 기준은 `tests/eval/faults/test_f7_broken_replay.py` 의 strict `xfail` 마커를 지우고 통과하는 것입니다. strict 라서 마커를 남긴 채 고치면 XPASS 로 실패합니다.
- PR 첫 모습 — 1안(503 + 키 지우기)을 골랐습니다. 깨진 값을 만나면 그 키를 지우고 이번만 503 으로 답합니다. 다음 재시도는 새 요청이 됩니다. 처음 주석은 2안을 뺀 이유를 "바로 새 요청으로 받으면 두 번 저장될 수 있어서" 라고 적었습니다.
- 작성자가 리뷰 포인트로 짚은 것 — 503 뒤 재시도도 새 요청이라 **두 번 저장을 막지는 못합니다.** 목적은 24시간 막힘을 재시도 한 번으로 줄이는 것이고, 답은 Redis 장애와 같게 맞췄습니다.
- 리뷰어 확인 — 503 + 키 지우기에 동의했습니다. 진짜 문제는 깨진 값이 24시간 재시도를 막는 것이고, 보호자는 한 번 더 누르는 것만 늘어납니다. `recall` 밖에 재생 값을 `json.loads` 하는 곳이 없다는 것도 확인했습니다(`remember` 는 `json.dumps` 로 쓰기만 합니다).
- 리뷰어 지적 1, 주석의 이유 — "바로 새 요청이면 두 번 저장될 수 있어서 뺐다" 는 틀린 근거입니다. 503 뒤에 보호자가 다시 눌러도 새 요청이라 두 번 저장될 가능성은 같습니다. 503 은 막는 게 아니라 그 한 번을 보호자의 "다시 시도" 에 맡기는 것입니다. 그대로 두면 다음 사람이 "503 이면 안전하다" 고 오해합니다.
- 리뷰어 지적 2, 로그 순서 — "지웠다" 로그를 지우기 **전에** 찍고 있었습니다. Redis 가 지우기에 실패하면 "지웠다" 와 "못 지웠다" 가 같이 남습니다. 리뷰어는 `try/except RedisError/else` 로 성공했을 때만 찍는 suggestion 을 달고, 로컬에서 `test_idempotency_redis.py` · `test_f7_broken_replay.py` 22 passed · ruff 통과를 확인했습니다.
- 작성자 반영(`c413c0f0`) — 로그 순서가 겹쳐 남는 것을 로컬에서 재현한 뒤 두 지적을 모두 반영했습니다. 주석은 "두 번 저장을 막지는 못한다, 24시간 막힘을 재시도 한 번으로 줄이는 게 목적" 으로 고쳤습니다. 로그는 `재생 값이 깨졌다 — 이번 요청은 503 <메서드> <경로>` 를 먼저, `깨진 재생 값을 지웠다 — 다음 재시도는 새 요청` 은 지우기에 성공했을 때만 남깁니다. 키에 `parent_id` 가 있어서 로그에는 창구(메서드 · 경로)만 싣습니다.
- 작성자가 리뷰를 돌리다 더 찾은 것 1, 모양이 틀린 값 — `123` · `[1, 2]` · `null` 처럼 JSON 으로는 읽히는데 str · dict 가 아닌 값이 그대로 통과했습니다. 이것도 깨진 값으로 같이 처리합니다.
- 작성자가 더 찾은 것 2, 늦은 정리의 경합 — 깨진 값을 지운 뒤 같은 키에 새 run 이 적히면, 옛 run 의 늦은 `forget_run` 이 새 run 의 재생 값을 지웠습니다. 재현한 뒤, `forget_run` 은 키가 아직 그 run 을 가리킬 때만 지우게 했습니다.
- 리뷰어 재확인 — 모양 검사는 정상 재생 값이 늘 run_id(str) 아니면 일정 응답(dict)이라 맞다고 봤습니다. `forget_run` 의 `r.get(idem) == json.dumps(run_id)` 비교는 Redis 가 bytes 로 돌려주면 늘 거짓이 되어 실패한 run 의 키가 안 풀릴 수 있어서 따로 봤습니다. `app/infra/redis.py` 가 `decode_responses=True` 이고 테스트의 fakeredis 도 같은 설정이라, 테스트와 운영이 같은 조건입니다. 문제없다고 보고 승인했습니다.
- 마무리 — `eval/faults.md` · `faults-issues.md` 의 F7 줄을 고친 상태(✅ · #935)로 맞췄습니다(`20c88f99`).

**결정** — 깨진 재생 값(못 읽는 값 · str/dict 가 아닌 값)을 만나면 키를 지우고 이번 요청만 503 `temporarily_unavailable` 로 답합니다. 다음 재시도는 새 요청입니다. 이 결정은 두 번 저장을 막는 장치가 아닙니다. 깨진 값으로는 처음 요청이 저장까지 끝냈는지 알 수 없어서, 어느 안이든 두 번 저장될 수 있습니다. 1안을 고른 이유는 24시간 막힘을 재시도 한 번으로 줄이면서, 답을 Redis 장애 때와 같게 두어 화면이 따로 처리할 것이 없기 때문입니다. 코드 주석도 이 이유를 사실대로 적습니다.

**결과**

**남은 것**

## 5. 복합 발화의 트랜잭션 경계 — "썼다"는 어디까지인가

**문제** — "급식 대신 두유 받았대. 저녁 뭐 먹일까?" 처럼 기록과 질문이 섞인 입력을 한 run 에서 처리합니다. 앞 문장은 저장해야 하고(급식 갱신), 뒤 문장은 추천을 만들어야 합니다. 추천이 실패해도 기록까지 되돌리면 안 되고, DB 연결과 잠금을 모델 호출 동안 오래 쥐어서도 안 됩니다. 그리고 run 이 실패로 끝나면 화면은 원문을 입력창에 돌려주는데, 무언가 저장된 run 을 실패로 끝내면 "저장 없음" 이라는 거짓 안내가 됩니다. 그래서 "이 run 은 썼다" 를 어디까지로 셀지가 결국 핵심이 됐습니다.

**처음 생각한 것 / 비교**

트랜잭션을 어떻게 나눌지부터 골랐습니다. 멘토 리뷰(PR · 커리어 멘토링)에서 받은 두 원칙 — 추천 실패가 기록까지 되돌리면 안 된다, 커넥션을 너무 길게 가져가면 안 된다 — 을 기준으로 봤습니다.

| | run 전체를 한 세션으로 | 단계마다 commit (고른 쪽) |
| --- | --- | --- |
| 추천 실패 때 | 기록까지 같이 롤백 | 기록은 이미 commit 돼 남음 |
| 연결 · 잠금 | Memory 이후 모델 호출 동안에도 쥠 | Memory 단계 동안만 쥐고, 도메인 단계는 포트를 부르는 순간만 짧게 엶 |
| run 의 끝 | 실패면 `failed` | commit 이 있었으면 `failed` 대신 `done` + `partial` |

그다음 "commit 이 있었다" 를 어떻게 셀지 작성자가 두 안을 물었습니다.

| | (a) 쓰기 포트를 감싸 실제 호출만 센다 | (b) 도메인 쓰기는 멱등이니 `committed` 에서 뺀다 |
| --- | --- | --- |
| 급식 수정(덮어쓰기) | 맞음 | 맞음 |
| Health 복약 기록(INSERT) | 맞음 | 두 번 적용하면 두 줄 |
| 급식은 바뀌었는데 실패한 run | `done` | `failed` — 규칙과 어긋남 |
| 구현 부담 | 포트마다 감싸야 함 | 작음 |

**흐름**

- PR 첫 모습 — 순서를 기록 단계 → 쓰는 도메인 task(`food:daycare_meal`) → 읽는 도메인 task 로 고정했습니다. 쓰는 task 도 20초 예산 안에서 셉니다. 러너가 넘긴 `commit` 을 Memory 직후에 한 번 부르고, `Saved` · note · `PendingReply` 는 그 뒤에 냅니다. commit 이 있었던 run 은 `failed` 대신 `done` + `partial` 로 끝납니다(`PipelineResult.committed`). Memory 단계는 트랜잭션 하나로 묶었습니다.
- 처음 구현의 구멍 — 쓰는 task 가 `run_one` 에 들어가기만 해도 commit 이 있었던 것으로 셌습니다. 작성자는 예산이 거의 0일 때만 문제라고 봤습니다.
- 리뷰어 지적 — 예산과 상관없이 생깁니다. Memory 쓰기 없이 급식 갱신만 있는 입력("급식 대신 두유 받았대")에서 Food Agent 가 DB 를 고치기 전에 모델 호출이 시간 초과 · 에러로 끝나도, 표시가 이미 남아 있어 저장 0건인데 `done` + `partial` 로 끝나고 원문이 입력창에 돌아가지 않습니다. 리뷰어는 (a) 를 골랐습니다. (b) 는 지금의 급식 갱신에는 맞지만 INSERT 인 복약 기록에서 깨지고, 급식이 바뀌었는데 `failed` 가 나가는 것도 규칙에 안 맞기 때문입니다. 표시는 쓰기 포트 호출이 성공하고 돌아온 뒤에 붙입니다.
- 리뷰어가 덧붙인 것 — (a) 에서도 `update()` 가 commit 을 보내고 응답을 기다리는 중에 취소되는 경우(매우 낮은 확률)가 남습니다. 중복 방지키나 commit 구간의 `asyncio.shield` 를 Health 구현 때 같이 보자고 했습니다.
- Memory 트랜잭션 길이 — 작성자는 쓰기마다 commit 하면 중간 실패 때 일부만 남는다는 멘토 의견에 따라 하나로 묶었습니다. 리뷰어도 동의했습니다. 전부 롤백하고 `failed` 로 끝내야 다시 보낼 때 안전합니다. 정확한 실측은 아니지만 리뷰어가 몇 번 돌려 본 결과 중간값은 1.7초 가까이였고, Memory 의 모델 턴은 최대 4번 정도(최대 5.8초)였습니다. 정확한 실측 뒤에 다시 보기로 했습니다.
- 무엇을 지금 정할지 — 리뷰어는 셋을 나눴습니다. 알레르기를 task 에서 한 번만 읽는 것은 안전 규칙이라 필터를 DB 에 붙이는 PR 에, 트랜잭션 경계는 러너 구조와 `failed` 의 뜻이 바뀌어 **지금 확정**, 어떤 값을 미리 읽어 넘길지는 리팩터링 때.
- 리뷰어 반례 — (a) 를 반영한 뒤에도 "썼다" 로 세는 범위가 넓었습니다. 질문만 한 run("저녁 뭐 먹일까?")에서 Food 가 계산하면서 영양 구간을 내부 저장하면 표시가 섭니다. 그 뒤 모델 호출이 실패하면 보여 줄 결과가 없는데 `done` 이 되고 원문이 입력창에 돌아가지 않습니다. 결론: "썼다" 는 **보호자 말을 반영한 저장**에서만 셉니다(그때 기준 급식 수정 · 삭제, 나중에 복약 기록). 영양 구간 저장과 메뉴 캐시 저장은 감싸지 않습니다. 쓰기 포트를 더할 때마다 감쌀지 정해야 하니 규칙 문서로 남기자고 했습니다.
- 작성자 반영 — 급식 수정 · 삭제만 감싸고, 영양 구간 · 메뉴 캐시는 감싸지 않게 바꿨습니다. 리뷰어 시나리오를 테스트로 넣었습니다. "덮어쓰기인지" 로 가르면 급식 수정도 덮어쓰기라 빠지므로, 감싸는 기준은 "보호자 말을 반영" 으로 두고 빼는 쪽 조건에 "내부 값 + 덮어써도 같은 값" 을 적었습니다.
- 리뷰어 지적, 문서 모호함 — 문서가 "내부 값이어도 INSERT 면 감싸거나 중복 방지키를 둔다" 였습니다. 감싸는 쪽을 고르면 질문만 한 run 이 실패해도 `done` 이 되는 경우가 다시 생깁니다. "중복 방지키를 두고 감싸지 않는다" 한쪽으로 적자고 했습니다.
- 작성자 반영 — `run_writes.py` docstring 과 `Agent_공통규약.md` §2 를 "감싸지 않고 중복 방지키를 둔다" 로 통일했습니다. 고치면서 공통 문서가 추천 카드를 "저장과 동시에" 내보낸다고 적은 것을 찾아, 저장 commit 이 끝난 뒤에 내보내는 것으로 고쳤습니다. 확인해 보니 질문만 한 run 에서 INSERT 가 나는 도메인 쓰기는 없었습니다. 추천 저장은 도메인 쓰기 포트가 아니라 pipeline 이 결과를 저장하는 것이고, 저장됐으면 결과가 있다는 뜻이라 어차피 `done` 입니다.
- 함께 정리된 것 — 영양 구간은 저장하지 않고 판정할 때마다 원본(`observation_food` · `daycare_meal`)에서 계산하기로 하고 별도 이슈(#205)로 뺐습니다. 메뉴 카탈로그 쓰기는 포트에서 막았습니다 — `MenuCatalogStore.put` 을 덮어쓰기에서 "없을 때만 넣는다"(`ON CONFLICT (menu_key) DO NOTHING`)로 바꿨습니다.
- 마지막 수정 — 일정 초안만 만든 run 은 `committed=False` 로 셉니다(DB 에 실제로 쓴 호출만 셉니다). Memory 가 반복 상한에 걸리면 commit 하지 않고 `failed` 로 끝냅니다 — 일부만 저장된 채 남지 않게 합니다. 되묻기 맥락은 이 트랜잭션에 넣지 않기로 해서 `Commit` 시그니처는 그대로 뒀습니다.

**결정**

- 트랜잭션은 단계마다 나눕니다. Memory 의 쓰기는 하나로 묶어 Memory 가 끝나면 commit 하고, 도메인 쓰기는 포트 호출 하나가 짧은 트랜잭션 하나로 바로 commit 됩니다.
- commit 된 쓰기가 있는 run 은 `failed` 가 아니라 `done`(+ `partial`) 으로 끝납니다.
- "썼다" 는 **보호자 말을 반영한 쓰기**가 성공하고 돌아온 뒤에만 셉니다. 그 쓰기 포트만 commit 판정 표시(`run_writes`)로 감쌉니다. 이유는 이 쓰기가 끝난 run 을 `failed` 로 끝내면 거짓 안내가 되고, 반대로 내부 값까지 세면 질문만 한 run 이 모델 실패에도 `done` 이 되어 원문이 입력창에 돌아가지 않기 때문입니다.
- 감싸지 않는 쓰기는 다시 보내도 안전해야 합니다. 덮어쓰기면 그대로 두고, 쌓이는 쓰기(INSERT)면 감싸지 않고 중복 방지키를 둡니다. 덮어쓰기인지는 감쌀지를 가르는 기준이 아닙니다.
- 이 규칙은 `docs/agents/shared/Agent_공통규약.md` §2 "쓰는 시점" 과 §7 "commit 뒤 실패" 줄에 고정했습니다. 지금 감싸는 것은 급식 수정 · 삭제와 Health 복약 중단(`record_medication_writes`)이고, 감싸지 않는 것은 메뉴 카탈로그(`MenuCatalogStore.put`) 하나입니다. commit 결과를 모르는 경우(commit 도중 연결이 끊긴 경우)는 표시가 남지 않아 `failed` 이고, 다시 보내도 안전하게 하는 것은 쓰기 쪽 멱등성의 몫입니다.

**결과**

- `uv run pytest tests/unit` 1199 passed. 새 테스트 22개(쓰기 순서 · commit 지점 · commit 뒤 `failed` 금지 · 기억 포트 다리)에, 질문만 한 run 이 내부 저장 뒤 모델 실패하면 `failed` 인 시나리오를 더했습니다.

**남은 것**

## 6. "잘못된 기록"과 "대화 삭제" — 같은 뜻, 다른 결과

**문제** — 기록을 없애는 길이 둘이었고, 두 길의 결과가 달랐습니다. 보호자에게는 둘 다 "이 기록은 없던 것으로" 하는 일입니다. 그런데 기록 탭에서 "잘못된 기록" 으로 고른 것은 목록에 남고, 대화에서 지운 것(#535)은 사라졌습니다. 검색 벡터도 한쪽만 지웠습니다.

| | 잘못된 기록 (`POST /corrections`, `wrong`) | 대화 삭제 (#712 확정 API) |
| --- | --- | --- |
| 상태 | `inactive` | `deleted` |
| 기록 탭 목록 | 남는다 (상태 필터 `inactive`) | 사라진다 |
| 임베딩(검색 벡터) | 남는다 | 지운다 |
| Curator 보류 정리 · 기억 재계산 | 한다 | 한다 |
| 고치기 이력(`correction`) | `wrong` 한 줄 | 남기지 않는다 |
| 건강 관찰 | 받지 않는다 | 받는다 |

그래서 기록 탭의 "잘못된 기록" 버튼을 "기록 삭제" 로 바꾸고, 두 길이 같은 함수로 지우게 하기로 했습니다.

**처음 생각한 것 / 비교**

이미 `inactive` 인 기록을 어떻게 할지 PM 에게 물었습니다.

| | 삭제로 옮기기 (고른 쪽) | 그대로 두기 |
| --- | --- | --- |
| 뜻 | "잘못된 기록" 을 누른 것은 없던 것으로 하려는 것 — 삭제와 같음 | 두 상태가 계속 섞임 |
| 처리방침 제5장 ④ | "화면에 보이지 않고 근거로도 쓰이지 않지만 서버에는 남아 있다" 와 맞음 | — |
| 이후 | 응답 · 상태 필터에서 `inactive` 를 아예 뺄 수 있음 | `inactive` 를 계속 지원 |
| 대가 | 예전 추천 카드가 "사용한 기록 0건" 으로 보일 수 있음 | 추천 카드 "사용한 기록" 에 계속 근거로 보임 |

마이그레이션 뒤 배포 틈에 새로 생길 `inactive` 는 두 안을 놓고 봤습니다.

| | prod 배포 뒤 UPDATE 를 한 번 더 돌리는 revision | 읽는 쪽이 `inactive` 도 지운 것처럼 거름 (고른 쪽) |
| --- | --- | --- |
| 롤백 중에 생긴 행 | 다시 놓침 | 언제 생겨도 막힘 |
| 배포 시점 의존 | prod 배포를 확인하고 revision 을 더 넣어야 함 | 없음 |

**흐름**

- 이슈 작성 — 기억의 하강 계산(W)은 **기억 단위** `wrong` 만 셉니다. 그래서 기록 단위 `wrong` 을 없애도 승격 · 강등은 달라지지 않는다고 적었습니다. 삭제는 고치기가 아니라 새 API(`DELETE /children/{child_id}/observations/{kind}/{observation_id}`)로 둡니다. #712 확정 API 는 AI 제안이 있어야 부를 수 있어서 기록 탭에 맞지 않습니다.
- 구현 전 재현(백엔드 팀원) 1, 기억 계산 — 로컬 DB 에서 같은 관찰을 `wrong`(`inactive`)으로 처리한 것과 삭제(`deleted`)한 것을 비교했습니다. 관찰 3건 / 1건(마지막 관찰 삭제) 둘 다 상태 · 강도 · `last_observed_on` 이 같았습니다. W 는 `PROFILE_AFFINITY` 대상 `wrong` 만 셉니다(`profile/repository.py:196`). 지운 기록 · `inactive` 기록은 Curator 목록(`list_unembedded`)에도 잡히지 않아 되살아나지 않았습니다.
- 재현 2, 지우는 함수가 이미 두 벌 — `observation/repository.py` 의 `delete_observation` 은 상태와 보류 기록(hold)만 정리하고, 임베딩 비우기 · 기억 재계산 · 아이 잠금이 없었습니다. `store/db_store.py` 의 `delete_observation` 은 아이 잠금 → 임베딩 비우기 → hold 정리 → `refresh_profile` 까지 했습니다. 같은 관찰을 지워 보니 repository 쪽은 기억이 `confirmed 0.55` 로 그대로였고, store 쪽은 `candidate 0.495` 로 맞춰졌습니다. repository 쪽은 테스트에서만 불려서 아직 문제는 아니었지만, 합칠 때 store 쪽 동작이 기준이어야 했습니다.
- 재현 3, 잠금 순서 — `/corrections` 의 기록 교정은 행을 `for_update` 로 잠그고 기억을 고치는 순서라 아이 잠금이 없습니다. Curator 와 같은 순서(관찰 → 마지막에 기억)로 겹치면 교착이 없었지만, 기억을 먼저 잠그는 반대 순서를 일부러 만들면 `DeadlockDetectedError` 가 났습니다. 지금은 버그가 아니라 Curator 의 접근 순서에 기대서 안전한 상태입니다. 그래서 새 API 는 store 처럼 아이 잠금을 먼저 잡기로 했습니다. Curator 트리거(`trigger.py`)는 commit 뒤 별도 세션에서 돌아서, 지운 뒤 commit 다음에 띄웁니다.
- 이슈 작성자 확인 — 남은 두 가지를 코드로 확인했습니다. `list_unlinked` 는 `status == ACTIVE` 이면서 임베딩이 있는 것만 읽습니다. `suggestion_evidence` 근거 행은 DB 에 남고, 화면(`evidence_view.py`)이 `deleted` 만 뺍니다. 그래서 지금 "잘못된 기록" 은 추천 근거로 계속 보이고 있었고, 이번 변경으로 오히려 바로잡힙니다. store 의 아이 잠금(#636)이 #712 브랜치에는 없어서 develop 을 합쳤습니다.
- PM 결정(11-06) — 삭제로 옮기기로 정했습니다. Curator 는 `active` 만 읽어서 옮겨도 기억 계산이 바뀌지 않는 것을 코드로도 확인했습니다. 운영 DB 의 "잘못된 기록" 은 비공개 테스트 중에 생긴 것뿐이라 놀랄 분이 거의 없습니다. 예전 추천 카드가 "사용한 기록 0건" 으로 보이는 것은 괜찮다고 봤습니다 — 대화로 지운 기록도 이미 그렇고, 근거 행은 남아 §2 "근거 0행" 기준에 걸리지 않습니다. FE 전환 전까지 새로 생기는 "잘못된 기록" 도 마지막 정리에서 같이 옮겨 달라고 했습니다.
- 진행 순서 — BE → FE → BE 정리 + FE 정리로 나눴습니다. BE 가 먼저 머지돼도 지금 화면의 버튼은 서버를 부르므로, FE 가 넘어갈 때까지 `wrong` 은 그대로 `inactive` 로 둡니다.
- 1단계 BE(#775) — 새 API 를 store 의 `DbMemoryStore.delete_observation` 으로 지웁니다. 순서는 키 재생 확인 → 아이 잠금 → 키 다시 확인 → store 삭제 → `flush_profiles()` → commit → 키 기억 → Curator 띄우기입니다. `Idempotency-Key` 필수, 응답 204, owner · member 모두 지울 수 있고, `deleted` 가 아닌 기록은 상태와 상관없이(`stand_alone` · `inactive` 포함), 관찰 다섯 종류 모두(건강 포함) 받습니다. 기록 탭 삭제는 보호자가 직접 누르는 삭제라 승인 게이트가 아니라 확인 창입니다.
- 1단계에서 바꾼 계획 — 처음에는 store 동작을 `domains` 함수로 옮기려 했습니다. 그런데 #745 이후 기억 재계산은 store 객체에 쌓아 두었다가(`_stale_profiles`) commit 직전 `flush_profiles()` 가 합니다. 독립 함수로 빼면 즉시 재계산이 되어 잠금 순서가 섞입니다(#717). 그래서 지우는 길을 store 하나로 두고, repository 쪽 `delete_observation` 은 없앴습니다. 아이 잠금은 라우터가 store 보다 먼저 잡습니다 — 잠금을 얻은 뒤 키를 다시 봐야 앞 요청을 기다린 같은 키가 재생되기 때문입니다. 같은 잠금(`lock_child_memory`)이라 store 가 다시 잡을 때 기다리지 않습니다. 204 재생 값은 `{"status_code": 204}` 로 적습니다.
- 1단계 리뷰 포인트(작성자) — 같은 키가 동시에 두 번 오면 드물게 뒤의 것이 404 를 받습니다. 아이 잠금은 commit 에서 풀리는데 키는 commit 뒤에 적기 때문입니다. 진짜 세션 둘로 겹쳐 보내 40번 중 10번 재현됐고, #712 확정 API 도 같은 순서(409)입니다. 키를 commit 앞으로 옮기면 commit 이 실패했는데 성공을 재생할 수 있어서 #774 로 넘겼습니다. 화면은 요청 중 버튼을 막아 두면 생기지 않습니다.
- 2단계 FE(#791) — 기록 상세의 버튼이 [이번만 그랬어요] [기록 지우기] 둘이 됩니다. 누르면 같은 자리에 확인 띠가 뜨고, 묶인 기억이 있는 기록에만 "묶인 기억은 다시 계산돼요" 를 붙입니다. 고친 기록에도 지우기가 섭니다. 404 는 실패가 아니라 "이미 지워진 기록이에요" 입니다. 키는 본문이 없어서 기록(`kind/id`)에 묶습니다 — 묶지 않으면 앞 기록의 키로 다음 기록을 지웁니다.
- 3단계 BE(#860) — `/corrections` 의 기록용 `wrong` 은 400 `validation_failed`, 기억의 `wrong` 은 그대로 201 입니다. `set_observation_status` 는 `stand_alone` 만 받아, 서버에서 `inactive` 를 만드는 길이 없어졌습니다. revision `90ac5aae7ad1` 이 다섯 표의 `inactive` 를 `deleted` 로 바꾸고 식사 · 교육 · 놀이는 검색 벡터를 비웁니다. 기억은 다시 계산하지 않습니다. status CHECK 의 `inactive` 값과 `ObservationStatus.INACTIVE` 는 남깁니다 — 빼면 CHECK 교체라 expand-only 에 걸립니다. 같은 이유로 API 가 받는 값(`OBSERVATION_VERDICTS_ACCEPTED`)과 CHECK 가 허용하는 값(`OBSERVATION_VERDICTS`)을 나눴습니다. downgrade 는 없습니다 — 옮긴 행과 원래 지운 행을 가를 수 없습니다.
- 3단계 리뷰 — 배포 틈이 문제였습니다. prod 화면에는 아직 "잘못된 기록" 버튼이 있고, `deploy.sh` 는 직전 api · web 이 떠 있는 채로 `alembic upgrade` 를 돌리고 헬스체크가 실패하면 이미지만 되돌립니다. 그 틈이나 롤백 중에 버튼을 누르면 `inactive` 가 새로 생기는데, revision 은 이미 찍혀 다시 돌지 않습니다. 처음에는 repository 의 `_not_deleted` 만 `inactive` 를 걸렀습니다(응답 `status` 에 `inactive` 가 없어 응답 검사에서 500 이 나기 때문 — 지난 대화는 하루치를 한 응답으로 줘서 그날 전체가 500). FE 리뷰어가 짚었습니다 — 그러면 그 행은 보호자가 못 보고 지울 수도 없는데 store 검색(`!= DELETED` 만 거름)에는 걸립니다. PM 리뷰어는 정확히 어디에 걸리는지 바로잡았습니다. 추천 Agent 4개는 `memory_bridge` 의 허용 목록(`active` · `stand_alone`)으로 이미 거르고, 걸리는 곳은 Memory Agent 의 기록 조회 · 수정 도구(`_query` · `_update`)입니다. 보호자가 "아까 그거 3시였어" 라고 고친 것이 안 보이는 행에 들어가 사라진 것처럼 될 수 있습니다.
- 3단계 반영 — 거르는 상태를 `observation/models.py` 의 `GONE_STATUSES`(`deleted` · `inactive`) 하나로 모으고, repository · store(`query_observations` · `get_observation` · `update_observation`) · `evidence_view` 가 같이 씁니다. `evidence_view` 는 리뷰에 없던 곳인데 조건이 같아 같이 맞췄습니다. store 의 `delete_observation` 은 그 행도 받습니다(지우면 `deleted` 가 될 뿐). 배포 직전에 앱을 열어 둔 보호자가 옛 버튼을 누르면 400 을 한 번 보는 것은 데이터가 망가지지 않아 그대로 뒀습니다.
- 3단계 FE(#888) — `Observation.status` 를 `active` · `stand_alone` 둘로 줄이고, 상태 필터에서 "잘못된 기록" 을 뺐습니다. 주소에 `status=inactive` 가 남은 예전 링크는 모르는 값이라 "전체" 로 엽니다. 리뷰어는 탭 · 분류 값도 모르는 값이면 기본값으로 읽고 주소를 지우지 않으니 같은 모양이라 괜찮다고 봤습니다. `VERDICT_LABEL.wrong` 은 기억 고치기 이력이 같은 표를 써서 남겼습니다. 상태 필터가 `status=inactive` 를 보내므로 #860 과 같이 머지했습니다.

**결정**

- "잘못된 기록" 은 기록 지우기와 같은 뜻이라 없앱니다. 기록에 대한 고치기는 `once_only`(이번만 그랬어요) 하나이고, `wrong` 은 기억 고치기에만 남습니다.
- 관찰을 지우는 길은 Memory store 의 `delete_observation` 하나입니다. 기록 탭 · 대화 삭제 · Memory Agent 가 모두 이 함수를 부르고, 모든 경로가 아이 잠금 → 관찰 → 기억 순서입니다. 기억 재계산은 부른 쪽이 commit 직전에 `flush_profiles()` 로 하고, Curator 는 commit 뒤에 띄웁니다.
- 남은 `inactive` 는 `deleted` 로 옮기되, 마이그레이션 뒤에 새로 생길 수 있는 `inactive` 는 읽는 쪽이 `GONE_STATUSES` 로 지운 것처럼 거릅니다. 배포 순서 · 롤백 시점과 상관없이 막히기 때문입니다.

## 7. Memory 가 저장하지 않고 "기록했어요" 라고 답한다

**문제** — 관찰 저장에는 사람 확인이 없습니다. 그래서 Memory 가 tool 을 부르지 않고 "기록했어요" 라고 답하면, 보호자는 저장된 줄 알고 다시 말하지 않습니다. 그 말은 run 이 끝나면서 조용히 사라집니다. 지금까지는 답의 말투를 패턴(`_SAVED_CLAIM`)으로 잡았는데, 패턴에 없는 새 말투가 나오면 그대로 나갔습니다.

**처음 생각한 것 / 비교**

| 안 | 결과 |
| --- | --- |
| 패턴에 말투를 계속 더한다 (#625 · #643) | #643 에서 "남겼 · 남길게 · 남겨 둘게" 를 더해 그 말투는 0회가 됐지만, 그 뒤에도 "기록했지만" 이 샜습니다. 말투는 끝이 없습니다 |
| 다시 쓴 뒤에도 쓰기가 없으면 무조건 고정 문구로 바꾼다 | "먹고 싶다는 바람이라 남기지 않았어요" 같은 정직한 설명까지 지웁니다. 하지 않았습니다 |
| 확인 문구에 "앞의 답이 맞으면 그대로 써도 된다" 를 넣는다 | 거짓 저장 답을 그대로 다시 냈습니다(100번 중 2번). 뺐습니다 |
| 이어받기와 같은 확인 문구("필요한 값이 없으면 그 값을 묻는다") | 맞게 설명한 답을 불필요한 질문으로 바꿨습니다("아이스크림을 실제로 먹었나요?", 수영에 장소 · 양 질문). 처음 run 용 문구를 따로 뒀습니다 |
| **말투가 아니라 실제 쓰기 성공으로 판정한다** | 채택. 리뷰어(Agent 파트)가 #643 리뷰에서 제안했습니다 |

**흐름**

- **#643 에서 확인한 것** — "며칠 전에 수영 했어" 를 400회 돌리니 20회(5%)가 tool 없이 "기록을 남겼어요 / 남길게요" 로 끝났습니다. 당시 패턴은 하나도 잡지 못했습니다. 말투를 더해 막았지만 "적어 뒀어요" 같은 새 말투가 나오면 다시 샌다는 점이 남았습니다.
- **이슈 #667 에서 범위를 정했습니다.** 이어받기 run 은 이미 쓰기 여부로 다시 확인하고(`recording`), 조회 · 수정만 맡은 run 은 보지 않습니다(`_lookup_only`). 말투에 기대는 것은 처음 run 뿐이었습니다.
    - 대상: 처음 run(`continuation is None`)이고 Supervisor 조각에 관찰(`observe`) · 일정(`schedule`)이 있는 run.
    - 조건: 일반 메시지(`kind=message`)로 끝났는데 필요한 종류의 쓰기 성공이 없으면 말투와 상관없이 한 번 다시 확인합니다. 되묻기(`kind=question`)로 끝난 답은 보지 않습니다.
    - 쓰기 성공은 그 run 의 `ToolCallRecord.success=True` 인 호출만 셉니다. 관찰은 `create_observation_*`, 일정은 `create_event` · `create_event_item` 입니다. 일정은 승인 전이라 **초안 생성 성공**을 뜻합니다.
    - 같은 종류 조각이 여럿이어도 그 종류 성공 1건이면 통과합니다. 조각마다 짝짓지 않는 이유는 모델이 조각을 나누거나 합쳐서 판정이 흔들리기 때문입니다.
    - Supervisor 조각이 없는 run(강등 · Memory 단독)은 지금처럼 `_SAVED_CLAIM` 으로 판정합니다.
- **PR #678 처음 구현**
    - 다시 쓰는 차례에는 tool 을 주지 않습니다(`tool_choice="none"`). 확인에 밀려 새로 저장하거나 두 번 저장하는 일을 구조로 막습니다.
    - 확인 문구는 "저장하지 않는 게 맞는 말(아직 하지 않은 계획, 먹고 싶다는 말처럼 실제로 먹지 않은 것, 알림 요청)이면 그 이유를 말하고, 날짜처럼 꼭 필요한 값이 빠졌을 때만 하나 묻는다" 입니다.
    - 알림 요청 일정 조각("…8시에 알려줘")은 대상에서 뺐습니다. 다시 써도 답이 글자까지 같아 호출만 늘었기 때문입니다(10번 모두). 조기 종료용 `_NEEDS_REPLY_CUES`(알림 · 알람)로는 "알려줘" 가 안 걸려서, 일정 조각에만 쓰는 `_REMINDER_REQUEST` 를 따로 뒀습니다.
- **1차 리뷰 — 리뷰어가 5건을 지적했고 모두 반영했습니다.** 핵심은 하나였습니다. 다시 쓰기는 답만 다듬는 호출인데 저장과 한 묶음이라, 실패하면 저장까지 취소됩니다. pipeline 은 Memory 가 예외로 끝나거나 7번 안에 못 끝내면 그 run 을 commit 하지 않습니다. 기존 다시 쓰기(#625 · #660)는 저장 0건일 때만 걸려 잃을 게 없었는데, 이 PR 이 처음으로 일부 저장 상태에서도 다시 쓰게 했습니다.

| 리뷰어 지적 | 반영 |
| --- | --- |
| 다시 쓰기 호출이 실패하면 이미 한 저장까지 롤백된다 | 다시 쓰기는 **run 전체 쓰기 성공이 0건일 때만**. 그 호출이 `LLMError` 면 `_UNSAVED_FALLBACK`("이번에는 아무것도 저장하지 않았어요.")으로 정상 종료 |
| 마지막 차례에서 다시 쓰기로 넘어가면 `completed=False` 로 끝난다 | 마지막 차례에서는 다시 쓰지 않고 고정 문구로 정상 종료. tool 호출 · 빈 답 · 스키마 밖 답도 같이 묶음 |
| `update_observation_*` 로 정상 수정한 것을 저장으로 안 센다 | `_DONE_BY` 를 따로 두어 `update_observation_*` · `update_event*` 도 성공으로 셈. `WRITES_FOR` 는 조기 종료가 써서 유지 |
| 위험 물질 거절 run 도 다시 쓰기가 일어나 `_HAZARD` 한 줄 안내와 충돌한다 | `HAZARD` · 알레르기 · 만성질환 거절(`SAFETY_RECORD`) run 은 건너뜀(`_blocked`) |
| 일부만 저장한 run 의 거짓 주장("사과도 기록했어요")을 못 막는다 | 다시 쓰기 대신 코드가 판정. 저장했다고만 말하면 tool 기록대로 만든 문장("식사 기록은 남겼어요. 일정 초안은 만들지 않았어요.")으로 바꾸고, 못 한 것도 말하면 모델 답을 둠(`_ADMITS_UNSAVED`) |

- **1차 반영 뒤 새로 드러난 문제** — 리뷰 전의 일부 저장용 확인 문구("이 종류는 저장하지 않았고 …")가 모델을 밀어서, 실제로 저장한 것을 "저장하지 않았어요" 라고 부정했습니다. "언젠가 놀이공원 가고 싶대" 를 놀이 관찰로 저장한 run 12번 중 6번입니다. 코드 판정으로 바꾼 뒤 0번이 됐습니다.
- **2차 반영 (작성자가 스스로 찾은 것)**
    - 확인 문구에 "저장하지 않는 게 맞는 말(계획 · 바람 · 알림 요청)" 이라고 적혀 있었는데, 아이의 바람은 관심이라 저장한다는 #624 기준과 어긋났습니다. "먹고 싶다는 말처럼 실제로 먹지 않은 것" 으로 좁혔습니다. 같은 거짓 첫 답에 30번씩 다시 쓰게 하니 거짓 반복 4 → 0, "기록할 수 있어요" 같은 애매한 답 5 → 0 이었습니다.
    - 1차에서 다시 쓴 답이 비면 바로 고정 문구로 끝냈는데, 빈 답이 30번 중 10번이라 날짜를 되묻지 못했습니다. 한 번 더 묻게 되돌렸고, 바꾼 뒤 "며칠 전에 수영 했어" 30번이 모두 날짜를 되물었습니다.
- **3차 — 리뷰어 재리뷰 2건.** 둘 다 이 PR 이 더한 문장 패턴이라, 고치기 전에 실측으로 대안과 비교했습니다.
    - `_ADMITS_UNSAVED` 는 부정 표현이 어느 일을 두고 한 말인지 보지 않습니다. 리뷰어는 "일부 저장이면 늘 코드 문장을 내자" 고 제안했습니다. 지난 실측에서 일부 저장 후 메시지로 끝난 답 74건을 직접 읽으니, 한 일 · 못 한 일을 바꿔 말한 답은 0건이었고, 늘 코드 문장을 내면 맞는 설명(이유 · 대상 이름) 44건(59%)이 사라졌습니다. 그대로 두고 한계를 문서에 적었습니다.
    - `_REMINDER_REQUEST` 가 "알림장" 에도 걸려 "알림장에 내일 소풍 간대" 같은 일정 조각이 판정에서 빠졌습니다. `알림(?!장)` 으로 고쳤습니다.
    - 리뷰어는 새 일정 + 알림 요청이 한 조각이면 일정 누락을 못 잡는다고도 지적했습니다. 실제 Supervisor → Memory 로 문장마다 10번씩 비교했습니다.

- **4차 — 리뷰어 질문: 일부 저장 답이 일정 쪽에서 무엇을 성공 · 실패했는지 구분하는가.** 구분하지 않았습니다. 일정 쪽 성공을 모두 "일정 초안은 만들었어요" 로 묶어, 준비물만 더한 run 도 새 일정을 만든 것처럼 말했습니다. 이미 있는 준비물(`added=False`) · 같은 값 수정(`changed=[]`)도 "만들었다" 로 셌습니다. 리뷰어는 넓은 문구("일정 관련 요청은 처리했어요")를 대안으로 냈지만, 판단 근거가 tool 기록에 다 있어 tool 결과로 문장을 정하게 고쳤습니다(`_schedule_done`: 새 일정 초안 / 준비물 추가 / 일정 수정 초안 / 준비물 수정 초안 / 챙김 표시). 실패한 뒤 끝내 성공하지 못한 호출은 "준비물은 더하지 않았어요" 처럼 덧붙입니다(`_schedule_undone`).
- **5차 — 리뷰어 재리뷰 2건과 작성자 전체 점검 3건.** 모두 tool 이름 · 문장 패턴 대신 tool 결과의 실제 값을 보게 고쳤습니다.
    - 챙김 해제도 "표시했어요" 로 말하던 것을 나눴습니다. `update_event_item` 결과에 챙김 전 값(`was_prepared`)을 싣고, 그대로면 "준비물은 이미 챙김 표시돼 있어요." 라고 말합니다. 이 값은 화면 이벤트로 나가지 않습니다.
    - 바뀐 것 없는 성공은 실패가 아니라 할 일이 없던 것이라 "준비물은 이미 일정에 있어요." · "일정은 이미 그렇게 되어 있어요." 로 말합니다.
    - 관찰 삭제(`update_observation_*(status=deleted)`)를 "기록을 남겼다" 로 세던 것을 뺐습니다.
    - `_ADMITS_UNSAVED` 가 "편식하지 않고" 처럼 저장과 상관없는 부정에도 걸리던 것을 저장 동사에 붙은 부정으로 좁혔습니다. 지난 실측 답 608개에서 바뀐 판정은 0건입니다.
    - `_REMINDER_REQUEST` 가 "키즈노트 알림 왔는데 금요일 현장학습이래" 를 알림 요청으로 보던 것을, 해 달라는 말이 붙을 때만 보게 좁혔습니다.
    - 각 지적마다 재현 테스트를 두었고, 새 테스트는 고치기 전 코드에서 모두 실패합니다.
- **승인 뒤 — 조각 단위 개선은 보류했습니다.** 작성자가 "같은 종류 안의 누락(김밥 · 카레 중 김밥만 저장)" 을 풀 안 셋을 비교했습니다. 끝 답에 조각별 결과를 적게 하는 안은 짝짓기 근거가 모델의 주장이라 다시 검증해야 하고, 조각마다 따로 실행하는 안은 Memory 가 원문 전체를 보고 Supervisor 실수를 바로잡을 기회를 잃습니다. 쓰기 tool 인자에 조각 번호(`hint_id`)를 다는 안이 가장 나았지만, 실측으로는 구조를 바꿀 근거가 없었습니다(같은 종류 안의 빠뜨림 20회 중 0건 · 일부 저장 답의 거짓 74건 중 0건 · 고친 문장 패턴 구멍 실제 답 608개 중 0건). 리뷰어가 동의했고, 이 한계와 다시 볼 조건을 `memory-agent-v1.md` 한 단락에 모았습니다.

**결정** — 관찰 · 일정 조각이 있는 처음 run 은 말투가 아니라 **조각 종류별 쓰기 성공**(`ToolCallRecord.success`)으로 저장 주장을 확인합니다. 다시 쓰기는 **run 전체의 쓰기 성공이 0건일 때만** 하고, 그 차례에는 tool 을 주지 않습니다. 일부만 저장한 run 은 다시 쓰지 않고 코드가 tool 결과로 판정합니다. 다시 쓰기가 끝나지 못하면 run 을 실패로 올리지 않고 고정 문구로 끝냅니다(`ended_by="unsaved_fallback"`). 다시 쓰기는 답만 다듬는 호출이라, 그 호출 때문에 이미 한 저장을 잃으면 안 되기 때문입니다.

**결과** — "며칠 전에 수영 했어" + 관찰 조각, 실제 Memory 모델로 200회씩 돌렸습니다. 새 판정만의 효과를 보려고 양쪽 모두 `_SAVED_CLAIM` 패턴을 끈 상태입니다. 판정은 패턴이 아니라 tool 내역과 최종 답을 대조했고, 걸린 답은 원문을 사람이 읽었습니다.

- 단측 Fisher p ≈ 3 × 10⁻¹⁶ 입니다. develop 의 거짓 답은 "기록했어요." 22번, "며칠 전 수영한 것으로 기록했어요." 17번 등이었습니다.

- 패턴을 켠 실제 조건에서도 "아이스크림 먹고 싶대"(T64, 정답은 저장 안 함)의 거짓 "기록했지만 …" 이 9/13 → 0/13 이 됐습니다(p ≈ 0.0002).

- 리뷰 반영 전후로 일부 저장 run 의 다시 쓰기 24/24 → 0/48, 평균 응답 6.8 → 4.4초, 실제 저장한 것을 부정한 답 6/12 → 0 이었습니다.

**남은 것**

- **조각이 없는 run, 다시 쓴 뒤의 판정, 일부 저장 run 의 판정은 여전히 말투 패턴입니다.** 새 말투는 샐 수 있습니다.
- **같은 종류 안의 조각 누락은 못 잡습니다.** 관찰 조각 2개 중 1개만 저장해도 관찰은 성공으로 봅니다. 실제 문제가 확인되면 `hint_id` 안을 그 사례에 적용해 비교합니다.
- **빠뜨린 저장은 되살리지 못합니다.** 다시 쓰는 차례에 tool 이 없어서 거짓 답만 막습니다(RC46).
- 초안도 질문도 없이 끝나는 새 일정 + 알림 요청 run 은 못 잡습니다(관찰 0/10).
- 계획 · 먹고 싶다는 말처럼 저장하지 않는 게 정답인 입력(T02 · T64)도 다시 쓰기 대상이라 매번 호출이 1번(약 1.2초) 늘어납니다. "계획인지 실제 일인지" 는 모델이 판단할 일이라 코드에서 빼는 신호를 두지 않았습니다.
- 다시 쓴 답이 건강 조언처럼 될 수 있습니다(RC23 "영양제는 임의로 먹이지 말고 의료진과 상담해 주세요"). Health Agent 쪽과 같이 보기로 하고 범위에서 뺐습니다.
- 알림 요청을 가르는 정규식은 리뷰어가 승인하며 "테스트를 더 해 보고 보강하면 좋겠다" 고 남겼습니다.

## 8. 근거 검사를 더하자 억지 추천이 늘었다

**문제** — 운영 QA 에서 일반 추천 "종이컵을 쌓아 올린 뒤 무너뜨리고 다시 쌓기" 에 "노래하며 손 씻기" 문서가 근거로 붙었습니다. 일반 추천은 근거가 문서 행뿐이라(루트 §2), 맞지 않는 문서가 붙으면 근거가 없는 것과 같습니다. 그래서 관련성 검사를 더했는데(#557), 같이 바꾼 프롬프트 지시가 모델을 시드 [예시] 쪽으로 끌어당겼습니다. 보호자가 놀이를 정해 물어도 상관없는 [예시] 놀이를 끼워 내는 억지 추천이 늘었습니다.

    - 너무 엄격함: "동물 흉내 내며 걷기" 를 참고해 "곰처럼 네 발로 걸어 보기" 를 내면 활동은 맞는데 낱말이 안 겹쳐 거절됩니다. 정상 변형을 막으면 재제출이 늘고 끝내 `failed` 가 날 수 있습니다.
- **작성자가 반영했습니다.**
    - 시드 행의 5%(최소 4행) 이상에 나오는 흔한 낱말(그림 · 놀이 …)은 빼고, 준비물 · 제목 · 본문 낱말로 봅니다. 행 수가 아니라 비율이라 시드가 늘어도 "종이컵" 같은 구체적인 낱말은 남습니다.
    - 본문까지 봐서 "곰처럼 네 발로 걸어 보기" 는 본문에 "곰처럼" 이 있는 "동물 흉내 내며 걷기" 로 통과합니다.
    - 안 맞는 인용은 떼고, 남는 근거가 없을 때만 `UNRELATED_DOC` 으로 거절합니다. 아이 기록이나 맞는 문서가 남으면 후보는 그대로 나갑니다.
    - 시드 80행: 자기 행 80/80 통과, 다른 행끼리는 6,320쌍 중 171쌍(2.7%)만 통과했습니다. 리뷰어가 든 세 경우를 테스트로 고정하고 머지했습니다.
- **머지 뒤 — Activity 가 시드 밖의 구체적인 요청에도 [예시] 놀이를 끼워 냈습니다.** 문제는 낱말 판정이 아니라 함께 바꾼 지시였습니다. 프롬프트가 "기억 근거가 없으면 [예시]의 활동이나 그 변형을 낸다 · 겹치는 예시가 없는 후보는 내지 않는다", 거절 안내가 "[예시]에 있는 활동으로 바꾼다" 였습니다. develop 에서 실제로 나간 예입니다.
    - "달걀 굴리기 놀이" → 가족 얼굴 그리기
    - "요거트로 손가락 그림" → 장난감 바구니에 넣으며 인사하기
    - "비 오는 날 뭐 하지" → 식탁에 수저 놓기
    - "전래놀이 해보고 싶어" → 쪽지 보물찾기
- 기획 문서는 일반 추천을 **막연히 물었는데 기록이 없을 때**의 대체 답으로 두고 "억지 추천 금지" 라고 적어 두었습니다(`service-plan.md:228` · `tech-spec.md:272`). 작성자는 #557 이 이 범위를 확인하지 않고 지시를 바꾼 것이 자기 실수라고 #590 에 적었습니다.

- **#597 — 정식 수정. 요청이 먼저입니다.** PM 과 정한 방향을 코드로 옮겼습니다.

- 모델이 `requested_play` 에 보호자가 정한 놀이 종류 · 소재 · 주제를 적고, 언제 · 어디서 · 얼마나만 말했거나 막연하면 비웁니다. 적었으면 [예시]는 결 참고로만 쓰고 근거로 달지 않아도 됩니다. `kind` 는 그대로 `general` 이라 DB · API 모양은 안 바뀝니다. 안전 필터(위험 용어 · 알레르기 · 월령)는 똑같이 탑니다.
- **#597 리뷰 — 리뷰어 지적과 반영**
    - **모델이 `requested_play` 를 지어 넣으면 근거 면제를 받는다.** "오늘 뭐 하고 놀까?" 에 모델이 `블록놀이` 를 적으면 근거 없이 통과합니다. 모델이 적은 놀이가 보호자가 이번에 쓴 글에 실제로 있을 때만 요청 기반으로 보게 했습니다(`rules.said_in_request`). 없으면 그 값을 무시하고 막연한 요청처럼 [예시] 근거를 요구합니다.
    - **재리뷰: 그래도 막연한 요청이 통과한다.** 리뷰어가 실제 함수로 돌려 보니 "놀이 추천해줘"(→ "놀이 추천"), "오늘 뭐 하고 놀까?"(→ "오늘"), "주말에 뭐 하고 놀까?"(→ "주말"), "비 오는 날 실내 놀이 추천해줘"(→ "실내 놀이") 4개가 모두 `True` 였습니다. 낱말 하나만 겹쳐도 통과했기 때문입니다. 언제 · 어디서 · 날씨 · 일반 표현(`rules._NOT_A_PLAY`: 오늘 · 주말 · 실내 · 비 · 추천 등)을 빼고, 남은 낱말이 **모두** 보호자 말에 있어야 요청 기반으로 고쳤습니다. 거절 쪽에 위 4개와 "비 오는 날 놀이" · "실내 블록놀이" 를, 통과 쪽에 물놀이 · 공놀이 · 티니핑 · 쿠키 만들기 · 전래놀이 · "물놀이 추천" · "주말 물놀이" 를 회귀 테스트(`TestSaidInRequest`)로 고정했습니다.
    - **공통 `build()` 의 면제가 Agent 를 가리지 않는다.** Food 가 레시피북에 없는 메뉴를 근거 없이 만들면 비용이 큽니다. `agent == "activity"` 일 때만 `requested` 로 문서 근거를 면제하게 했고, 저장 검사(#599)도 같은 조건으로 맞췄습니다.
    - **후보가 요청에 맞는지는 아무도 보지 않는다.** "전래놀이" 에 종이컵 쌓기가 나와도 통과합니다. 작성자는 코드로 막기 전에 실제로 얼마나 벗어나는지 쟀습니다. 지난 실험의 요청 기반 후보 391개를 다른 모델에게 판정하게 하고, 판정 모델을 검증하려고 다른 요청의 후보를 일부러 붙인 대조군 120개를 같이 넣었습니다.

## 9. 알레르기를 막으면 새고, 풀면 오탐이 난다

- **17 → 3 은 #582 로컬 실험 숫자입니다.** 실험은 #557 전 코드 위에서 돌렸고, #743 머지 뒤 같은 54케이스 라이브 재측정은 다음 단계로 남아 있습니다.
- 가공 재료(단무지 · 잼 · 호박죽)와 복합어(전복죽 · 밤죽)는 계속 "확인 못 함" 이라 음식 알레르기 아이에게서 빠집니다. `known_foods` 는 손질하지 않은 재료만 넣는 기준입니다.
- "음식 알레르기가 있다" 는 사전이 못 찾은 이름이 식품 아닌 알레르기 표(꽃가루 · 라텍스 · 동물털)에 없으면 음식으로 봅니다. 표에 없는 환경 알레르기(예: 먼지)가 있는 아이도 음식 놀이가 빠질 수 있습니다.
- 문장 쪽에 띄어쓰기가 끼면(`땅 콩`) 놓칩니다. "음식 행 × 별칭" 방향 전수 테스트는 후속으로 제안됐습니다.
- 질식 주의(`caution`) 문구를 Activity 에 싣는 것은 하지 않았습니다. 지금은 막는 것만 봅니다.
- 0개일 때는 Activity 도 공통 `suggestion.empty` 를 그대로 씁니다. 0개용 문구를 따로 두면 Food 와 같이 바꿉니다.
