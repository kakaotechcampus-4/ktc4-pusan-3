## 1. 중복 요청 방어 — 프로세스 메모리에서 Redis 로, 그리고 Redis 가 죽으면 막는다

**원래 계획** — `Idempotency-Key` 를 받은 요청의 결과를 프로세스 메모리(dict)에 기억했습니다. 같은 키가 다시 오면 처음 응답을 그대로 돌려줍니다. 보호자가 버튼을 다시 눌렀을 때 같은 한 줄이 관찰 N건으로 두 번 저장되는 것을 막는 장치입니다.

**계기** — 서버를 재배포하면 기억이 사라져, 배포 직전에 보낸 요청의 재시도가 새 요청이 됐습니다. 메모리에는 만료도 없어서 재시작 전까지 계속 쌓였습니다 (#279).

**바꾼 것** (#280)
- 키는 `idem:{parent_id}:{method}:{path}:{key}` 입니다. 보호자 · 창구별로 나눠서 키가 서로 섞이지 않습니다. TTL 은 24시간입니다.
- 기억하는 것은 **성공뿐**입니다. 실패로 끝난 run 이 남으면 "다시 시도" 가 닫힌 실패만 계속 돌려받습니다. 실패한 run 의 키를 지우려면 값(run_id)으로 키를 찾아야 하는데 Redis 는 값으로 조회할 수 없어서, 역인덱스 `idem-run:{run_id} → 원래 키` 를 같은 TTL 로 함께 씁니다.
- 한 줄 입력은 러너를 띄우기 **전에** 키를 적습니다. 접수가 끝난 뒤에 온 같은 키는 전부 처음 run 을 돌려받습니다(같은 키 10번 → run 1개 · 저장 1건).

**운영하면서 한 번 더 바꾼 것 — 장애 때 메모리로 넘어가지 않는다** (#671 · #729)
- 처음에는 Redis 가 죽으면 메모리로 받게 했습니다. 그런데 장애 직전에 Redis 에 적힌 키는 메모리에 없어서, 그 사이 재시도가 새 요청이 되어 **두 번 저장됩니다.** 중복을 막는 장치가 장애 때만 조용히 꺼지는 셈이라, Redis 장애면 아무것도 처리하지 않고 `503 temporarily_unavailable` 로 막도록 바꿨습니다. 같은 키로 다시 보내면 되는 오류입니다.
- 읽기만 확인해서는 부족했습니다. RDB 저장에 실패한 Redis 는 읽기는 받고 쓰기만 `MISCONF` 로 거절합니다(`stop-writes-on-bgsave-error`). 읽기가 된다고 통과시키면 DB 저장과 commit 이 끝난 뒤에야 키를 못 남기는 것을 알게 됩니다. 그래서 처음 보는 키일 때는 탐침 키를 한 번 써 보고 통과시킵니다.
- 이미 commit 이 끝난 창구에서 키 쓰기만 실패하면 실패로 답하지 않습니다. 실패로 답하면 보호자가 다시 눌러 겹칩니다. 반대로 아직 아무것도 저장하지 않은 창구(한 줄 입력)는 503 으로 끝냅니다.
- 클라이언트는 동기(redis-py)입니다. 연결 · 응답 상한을 1초로 두고, 오류가 한 번 나면 10초 동안 Redis 를 부르지 않는 차단기를 뒀습니다. 느린 Redis 에서 왕복이 늘지 않게 `HELLO` · `CLIENT SETINFO` 를 보내지 않습니다(`protocol=2`, `driver_info=None`). 요청 경로의 호출은 `asyncio.to_thread` 로 이벤트 루프 밖에서 부릅니다.

**대가와 남은 것**
- Redis 가 죽으면 되돌릴 수 없는 POST 가 전부 503 입니다. 중복 저장보다 낫다고 판단했습니다.
- 러너가 실패한 run 의 키를 지우는 호출(`forget_run`)은 아직 루프 안에서 동기로 부릅니다. 차단기가 열리기 전 첫 호출은 최대 2초(연결 + 명령) 루프를 멈출 수 있습니다.
- Redis 장애 중에 못 지운 실패 run 은 프로세스 안의 집합으로 가립니다. 서버를 늘리면 이 표시를 DB 로 옮겨야 합니다.
- **같은 키가 정확히 동시에 오면 막지 못합니다.** 키를 읽는 것(`GET`)과 적는 것(`SET`)이 따로라서, 처음 보는 키로 4개를 같은 순간에 보내면 run 이 4개 뜨고 같은 관찰이 4건 저장됩니다(11-11 로컬 실측). 화면은 보내는 동안 버튼을 막아 보통 사용에서는 나오지 않고, API 를 직접 부를 때의 구멍입니다. 읽기와 쓰기를 `SET … NX EX` 한 번으로 합치면 Redis 가 하나만 통과시킵니다 — 아직 고치지 않았습니다.
- 같은 키 · 다른 본문(422)과 처리 중 충돌(409)은 서버에 없습니다. 웹이 키를 요청 본문에 묶어서(같은 본문 → 같은 키, 고친 본문 → 새 키) 그 경우가 생기지 않게 했습니다.
- redis 컨테이너에 볼륨이 없어서 컨테이너를 다시 만들면 키가 비워집니다. 보관이 24시간이라 영향은 작습니다.

**근거** — `apps/api/app/api/idempotency.py` · `apps/api/app/infra/redis.py` · `docs/api/idempotency-v1.md` · #279 · #671 · #729

## 2. 워커를 늘리기 위한 상태 저장소 — Redis 가 더 잘 맞는 도구인데 PostgreSQL 을 골랐다

**원래 계획** — 되묻기 맥락, 다시 시도 맥락, 사진 읽은 결과, run 채널(SSE 이벤트), 하루 입력 횟수, 초대 실패 횟수를 프로세스 메모리에 뒀습니다. 그래서 api 는 `--workers 1` 전제였습니다(#134). 되묻기 맥락은 10-06 에 "DB 로 옮기지 않는다" 로 정했습니다. 이유는 아이 이야기 원문 조각을 디스크와 백업에 남기지 않기 위해서였고, 다시 볼 조건으로 "서버가 2대 이상이 될 때" 를 같이 적어 뒀습니다.

**계기** — 워커가 둘이면 되묻기 답이 맥락 없는 워커로 가고, POST 를 받은 워커와 SSE 를 연 워커가 다르면 화면이 이벤트를 못 받고, 하루 한도는 워커 수만큼 늘어납니다 (#877).

**비교** — 옮길 것은 작업 큐가 아니라 "만료가 있는 공유 보관함 + 카운터 + 이벤트 전달" 입니다. 이 셋에는 Redis 가 더 잘 맞습니다.

| 기준 | Redis | PostgreSQL |
| --- | --- | --- |
| 만료 | TTL 로 제때 지워진다 | 읽을 때 `expires_at` 로 거르고, 실제 삭제는 따로 돌려야 한다 |
| 카운터 | `INCR` + `EXPIRE`, 1시간 창은 ZSET | 사건 행을 넣고 창 안의 행을 센다 |
| 이벤트 전달 | Streams(`XADD` / `XREAD`)가 "처음부터 다시 받기 + 새 이벤트 기다리기" 와 그대로 맞는다 | 이벤트 테이블을 짧은 주기로 읽는다 |
| "사용 중" 표시 | `SET NX` 또는 Lua | `UPDATE … WHERE in_use = false … RETURNING` 한 문장 |
| 장애 범위 | 지금은 Redis 가 죽으면 idempotency 만 503. 옮기면 되묻기 · SSE · 한도까지 같이 멈춘다 | 새 장애 지점이 없다. DB 가 죽으면 어차피 서비스가 멈춘다 |
| 클라이언트 | 동기 클라이언트라 요청마다 부르려면 `redis.asyncio` 전환과 예외 처리가 따라온다 | asyncpg 를 이미 쓴다 |
| 트랜잭션 | 관찰 commit 과 맥락 삭제를 묶을 수 없다. 사이에 죽으면 어긋난다 | 한 commit 으로 묶는다 |
| 테스트 | 테스트는 `REDIS_URL` 이 비어 메모리 폴백을 탄다. Redis 경로가 CI 에서 돌지 않는다 | 통합 테스트가 실제 Postgres 로 돈다 |

**바꾼 것** — 전부 PostgreSQL 로 옮겼습니다(#899, 11-10 머지). 이 트래픽에서는 Redis 의 속도 이점이 드러나지 않고, 장애 지점과 테스트 안 되는 경로를 늘리지 않는 쪽을 골랐습니다. idempotency 는 이미 Redis 에서 동작하므로 옮기지 않았습니다.

고르면서 생긴 대가는 하나씩 메웠습니다.
- **만료가 제때 안 지워진다** → 하루 1회 정리 배치로는 처리방침의 "15분 안에 지웁니다" 를 못 지킵니다. 만료 행을 1분마다 지웁니다(`hold_purge`).
- **원문이 WAL 과 백업에 남는다** → 네 표(`run_hold` · `rate_event` · `run_channel` · `run_event`)를 `UNLOGGED` 로 만들고, 백업은 `pg_dump --exclude-table-data` 로 내용을 뺍니다. 복원해도 이미 만료된 값이라 쓸 데가 없습니다. 10-06 에 메모리를 고른 이유(원문을 디스크 · 백업에 안 남긴다)를 이 두 가지로 지켰습니다.
- **동시에 온 두 답** → 전에는 "확인과 표시 사이에 `await` 가 없다" 는 단일 이벤트 루프의 성질에 기댔습니다. 워커가 둘이면 성립하지 않습니다. 확인과 표시를 `UPDATE … SET in_use = true WHERE … AND in_use = false AND expires_at > now() RETURNING payload` 한 문장으로 합쳤습니다. 행 잠금 뒤에 조건을 다시 보므로 하나만 값을 받습니다.
- **SSE 전달** → `LISTEN/NOTIFY` 는 워커마다 전용 연결이 필요하고 내용이 8,000바이트로 제한되어 미뤘습니다. run 을 돌리는 워커는 메모리 채널에 쓰면서 표에도 순서대로 쓰고, 다른 워커는 그 표를 0.25초마다 읽습니다.
- **탈퇴 · 아이 삭제 · 연결 끊기** → 탈퇴와 아이 삭제는 FK `ON DELETE CASCADE`, 연결 끊기는 둘 다 남아 CASCADE 가 안 걸리므로 직접 지웁니다.

**검증** — 실제 서버 두 개를 띄워 확인했습니다. 다른 서버로 간 되묻기 답이 202, 동시에 보낸 답 10개 중 202 는 하나, A 에 입력하고 B 의 SSE 로 `done` 까지 수신, 하루 입력 카운터는 두 서버 합으로 집계.

**지금 얻는 것** — 서버는 한 대이고 워커도 1개 그대로입니다. 그래도 옮긴 효과는 지금 있습니다. 상태가 메모리에 있을 때는 재배포할 때마다 되묻기 맥락이 사라져 답하던 보호자가 처음부터 다시 적어야 했고, 하루 입력 한도와 초대 코드 실패 횟수가 0 으로 돌아가 크레딧 보호와 대입 공격 제한이 풀렸습니다. 지금은 재배포해도 남습니다.

**대가와 남은 것**
- 워커 수는 올리지 않았습니다. 제공받은 서버가 한 대(4GB 에 dev 와 운영이 같이 뜸)라 올려도 서버 장애는 그대로이고, 메모리 여유도 실측이 필요합니다. 이번에 한 것은 서버를 늘릴 때 **코드가 막지 않게** 해 둔 것까지입니다.
- 완전한 stateless 는 아닙니다. run 은 받은 워커의 백그라운드 작업으로 돌기 때문에 그 워커가 죽으면 그 run 은 잃습니다. 저장은 0건으로 남고(반쯤 저장되지 않습니다), SSE 는 끝 이벤트 없이 끊깁니다. 러너가 통째로 죽어 키를 지울 주체가 없어서, 같은 키로 다시 보내면 새 run 이 아니라 죽은 run 이 재생됩니다. 화면은 이 경우를 "저장됐는지 확인하지 못했어요" 로 보여 주고 기록 탭 확인과 고쳐 쓰기(새 키)로 안내합니다. run 채널의 원본도 워커 메모리에 있고 표에는 복사본을 씁니다. 외부 API 캐시는 워커마다 따로라 결과는 같고 호출 수만 늘어납니다.
- 한 uvicorn 에 워커 2개(`--workers 2`)로도 로컬에서 돌려 봤습니다(11-11 · 실제 LLM run 39개). 입력 16개가 모두 `done` 까지 갔고 그중 7개는 run 을 돌린 워커와 SSE 를 준 워커가 달랐습니다. 되묻기 답 3/3 저장, 동시에 보낸 답 10개 중 202 는 1개, 하루 카운터는 두 워커 합과 일치했습니다. 워커 하나를 강제로 죽이면 약 1.5초 만에 새 워커가 뜨고 그 사이 요청은 남은 워커가 받았습니다. Curator · 사진 · 다시 시도 경로와 메모리 사용량은 확인하지 못했습니다. 전체 기록은 [워커 2개로 돌려 본 기록](../ops/workers-2-check-v1.md)에 있습니다.
- 그 실험에서 찾은 것: 다른 워커에 붙은 SSE 를 화면이 `done` 직후 닫으면 DB 연결 하나가 정리되지 못하고 버려져 ERROR 로그가 남습니다. 동작은 맞고 워커 1개에서는 타지 않는 경로라 지금 운영에는 없는 현상입니다.
- 네 표가 `UNLOGGED` 라 PostgreSQL 이 비정상 종료 뒤 복구되면 내용이 비워집니다. 전부 만료가 있는 값이고, 메모리에 있을 때의 동작(재시작하면 사라짐)보다 나빠지지 않습니다.
- 0.25초 폴링은 다른 워커에 붙은 SSE 연결 수만큼 조회가 늘어나는 구조입니다. 연결이 많아지면 `LISTEN/NOTIFY` 나 Redis Streams 로 다시 봐야 합니다.
- 프로세스가 죽으면 Docker 가 다시 띄웁니다(약 9초). 컨테이너 상태는 1분마다 보고 달라지면 Discord 로 알립니다.

**재시작 · 재배포 사이의 요청 — 프록시가 붙잡는다** (#883)

api 컨테이너는 한 번에 하나만 뜨기 때문에, 교체되는 동안 들어온 요청은 원래 502 를 받습니다. Caddy 에 `lb_try_duration 150s` 를 줘서 그 시간 동안 다시 연결을 시도하게 했습니다. 재시작 9초가 보호자에게 "오류" 가 아니라 "느린 응답" 이 됩니다. 넣으면서 확인한 것이 셋입니다.

- **중복 저장이 생기지 않는가** — Caddy 는 연결 자체가 안 된 요청만 다시 보냅니다. upstream 이 이미 받은 POST 는 두 번 가지 않습니다. 프록시에서 한 번, `Idempotency-Key` 로 앱에서 한 번, 두 층에서 막습니다.
- **POST 가 재시도되는가** — 설정만 넣었을 때는 POST 가 재시도에서 502 였습니다. 첫 시도가 요청 본문을 이미 흘려보내 다시 보낼 본문이 없었기 때문입니다. `request_buffers 1MB` 로 본문을 잡아 두게 했습니다. 1MB 를 넘는 본문은 그대로 502 인데, 사진은 대부분 S3 로 직접 올라가 이 경로를 타지 않습니다.
- **대가** — 배포가 아니라 api 가 정말로 죽어 있을 때도 화면은 502 를 바로 받지 못하고 150초를 기다립니다. 빨리 실패하는 것과 배포 중 오류를 없애는 것 중 뒤쪽을 골랐습니다. 헬스 감시는 프록시를 거치지 않고 컨테이너에 직접 물으므로 이 대기의 영향을 받지 않습니다.

**근거** — `docs/ops/stateless-v1.md` · #877(비교 표 원문) · #899 · `apps/api/app/domains/run_hold/repository.py` · `apps/api/app/api/runs/registry.py` · `sse.py` · `deploy/scripts/backup.sh` · `deploy/caddy/Caddyfile` · `deploy/scripts/health-alert.sh`

## 3. 같은 대상인지 판단 — 임베딩 유사도에서 LLM 판정으로

**원래 계획** — 새 관찰이 기존 기억과 같은 대상인지(계란 = 달걀)를 임베딩 유사도 임계값으로 판단하려 했습니다.

**계기** — 임계값 실험에서 유사도는 뜻이 아니라 글자 겹침을 따라갔습니다. 계란–달걀이 0.20 인데 장난감 기차–비행기가 0.76 이었습니다. 잘못된 연결이 0 이 되도록 임계값을 올리면 같은 대상의 74% 를 놓쳤습니다.

**바꾼 것** — "같은 대상인가" 하나만 묻는 판정기(LLM)를 두고, 반대 방향으로도 물어 답이 갈리면 연결하지 않습니다. 벡터는 후보가 많을 때 판정기에 보여 줄 후보를 추리는 데만 씁니다. 판정기에 보내는 값은 대상 이름 · 도메인 · 후보 키뿐이고 원문과 아이 id 는 보내지 않습니다.

**대가와 남은 것** — 반대 방향 확인으로 호출 수가 약 두 배가 됐습니다. 최종 확인 세트에서 잘못된 연결이 3건 남았는데, 딸기–딸기잼처럼 사람도 판단이 갈리는 쌍입니다.

**근거** — `docs/memory/curator-linking-v1.md` · `apps/api/app/agents/curator/embedding/link_step.py`

## 4. 추천 근거 고르기 — 임베딩 검색이 아니라 코드가 줄을 세운다

**원래 계획** — 도메인 Agent 가 아이 기록을 임베딩으로 검색하려 했습니다. 관찰마다 벡터를 만들어 저장하는 것까지는 구현했습니다.

**지금** — Agent 검색에는 벡터를 쓰지 않습니다. 근거는 코드가 정한 순서로 줄을 세워 모델에 넘깁니다. ① 확정된 성향 ② 강도가 기준을 넘고 이틀 이상 관찰된 후보 ③ 최근 14일 관찰 순서이고, 전부 0건이면 일반 추천으로 갑니다.

**이유** — "확정된 관심을 먼저 봐라" 를 프롬프트에 쓰면 테스트로 검증할 수 없고, 결과가 길어지면 모델이 뒤쪽을 무시합니다. 순서를 코드에 두면 "어떤 기록이 근거로 뽑히는가" 를 단위 테스트로 고정할 수 있습니다.

**대가와 남은 것** — 낱말이 달라도 뜻이 같은 기록을 찾는 검색은 없습니다. 같은 대상은 3번의 판정기가 저장 시점에 미리 묶어 두는 것으로 대신합니다. 관찰 벡터를 읽는 곳은 지금 Curator 뿐입니다.

**근거** — `apps/api/app/agents/common/evidence.py` · `link_step.py` 28행

**대가와 남은 것** — 긴 알림장은 한 줄 입력이 아니라 사진 읽기 경로로 받습니다.

## 6. AI 품질 평가 — 케이스 10개에서 "능력 × 규칙" 스위트로

**원래 계획** — 기획 때 정한 케이스 10개로 평가하려 했습니다.

**계기** — 10개가 전부 한 줄짜리라, 서비스의 핵심 주장(여러 날에 걸쳐 기억이 쌓인다)인 승격 · 3일 규칙 · 낡은 기억 · 정정을 볼 수 없었습니다. 만들면서 기능이 바뀌어 지금 코드와 다섯 군데가 어긋났습니다.

**바꾼 것** — 능력(무엇을 할 줄 아나) × 절대 규칙(무엇을 어기면 안 되나)으로 다시 짰습니다. 단발 34케이스 × 3회, 일주일 시나리오, 절대 규칙을 코드로 판정하는 불변식 14개입니다. 원래 10개는 표시를 달아 따로 세어 "N/10" 으로 보고합니다.

**결과** (11-10 기준선) — 헤드라인 8/10, 불변식 위반 0건(143 run), 단발 31/34. 실패한 칸은 원인을 하나씩 적어 두었습니다.

## 7. 저장하기 전 승인 — 뺐다

**원래 계획** — 한 줄을 받으면 "이렇게 이해했어요" 를 먼저 보여 주고, 보호자가 "맞아요 / 수정할게요 / 아니에요" 를 고른 뒤에 저장하려 했습니다.

**이유** — 사람을 세우는 기준을 "틀렸을 때 되돌릴 수 있나" 하나로 정했습니다. 기록 저장은 되돌릴 수 있습니다. 기록 탭에서 지울 수 있고, "이번만 그랬어요" 로 기억 집계에서 뺄 수 있습니다. 그리고 기록 저장은 이 서비스에서 가장 자주 일어나는 일입니다. 매번 확인을 받으면 "부모가 따로 정리하지 않아도 된다" 는 목표가 사라집니다.

**바꾼 것** — 승인 없이 바로 저장하고, 화면은 "이렇게 저장했어요" 로 무엇이 저장됐는지 보여 줍니다. 사람 앞에 세우는 것은 되돌릴 수 없는 세 곳(캘린더에 넣기 · 건강과 알레르기 기록 확정 · 대화로 지울 때의 삭제 확정)뿐입니다.

**대가와 막는 장치** — 잘못 저장된 기록은 보호자가 고치기 전까지 남습니다. 그래서 두 가지를 같이 뒀습니다.
- 한 번의 관찰로 성향을 확정하지 않습니다. 승격은 반복 집계(규칙)로만 일어나므로, 잘못된 한 건이 "우리 아이는 이렇다" 가 되지 않습니다.
- 알레르기 · 건강 정보는 이 경로로 저장하지 않습니다. 보호자가 말로 "땅콩 알레르기 있어" 라고 해도 LLM 이 대신 저장하지 않고, 직접 입력하는 화면으로 안내합니다.

**근거** — 루트 CLAUDE.md §2 실행 · §3 자율성 경계 · §4 · `apps/api/app/api/v1/routers/observations.py`(지우기) · `corrections.py`("이번만 그랬어요")

## 8. 근거가 없을 때 — "추천하지 않는다" 에서 "일반 추천임을 밝히고 낸다" 로

**원래 계획** — 아이 기록이 없으면 추천을 만들지 않고 "기록이 부족해요" 와 질문 1개만 내려 했습니다. 근거 없이 "우리 아이 맞춤" 인 척하지 않으려는 규칙이었습니다. (기획 단계인 09-05 에 바꿨습니다.)

**이유** — 콜드 스타트 문제입니다. 가입 직후에는 누구나 기록이 0건입니다. 그때 아무것도 내지 않으면 보호자는 기록을 쌓을 이유를 느끼기 전에 떠납니다. 아무것도 안 나가는 것보다 또래 기준의 적절한 추천이 나가는 편이 낫다고 판단했습니다.

**바꾼 것** — 근거가 없으면 또래 기준 일반 추천을 냅니다. 원래 규칙이 지키려던 것("맞춤인 척하지 않는다")은 세 가지로 지킵니다.
- 화면에 일반 추천임을 적고, 쌓인 기록 건수를 그대로 보여 줍니다.
- 개인화 추천과 일반 추천은 타입으로 구분합니다. 개인화는 아이 기록을, 일반은 문서 행을 근거로 답니다.
- 되물을 때는 질문을 1개만 냅니다.

**만들면서 한 번 더 바꾼 것** — "주말에 물놀이 갈 만한 데" 처럼 보호자가 무엇을 원하는지 정해서 물으면, 기록이 없어도 또래 기준이 아니라 그 요청에 맞춰 냅니다. 이때는 화면에 "또래" 라는 말을 쓰지 않고 "요청하신 놀이를 바탕으로 골랐어요" 라고 적습니다 (#597 놀이 · #702 교육 · #740 식사).

**대가와 남은 것** — 일반 추천이 개인화 추천으로 집계되면 품질 지표("근거 없는 개인화 추천 0건")가 무의미해집니다. 그래서 한 필드에 섞지 않고 타입으로 나눴습니다.

**근거** — 루트 CLAUDE.md §2 기억 · `apps/api/app/agents/common/evidence.py`(전부 0행이면 `kind="general"`) · `docs/web/mock-screens-v1.md`(05 근거 부족 · 요청에 맞춘 일반 추천)
