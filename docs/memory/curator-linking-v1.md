## 1. 유사도 대신 판정기

이슈 #146 은 "유사도 임계값으로 연결"이었다. 실험 1 · 2 에서 유사도는 뜻보다 글자 겹침을 따라갔다.

- 계란–달걀 **0.20**, 딸기–딸기잼 **0.90**
- 잘못된 연결을 0건으로 맞추는 임계값에서 같은 대상의 **74%** 를 놓쳤다

그래서 연결 판단은 판정기가 하고 벡터는 두 곳에만 쓴다 — 후보가 많을 때(30개 초과) 판정기에 보여 줄 후보를 추리는 것, 반대 방향으로 물을 후보를 고르는 것. 관찰 벡터의 본래 쓰임은 도메인 Agent 의 검색이다.

**Jev 를 고른 이유** (실험 3 · 4) — 같은 조건에서 Gemini 3.5 Flash Lite 는 잘못된 연결이 6~11건, Jev 는 0건이었다. 비용은 513번 호출에 약 ₩18 이었다.

**남은 한계** (실험 5) — 최종 확인에서 잘못된 연결이 3건 있었다. 모두 딸기–딸기잼처럼 같은 대상인지 사람도 판단이 갈리는 쌍이었고 Jev 도 확신이 낮았다. 분명한 쌍은 틀리지 않았다.

판정기는 답만 한다. 답이 후보 목록에 있는지 확인하고 연결하는 것은 코드다 (루트 CLAUDE.md §3).

## 2. 반대 방향 확인

**문제** — 관찰이 들어온 순서에 따라 같은 대상이 둘로 나뉜다. "홍당무" Profile 이 있을 때 "당근"이 들어오면 판정기가 "당근과 같은 후보는 없다(`none`)"고 답한 경우가 실험 3 에서 43번 중 4번 있었다.

**규칙**

- 판정기가 `none` 이라고 답했을 때**만** 한다. 후보를 고르거나 `uncertain` 이면 하지 않는다
- 후보가 3개 이하면 모두, 넘으면 관찰 벡터와 가까운 순서로 3개를 고른다
- 후보를 subject 로, 원래 subject 를 유일한 후보로 넣어 묻는다 ("홍당무와 같은 것이 당근인가?")
- 그렇다는 답이 나오면 그 후보에 연결한다. 모두 아니면 원래 답대로 새 candidate
- **반대 방향 호출이 실패하면 새로 만들지 않고 보류한다.** 장애 때문에 같은 대상이 둘로 나뉘면 합칠 방법이 없다

**대가** — 실험 5 조정용 데이터에서 판정기 호출이 284번 → 578번으로 약 2배가 됐다. 나뉘는 경우는 없어졌다.

**한계** — 물을 후보를 유사도로 고르기 때문에 후보가 4개 이상이면 같은 대상이 3위 안에 못 들 수 있다 (계란–달걀처럼 글자가 겹치지 않는 쌍).

## 3. uncertain 3회 규칙

**문제** — 판정기가 "모르겠다(`uncertain`)"고 답하면 관찰을 보류하고 다음 실행에서 다시 묻는다. 같은 답이 계속 나오면 그 관찰은 영영 Profile 이 되지 못하고 반복 집계에서도 빠진다.

**규칙**

- 같은 관찰이 `uncertain` 으로 **3번째** 보류되면 새 candidate 를 만든다
- 이때 생기는 실수는 같은 대상이 두 Profile 로 나뉘는 것뿐이다. 다른 대상의 기록이 한 Profile 에 섞이지는 않는다 — 잘못 합치는 것보다 덜 위험하다

**세지 않는 것**

| 사유 | 세지 않는 이유 |
| --- | --- |
| 판정기 오류 (장애 · 인증 · 잔액) | 기다리면 풀린다. 세면 장애 동안 들어온 관찰이 한꺼번에 새 Profile 이 된다 |
| 후보 목록에 없는 답 | 형식 문제에 가깝다. 다음 실행에서 정상 답이 나올 수 있다 |

판정기가 오래 망가지는 것은 관찰 하나보다 서비스 전체의 문제라서 보류 기록 대신 로그(`reason=judge_failed`)로 알아차리고 판정기를 바꿔 대응한다 (`IdentityJudge` Protocol). 보류된 관찰은 잃어버리지 않고 남아 있어서 판정기가 돌아오면 다음 실행에서 처리된다.

**subject 가 바뀌면 다시 센다** — 보호자가 관찰을 고치면 대상이 달라졌을 수 있다. 보류할 때 subject 해시를 같이 남기고 지금 subject 의 해시와 다르면 1 부터 센다. 해시는 `same_name_key`(공백 제거)로 다듬은 뒤 만든다 — 띄어쓰기만 고친 것은 같은 이름이라 이어서 센다.

## 4. 보류 기록 테이블

관찰 테이블에 칸을 더하지 않고 `observation_link_hold` 로 따로 둔다.

| 칸 | 뜻 |
| --- | --- |
| `food_id` · `activity_id` · `education_id` | 보류된 관찰. **셋 중 하나만** 채운다 (CHECK `observation_link_hold_one_target`) |
| `uncertain_count` | 1~3 (CHECK). 3이 되면 새 Profile 을 만들고 행을 지운다 |
| `subject_hash` | `same_name_key(subject)` 의 sha256 |

**FK 를 칸 셋으로 둔 이유** — 관찰은 도메인마다 테이블이 달라서 칸 하나로는 FK 를 걸 수 없다. `correction.target_id` · `suggestion_evidence.source_id` 는 FK 없이 두지만 이 테이블은 **삭제를 DB 가 보장해야 해서** 칸을 나눴다(exclusive arc). 해시는 익명화가 아니다 — "딸기" 같은 짧은 단어는 해시로 원래 값을 찾을 수 있어서 관찰이 지워지면 같이 지워져야 한다 (`ON DELETE CASCADE`).

**행이 사는 기간** — 첫 `uncertain` 에서 생기고 관찰이 어떤 경로로든 Profile 에 연결되면 지운다. 테이블에는 지금 보류 중인 관찰의 기록만 남는다.

**두지 않은 것** — 판정 모델 · confidence · 세지 않는 사유의 이력. 이런 값은 운영 중 판정 품질을 보는 데 쓰인다. 개인정보 처리방침 초안 8장이 "회원의 기록을 품질 평가에 사용하지 않는다, 필요해지면 선택 동의를 새로 받는다"고 정하고 있어서 규칙에 필요한 것만 둔다.

## 5. 같은 대상의 기준

- **판단이 갈리는 쌍은 다른 대상으로 본다.** Profile 은 대상 하나에 대한 선호라서 근거가 주장을 그대로 뒷받침해야 한다. 딸기를 좋아한다는 기록과 딸기잼을 좋아한다는 기록은 따로 센다 (기준: Notion [애매한 대상의 동일성 기준 — 팀 논의](https://app.notion.com/p/3e862f3841518153a8cce5880878c70e?source=copy_link))
- **별칭 목록을 만들지 않는다.** "방방은 트램펄린" 같은 목록은 계속 관리해야 한다. 대신 이런 이름을 놓치는 쪽을 택했다 — 놓치면 반복이 둘로 나뉘어 세어질 뿐이고 잘못 합치면 다른 대상의 기록이 섞인다
- **Profile 이름(`merge_key`)은 먼저 저장된 관찰의 subject 다.** 연결할 때 바꾸지 않는다

## 6. 밖으로 나가는 것

Jev 는 OpenRouter 를 거쳐 부른다. 보내는 값은 셋뿐이다.

| 보내는 것 | 보내지 않는 것 |
| --- | --- |
| 관찰 대상 이름(subject) · 도메인 · 후보 Profile 이름(`merge_key`) | 관찰 원문(`raw_text`) · 아이 id · 보호자 정보 |

반대 방향 확인도 같은 값을 자리만 바꿔 보낸다.

🔶 **개인정보 처리방침에 반영해야 한다.** OpenRouter · Jev 와 보내는 항목을 추가해야 한다. 초안의 6장(위탁) · 7장(국외 이전)에는 엘리스와 AWS 만 있다 — PM 에게 요청 (루트 CLAUDE.md §10 "외부 LLM 전달 범위").

## 7. 이번 범위 밖

| 항목 | 상태 |
| --- | --- |
| `last_observed_on` 갱신 | Curator 통합 때 처리한다 (김명성). 연결 단계는 새 Profile 을 만들 때만 첫 관찰 날짜를 넣는다 — 관찰이 지워진 것을 알 수 없어서 연결할 때마다 날짜를 올리면 틀린 값이 남는다. 통합 쪽에서 "연결된 active 관찰 중 가장 늦은 `observed_on`" 으로 다시 계산한다. 🚨 감쇠가 돌기 전에 되어 있어야 한다 — 없으면 관찰이 계속 붙는 Profile 도 첫 관찰 날짜 기준으로 오래된 관심이 되어 근거에서 빠진다 |
| DB `CuratorStore` 구현 · 실행 흐름 연결 | DB 구현은 `clear_hold` 를 `link` 와 같은 트랜잭션에서 해야 한다. 지금은 Protocol 과 인메모리 구현뿐이다 |
| 동시 실행 | 같은 아이에 대해 두 실행이 동시에 돌면 같은 대상으로 candidate 가 두 번 생길 수 있다. 부르는 쪽이 막는다 |
| 연결된 관찰 이름 활용 | 후보를 `merge_key` 뿐 아니라 연결된 관찰들의 이름과도 비교하면 두 번째 "당근"부터 판정기를 부르지 않아도 된다. 다만 잘못된 연결이 번진다 (딸기잼이 한 번 딸기에 붙으면 이후 딸기잼이 모두 딸기로 간다). 운영 뒤에 볼 개선 후보 |
