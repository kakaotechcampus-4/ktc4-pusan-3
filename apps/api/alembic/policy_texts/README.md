# 약관 원고 — `policy_version` 에 들어가는 글

보호자가 동의 화면에서 읽는 글이다. 버전 폴더마다 scope 하나에 파일 두 개가 있다.

| 파일 | 무엇 | DB |
| --- | --- | --- |
| `<scope>.md` | 원고 (사람이 쓰고 고치는 것) | `policy_version.content` · `content_hash` |
| `<scope>.html` | 원고로 만든 **정본** — 보호자가 "전문 보기" 에서 보는 페이지 | `policy_version.content_html` |

마이그레이션이 두 파일을 **한 글자도 바꾸지 않고** 넣는다. 동의 화면은 `GET /api/v1/policies` 로 버전과
정본 주소(`html_path`)를 받고, "전문 보기" 는 `GET /api/v1/policies/{scope}/{version}` 을 **손대지 않고** 띄운다.
서버가 만든 완성본을 화면이 그대로 보여 줘야 "저장된 정본 = 보호자가 본 것" 이 된다 (멘토 #71-4).

## 새 버전을 만드는 순서

1. `<새 버전>/<scope>.md` 원고를 넣는다 (바탕화면 원고의 `본문 시작`~`본문 끝` 사이만)
2. `<새 버전>/meta.json` 에 scope 마다 제목(`label`) · 법적 근거(`legal_basis`)를 적는다 — 제목을 안 바꿔도 새로 적는다
3. `cd apps/api && uv run python -m scripts.render_policy_html <새 버전>` — 옆에 `.html` 이 생긴다 (제목은 meta.json 에서)
4. 원고 · meta.json · HTML 의 해시를 고정하는 마이그레이션을 만든다 (`50ceeb7cedfe` · `bf14612a1d9c` 참고). 옛 버전 행에는 `ended_at`
5. 생성된 HTML 을 브라우저로 열어 한 번 읽어 본다 — 서버가 보호자에게 내주는 페이지가 이것이다.
   글꼴 · 줄바꿈 · 밝은/어두운 화면은 기기마다 달라도 **글(내용)은 같다.** 서버가 증명할 수 있는 것은
   "무엇을 내줬는가" 이고, 그 글이 이 파일이다

이미 HTML 이 있는 버전 폴더에서 스크립트를 돌리면 멈춘다 — 등록된 정본을 덮어쓰지 않는다.
아직 등록(머지) 전인 버전을 고쳐 다시 만들 때만 `--force` 를 쓰고, 마이그레이션의 해시도 같이 고친다.

체크박스 옆 **제목 · 법적 근거**는 같은 폴더의 `meta.json` 에 둔다. 본문처럼 그 버전의 글이라 버전마다
저장한다 — 코드 한 곳에 두면 제목을 바꾸는 순간 옛 동의 기록에도 새 제목이 붙는다 (#168 리뷰).

## 규칙

- 🚨 **등록한 원고는 고치지 않는다.** 누군가 이미 동의한 글이 바뀌면 동의 증빙이 증빙이 아니게 된다.
  마이그레이션이 파일 해시를 고정해 두고, 파일이 바뀌면 등록하지 않고 멈춘다.
  고치려면 **새 버전 폴더 + 새 마이그레이션**을 만든다 (옛 버전 행에는 `ended_at` 을 찍는다).
- 🚨 **동의로 받는 정보의 항목 · 목적 · 보내는 곳이 늘거나 보관 기간이 길어지는 개정이면, 기존 회원에게 다시 묻는다.**
  이용약관 제3조 ⑥ 과 개인정보 보호법 제15조 ② 가 요구한다 (2026-11-03 조문 확인). 제15조 ② 는 **동의로 받은 처리**에 걸린다 —
  계약 이행(제15조 ①4호)으로 처리하는 보호자 본인의 계정 정보 등은 처리방침 공개로 끝난다. 건강정보는 제23조 ① 이 별도 동의를
  요구해서 이 길이 없고, 아이는 계약 당사자가 아니라서 동의로 받는다.
  새 기능의 **선택 동의**로 받으면 그 기능을 처음 쓸 때 물으면 되고 장치가 필요 없다. **필수 동의**의 항목이 늘 때만 장치가 먼저다 —
  지금 서버는 "한 번이라도 동의했는가" 만 보고 버전을 보지 않는다 (`missing_account_scopes`).
  문장만 다듬는 개정은 다시 묻지 않아도 된다.
- **운영자 연락처는 `draft-2` 부터 원고에 직접 적는다** (2026-10-15 PM 결정). 주소는 도로명과 건물번호까지만
  (상세주소 없음), 전자우편 · 전화는 서비스용으로 새로 만든 값이다. 그래서 빈칸을 채우는 장치 없이 원고 그대로
  등록한다. 🚨 이 저장소는 public 이고 한 번 커밋한 값은 기록에서 지울 수 없다 — 개인 연락처나 상세주소를 넣지
  않는다. 주소를 옮기면 새 버전으로만 바꿀 수 있다 (옛 버전 정본에는 그때 주소가 남는다).
  ⚠️ `draft-1` 에는 `{{운영자_주소}}` · `{{운영자_전화}}` 빈칸이 그대로 남아 있다 — 해시로 고정돼 고칠 수 없다.
  위치 약관은 `2026-11-03` 판부터 연락처가 채워진다.
- **적용일을 미래로 등록할 수 있다.** `effective_at` 이 지나기 전까지 `GET /policies` 는 앞 판을 내주고,
  그 시각에 저절로 새 판으로 바뀐다. 약관 제3조 ③ 의 공지 기간을 두려고 쓴다. 앞 판의 `ended_at` 도 같은 시각으로 찍는다.
  🚨 처리방침은 다르다 — 파일을 머지하는 순간 고정 주소가 새 글을 내준다 (`routers/privacy_policy.py`).
- 파일은 보호자가 읽는 **본문만** 담는다. 누가 왜 이렇게 썼는지는 [`docs/safety/consent-texts-v1.md`](../../../../docs/safety/consent-texts-v1.md) 에 둔다.

## 버전 이름

| 단계 | 이름 | 예 |
| --- | --- | --- |
| 초안 (일반 공개 전) | `draft-N` — 본문이 바뀔 때마다 N 을 올린다 | `draft-1`, `draft-2` |
| 공개본 (일반 공개부터) | 적용일 `YYYY-MM-DD` | `2026-11-03` |

#91 은 처음부터 날짜로 쓰려 했지만, 초안 단계에서도 본문이 바뀔 때마다 버전을 올려야 동의 기록이
어느 글을 가리키는지 분명해서 초안은 `draft-N` 으로 쓴다 (#172).

🔄 2026-11-03 PM: 원래 "법률 검토 후부터 날짜" 였는데 **일반 공개 판부터 날짜**로 바꿨다. 버전 이름이 정본 머리말(`버전 …`)과
10 설정(`… 판이에요.`)에 그대로 보여서, 보호자가 동의하는 글에 초안 이름을 달 수 없다. 처리방침 버전도 시행일이다.
법률 검토로 글이 바뀌면 그날 날짜로 새 판을 낸다.
